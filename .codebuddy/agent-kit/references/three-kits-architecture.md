## 一、结论：一套方法论，三个组成部分

Karpathy 的行为纪律、Superpowers 的工程技能集、Anthropic 的 AI Native 协作方法论，解决的不是同一件事的三个替代品，而是**同一件事的三个侧面**。合起来才是一套完整方法论：

| 组成 | 来源 | 回答的问题 | 实体 |
|---|---|---|---|
| **行为准则** | Karpathy | 代码产出怎么写才不跑偏 | `kits/L1-karpathy/` |
| **执行手段库** | Superpowers | 工程动作怎么做才不偷懒 | `kits/L2-superpowers/` |
| **协作主干** | Anthropic | 任务怎么组织、判据怎么定、人在哪审 | `skills/rd-digital-agent/` |

结构是**一条主干 + 两层纪律**，不是三套并列：

```
协作主干（阶段 / 判据 V1…Vn / 人审）   ← 唯一编排入口
   ├─ 调用 执行手段库（TDD / 调试 / 验证 / 并行分派 / worktree / 评审）
   └─ 约束 所有代码产出 ← 行为准则（简洁 / 精准 / 可验证）
```

主干决定「做什么、按什么顺序、拿什么算做成」；手段库提供「这一步具体怎么干」；行为准则约束「每次落笔的质量」。三者不竞争，缺任何一个都会出现特征性失效（见 §五）。

## 二、三部分怎么咬合

| 阶段 | 协作主干 | 调用的执行手段 | 行为准则介入点 |
|---|---|---|---|
| 需求转换 | `requirement-translation`（EARS 判据 / 反例 / 待确认） | — | — |
| 方案探索 | `rd-brainstorm` | — | — |
| 计划 | `rd-plan`：TODO + **验证判据表 V1…Vn** | — | 判据须可验证（能跑出 PASS/FAIL） |
| 执行 | `rd-execute` | TDD（RED→GREEN→REFACTOR）、`systematic-debugging`、并行分派、worktree | 简洁至上、精准改动、先想后做 |
| 收尾 | `rd-execute` 完成验证门按 V1…Vn 勾核 | 完成前验证（先跑后说） | 回应四段式（Assumption/Changed/Verified/Risk） |
| 审查 | `rd-review` → `test-verification` 盲测 | 请审 / 接审纪律 | 不顺手改无关代码 |
| 复盘 | 反馈回灌为下一轮 intent | — | — |

判据的**定义**归主干，**执行**归手段库，**可验证性**归行为准则——同一件事分工不同，不重复定义。

## 三、风险与消解

> 三部分本身不冲突；以下风险来自**宿主环境**与**落地方式**，列出的是已知会真实发生的退化形态。

### R1 · 宿主环境存在第二套编排技能

- **现象**：宿主持有 Superpowers 的 `brainstorming` / `writing-plans` / `executing-plans` / `spec-driven-development` 等。
- **风险**：Agent 在「环境里正好有」时改走那套，而其计划模板不含「交付物定义 + 验证判据先行」→ 设计与交付的判据链断开，表现为「设计时看不到交付验证」。
- **解法（按优先级）**：
  1. **补齐字段（首选）**：在宿主那套流程的 plan/spec 模板中补「交付物定义 + 验证判据表 V1…Vn」两节，使其与主链同构。不删除任何技能，工程纪律全部保留——冲突消解于「同构」而非「排除」。
  2. **统一入口（次选）**：无法改宿主模板时，同域/同名冲突一律以 `rd-*` 为准；非编排类技能（TDD、调试、验证、并行分派、worktree、评审）**照常启用**。
  3. **整体卸载（最后手段，不推荐）**：`scripts/uninstall-superpowers.sh` 保留为应急手段，但代价是连 TDD 铁律、完成前验证、并行分派一起丢掉（历史上一次卸载 20 个技能即为此形态）。仅在确认宿主无需任何工程纪律时使用。
- **判定**：检查宿主 plan 模板是否含「验证判据」字段——含则走解法 1，不含则走解法 2。

### R2 · 同一纪律出现两个真相源

- **风险**：TDD / 系统化调试 / 完成前验证已由主干收编（`rd-execute`、`skills/systematic-debugging`），若执行手段库再写一份，改一处漏一处。
- **解法**：单一真相源 + 指针——手段库只声明「触发时机 + 刚性等级」，实体指向主干；只有主干未覆盖的能力（并行分派、worktree、评审请接、写技能）才写完整步骤。

### R3 · 纪律堆叠导致仪式过重

- **风险**：三层纪律叠加，琐碎任务被拖成全流程。
- **解法**：分级——分级只压缩**过程仪式**（评审链、文档体量），不压缩**交付物定义 + 验证判据**；Rigid 条目只保留三条（TDD、系统化调试、完成前验证），其余按场景取舍；行为准则明示「琐碎任务自行判断，不教条执行」。

### R4 · 层次误用

- **风险**：用执行手段库的技能去编排任务（跳过判据定义），或把行为准则当流程走。
- **解法**：边界表（见 §二 末行）——判据定义归主干，判据执行归手段库，代码质量归行为准则；手段库不产出计划、不定义判据。

## 四、加载与路由

```
kits/README.md          → 组成索引与选型（人读）
kits/L1-karpathy/       → 常驻（SKILL.md） + 人面（RATIONALE.md）
kits/L2-superpowers/    → 常驻（SKILL.md 索引） + 按需（references/rigid-disciplines.md）
kits/L3-anthropic/      → 常驻（SKILL.md 指针） + 实体（skills/rd-digital-agent）
```

- 全量加载：三个 `SKILL.md` 全部常驻（合计约 250 行，可控）。
- 最小加载：只要代码克制 → `L1-karpathy/SKILL.md`；只要工程纪律 → `L2-superpowers/SKILL.md` + 其 references。
- 同步到宿主项目：`scripts/sync-to-target.sh` 一并拷贝 `kits/`。

## 五、三部分的互不替代（缺哪部分会怎样）

| 失效形态 | 缺哪部分 |
|---|---|
| 判据写得很全，但代码过度设计、顺手改了无关文件 | 行为准则 |
| 流程都走了，但测试后补、bug 靠猜、完成靠「应该没问题」 | 执行手段库 |
| 每一步都很规范，但没有判据、没人审、产物不落盘 | 协作主干 |
