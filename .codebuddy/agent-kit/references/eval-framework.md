# 评测体系 · 定稿

> 融合「分层过滤法」（原方案 A）的骨架 + 「统一 Rubric 任务基准法」（原方案 B）的内核。本文是评测体系的唯一权威定义，`evals/` 下的用例、脚本、报告均以本文为准。

## 0. 定位

回答一个问题：**这套 kit 每次变更后，如何证明它真的让加载它的 Agent 变好了，而不是「看起来变好了」。**

两条铁律贯穿始终：

1. 评测对象是**加载了指南的 Agent 的行为**，不是文档本身；
2. 评测体系是**红线三（变更后具备回归手段）在 kit 自身的落地**，是产物链的一环（intent → 评测报告 → 复盘 → 下一轮变更），不是外挂质检。

## 1. 结构：静态 / 动态二分 + 五层过滤

```
静态层（近零成本，每次必跑）── 机器检查，不依赖模型
动态层（有成本，分层按需跑）── golden 基准集 + 统一 rubric
```

| 层 | 测什么 | 手段 | 成本 | 频率 |
|---|---|---|---|---|
| **L1 结构完整性** | 文件齐全、无孤儿 skill、frontmatter 完整、占位残留、路由指向的 skill 存在 | 静态脚本 + CI | 近零 | 每次 push |
| **L2 路由准确率** | Hub 是否把请求分派到正确子技能 | golden 路由用例，**全自动二元判定** | 低 | 每次更新 |
| **L3 行为遵循度** | Agent 是否真按方法论执行（陷阱场景） | 场景注入 + rubric（LLM-as-judge + 人工抽检） | 中 | 每次更新 |
| **L4 端到端质量** | 完整产物链的产出质量与成本 | 任务卡 + 五维 rubric + 产物清单核对 + token 成本 | 高 | 重大版本 |
| **L5 实战验证** | 真实世界是否变好 | 真实项目人审打回率、红线拦截次数、复盘回灌记录 | 极高 | 季度 |

**成本策略**：L1/L2 近零成本、全自动，高频迭代必跑；L3 每次更新跑；L4 只在触及 `skills/`/`rules/` 的结构性变更时跑；L5 靠真实数据积累，不主动跑。

## 2. 评分内核：统一五维 Rubric + 一票否决

所有动态层任务共用一张评分表，每维 0~3 分。**每个维度严格对应 kit 的一个实际组件**，维度不是拍脑袋定的，是 kit 自己的红线映射出来的：

| 维度 | 考察 | 对应 kit 组件 |
|---|---|---|
| **D1 产物落盘** | intent → spec → 交付 → 审查记录是否真实落盘、可独立追溯 | 红线 03 `versioned-artifacts` |
| **D2 流程遵循** | 分派是否正确、阶段是否完整、是否以上一阶段产物为输入 | Hub 分派决策树（`rd-digital-agent`） |
| **D3 人审节点** | 三处把关是否触发、顺序是否 逻辑→合规→spec | 红线 02 `human-in-loop` |
| **D4 产出质量** | 是否可直接交付、人工修改量 | 各 skill 的质量门（`verification-before-completion` 等） |
| **D5 上下文工程** | 是否拆独立子任务、主线程只留摘要、即时加载 | 方法论第四节 + 红线 04 `subagent-isolation` |

**通过线（带一票否决）**：

```
总分 ≥ 11  AND  D1 ≥ 2  AND  D4 ≥ 2
```

D1（产物落盘）和 D4（产出质量）是**不可妥协的底线**。流程走得再漂亮，产物没落盘、或质量不可用，直接判不通过。

## 3. 用例组织：分层 + 任务卡并存

- **L2 路由用例**：小用例，一条请求 → 一个期望分派，二元判定（对/错），全自动。**覆盖 Hub 分派决策树的全部 9 个分支**：brainstorm / plan / execute / review / debug / refactor / explore / tech-review / verification。
- **L3 陷阱用例**：小用例，一个陷阱场景 → 一个期望行为，测红线是否被静默违反。四类高价值陷阱：复现不稳定的 bug、交付不附验证证据、模糊需求直接开工、重构顺手改 bug。
- **L4 任务卡**：重任务卡 T1~T6（brainstorm / plan / execute+review / debug / review / full-loop），一张卡跑全链路，一次评完 D1~D5。

每张任务卡三要素，缺一不可：

1. **固定输入**（原样任务原文，一经固定不得修改）；
2. **期望产物清单**（`intent.md`、`spec.md`……文件系统核对清单，**存在性检查可脚本化，机器可判定**，不依赖 judge）；
3. **质量评分点**（4 条左右具体问题，喂给 judge）。

## 4. 防漂移：四道闸

LLM-as-judge 最大的风险是评分标准漂移，导致纵向对比作废。四道闸全部保留：

1. **Rubric 冻结**：改 rubric = 基线重置，必须显式声明并在报告里标注；
2. **输入冻结**：改任务卡输入 = 换基准 = 基线重置；
3. **季度全量人工校准**：judge 与人工分差 > 2 分的维度，以人工为准；
4. **judge 隔离**：judge 与被测 Agent 不得在同一会话，初评全量 + 人工复检 ≥ 20%。

外加**多轮取均值**（每任务跑 2~3 次）抑制模型随机性。

## 5. 进化度量：趋势线 + 成熟度标尺

单次分数无意义，**「随版本单调改善」才是进化**。看 `reports/` 时间序列：

- 一次通过率 ↑、D1~D5 各维均分 ↑、产物落盘率 → 100%、人工修改量 ↓、红线违规数 ↓。

**回归判定**：任一维度均分下降 ≥ 0.5，或通过率下降 → 判退化，本次变更不合并。

**成熟度标尺（合并两案，统一对齐）**：

| 级 | 判据（能力有无，非分数高低） |
|---|---|
| L0 | 无指南，靠对话临时指挥 |
| L1 | 有指南层（`AGENT.md` 存在并被加载） |
| L2 | 有 SOP + 版本化产物链（skills 就位，产物落盘率 ≥ 80%） |
| L3 | 红线机器化（反复错误有 CI/机器拦截） |
| L4 | 回归评测闭环（每次演进有基准对比，退化可发现可阻断） |
| L5 | 实战验证（真实项目人审打回率下降、复盘回灌有记录） |

标尺是**里程碑**（有没有产物链/有没有机器拦截），分数是**趋势线**（纵向改善），两者不混用。

## 6. CI 门禁

`eval-gate.yml` 两道关：

1. **结构完备性**：必需文件存在、无孤儿 skill、占位残留检查（每次 PR 必跑，近零成本）；
2. **评测报告门禁**：PR 改了 `AGENT.md / skills/ / rules/ / references/` 而 `evals/reports/` 无新增报告 → 拦截。纯排版变更可显式豁免。

## 7. 与 kit 的对应关系（可靠性来源汇总）

| 测评组件 | 对应 kit 实际内容 | 判定方式 |
|---|---|---|
| L1 结构 | 三层结构、11 个 skills、5 条红线 | 脚本，机器判定 |
| L2 路由 | `rd-digital-agent` 分派决策树（9 分支） | 二元判定，全自动 |
| L3 陷阱 | 红线 01/02/05 + 各 skill 质量门 | rubric + 人工抽检 |
| L4 任务卡 | 红线 03 产物链 + 红线 04 上下文隔离 | 五维 rubric + 产物清单机器核对 |
| D1~D5 | 红线 03 / Hub / 红线 02 / 质量门 / 红线 04 | 见 §2 映射表 |
| 报告 | 红线 01 Loop（intent→报告→复盘→下一轮） | 报告即产物链，版本化落盘 |

## 8. 落地结构

```
evals/
├── README.md                 # 运行手册（怎么跑、成熟度标尺）
├── run-baseline.md           # 基线运行手册（干净上下文 + judge 隔离）
├── cases/
│   ├── structure.md          # L1 静态结构检查清单（机器检查的用例化）
│   ├── routing.md            # L2 路由用例（20 条，二元判定）
│   └── behavior.md           # L3 陷阱用例（6 条，测红线静默违反）
├── golden-tasks/
│   ├── README.md             # 任务卡说明与使用规则
│   ├── RUBRIC.md             # 五维评分标准（评分内核）
│   └── T1~T6                 # 端到端任务卡（固定输入 + 期望产物 + 质量评分点）
└── reports/
    └── TEMPLATE.md           # 评测报告模板（含趋势对比与回归判定栏）
```

## 9. 落地路径（MVP 起步）

1. 锁定五维 rubric（已实现 `RUBRIC.md`）；
2. 写用例：L1 结构清单 + L2 路由 20 条 + L3 陷阱 6 条 + L4 任务卡 6 张（均已实现）；
3. 跑**首份基线报告**（没有基线就没有趋势线，这是当前唯一未完成项；须按 `run-baseline.md` 在干净上下文执行）；
4. L1 静态脚本进 CI（已实现 `eval-gate.yml`，覆盖 structure.md 的 S1~S5）；
5. 之后每次更新遵循闭环：**改 → 评 → 对比 → 决定是否合并**，报告落 `evals/reports/`。

## 10. 可靠性四机制

这份方案把「可靠性」落实到四个机制上，任何一个都能独立砍掉一大块「看起来变好了」的假象：

1. **机器判定优先**：产物清单存在性检查、路由二元判定均可脚本化，不依赖 judge；
2. **一票否决**：D1/D4 不可妥协，防止「分够了就行」的橡皮图章；
3. **防漂移四闸**：rubric 冻结 + 输入冻结 + 季度校准 + judge 隔离；
4. **多轮取均值**：每任务 2~3 次，抑制模型随机性。
