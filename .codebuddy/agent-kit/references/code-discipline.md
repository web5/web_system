# 产出纪律 · 长版（反例与判定方式）

> 常驻版是 `AGENT.md` §产出纪律（祈使句，≤15 行）。本文承载**反例、来源与判定方式**，按需加载。
> 设计理由（为什么单独成层、为什么不做成红线）见 `methodology-design.md` §一/§六。

## 一、五条纪律

### 1. 动手前先想

**约束**：显式列出假设、风险与未确认项；不确定就停下提问，不替用户做无据假设、不隐瞒疑惑。存在多种理解时把选项摆出来让用户选；有更简单方案时直接说，必要时反驳。保持独立判断，不因用户倾向而放弃更合理的方案。

**反例**：用户说「加个缓存」，直接引 Redis 并假设部署环境已就绪——假设未声明，返工成本在部署时暴露。

### 2. 简洁至上

**约束**：不做需求外的功能；不为单次使用的代码做抽象；不做没被要求的「灵活性 / 可配置性」；不处理不可能发生的异常。写了 200 行而 50 行能解决 → 重写为 50 行。

**反例**：为「以后可能扩展到多数据源」引入工厂 + 策略 + 配置层，而当前只有一个数据源。

### 3. 精准改动

**约束**：不「顺手优化」相邻代码、注释或格式；不重构没坏的东西；跟随既有风格。发现无关死代码提出来、不删除，除非用户明确要求。**自己改动造成的孤儿（无用 import / 变量 / 函数）必须清掉**；改动前就存在的不动。

**反例**：修一个空指针，顺手把同文件另外 3 处命名与格式一起改了——评审无法区分哪些是必要改动。

### 4. 目标驱动

**约束**：模糊任务先转成可验证目标。

| 用户原话 | 转成可验证目标 |
|---|---|
| 加校验 | 写出覆盖无效输入的测试，并让它通过 |
| 修 bug | 写出能复现 bug 的测试，修复后让它通过 |
| 重构 X | 确保重构前后测试都通过 |

多步任务给简短计划，每步带验证：`1. [步骤] → 验证: [检查项]`。**判据来源**：本任务的验证判据表 `V1…Vn` 优先；无流水线时按上表自拟并回读用户确认。

### 5. 回应四段式

汇报结果必答：**Assumption**（假设了什么、为什么）/ **Changed**（改了哪些文件、行）/ **Verified**（跑了什么检查、结果是什么）/ **Remaining risk**（还可能错在哪）。

## 二、两条硬约束

- **Pushback**：对非必要的范围膨胀说不并报出代价（「这增加 X 复杂度，无用户可见收益」）；请求与既定目标矛盾时先问再做。
- **删除安全**：禁止通配删除与递归清理非自己创建的目录；删除前先确认范围，范围可疑先确认再执行。

## 三、判定方式（哪些可机器判定）

| 纪律 | 判定方式 | 类型 |
|---|---|---|
| 精准改动（无无关改动） | `git diff --stat` 逐文件对应到请求；评审检查项 | 半机器 |
| 精准改动（孤儿清理） | lint：`no-unused-vars` / `tsc --noUnusedLocals`；由 `rd-review` 检查项兜底 | 机器 |
| 四段式汇报 | 交付消息含四段标题 | 半机器 |
| 简洁至上（无需求外功能 / 无过早抽象） | `rd-review` 检查项：是否有更简单方案、是否有未被要求的灵活性 | 人工 |
| 动手前先想（假设显式化） | `rd-review` 检查项：假设与未确认项是否列出 | 人工 |
| 目标驱动（判据可验证） | 判据表每条有可执行手段与 PASS 条件（`rd-plan` 门禁） | 机器 |

> 因此本层**不进 `rules/`**：一半条目无法给出可跑命令，而 `rules/` 的门槛是「写不出判定命令即未定义清楚」（见 `rules/general/05-red-line-check.md`）。

## 四、自查（产出代码前）

- [ ] 假设已显式声明并经用户确认？
- [ ] 是否有更简单的方案被忽略？
- [ ] 是否改动了与需求无关的代码？
- [ ] 成功标准是否可验证（能跑出 PASS/FAIL）？
