# 智能体定义方法论

> 回答一个问题：**建设一个新智能体时，如何快速、无歧义地定义它，使定义可评测、可回归，而不是每次临场发挥。**
>
> 本 kit（第 0 号实例）与数字人 `rd-digital-agent`（第 1 号实例）是这套方法论的事实来源：数字人是怎么被定义出来的，本文把这个过程显式化、通用化，供后续所有智能体复用。
>
> 配套操作件：`references/agent-definition-template.md`（逐维填写模板，含数字人完整样例）；评测底座：`references/eval-framework.md`（五层过滤 + 五维 Rubric）。

## 一、三条核心洞察

1. **定义与评测同构**：一个智能体定义得清不清楚，判据是它能否被评测——每个定义维度都必须配得上可执行的评测手段（见 §二 表"评测实例化"列与 §四 的实例化规则）；评测手段写不出来的维度，说明定义还停留在形容词层。本方法论自身（第 0 号实例）就受这一定律约束：它的**方法论评测**（`eval-framework.md`，见 §四）用五层过滤 + 五维 Rubric（D1 产物落盘 / D2 流程遵循 / D3 人审节点 / D4 产出质量 / D5 上下文工程）评测"加载了本 kit 指南的 Agent 的行为"，D1~D5 各自映射 kit 的红线与组件，为每次变更提供回归证据。因此「定义清楚」与「可评测」是同一件事的两面。
2. **维度是变体，描述语言是不变量**：每个智能体的定位、特征、边界、能力都不同，但"描述清楚"的语言不随智能体变——统一复用辨证语法（见 §三）。这是"快速定义"的杠杆。
3. **定义资产与评测用例捆绑交付**：一份定义文档若不附带可跑的评测用例与首份基线报告，等于未交付。这与红线三（版本化产物必须落盘）及 `eval-gate.yml`（改 kit 必须附评测报告）同源。

   **交付分期**：允许第一期先交「定义 + 判据（书面）」，**评测实例化与首份基线属第二期**；第一期交付须**显式标注**本缺口（登记在交付物清单或报告头部），不得默认省略——**分期是排期，不是豁免**。

## 二、七个定义维度

定义智能体 = 逐维回答下表七个问题。每个维度对应 kit 中的实际组件，并在评测层有对应的实例化手段。

| # | 维度 | 定义什么（一句话） | **答案来源** | kit 对应组件 | 评测实例化 |
|---|------|--------------------|--------------|--------------|-----------|
| 1 | 定位与意图 | 这个智能体做什么、为谁做、什么算做成 | **自定**（本体方给；外部方法论不提供此项） | `AGENT.md`「定位」；spec 的需求辨证 | L4 任务卡：能否产出可验证的"做成"定义 |
| 2 | 特征与风格 | 以什么人格/风格与人协作。**默认白板型**（通用预设：本体不固定人格，由宿主项目注入）；需要固定人格时选本体型（辨证定义可观测特征，如本 kit 数字人 = 技术型产品经理） | **自定**（人格）+ 贯穿约束②（产出姿态） | 模板「特征与风格」节；`project-context.md` 风格常量 | 本体型：风格一致性陷阱用例；白板型：注入承载位检查 |
| 3 | 输入空间与边界 | 接什么请求、按什么条件分流、什么不接 | **自定**（决策树）+ 红线提供拒答出口 | Hub 分派决策树（`rd-digital-agent/SKILL.md`） | L2 路由用例：请求 → 期望分派，二元判定 |
| 4 | 工作流与过程约束 | 任务如何分阶段流转、产物链是什么、人在哪些节点把关 | **Anthropic AI native 主干** | 各 skill 工作流；红线 01/02/03 | L4 任务卡：产物清单机器核对（D1）+ 人审触发（D3） |
| 5 | 能力集 | 拥有哪些子能力、各自触发条件/流程/输出/不做什么 | **Superpowers 执行手段库** | `skills/*/SKILL.md` | L4 任务卡：产出质量（D4） |
| 6 | 红线与机器化 | 哪些绝对不能做、每条如何被可执行地检查 | **自定**（业务禁区）+ 本 kit 约定（机器化手段） | `rules/general/` 五条红线 | L3 陷阱用例：红线被静默违反的场景 |
| 7 | 上下文与知识策略 | 知识从哪来、何时加载、如何防上下文膨胀 | **本 kit 约定**（双面分层 + 按需加载表） | 各 skill 的 references/ 表；`project-context.md` | D5 上下文工程（子任务隔离、即时加载） |

> **两条贯穿约束（不单列为维度）**——它们施加在**所有**维度上，硬塞进任一维都会让该维不纯：
> 1. **评测**：每个维度在定义时就要回答"如何证明它被兑现"（见 §四）；
> 2. **产出姿态**（Karpathy 实现原则：动手前先想 / 简洁至上 / 精准改动 / 目标驱动 / 四段式汇报）：约束每一次产出，与流程编排正交。落地实体 = `AGENT.md` §产出纪律 + `references/code-discipline.md`。

### 直觉六问的工程化（七个维度从哪来）

七个维度不是凭空定的，它们来自定义智能体时人最直觉的六个问题：**它成为谁？有什么特征？有什么技能？应该怎么思考？怎么解决问题？不能做哪些事？** 维度是这六问的工程化落点：

- 成为谁 → 维度 1 定位与意图（做成 = 一句话可验证）
- 有什么特征 → 维度 2 特征与风格（**默认白板型**：本体不固定人格、由宿主注入；需本体人格时切本体型并辨证定义）
- 有什么技能 → 维度 5 能力集（触发 / 流程 / 输出 / 不做什么）
- 怎么解决问题 → 维度 4 工作流与过程约束（阶段、产物链、人审节点）
- 不能做哪些 → 维度 3 输入空间与边界（入口拒绝）+ 维度 6 红线与机器化（行为禁区）

**"特征"直接成维**：它是本体属性（以什么姿态存在）。**方法论默认白板型**——白板是通用预设，复制模板建新智能体时默认按白板作答（答"本体不固定、由宿主注入"，不是留空）；本体型是需要固定人格时的特例（客服、导师、特定角色，以及本 kit 的数字人 = 技术型产品经理），须把每个特征翻译成可观测口径、配"风格一致性"陷阱用例。

**"思考"走显式下沉**（这是设计，不是遗漏）：默认沿用 `thinking-checklist` 辨证纪律（辨证先行、答不出 = 待确认、不脑补），不单独成维——它与"怎么解决问题"同质，属于过程约束；有独特思维模式要求的特例（如"必须苏格拉底式反问"）在维度 4 必答项声明。

成维判据：**本体属性（是什么、以什么姿态存在）必须成维；过程约束（怎么运转）进工作流维；纯工程约束（知识怎么管）独立成维。**

直觉六问都能在七个维度中找到落点与评测手段：既没有一问答不上来，也没有一维是重复叙述。

## 三、每个维度怎么定义（不变量：统一辨证语言）

描述语言全部来自 `spec-workflow.md` 与 `thinking-checklist.md`（辨证与本质思考清单），不随智能体变化：

- **做成 = 一句话可验证定义**；**不算做成 = 边界/反例**。答不出这两句，维度未定义完。
- **约束逐条分层标注** `[物理必然｜业务规则｜惯例｜猜测]`，禁止混为一谈；`惯例` 项标红待审。
- 每个关键决策配 **2 个反例（各配回应）+ 必然失败清单（3 种做法各配规避手段）+ 最坏情形（可观测的失败场景与触发条件）**。
- **答不出 = 待确认**，交用户定夺，禁止自行脑补（与兜底红线同源）。
- 关键论断区分 **事实（标来源）与推断（标推理链）**。
- 禁用形容词定义：`稳定`、`好用`、`智能` 必须翻译成可观测口径（如"单轮任务一次通过率"）。特征维尤甚：`亲和`、`专业`、`克制` 必须给出可观测操作（字数上限、不主动发散、回复模板）。

### 逐维必答问题总表

| 维度 | 必答问题 | 怎么算答好 |
|------|---------|-----------|
| 1 定位与意图 | 做成 = 一句话？不算做成 = 哪个反例？驱动方是谁、不做损失什么？核心领域掌握程度？ | 定义可被 L4 任务卡直接引用 |
| 2 特征与风格 | 类型判定：默认白板型，是否切本体型？若切，理由是什么？白板型的注入承载位在哪？本体型下每个特征是否已翻译成可观测口径？ | 白板型标注承载位；本体型有切换理由、无形容词残留、配风格一致性陷阱用例 |
| 3 输入空间与边界 | 所有输入按什么条件归到哪个分支？什么请求明确不接（返回什么）？边界外请求是否有定义好的出口？ | 分派决策树能穷举全部请求类别而无"其他"黑洞（数字人样例为 10 类） |
| 4 工作流与过程约束 | 分几个阶段？每阶段产出什么产物？下一阶段读哪个产物？人在哪些节点审？思维模式是否有特例（默认沿用辨证纪律，见 §二）？ | 产物清单可机器核对；节点顺序固定 逻辑→合规→对照 spec |
| 5 能力集 | 哪些能力必不可少、哪些可后补？每个能力的触发/流程/输出/不做什么？能力间如何接管？ | 每个 SKILL.md 都有"不做什么"节；无职责重叠 |
| 6 红线与机器化 | 哪几条绝对不做？每条红线怎么被检查（脚本/CI/清单）？靠人自觉的红线不算红线？ | 反复错误类红线已机器化；行为红线有陷阱用例 |
| 7 上下文与知识策略 | 常驻加载什么、按需加载什么？参考文档何时加载（触发表）？复杂任务如何拆子上下文？ | 主线程只保留摘要；参考文档按"何时加载"而非全量预载 |

### 三类答案来源（七维由谁回答）

七维是**提问清单**；回答它的来源只有三类，另加两条贯穿约束：

| 来源 | 回答哪几维 | 缺了会怎样 |
|---|---|---|
| **自定**（本体方给） | 1 定位与意图、2 特征与风格（人格部分）、3 输入空间与边界、6 红线的业务禁区 | 定义出来的是"通用模板"，不是"这个智能体" |
| **Anthropic AI native 主干** | 4 工作流与过程约束 | 阶段 / 判据 / 人审没定，产物链断裂 |
| **Superpowers 执行手段库** | 5 能力集 | 工程动作无纪律：测试后补、bug 靠猜、完成靠「应该没问题」 |
| **本 kit 工程约定**（自研） | 6 的机器化手段、7 上下文与知识策略 | 红线靠自觉、上下文膨胀 |
| 贯穿约束 ① **评测** | 全部（每维都要写"怎么证明"） | 定义了但无法证明兑现 |
| 贯穿约束 ② **产出姿态**（Karpathy） | 全部（约束每一次落笔） | 过度设计、乱改无关代码、无证据宣称完成 |

**归属判据（防越界）**：一个来源若同时回答两个维度 → 说明它该拆。

> 反例：历史上把 Superpowers 整体当"一层"处理即违反此判据——它 20 个技能里只有 4 个属编排层（与 Anthropic 主干冲突），其余属维度 5 的工程纪律；整体对待会把维度 5 一起丢掉。

## 四、怎么证明定义兑现（评测贯穿）

每个智能体产品的定义交付物 = **定义文档 + 技术产品型评测集**，缺一不可：

> **两类评测不要混同**：
> - **方法论评测**（`eval-framework.md` + `evals/`）：评测对象是**方法论本身**——用"加载了本 kit 指南的 Agent"跑任务，验证方法论变更是否真的让行为变好（kit 仓库内部的纵向回归）。它回答"方法论变好了吗"。
> - **技术产品型评测（智能体产品评测）**（§二 表"评测实例化"列 + 下方规则）：评测对象是**按本方法论定义出来的具体智能体产品**——当前第 1 号实例即数字人 agent。逐维验证产品是否符合定义与技术产品表现：路由用例证维度 3 分派、风格一致性用例证维度 2（技术型产品经理人格）、陷阱用例证维度 6 红线……它回答"这个智能体产品符合定义吗、像个合格的技术产品吗"。
>
> 五维 Rubric 映射的是 kit 红线与组件，**不是**定义维度的镜像；定义维度自己的评测手段以 §二 表与本节为准。跑方法论回归用 `evals/` 基线流程，写智能体产品评测以本节与模板 §8 为准。
>
> **评测资产三层**：框架（`references/eval-framework.md`：规则，唯一权威）→ 模板（`evals/` 下可复制的空白件：RUBRIC / 报告 TEMPLATE / 任务卡骨架）→ 实例（`evals/` 的 cases、T1~T6、历次报告：输入冻结、不可改）。
>
> **智能体产品评测集的归属**：属于该智能体产品的定义资产，随其 definition 文档建独立评测子目录，**不并入 kit 的 `evals/`**（`evals/` 是方法论评测，不评测任何具体智能体产品）；可参考 `evals/` 的骨架与模板，不复用其用例内容（内容按本节逐维实例化）。

1. **L2 路由用例**：数量 = 分派决策树分支数（含边界/拒答分支），二元判定，全自动。覆盖决策树全部分支。
2. **L3 陷阱用例**：每条红线配一个"静默违反"场景（如交付不附验证证据、模糊需求直接开工）；维度 2 判为**本体型**的智能体另配"风格一致性"用例。
3. **L4 任务卡**：至少一张端到端主链路卡（固定输入 + 期望产物清单 + 质量评分点三要素），产物清单存在性检查可脚本化。
4. **首份基线报告**：按 `evals/run-baseline.md` 在干净上下文跑，judge 与被测 Agent 隔离。没有基线就没有进化曲线。（**第二期**：第一期不以此阻塞交付，但须显式标注未满足。）
5. **防漂移**：复用 `eval-framework.md` §4 四道闸（Rubric 冻结 / 输入冻结 / 季度人工校准 / judge 隔离）+ 多轮取均值。

**回归判定**：任一维度均分下降 ≥ 0.5 或通过率下降 → 判退化，本次变更不合并。

## 五、落地流程（建设一个新智能体，五步）

1. **辨证**（intent）：要不要建、做成是什么、不做损失什么——先于一切动手。
2. **填模板**：复制 `references/agent-definition-template.md` 逐维填写；先画分派决策树（最易返工维度），再填其余各维。
3. **实例化评测**：按 §四 生成路由用例 / 陷阱用例 / 任务卡。
4. **跑首份产品基线报告**：在干净上下文执行（judge 隔离等方法见 `evals/run-baseline.md`），报告落盘于该智能体产品的评测子目录——随定义走，**不并入 kit `evals/`**（后者是方法论评测报告）。
5. **进迭代闭环**：改 → 评 → 对比 → 决定是否合并；报告落盘，趋势线随版本单调改善才是进化。

## 六、方法论自身的约束

- 不发明新描述语言：一律复用辨证语法（§三），新维度表述必须能落进模板与评测。
- 不给未定义行为发明兜底：边界外的行为走显式报错/待确认，不自行降级（呼应 AGENT.md 兜底红线）。
- 每次变更须过评测门禁：改定义/模板 = 改 kit，须附评测报告（`eval-gate.yml`）。
- 维度或模板变更须**同步**更新本文与模板及实例化清单，防模板漂移。
- 本仓库 `references/` 受 L1/S4 占位残留检查与报告门禁监管，禁止未替换占位符入库。
- 所有定义资产（rules / skills / references）须遵守**双面分层**（`references/dual-audience-design.md`）：AI 面（指令，常驻、有体积上限）与人面（设计理由，外置 `RATIONALE.md` 按需加载）分离，只有判据类内容双面同源同编号；人面与 AI 面版本不一致即 CI 失败（S8-2）。

## 七、自指说明

这套方法论自身也在定义自己的进化方式：

- 本 kit = 第 0 号实例："定义智能体方法论"的方法论（本文 + `ai-methodology.md` + `eval-framework.md`），其进化由**方法论评测**（`evals/`）守护；
- 数字人 agent = 第 1 号实例：用本方法论定义的智能体产品，对它的评测为**技术产品型评测**（随其定义走，见 §四）；
- 本文的变更同样走产物链：intent → spec → 评测报告 → 复盘 → 下一轮，不例外。
