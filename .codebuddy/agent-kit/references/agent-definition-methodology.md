# 智能体定义方法论

> 回答一个问题：**建设一个新智能体时，如何快速、无歧义地定义它，使定义可评测、可回归，而不是每次临场发挥。**
>
> 本 kit（第 0 号实例）与数字人 `rd-digital-agent`（第 1 号实例）是这套方法论的事实来源：数字人是怎么被定义出来的，本文把这个过程显式化、通用化，供后续所有智能体复用。
>
> 配套操作件：`references/agent-definition-template.md`（逐维填写模板，含数字人完整样例）；评测底座：`references/eval-framework.md`（五层过滤 + 五维 Rubric）。

## 一、三条核心洞察

1. **定义维度 = 评测维度（同构）**：一个智能体定义得清不清楚，判据是它能否被评测。`eval-framework.md` 的五维 Rubric（D1 产物落盘 / D2 流程遵循 / D3 人审节点 / D4 产出质量 / D5 上下文工程）不是拍脑袋定的，它恰好映射智能体定义的各维度。因此「定义清楚」与「可评测」是同一件事的两面。
2. **维度是变体，描述语言是不变量**：每个智能体的定位、边界、能力都不同，但"描述清楚"的语言不随智能体变——统一复用辨证语法（见 §三）。这是"快速定义"的杠杆。
3. **定义资产与评测用例捆绑交付**：一份定义文档若不附带可跑的评测用例与首份基线报告，等于未交付。这与红线三（版本化产物必须落盘）及 `eval-gate.yml`（改 kit 必须附评测报告）同源。

## 二、六个定义维度

定义智能体 = 逐维回答下表六个问题。每个维度对应 kit 中的实际组件，并在评测层有对应的实例化手段。

| # | 维度 | 定义什么（一句话） | kit 对应组件 | 评测实例化 |
|---|------|--------------------|--------------|-----------|
| 1 | 定位与意图 | 这个智能体做什么、为谁做、什么算做成 | `AGENT.md`「定位」；spec 的需求辨证 | L4 任务卡：能否产出可验证的"做成"定义 |
| 2 | 输入空间与边界 | 接什么请求、按什么条件分流、什么不接 | Hub 分派决策树（`rd-digital-agent/SKILL.md`） | L2 路由用例：请求 → 期望分派，二元判定 |
| 3 | 工作流与过程约束 | 任务如何分阶段流转、产物链是什么、人在哪些节点把关 | 各 skill 工作流；红线 01/02/03 | L4 任务卡：产物清单机器核对（D1）+ 人审触发（D3） |
| 4 | 能力集 | 拥有哪些子能力、各自触发条件/流程/输出/不做什么 | `skills/*/SKILL.md` | L4 任务卡：产出质量（D4） |
| 5 | 红线与机器化 | 哪些绝对不能做、每条如何被可执行地检查 | `rules/general/` 五条红线 | L3 陷阱用例：红线被静默违反的场景 |
| 6 | 上下文与知识策略 | 知识从哪来、何时加载、如何防上下文膨胀 | 各 skill 的 references/ 表；`project-context.md` | D5 上下文工程（子任务隔离、即时加载） |

> "评测"不单列为第 7 维：它是贯穿轴——**每个维度在定义时就要回答"如何证明它被兑现"**（见 §四）。

## 三、每个维度怎么定义（不变量：统一辨证语言）

描述语言全部来自 `spec-workflow.md` 与 `thinking-checklist.md`（核心 7 问），不随智能体变化：

- **做成 = 一句话可验证定义**；**不算做成 = 边界/反例**。答不出这两句，维度未定义完。
- **约束逐条分层标注** `[物理必然｜业务规则｜惯例｜猜测]`，禁止混为一谈；`惯例` 项标红待审。
- 每个关键决策配 **2 个反例（各配回应）+ 必然失败清单（3 种做法各配规避手段）+ 最坏情形（可观测的失败场景与触发条件）**。
- **答不出 = 待确认**，交用户定夺，禁止自行脑补（与兜底红线同源）。
- 关键论断区分 **事实（标来源）与推断（标推理链）**。
- 禁用形容词定义：`稳定`、`好用`、`智能` 必须翻译成可观测口径（如"单轮任务一次通过率"）。

### 逐维必答问题总表

| 维度 | 必答问题 | 怎么算答好 |
|------|---------|-----------|
| 1 定位与意图 | 做成 = 一句话？不算做成 = 哪个反例？驱动方是谁、不做损失什么？核心领域掌握程度？ | 定义可被 L4 任务卡直接引用 |
| 2 输入空间与边界 | 所有输入按什么条件归到哪个分支？什么请求明确不接（返回什么）？边界外请求是否有定义好的出口？ | 分派决策树能穷举 9 类请求而无"其他"黑洞 |
| 3 工作流与过程约束 | 分几个阶段？每阶段产出什么产物？下一阶段读哪个产物？人在哪些节点审？ | 产物清单可机器核对；节点顺序固定 逻辑→合规→对照 spec |
| 4 能力集 | 哪些能力必不可少、哪些可后补？每个能力的触发/流程/输出/不做什么？能力间如何接管？ | 每个 SKILL.md 都有"不做什么"节；无职责重叠 |
| 5 红线与机器化 | 哪几条绝对不做？每条红线怎么被检查（脚本/CI/清单）？靠人自觉的红线不算红线？ | 反复错误类红线已机器化；行为红线有陷阱用例 |
| 6 上下文与知识策略 | 常驻加载什么、按需加载什么？参考文档何时加载（触发表）？复杂任务如何拆子上下文？ | 主线程只保留摘要；参考文档按"何时加载"而非全量预载 |

## 四、怎么证明定义兑现（评测贯穿）

每个新智能体的定义交付物 = **定义文档 + 实例化评测集**，缺一不可：

1. **L2 路由用例**：数量 = 分派决策树分支数（含边界/拒答分支），二元判定，全自动。覆盖决策树全部分支。
2. **L3 陷阱用例**：每条红线配一个"静默违反"场景（如交付不附验证证据、模糊需求直接开工）。
3. **L4 任务卡**：至少一张端到端主链路卡（固定输入 + 期望产物清单 + 质量评分点三要素），产物清单存在性检查可脚本化。
4. **首份基线报告**：按 `evals/run-baseline.md` 在干净上下文跑，judge 与被测 Agent 隔离。没有基线就没有进化曲线。
5. **防漂移**：复用 `eval-framework.md` §4 四道闸（Rubric 冻结 / 输入冻结 / 季度人工校准 / judge 隔离）+ 多轮取均值。

**回归判定**：任一维度均分下降 ≥ 0.5 或通过率下降 → 判退化，本次变更不合并。

## 五、落地流程（建设一个新智能体，五步）

1. **辨证**（intent）：要不要建、做成是什么、不做损失什么——先于一切动手。
2. **填模板**：复制 `references/agent-definition-template.md` 逐维填写；先画分派决策树（最易返工维度），再填其余各维。
3. **实例化评测**：按 §四 生成路由用例 / 陷阱用例 / 任务卡。
4. **跑首份基线报告**：落盘 `evals/reports/`。
5. **进迭代闭环**：改 → 评 → 对比 → 决定是否合并；报告落盘，趋势线随版本单调改善才是进化。

## 六、方法论自身的约束

- 不发明新描述语言：一律复用辨证语法（§三），新维度表述必须能落进模板与评测。
- 不给未定义行为发明兜底：边界外的行为走显式报错/待确认，不自行降级（呼应 AGENT.md 兜底红线）。
- 每次变更须过评测门禁：改定义/模板 = 改 kit，须附评测报告（`eval-gate.yml`）。
- 维度或模板变更须**同步**更新本文与模板及实例化清单，防模板漂移。
- 本仓库 `references/` 受 L1/S4 占位残留检查与报告门禁监管，禁止未替换占位符入库。

## 七、自指说明

这套方法论自身也在定义自己的进化方式：

- 本 kit = 第 0 号实例（"定义智能体方法论"的方法论，即本文 + `ai-methodology.md` + `eval-framework.md`）；
- 数字人 = 第 1 号实例；
- 本文的变更同样走产物链：intent → spec → 评测报告 → 复盘 → 下一轮，不例外。
