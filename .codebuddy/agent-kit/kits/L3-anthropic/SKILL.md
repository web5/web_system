# L3 · 协作主干（AI Native 编排层）

## 定位

**唯一编排入口**：决定任务怎么分阶段、判据怎么定义、人在哪里审、上下文怎么切分。本层不写具体工程动作的做法（那是 L2 执行手段库），也不重复定义代码质量（那是 L1 行为准则）。

## 入口与流水线

入口：`../../skills/rd-digital-agent/SKILL.md`（Hub，按任务类型与复杂度分派）

```
需求转换 → 方案探索 → 计划（判据表 V1…Vn）→ 执行（TDD + 完成验证门）
        → 实现自查 → 独立盲测 → 人审交付 → 复盘
```

向下调用：

- 执行阶段调用 `L2-superpowers`（TDD / 调试 / 验证 / 并行分派 / worktree / 评审）
- 所有代码产出受 `L1-karpathy` 约束

## 三条不变量

1. **开工前置**：任何任务动手前先定「交付物定义 + 验证判据」，不因任务小而豁免（分级只压缩过程仪式）。
2. **设计与交付验证同构**：设计阶段落盘 `V1…Vn`（四列：判据 / 验证手段 / PASS 条件 / 不通过怎么办），交付阶段按**同一编号**逐条给证据——全程只有这一份清单。
3. **人审三节点**：意图确认 / 设计确认 / 交付前审查，顺序固定 逻辑 → 合规红线 → 对照 spec。

## 红线（机器化）

`../../rules/general/01–05`：循环工作流 / 人审节点 / 版本化产物链 / 子任务隔离 / 红线机器化，每条含判定手段。

## 编排权唯一

本层是**唯一编排入口**：任务怎么分阶段由 `rd-*` 决定。宿主环境若存在同域/同名的第二套编排技能，同域同名冲突以本层 `rd-*` 为准。

这不等于「只许有一种方法论」——L2 执行手段库（TDD / 调试 / 验证 / 并行分派 / worktree / 评审）与 L1 行为准则由本层调用，属本套方法论的组成部分，不属第二套工作流。宿主存在第二套编排时的处理优先级（首选补齐判据字段使其与主链同构，而非整体卸载）见 `../../references/three-kits-architecture.md` §三 R1。
