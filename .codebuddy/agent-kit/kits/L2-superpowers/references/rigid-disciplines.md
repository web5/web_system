# L2 工程纪律 · 详细条目

> 本文件为 `L2-superpowers/SKILL.md` 的按需加载补充。代码产出同时受 `../L1-karpathy/SKILL.md` 约束。

## 1. 强制调用纪律（适用于全部条目）

- 命中即调用：判断某技能有 1% 可能适用，先调用再看，不「先做一步再说」。
- 流程技能优先：决定「怎么做」的技能（调试、验证）优先于「怎么实现」的技能。
- Rigid 条目不可变通：不得以「这次情况特殊」为由跳过步骤；确有冲突应说明为何不适用，而非静默省略。
- 常见自我合理化（出现即停）：
  - "这只是个小问题" → 小问题也会累积成不可回溯的改动
  - "我先探索一下代码库" → 技能会告诉你怎么探索
  - "我记得这个技能的内容" → 技能会演进，读当前版本
  - "这个技能太重了" → 简单的事会变复杂，用它

## 2. dispatching-parallel-agents（Flexible）

**何时用**：一个任务可拆成多个子任务，且子任务之间**无共享文件、无顺序依赖**。

**铁律**：
- 分派前先确认依赖：任一子任务会改到另一子任务要读/改的文件 → 不可并行，改为串行。
- 每个子 agent 独立上下文，完成后立即释放。
- 结果回收格式固定为三项：**结论 + 依据 + 未决项**，缺一视为信息丢失（与 L3 子任务隔离红线同源）。
- 子 agent 返回的是精炼结论，不是全过程流水。

**不用**：子任务间有共享状态 / 需要同一份中间产物 / 总数小于 2。

## 3. using-git-worktrees（Flexible）

**何时用**：需要在不污染当前工作区的前提下改动代码——并行推进多个改动、长任务中途插入紧急修复、需要保留可对比的基线。

**铁律**：
- 改动前建 worktree，不在主工作区直接开新分支改。
- 任务结束后显式清理 worktree，不留下悬挂目录。
- 删除 worktree 前确认其中无未提交改动（与 L1 删除安全同向）。

**不用**：单线小改动、只读探索。

## 4. requesting-code-review（Flexible）

**何时用**：完成一个可评审的变更单元，准备提交或交人审前。

**铁律**：请审必须附齐三项，缺项视为未准备好：
1. **变更范围**：改了哪些文件/模块，一行说清意图
2. **验证证据**：跑了什么检查、结果（对应 L3 的 `V1…Vn` 逐条结果）
3. **已知取舍**：为简洁/性能/兼容做了什么妥协

## 5. receiving-code-review（Flexible）

**何时用**：收到任何评审意见（人、AI、CI）。

**铁律**：
- 先复现再改，不在未复现的情况下照改或辩解。
- 不认同意见时须给出**具体反例或必然失败清单**，不以"我觉得"回应（与 L3 `challenge-playbook` 同格式）。
- 每条意见要么改、要么给出反证，不允许静默忽略。

## 6. writing-skills（Flexible）

**何时用**：新增或修改本 kit 的任意技能 / 红线 / 参考文档。

**铁律**：
- 技能必须同时写清「何时用」与「何时不用」——只写触发条件会导致触发漂移。
- AI 面（`SKILL.md`）只留可执行指令，设计理由进 `RATIONALE.md`（双面分层，见 `references/dual-audience-design.md`）。
- 新增技能须同步：`skills/` 白名单（`eval-gate.yml` S2/S5）、路由决策树、路由用例（`evals/cases/routing.md`）。
- 改动后须附评测报告或 `skip-eval` 说明（见 README §改动 kit 的门禁）。
