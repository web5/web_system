# RATIONALE · 执行手段库（人面）

## 为什么与协作主干是调用关系，不是竞争关系

主干解决「做什么、按什么顺序、拿什么算做成」，本库解决「这一步具体怎么干」。后者只在被前者调用时生效，本身不决定阶段、不产出计划、不定义判据——因此不存在「该走哪套流程」的选择问题。

判断归属的简易标准：**会不会产出「任务下一阶段是什么」这个结论**。会 → 属主干；不会 → 属本库。TDD、调试、完成前验证、并行分派、worktree、评审请接都不产出阶段结论，故全部归入本库。

## 为什么 A 类只写指针、不重写

主干已收编 TDD / 系统化调试 / 完成前验证 / 增量重构（`skills/rd-execute`、`skills/systematic-debugging`、`skills/incremental-refactoring`）。若本库再写一份，同一纪律会出现两个真相源，改一处漏一处——这正是本 kit 反复防的退化形态。因此 A 类只声明「刚性等级 + 触发时机」，实体指针指向主干。

## 强制调用纪律（1% 规则）的取舍

「命中即调用」对 Agent 的偷懒倾向有效，代价是琐碎任务被仪式化。本库的处理：
- 保留命中即调用为默认——漏用技能的代价（跳过 TDD/验证）远大于多读一个索引；
- 用 Rigid / Flexible 分级吸收过度仪式化：只有三条标 Rigid（TDD、系统化调试、完成前验证），其余按场景取舍；
- 与主干的「分级只压缩过程仪式，不压缩交付物定义与判据」同向，不叠加负担。

## 历史教训（归入风险 R1，非本层固有冲突）

曾为排除 Superpowers 的编排类技能，整体卸载 20 个技能（`scripts/uninstall-superpowers.sh`），代价是连 TDD 铁律、完成前验证、并行子 agent 一并丢失。这属于**落地方式**造成的退化，不是三部分之间的固有冲突。现行解法首选「补齐判据字段使宿主流程与主链同构」，整体卸载降为最后手段——详见 `../../references/three-kits-architecture.md` §三 R1。
