# 人在关键节点审核（Human-in-the-loop）

人在三个固定节点把关，而非全程逐字监管：
1. 意图确认：目标与范围是否清晰。
2. 设计确认：结构与方案是否合理。中大型方案按评审链把关：AI 先以 product-review-checklist（产品方案评审）、review-checklist（技术方案评审）自查，人按清单复核结论与依据，而非逐字检查。
3. 交付前审查：逻辑、事实、合规与红线。

审查顺序固定：先逻辑，再合规/红线，最后对照 spec 确认一致性。

评审链：产品方案评审 → 技术方案评审 → 代码评审（rd-review）。小改动走简化档、不走全链——**分级只压缩过程仪式**（评审链 / 辨证问数 / spec 体量），**不豁免定义**：小改动仍须「开工前置」两件套（交付物定义 + 验证判据先行，见 AGENT.md 与 thinking-checklist 简化档 · 最小交付卡）。

AI 负责产出初稿，人负责判断与决策。

## 判定手段

- 条文存在性：`grep -q '人审节点' AGENT.md`（`eval-gate.yml` S6 类检查，删除即 CI 失败）。
- 行为验证：`evals/cases/behavior.md` L3 陷阱用例（「跳过确认直接开工」类静默违反场景）+ L4 任务卡 D3（人审节点）。
- 顺序正确性：独立 judge 按 RUBRIC D3 判定是否 逻辑 → 合规/红线 → 对照 spec。

## 不适用

- 用户已显式预授权「自主完成到底」的任务；仍须在交付时给出可复核记录。

> 为什么固定三处、为什么顺序不可换：见 [`RATIONALE.md`](RATIONALE.md) §2。
