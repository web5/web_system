# 红线设计理由（人面）

> 本目录五条红线的「为什么」集中于此。`NN-*.md` 是 AI 面（约束 + 判定手段），本文件是人面（决策背景 + 失败形态），AI 默认不加载。
> 分层规范见 `references/dual-audience-design.md` §5.2。

## §1 为什么工作以循环组织（01）

**替代方案与其失败形态**：一次成型（拿到需求直接做到底）在需求清晰时最快，但需求稍微含糊，纠偏就发生在交付之后——返工成本随阶段数指数上升。循环的价值不是仪式，而是**把纠偏点前移到下一阶段的输入处**：每阶段产出可供人检查的产物，错误在成为下一阶段输入前被截住。

五阶段的划分依据是「决策性质变化」而非工作量：意图（要不要做）→ 设计（怎么做）→ 执行（做）→ 交付（给出去）→ 复盘（下次怎么更好）。相邻阶段合并的前提是这两种决策可以被同一次判断覆盖。

## §2 为什么人审固定三处、顺序不可换（02）

- **数量**：三处是经验折中——更多人不堪重负（人一旦疲于确认就会机械通过，把关名存实亡），更少则失控。
- **位置**：这三处对应三次不可逆决策——意图（范围锁定）、设计（方案锁定）、交付（对外发布）。错过就无法低成本回退。
- **顺序**：`逻辑 → 合规/红线 → 对照 spec`。倒过来会让合规问题被逻辑讨论掩盖——先聊「这个实现很优雅」，红线就不好意思提了。这是顺序固定而非建议的唯一理由。

## §3 为什么「只在对话里」不算落盘（03）

对话态上下文有三个硬伤：**不可回溯**（会话关闭即失）、**不可交接**（换人换会话看不到）、**可被静默改写**（长任务中先前的口头结论会被后续内容稀释或反向覆盖）。产物落盘把结论变成可引用、可 diff、可交接的对象。

反面证据：判据只口头回读时，设计侧与交付侧各生成一份清单（详见 `skills/rd-plan/RATIONALE.md` §1）。

## §4 为什么子任务要隔离上下文（04）

上下文是有限资源。主线程被细节占满后，指令权重被稀释，表现为「后半段质量明显下降、忘记前面的约束」。隔离不是为省 token，而是**保证每个子判断在干净的上下文里做**，只把结论摘要回传。

已知缺口：本条目前半机器化（D5 依赖 judge 评分），是五条中机器化程度最低的一条。

## §5 为什么文本红线必然退化（05）

文本约定依赖「被读到」，而人会读一次、不会读第二次——新成员看不到、老成员不再看。机器检查依赖「被执行」，只要配置在 CI 里就必然发生。所以「靠自觉的红线不算红线」，须降层为命令或 CI 项。

推论：**一条红线写不出来判定命令，说明它还没定义清楚**（要么拆细，要么它不是红线而是偏好）。

## §6 变更约定

改任一 `NN-*.md` 的**约束**时，同步回答：判定手段是否仍成立？本文件对应节的理由是否仍成立？理由变了而没写下来，下一次改动就失去判断依据。
