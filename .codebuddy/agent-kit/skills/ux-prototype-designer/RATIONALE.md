# ux-prototype-designer 设计理由（人面）

> 本文件不在 AI 执行路径上：AI 默认不加载，只在判断「能否跳过质检 / 能否直接替用户拍板」时按需跟随。
> 改 `SKILL.md` 必须 bump `version` 并同步本文件 `reviewed-at-version`，否则 CI 失败（`eval-gate.yml` S8-2）。
> 分层规范见 `references/dual-audience-design.md`。

## §1 为什么这个角色必须独立（不能由前端或产品代劳）

**会写 HTML ≠ 会做设计判断。** 三者的判断对象不同：

| 角色 | 判断什么 | 代劳的后果 |
|---|---|---|
| 产品 | 做不做（价值） | 由前端代劳 → 产出向「好实现」倾斜，交互问题压到实现后才暴露 |
| **UX（本角色）** | 长什么样、怎么用 | — |
| 前端 | 怎么实现 | 由 UX 代劳 → 原型带上实现约束，失去「廉价试错」的意义 |

与 `skills/rd-plan/RATIONALE.md` §2 同源：编码角色代劳 UI 原型是kit 里返工成本最高的失败模式之一。

## §2 为什么「独立交互质检」与「产品确认」是两件事

- **质检**判「交互是否合格」（信息架构 / 任务流闭环 / 状态矩阵 / 可用性…）；
- **产品确认**判「做不做对的事」。

两者互不替代：产品通过不代表交互合格，交互合格不代表值得做。因此 `SKILL.md` 写死两条：**质检不通过不得宣布完成**、**不以产品确认替代质检**。这不是流程洁癖——把两件事合一，交互缺陷就会以「反正产品已经拍板了」被放行。

## §3 为什么原型不进应用代码目录、不产出 WXML / 原生代码

原型是**沟通产物**，不是实现。进了应用代码目录就会被当作实现（后续被引用、被构建、被误改为"先这样上线"）；产出 WXML / 原生页面则直接越界到前端职责。

非 Web 端（App / 小程序）用 HTML 画**宿主元素**做模拟：目的是让人看到导航、胶囊、TabBar 这些真实环境约束，而不是复刻运行环境。平台原生能力（分享 / 授权 / 支付）HTML 无法真实模拟，因此做「占位入口 + 标注真机语义」——**不假装已实现**是底线（与兜底红线同源：无业务定义走显式标注，不自行发明行为）。

## §4 返工教训：先原型、后实现，与后端是否就绪无关

**实际踩过的**：一次多操作功能开发中，后端能力（数据模型 / 执行器 / 结果回传）先行实现并发布，但多操作的编辑 UI 形态未出原型确认就落地——结果是交互形态被实现倒逼，用户明确指出应先出原型确认再写实现。

**结论**：**即便后端能力已具备，UI 形态仍须先原型确认再落地**。原型的价值是让「范围与交互」在廉价介质上先对齐，而不是等实现完再看。这条适用于任何「后端先行」的场景。

## §5 已知缺口

- 一稿聚焦一个主目标端（不混壳、不做跨端响应式）是强约束；多端需求需分稿或分区标注，尚无自动校验手段。
- 视觉 token 与项目 tokens 对齐依赖项目是否提供 token 文件；不提供时按通用方法产出，需人工确认一致性。
