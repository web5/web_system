# 技术方案评审 (Tech Review / Design Review)

> 定位：评审链中「怎么实现」一环 —— 产品方案评审（做不做对的事）→ **本技能（怎么实现）** → rd-review（实现好不好）。
> 与 rd-review 分工：本技能审方案（架构/选型/结构/契约/风险），rd-review 审实现代码。
> 详细检查清单：`references/review-checklist.md`（评审前逐项自查，材料须自足）。

## 何时触发

当用户给出或 AI 提出涉及以下任一方面的方案时，自动启动审查：
- 新建 / 拆分资料或模块
- 信息结构或存储方案变更
- 对外交付物 / 契约设计
- 内容架构或模板结构变更
- 发布 / 运行方案
- 安全相关（权限、数据保护）
- 第三方工具选型
- 工具链 / 技术选型

不触发：小修、文案修改、单文件微调。

---

## 审查维度

### 1. 结构与边界
- 单元职责是否单一？
- 是否需要新建，还是可复用现有？
- 单元间是否通过明确契约通信？

### 2. 安全设计
- 是否需要权限模型？是否最小权限？
- 敏感数据是否加密 / 脱敏？
- 是否有操作记录？

### 3. 信息设计
- 是否满足结构规范与检索 / 复用模式？
- 是否有清晰的分类 / 标签 / 索引？
- 是否需要版本 / 草稿状态标记？

### 4. 规模与复用
- 是否有重复内容可模板化复用？
- 长任务是否拆分为可独立交付的单元？
- 是否支持多人 / 多渠道复用？

### 5. 可维护性
- 是否有质量校验 / 可验证手段？
- 关键修改是否有记录 / 版本？
- 约定是否可配置 / 集中管理？

### 6. 前提与反例（辨证复核）
- 方案底线假设是否显式标注并验证（`thinking-checklist.md` S3/F1/F3）？
- 反例 / 必然失败清单是否被回应与规避（S5/M1），还是走过场？
- 能力圈外的决策是否已声明并转交确认（M3）？

详细标准见 `references/design-principles.md`；辨证问题见 `skills/rd-plan/references/thinking-checklist.md`；逐项检查见 `references/review-checklist.md`。

## 输出格式

审查完成后，按以下格式输出：

```markdown
## 方案审查

### 方案概述
> 一句话描述

### ⚠️ 风险项（必须解决）
- [ ] 风险1：描述 + 建议

### 💡 优化建议（建议采纳）
- [ ] 建议1：描述

### ✅ 合理项（无需改动）
- 项1：理由

### 综合评分
结构: ⭐⭐⭐⭐ / 安全: ⭐⭐⭐ / 信息: ⭐⭐⭐⭐ / 规模: ⭐⭐⭐

### 结论
✅ 通过（建议优化后执行）/ ⚠️ 有条件通过 / ❌ 需重新设计
```
