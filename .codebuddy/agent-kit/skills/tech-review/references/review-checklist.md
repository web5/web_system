# 技术方案评审清单（Tech Design Review Checklist）

> 写码前对技术方案（design.md / 架构 / 选型 / 接口 / 数据模型）的系统性评审。
> 评审链定位：产品方案评审（做不做对的事）→ **本清单（怎么实现）** → rd-review（实现好不好）。
> 与 rd-review 分工：本清单审「方案对不对、值不值、会不会翻车」；rd-review 审「实现好不好」。
> 前置：方案必须先过需求辨证与产品方案评审（thinking-checklist S1/S2 + product-review-checklist），不评审「解决错误问题的漂亮方案」。

## 评审前置（材料自足）

- [ ] 只读文档能完成评审，不依赖作者演讲带节奏；缺料退回补文档
- [ ] 每个关键决策可追溯：为什么 + 依据 + 备选对比
- [ ] 明写本期范围与「不做的事」

## A. 需求覆盖与价值

- [ ] 解决的是被批准的那个问题
- [ ] 无业务定义、自行发明/兜底的部分为零（兜底红线）
- [ ] 成本（人日）与可观测收益匹配；无更低成本替代（性价比）

## B. 架构与结构

- [ ] 模块边界清晰、职责单一、依赖方向正确
- [ ] 复用现有能力，而非重复造轮子
- [ ] 与现有系统/存量数据兼容：数据迁移、多端/后台/API 同步（系统性检查）
- [ ] 无超越需求的过度设计（KISS，不过早优化）

## C. 非功能需求（最易漏）

- [ ] 性能：响应/吞吐/容量预期 + 验证手段
- [ ] 可用性：单点、降级（只允许有业务定义的降级）、恢复
- [ ] 安全：鉴权 / 最小权限 / 敏感数据
- [ ] 兼容 / 多端 / 升级策略

## D. 技术选型

- [ ] 每个选型有 ≥2 备选对比 + 选定理由
- [ ] 退出成本 / 替换路径明确（不被选型锁死）
- [ ] 成熟度与团队熟悉度匹配风险

## E. 数据与接口

- [ ] 数据模型与核心接口定义完备
- [ ] API 契约语义清晰，无「表象相似实际不同」的坑
- [ ] 存量数据与历史版本兼容

## F. 风险与演进

- [ ] 反例 ≥2 已回应；必然失败的 3 种方式有规避（thinking-checklist S5/M1）
- [ ] 最坏情形与触发条件明确（S6）
- [ ] 演进不被锁死：推翻某惯例/选型的代价已推演（F4 / 终盘反推）

## G. 可执行与交付

- [ ] 任务可独立验证（plan 联动）
- [ ] 上线 / 回滚路径与结果指标口径明确（verification + 结果指标联动）

## 反模式

- 未先辨证需求 / 过产品评审就评审方案
- 评审现场补文档 / 演讲带节奏
- 只审结构，漏非功能与存量数据
- 选型只说「我选它」，不说「为何不选别的」
- 为低频需求付不成比例的架构代价（性价比反模式）
