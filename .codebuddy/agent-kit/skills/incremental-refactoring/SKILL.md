# 🔧 Incremental Refactoring（增量重构）

## 职责

在不改变外部行为的前提下改善内部结构，每一步都有验证保护、可独立回退。

## 触发条件

- "重构"、"清理"、"优化结构"、"消除重复"
- tech-review 指出结构问题后
- TDD 的 REFACTOR 阶段

## 前置条件（不满足则先补）

- [ ] 有行为保护网：测试/校验已存在且全绿；没有 → 先补测试再重构
- [ ] 明确不变式：哪些外部行为必须保持不变

## 工作流

```
重构目标
  ↓
0. 保绿基线：运行全部相关测试，记录绿色基线
  ↓
循环（每轮 = 一个单一意图的小改动）：
  1. 选一个最小结构改动（重命名/提取/内联/移动，一轮只做一种）
  2. 执行改动（优先用工具自动化：符号重命名而非手动替换）
  3. 验证：测试保持绿、不变式未破坏
  4. 记录：本轮改了什么、为什么
  ↓
全部轮次完成 → 全量回归 → verification-before-completion
```

## 步骤粒度标准

| 改动类型 | 一轮的规模 |
|---------|-----------|
| 重命名 | 一个符号的全量替换 |
| 提取 | 一个函数/模块的提取 |
| 移动 | 一个单元的迁移 |
| 内联 | 一处间接层的消除 |

> 经验值：一轮改动控制在「出问题时 10 分钟内可定位回退」的规模。

## 红线

- ❌ 混合意图：同一轮里既重构又修 bug / 加功能
- ❌ 无保护网重构："测试以后再补"
- ❌ 跳过中间验证，攒一大波再测
- ❌ 重构中途顺手"改进"外部行为

## 输出格式

```markdown
## 重构记录

### 不变式
> 必须保持不变的外部行为

### 改动序列
| # | 意图 | 改动 | 验证 |
|---|------|------|------|
| 1 | 提取 <函数> | <文件> | ✅ 全绿 |
| 2 | 重命名 <符号> | <N 文件> | ✅ 全绿 |

### 结果
- 全量回归：N/N 通过
- 结构改善：<before → after 一句话>
```

## 接管规则

- 重构中发现 bug → 单独记录，开独立任务走 `systematic-debugging`，不顺手修
- 涉及跨模块结构重组 → 先走 `tech-review` 评估方案
