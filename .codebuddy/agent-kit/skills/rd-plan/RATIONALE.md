# rd-plan 设计理由（人面 · L2）

> 本文件不在 AI 执行路径上：AI 默认不加载，只在需要判断「能否绕过某步骤」「改动是否破坏设计意图」时按需跟随。
> 改 `SKILL.md` 必须 bump `version` 并同步本文件 `reviewed-at-version`，否则 CI 失败（`eval-gate.yml` S8-2）。
> 分层规范见 `references/dual-audience-design.md`。

## §1 为什么验证判据必须编号落盘（V1…Vn）

**失效形态（实测）**：判据只存在于对话回读时，设计侧与交付侧会各自生成一份清单——设计说「要支持批量导入」，交付说「导入功能完成」，两条都对不上、也无法判定谁违约。宿主项目的计划模板里甚至没有判据字段，表现为「执行过程中设计时看不到交付验证」。

**为什么编号能解**：编号把「设计 ↔ 交付」的同构从口头约定变成可机器核对的事——`tasks.md` 每项绑 V#，交付验证门按**同一编号**逐条给证据。没有编号，就不存在「漏了一条」这个可判定的状态。

**来源口径**：Anthropic *Best practices for Claude Code* — "The most useful specs are self-contained: … they finish with an end-to-end verification step" / "Give Claude a way to verify its work"。本 kit 把它翻译成「判据表作为 spec 收尾章节 + 编号契约」，是本地实现，非原文主张。

**为什么「先写后跑」是硬约束**：实现完再补判据 = 用结果倒推标准，判据就失去 stop condition 的资格。

## §2 为什么可点击原型稿不由本环节代劳

三个角色各管一段，职责混了会在源头丢失判断：

| 角色 | 判断什么 |
|---|---|
| 产品（人 + AI 辅助） | 做不做（价值） |
| UX 设计（`ux-prototype-designer`） | 长什么样、怎么用 |
| 编码（`rd-plan` / `rd-execute`） | 怎么实现 |

**失败案例**：编码角色代劳 UI 原型时，产出会天然向「好实现」倾斜，交互问题被压到实现后才发现，返工成本最高。

**另一条教训**：原型是给人确认交互与范围的，因此**先出原型确认、再写实现代码**——即便后端能力已具备，UI 形态未确认就落地等于用实现倒逼需求。

形态细节（目标端确认、状态矩阵、视觉 token）属 UX 角色职责，本文件与 `SKILL.md` 均不重复定义。

## §3 为什么要求 EARS ↔ V# 覆盖映射

EARS 定义「系统应做什么」，V# 定义「怎么证明它做了」。两者是一一对应的两面：只写 EARS 则会产出无法验收的需求，只写 V# 则会产出没有行为语义的技术动作。覆盖映射是防止「有需求无验证」的唯一机械手段。

## §4 已知反例（评审时按此退回）

| 反例 | 为什么不合格 |
|---|---|
| 「看着对」「改完看效果」「review 一下」当判据 | 无执行手段、无法判定 PASS → 伪判据，退回重写 |
| 判据为空的任务项进 `rd-execute` | 交付物未定义，等于允许边做边定标准 |
| EARS 有 8 条、V# 只有 3 条 | 覆盖缺口，未映射的行为等于没定义验证 |
| 用小改动当理由跳过判据 | 简化档只压缩数量（1–2 条 V#），不豁免存在性 |
