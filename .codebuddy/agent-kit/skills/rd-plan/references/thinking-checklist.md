# 辨证与本质思考清单（Thinking Checklist）

面向「需求澄清 → 方案设计」阶段的底层思考方法。三套方法论融合，各管一件事，避免「做对了但不本质」或「聪明地做蠢事」：

- **苏格拉底式辨证（S）**：防做错事 —— 澄清定义、检验假设、分离证据、证伪、推演后果。
- **第一性原理（F，马斯克）**：做本质的事 —— 锁定底线、拆到原子、区分必然与惯例、从底线重推。
- **芒格思考法（M）**：防聪明地做蠢事 —— 逆向失败清单、误判心理自查、能力圈声明。

## 何时使用

| 场景 | 分级 | 使用方 |
|------|------|--------|
| 日常小改动 / 单点修改 | 简化档 · 最小交付卡（4 行） | 任意实现前 |
| 所有需求澄清与方案设计 | 核心（7 问） | rd-brainstorm / rd-plan |
| 重大 / 模糊 / 跨模块方案 | 强化（10 问） | rd-plan / tech-review（人审复核） |

只作用于需求与设计阶段产物，不适用于执行阶段。简单任务跑全套 = 过度设计，同样违反本清单的初衷。但「全套」仅指辨证问数与文档仪式——**交付物定义与验证判据不在可省之列**：任何任务动手前须产出「简化档 · 最小交付卡」（见下），分级只压缩过程重量，不压缩这两项内容不变量（与 Anthropic「任务开工前先给验收判据」的工作方法论对齐，落点审计见 `../../../references/anthropic-workflow-mapping.md`）。

## 共用执行纪律（铁律，先于一切问题）

1. **答案必须落盘**：写进 `requirements.md` / `design.md` 对应字段；只在脑子里过一遍 = 没做。
2. **答不出 = 待确认**：标为待确认项交给用户，禁止自行脑补（与「兜底红线」同源）。
3. **禁止走过场答案**：找不出反例、写不出规避手段，说明没想透，方案不得定稿。

## 核心 7 问（所有需求/方案必跑）

| # | 来源 | 问什么（AI 自问句） | 怎么算答好 | 落盘字段 |
|---|------|---------------------|-----------|---------|
| 1 | S1 | 用户要的 **X** 到底是什么？ | 一句话可验证的「做成」定义 + 明确「不算做成」的边界 | requirements · 需求辨证 |
| 2 | S2 | 解决的是最原始的问题吗？为什么现在做？**不做/只做一半**损失什么？ | 能指出驱动方是用户/业务/合规，而非惯性；不做代价具体化 | requirements · 需求辨证 |
| 3 | S3+F1+F3 | 方案预设了哪些前提与约束？ | 逐条标 `[物理必然｜业务规则｜惯例｜猜测]`；`惯例` 标红待审 | design · 假设与必然 |
| 4 | S4 | 每个关键论断是**事实还是推断**？ | 论断旁标 `[事实+来源]` / `[推断+推理链]`；空口主张删除或标 TODO | requirements + design 通篇 |
| 5 | S5+M1 | 最可能推翻本方案的 2 个反例？**必然让需求失败的 3 种做法**是什么？ | 反例各配回应；失败做法各配规避手段 | design · 风险与权衡 |
| 6 | M3 | 本方案核心领域我掌握到什么程度？ | 不懂的关键点已显式标出，交用户或查证，不装懂 | requirements / design · 待确认区 |
| 7 | S6 | 推论链走到头：最坏结果、隐性成本、连带改动是什么？ | 列出可观测的最坏情形与触发条件 | design · 风险与权衡 |

## 强化 3 问（仅重大 / 模糊 / 跨模块方案加跑）

| # | 来源 | 问什么（AI 自问句） | 怎么算答好 | 落盘字段 |
|---|------|---------------------|-----------|---------|
| 8 | F2 | 方案能拆到**不能再省的原子**是什么？ | 每个原子写出不可替代职责；任何「为完整而加」的单元在此暴露 | design · 概要/结构 |
| 9 | F4 | 惯例若全部推翻、从底线重算，会得到什么？ | 给出替代方案与成本差；维持惯例也须写「重推后仍维持，因为 ___」 | design · 关键决策 |
| 10 | M2 | 当前推荐是否被以下偏误污染：只找支持证据、锚定首个方案、沉没成本、随大流、过度自信？ | 逐项自检并写明被哪项影响、如何校正 | design · 关键决策旁注 |

## 简化档 · 最小交付卡（日常小改动，任何实现/动手前必答）

> 不变量：交付物定义 + 验证判据**任何任务不可缺省**（不分级）。本卡把「交付物 + 验证」压缩到最少但必答的 4 行；省略的是辨证深度与文档仪式，不是这两项。

1. （S1a）**交付物定义**：做成 = <一句话可验证>；不算做成 = <边界/反例>；改动点/产物清单 = <哪个文件 · 哪处改动 · 哪个接口，可机器核对>。
2. （S1b）**验证判据先行**：动手前写出「怎么做成判定」——代码类：明确或先写测试（对接 rd-execute 的 TDD RED）；文档类：对照 spec/大纲的核对点；探索/发散类：收敛判据 + 质量评分点。禁止用「改完看效果」充当判据。**须编号落盘为 V1…Vn**（四列：判据 / 验证手段 / PASS 条件 / 不通过怎么办），格式见 rd-plan「验证判据表」节——默认回读给用户，跨会话 / 多轮任务随计划落盘，不留在对话里。
3. （S3/F3）我预设了什么？哪条最可能错？
4. （S5/M1）这个做法在什么情况下会失败 / 不成立？

- **产出时机**：动手前完成。可直接回读给用户作最小意图确认；验证判据的 V# 表须落盘（spec 或任务记录），不得只留在对话里。
- **完成引用**：收尾时按 `rd-execute` 的完成验证门，对照同一份 V1…Vn 逐条给证据，禁止退回口头「应该没问题」。

**非代码任务（写作/文档/方案/报告类）的判据先行最小形态 = 动笔前先写「验收核点节」**——第 2 问「文档类：对照 spec/大纲的核对点」的可勾核落地版（代码任务的对等物是 TDD 测试）。最小模板四类核点，可按任务增减：

```markdown
## 验收核点（动笔前先写；交付时逐条勾核并附证据）
- [ ] 内容判据：正文每个关键论断都有出处（原始材料/数据/调研来源），无来源断言 = 不算做成
- [ ] 覆盖判据：<范围/大纲清单> 全部条目在正文体现，无遗漏
- [ ] 边界判据：<不算做成的边界清单> 逐条未越界（如字数 ±30%、不含实现细节、不替读者拍板）
- [ ] 形式判据：符合 <项目写作纪律/格式约定>（可机器抽查）
```

> 引用方：写作/文档型任务卡（`evals/golden-tasks/T3/T5/T6`，及 `digital-agent-eval` 对应卡）按本节形态实例化「期望产物 + 评分点」；宿主项目的写作任务模板可直接复用本节为「验收核点节」。

## 落盘字段模板（与 spec-workflow 对齐）

### requirements.md · 需求辨证（问 1、2、6）

```markdown
## 需求辨证
- 做成 = <一句话可验证定义>
- 不算做成 = <边界 / 反例>
- 原始问题 / 为什么现在做 / 不做的损失 = <驱动方 + 具体代价>
- 能力圈声明 = <本需求核心领域掌握程度；不懂点已标出>
```

### design.md · 假设与必然（问 3、8、9）

```markdown
## 假设与必然
- 底线事实（不可突破） = <F1 答案>
- 约束与前提逐项标注 = [物理必然｜业务规则｜惯例｜猜测] ...
- 最小基本单元 = <F2 答案；含单元职责>
- 惯例项重推 = <F4 答案：替代方案 / 成本差 / 维持理由>
```

### design.md · 风险与权衡（问 5、7、10）

```markdown
## 风险与权衡
- 反例 = <2 个，各配回应>
- 必然失败清单 = <3 种做法 + 规避手段>
- 最坏情形 = <可观测的失败场景与触发条件>
- 误判自检 = <M2 结果>
```

## 与其它约定的关系

- 兜底红线（AGENT.md）：本清单「答不出 = 待确认」是其在需求/设计阶段的执行入口。
- 迭代-校验工作流：本清单校验的是「方向与前提」，产出落在草案阶段；执行质量由 `rd-execute` 的完成验证门负责（对照设计阶段同一份 V1…Vn）。
- 人审节点：tech-review 的「先逻辑」环节按本清单第 3/4/5/7/10 问复核答案质量，防止 AI 自问自答走过场。
