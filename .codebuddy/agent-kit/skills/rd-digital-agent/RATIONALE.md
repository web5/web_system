# rd-digital-agent（Hub）设计理由（人面 · L2）

> 本文件不在 AI 执行路径上：AI 默认不加载，只在判断「能否绕过某条分派 / 门禁规则」时按需跟随。
> 改 `SKILL.md` 必须 bump `version` 并同步本文件 `reviewed-at-version`，否则 CI 失败（`eval-gate.yml` S8-2）。
> 分层规范见 `references/dual-audience-design.md`。

## §1 为什么编排权必须唯一

**双主链的实测失效形态**（宿主项目）：入口一度改走另一套工作流（Superpowers 系列 `brainstorming` / `writing-plans` / `executing-plans`），其计划模板**没有「交付物定义 + 验证判据」字段**，于是下游拿不到判据，验证链被整体架空——实测表现是「执行过程中设计时看不到交付验证」。

**为什么不能两套并存**：两套工作流 = 两个真相源。同一个请求走哪一套，取决于宿主环境里恰好装了什么、甚至取决于加载顺序，行为因此不可预测、不可回归。判据编号（V1…Vn）的契约也会退化：A 链路产生的计划没有编号，B 链路的完成验证门无处对照。

**为什么「环境里正好有」不是选用理由**：可用性 ≠ 适用性。判定标准是「这套流程的产物是否含交付物定义 + 验证判据」，不是「它是否已安装」。

**为什么不优先整体卸载**：冲突面只有 4 个编排类技能（brainstorming / writing-plans / executing-plans / spec-driven-development），卸载面却是 20 个，代价是连 TDD 铁律、完成前验证、并行子 agent 一起丢掉。优先级：补齐判据字段使其与主链同构（首选）→ 同域同名以 `rd-*` 为准 → 整体卸载（最后手段，`scripts/uninstall-superpowers.sh`，幂等可回滚）。完整风险与解法见 `references/three-kits-architecture.md` §三 R1。

## §2 何时把角色升为独立 agent（「三信号」）

默认形态：**单本体 + 分身扮演异质视角**（perspective-taking）。同一个数字人以不同角色立场互相质疑——成本低、上下文可共享。

出现下列任一信号才升为**独立 agent**（独立利益 / 独立上下文 / 独立产出归属）：

1. **需要独立利益或独立汇报线**——如测试角色需对开发结论拥有 veto 权；分身没有真实利益冲突，质疑会软化。
2. **上下文必须硬隔离**——某角色不能看到另一角色的推理过程（例如盲测：测试若看到实现思路，就构造不出独立的反例）。
3. **产出归属需独立可审计**——需要对外部证明「这份结论由独立第三方给出」。

**不升级的代价也要记**：独立 agent 之间上下文不共享，结论必须显式传递，**摘要质量成为协作质量的瓶颈**。因此默认不升级，升级要写出理由。

## §3 为什么需要子 Agent（单 Agent 顺序执行的代价）

| 方式 | 代价 |
|---|---|
| 单 Agent 顺序执行 | 全部历史堆在一个上下文：token 越积越多，指令权重被稀释，表现为后半段质量下降、遗忘前面的约束 |
| 子 Agent 并行 / 接力 | 每 Agent 独立上下文、完成即释放，主 Agent 只留摘要；代价是结论必须显式摘要回传 |

**关键权衡**：子 Agent 不是为省 token，是为让每个子判断发生在干净上下文里。而它的代价正是**摘要质量**——摘要丢信息 = 后续阶段基于残缺输入决策，所以「主线程只保留摘要」这条纪律必须配「摘要要含结论 + 依据 + 未决项」，不是一句话了事（见 `rules/general/04-subagent-isolation.md`）。

## §4 为什么评审链是这个顺序

链：需求转换 → 产品方案评审 → UX 交互质检 → 技术方案评审 → 代码评审 → 测试验证。

- **每道评审对应一类不可逆决策**，越靠前纠正越便宜：需求错了，后面全白做；交互错了，实现完才发现返工成本最高。
- **UX 质检独立于产品评审**：前者判「交互是否合格」，后者判「做不做对的事」。二者互不替代——产品通过不代表交互合格，反之亦然。这是它单列一级而非并入产品评审的原因。
- **测试验证在最后且必须盲测**：若由开发者自证，验证标准会被实现牵引（见 `skills/rd-execute/RATIONALE.md` §2）。盲测的意义是让验证方只按需求 spec 的判据构造反例，看不到实现思路。

## §5 分派决策树的维护约定

决策树的**分支数**决定 L2 路由用例数（`digital-agent-eval/cases/routing.md` 当前 13 条）。新增分支必须同步补路由用例，否则出现「有分支、无验证」的黑洞；删分支同理要删用例。禁止出现「其他」兜底分支——不可分派 = 未定义行为。
