# 🐛 Systematic Debugging（系统化调试）

## 职责

把「凭直觉改到好」变成「先证明根因，再修复」。修复必须建立在被验证的根因假设上。

## 触发条件

- 任何报错、测试失败、意外行为
- 用户说"为什么"、"不生效"、"有 bug"、"帮我修"
- 改动后行为与预期不符

## 核心红线

- ❌ 看到报错就直接改代码碰运气
- ❌ 同时改多处再一起测（无法定位是哪处起效）
- ❌ 修复后不验证就宣称解决

## 四阶段工作流

```
症状
  ↓
1. 读全错误（READ）
   - 完整读取错误信息/日志，不截断
   - 定位：错误类型、位置、首个与最末堆栈帧
   - 区分：根因 vs 连带症状
  ↓
2. 最小复现（REPRODUCE）
   - 找到稳定触发路径；不能复现先解决复现
   - 缩小范围：二分（注释/回退/开关）定位最小触发集
  ↓
3. 假设与验证（HYPOTHESIZE）
   - 提出可证伪的根因假设（1-2 个，按概率排序）
   - 用最小改动/日志/断点验证假设，而非直接修复
   - 假设被推翻 → 换下一个；全部被推翻 → 回到阶段 1，检查隐藏前提
  ↓
4. 修复与回归（FIX & VERIFY）
   - 针对已验证根因做最小修复
   - 补一个「修复前会失败」的防回归测试
   - 运行受影响测试全量，确认无连带破坏
```

## 输出格式

```markdown
## 调试报告

### 症状
> 一句话 + 关键报错

### 根因（已验证）
> 描述 + 验证方式（如何证明是它）

### 修复
> 改动点 + 为什么是最小修复

### 防回归
- [x] 新增测试 xxx（修复前失败，修复后通过）
- [x] 受影响测试全绿
```

## 常见陷阱

| 陷阱 | 对策 |
|------|------|
| 修症状不修根因 | 对错误连问三次"为什么会这样" |
| 复现不稳定 | 先固化复现（固定输入/种子/环境），再调试 |
| 一次改多处 | 每次只改一处，验证后再继续 |
| 隐式前提出错 | 列出依赖的前提（版本/环境/数据），逐个证实 |

## 接管规则

- 根因是跨模块的结构性问题 → 停止修补，转 `tech-review` 评估方案
- 修复完成 → 必须走 `verification-before-completion` 再交付
