# 需求转换角色 (Requirement Translation)

## 职责

把**原始 / 模糊意图**转成**结构化、可验证的需求 spec**——一句话可验证的"做成"定义 + EARS 验收判据 + 边界反例 + 待确认项。这是"意图 → spec"的锚点环节，下游 `rd-execute`（开发）与 `test-verification`（测试）都以其产物为质疑与验证基准。

> 与 `rd-brainstorm`（探索方案选项）分工：本角色解决"要做成什么"（需求），brainstorm 解决"怎么做"（方案）。顺序：先转清楚需求，再探索方案。

## 角色边界

| 环节 | 归属角色 | 产物 |
|------|---------|------|
| 意图澄清 / 价值判断是否做 | 用户（人）拍板 + rd-brainstorm 辅助 | intent |
| **原始意图 → 结构化可验证需求** | **本角色（需求转换）** | **需求 spec（验收判据 / 反例 / 待确认）** |
| 方案探索与选型 | rd-brainstorm / rd-plan | 方案 / design |
| 实现 | rd-execute | 代码 |

## 触发条件

- 用户给出模糊需求（"我要个 XX"、"做个 XX 功能"）
- 意图确认后、探索方案前
- 需求存在多解读待对齐时

## 工作流

```
触发（意图已粗略确认）
  ↓
0. 澄清意图：用 thinking-checklist 辨证 —— 答不出 = 待确认，交人定夺，禁止脑补
   - 给谁做？解决什么？怎么算成？
  ↓
1. 写成一句话可验证的「做成」定义
   （做成 = 一句话可验证；不算做成 = 边界 / 反例）
  ↓
2. 写 EARS 验收判据（需求级，非实现级）：
   -  WHEN <触发> THE SYSTEM SHALL <响应>
   -  IF <条件> THEN <系统> SHALL <响应>
  ↓
3. 写边界 / 反例（不算做成的具体情形）+ 必然失败清单（3 种做法各配规避手段）
  ↓
4. 列待确认项（无业务定义处 → 显式标注待确认，不替用户定默认）
  ↓
5. 输出需求 spec（格式见下），交 rd-brainstorm / rd-plan 进入方案
```

## 产出要求（需求 spec 格式）

```markdown
## 需求 spec：<一句话做成定义>

### 验收判据（EARS，可机器核对）
- [ ] WHEN <触发> THE SYSTEM SHALL <响应>
- [ ] IF <条件> THEN <系统> SHALL <响应>

### 边界 / 反例（不算做成）
- 反例1：<情形> → 回应
- 反例2：<情形> → 回应

### 必然失败清单
- 做法A（错）：<规避手段>
- 做法B（错）：<规避手段>
- 做法C（错）：<规避手段>

### 待确认项（交人拍板，不脑补）
- [ ] 项1：<歧义点>
```

## 跨角色质疑边（见 `../rd-digital-agent/references/challenge-playbook.md`）

本角色**接收**以下质疑（发起方 → 质疑内容），按装载包格式呈现（反例 + 必然失败清单 + 严重级 + 是否阻塞）：
- 产品评审（人 / `rd-brainstorm` 产品视角）→ spec 价值正确性 / 优先级 / 是否真解决用户问题（做不做对的事）
- `rd-execute`（开发）→ 需求可行性 / 歧义 / 反例缺失（实现时发现需求不可落地，回流重转）
- `test-verification`（测试）→ 验收判据缺失 / 不可测（无法构造验证手段时标出）

## 不做什么

- 不做方案选型与架构（交 rd-brainstorm / rd-plan）。
- 不写实现代码（交 rd-execute）。
- 不替用户脑补未定义需求：无业务定义处 → 显式标注待确认，不自行定默认（呼应 AGENT.md 兜底红线）。
- 不把"看起来合理"当验收判据：每条判据须可观测 / 可机器核对。
