# RATIONALE.md · design-reviewer 设计理由与返工教训

> 人面文件，**不在 AI 执行路径上**（`SKILL.md` 不 loads 本文件）。改 `SKILL.md` 版本须同步 `reviewed-at-version`。
> 回答三个问题：**为什么这么设计 / 踩过什么坑 / 完整接线长什么样**。

---

## §1 为什么必须独立（不是"多一道检查"）

**根因**：出稿者自审必然护短。这不是态度问题，是结构问题——一个人无法同时客观评价自己刚做的决策。

早期做法是「出稿 + 自检清单」，结果：
- 清单能拦住"忘了做空态"这类**遗漏**
- 拦不住"这个交互设计本身就不对"这类**判断**

后者需要第三方视角。所以把「生产」与「评审」拆成两个角色，且**评审方禁止读出稿方的自辩段**（机制①）。

> 这条是三条独立性机制里最容易被忽略、也最容易被破坏的一条。若评审时顺手读了「设计决策记录 · 为什么这么设计」，评审水位会立刻掉回自审。

---

## §2 三条独立性机制怎么来的

| 机制 | 解决的失效模式 |
|---|---|
| ① 盲审隔离（先读判据再看产物） | 评审被产物"锚定"：看到实现就默认它是对的，只挑小毛病 |
| ② 独立上下文（sub-agent 执行） | 主 Agent 已知出稿过程，评审结论被污染 |
| ③ 判据外部化（必须指编号） | 评审变成审美争论，谁也说不服谁，最后看谁嗓门大 |

**机制③是关键设计**：它把"我觉得"和"判据说"分开。指不到编号的意见**自动降级**，这既保护了被评审方（不会被个人偏好绑架），也保护了评审方（不必为审美分歧辩护）。

## §3 判据为什么做成编号条目

早期判据是散文式描述（"层级要清晰""颜色要克制"），问题是**不可裁决**——读到就能回答"这份稿合格吗"吗？答不了。

改造成编号条目后，每条含三要素：

```
ID + 判据一句话 + 不合格形态（反例）
```

反例是关键。没有反例的判据等于没写，因为「不合格」的样子说不出来，就判不了。

现 76 条分布：P(原则)6 / E(层级·密度)13 / F(间距)6 / G(色彩·圆角)12 / M(交互模式)6 / A(锚点)4 / S(状态)9 / H(文案)6 / I(端差异)5 / X(反模式)9。

## §4 web_system 的完整接线（L3 参考实现）

本专家的 L3 接线在 web_system 已落地。**这是项目层配置，不在专家交付范围内**，列出供需要 L3 的项目参考：

| 组件 | 位置 | 作用 |
|---|---|---|
| commit 凭证校验 | `scripts/redline/check-commit-msg.sh` | UI commit 须带 `Proto: <sha>` + `Design: pass` |
| CI 兜底 | `.github/workflows/quality-gate.yml` → `scan-rules.sh` R11（error 级） | 校验报告落盘 + `阻塞: 0` |
| IDE hook（4 个） | `.codebuddy/settings.json` | PreToolUse 拦 Write/Bash 改 UI；SessionStart 注入门禁上下文 |
| 锚点机检 | `scripts/redline/scan-design-drift.py` | `data-dr` 锚点比对实现是否漂移原型 |
| 分档开关 | `DESIGN_ANCHOR_MODE=off\|warn\|scoped\|strict` | 存量回填完成前不 error，避免一次性炸出上百条 |

**关键经验**：`DESIGN_ANCHOR_MODE` 的四档渐进是必要的。web_system 有 129 个界面文件需要补锚点，一开始就 `strict` 会让 CI 全是红色、团队直接关掉门禁——**门禁一旦被关，就再也开不回来**。
