# Spec 工作流（方案文档规范）

## 何时产出 spec 文档

以下情况建议在 `<feature>/` 下生成正式文档：
- 新建一个独立模块 / 产品 / 流程
- 跨 2 个以上子团队或子系统的改动
- 信息结构 / 对外交付物变更
- 范围模糊、需要先对齐再动手
- 用户明确说「写文档」或「记录方案」

## 文档模板

> 「需求辨证」「假设与必然」「风险与权衡」三节的必答问题见 `skills/rd-plan/references/thinking-checklist.md`（苏格拉底辨证 + 第一性原理 + 芒格反例/能力圈，按复杂度分层取用）。答不出即列为待确认，禁止自行脑补。
> 评审链：requirements 定稿过产品方案评审（`rd-digital-agent/references/product-review-checklist.md`）；design 定稿过技术方案评审（`tech-review/references/review-checklist.md`）；执行完成后由 rd-review 审实现。

### 1. requirements.md（需求）

```markdown
# <名称> · 需求文档

## 背景与问题
<一句话描述为什么要做>

## 目标用户 / 受众
- 作为 <角色>，我希望能 <功能>，以便 <价值>

## 验收标准
- 当 <触发条件>，应 <行为>
- 在 <前提> 下，当 <触发>，应 <行为>

## 约束
- 性能：<如响应时间>
- 合规：<如权限要求>
- 兼容：<如不影响现有能力>

## 需求辨证
- 做成 = <一句话可验证定义>
- 不算做成 = <边界 / 反例>
- 原始问题 / 为什么现在做 / 不做的损失 = <驱动方 + 具体代价>
- 能力圈声明 = <核心领域掌握程度；不懂点已标出>
```

### 2. design.md（设计）

```markdown
# <名称> · 设计方案

## 概要
<用文字或图示描述结构关系>

## 关键决策
<选型与权衡（含惯例重推结论、误判自检）>

## 假设与必然
- 底线事实（不可突破）= <F1>
- 约束与前提逐项标注 = [物理必然｜业务规则｜惯例｜猜测] ...
- 最小基本单元 = <F2；含单元职责>
- 惯例项重推 = <F4；替代方案 / 成本差 / 维持理由>

## 对外交付物
<格式 / 结构 / 约定>

## 风险与权衡
- 反例 = <2 个，各配回应>
- 必然失败清单 = <3 种做法 + 规避手段>
- 最坏情形 = <可观测的失败场景与触发条件>
- 风险：<描述> → 缓解：<措施>
```

### 3. tasks.md（实施计划）

```markdown
# <名称> · 实施计划

- [ ] 1. <任务标题>
  - <具体步骤>
  - _验收：<标准>_
```

## 不写 spec 的情况

- 单点小修（无结构变更）
- 文案 / 样式微调
- 已有清晰任务清单的简单改动
- 用户说「不用写文档，直接改」

## 行为约束

1. 每个阶段必须求确认：brainstorm 方案 → 确认 → plan → 确认 → execute。
2. 不猜测未明确的意图：需求模糊时主动追问。
3. 保持文档简短：不追求完整，追求可执行。
