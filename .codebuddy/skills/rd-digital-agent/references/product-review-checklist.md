# 产品方案评审清单（Product Review Checklist）

> 对「产品方案 / 需求」在进入技术方案前做系统性评审：问题真不真、值不值、怎么算成功、范围对不对。
> 评审链定位：**本清单（做不做对的事）** → 技术方案评审（review-checklist）→ rd-review（实现好不好）。
> 与 thinking-checklist 分工：S1/S2 需求辨证是产出时的自问工具；本清单是在固定节点对产物做检查的工具（评审「辨证是否过关、值不值、范围对不对」）。
> 前置：需求已过需求辨证（thinking-checklist S1/S2）；材料自足，不演讲带节奏。

## 评审前置

- [ ] 一句话价值主张：给谁、解决什么问题、为什么由我们做
- [ ] 目标用户与核心场景明确——不是「虚拟用户」，需求方不能代表用户

## A. 问题真实性

- [ ] 真问题还是伪需求？有证据（用户访谈 / 数据 / 反馈），不是想象
- [ ] 用户说「要功能 X」背后要完成的真实任务是什么（不拿现象当需求）
- [ ] 频次与影响：高频低成本优先；低频高成本须有证据支撑

## B. 价值与优先级

- [ ] 必要四问：不做会怎样？做了用户明显变好吗（价值可证伪）？现在必须吗？最小可行是什么？
- [ ] 优先级与范围：本期做哪些 / 明确不做哪些，有取舍依据
- [ ] 成本（人日 / 资源）与可观测收益匹配；无更高性价比替代

## C. 成功指标

- [ ] 有结果指标（可观测口径），不只行为验收
- [ ] 指标分级（北极星 → 次级）；上线前埋点口径已定

## D. 竞品与惯例

- [ ] 有同类先例？符合用户操作心智（反「伪创新」）
- [ ] 违背惯例处有明确理由；一致性（交互 / 组件 / 术语）有约定支撑

## E. 需求完整性（动到系统哪些部分）

- [ ] 系统性：后台 / 多端 / API / 存量数据 / 与其他功能逻辑冲突
- [ ] 非功能边界显式声明，或明确标注「未定，待技术方案评审」
- [ ] 变更成本被严肃对待：涉及存量数据迁移 / 版本兼容的变更不是「改点代码」

## F. 可评审性与闭环

- [ ] 材料自足、每个决策可追溯（为什么 + 依据 + 备选）
- [ ] 验收标准（EARS）与结果指标两者齐备
- [ ] 评审结论落盘：问题 → todo，进下一阶段

## 反模式

- 用「创新」当违背惯例的挡箭牌
- 虚拟用户 / 拿需求方当用户
- 只给行为验收不给结果指标
- 灵光一现就上会（需求未经冷却沉淀）
- 只改单端，不看系统性影响

## 参考源（仅取可执行内核，非官方规范）

- 腾讯需求评审五维（系统性 / 惯例 / 一致性 / 非功能 / 性价比）
