# 迭代-校验工作流（Iterate-Verify）

任何需要质量的产出，遵循「草稿 → 校验 → 精修」循环，而非一次成形。

## 三个阶段

1. **草稿（Draft）**：先产出最小可用版本，明确预期行为与边界，不追求完善。
2. **校验（Verify）**：对照验收标准自检，此时应发现问题（未达标）。
3. **精修（Refactor）**：在不改变结论/意图的前提下优化表达与结构，保持达标。

## 何时使用

| 场景 | 建议 |
|------|------|
| 新方案 / 新文档 | 强烈推荐：先写骨架，再补全 |
| 修正问题 | 推荐：先复现问题，再修正 |
| 重构 / 改写 | 必须：确保有对照标准再改 |
| 简单微调 | 可选 |

## 步骤

### 1. 明确验收标准
界定产出要满足什么、面向谁、成功标准是什么。输出清晰的验收点。

### 2. 写最小草稿（Draft）
只求覆盖核心预期，可接受不完整，但结构清晰。

### 3. 对照校验（Verify）
逐条对照验收标准，标记未达标项。验证：应能指出具体差距。

### 4. 补充与扩展
覆盖更多场景与边界，驱动内容完善。重复草稿-校验循环。

### 5. 精修（Refactor）
优化结构与表达，消除重复，改善命名，保持验收全部通过。验证：整体达标且更清晰。

## 编写原则

- 描述性标题：每个小节说明其主张，而非「说明1」「测试1」。
- 单一职责：一个段落只表达一个主张。
- 显式边界：明确范围外的内容，避免隐含假设。

## 常见陷阱

- 校验实现细节而非行为：应校验对外可见的结果。
- 校验过于复杂：拆分为多个独立小项。
- 跳过精修：草稿达标后直接推进下一项，技术债累积。

## 总结

| 阶段 | 目标 | 验证 |
|------|------|------|
| Draft | 最小可用草稿 | 结构存在、核心覆盖 |
| Verify | 对照标准找差距 | 能指出未达标项 |
| Refactor | 优化表达结构 | 验收保持通过 |

核心理念：迭代-校验不是为了「测试」，而是为了「设计」——校验只是副产品。
