# 评审链：环节 × 角色（细节真相源）

> 本文是 `rd-digital-agent` 评审链的**展开细节**，由 `SKILL.md` 按需加载。
> **为什么分离**：Hub 属 `hub` 类技能（行数上限 260），评审链完整展开会挤占编排决策的上下文预算；
> 而「环节 × 角色」必须给出完整表格才能真用。SKILL.md 只留骨架与触发条件，展开落在这里。

---

## 一、模型：环节 × 角色（不是一条链）

早期把评审写成一串编号（0→7）会掩盖一个事实：**同一条链上，生产与评审是两种角色**。
真实结构是二维的——环节有先后，但每个环节内并列三种角色 + 一个人审节点：

| 角色 | 含义 | 判定 |
|---|---|---|
| **生产者** | 产出该环节主产物 | — |
| **自查** | 生产者自过，是**下限** | 挂在环节内（`.1`），**不替代第三方** |
| **独立评审** | 第三方盲审 | 盲审隔离 + 独立上下文 + 判据外部化，**缺一即退化为自审** |
| **人审** ◆ | 人裁决 | 确认权始终在人；AI 无权替自己确认 |

> 判据：**凡是"生产者自己过一遍"，都不是第三方评审。** 两者差异不在清单长短，在**上下文与利益是否分离**。

## 三、跨角色回流边（评审的价值在回流，不在结论）

沿用 `challenge-playbook.md` 的质疑格式：**反例 + 判据编号 + 严重级 + 是否阻塞**，禁止"感觉不对"式否定。

核心边（角色未装配时该边不生效，不视为未定义分派）：

| 边 | 发起 → 目标 | 内容 | 回流 |
|---|---|---|---|
| 可测性→需求 | `test-verification` → `requirement-translation` | 判据不可测 / 反例缺失 | 补判据 |
| 契约→方案 | `contract-reviewer` → `rd-plan` | 破坏性变更无迁移路径 / 无消费方清单 | 改方案或补消费方清单 |
| 契约→开发 | `contract-reviewer` → `rd-execute` | 消费方未同步（如 import 型消费方仍用已删类型） | 交开发整改 |
| 设计→原型 | `design-reviewer` → `ux-prototype-designer` | 阻塞项（含反例） | 退回重出，**不代改** |
| 设计→开发 | `design-reviewer` → `rd-execute` | 实现漂移项 | 交开发修复 |
| 发布→开发/方案 | `release-reviewer` → `rd-execute` / `rd-plan` | 依赖顺序错 / 配置不一致 / 无回滚锚点 | 整改后放行 |
| 测试→开发 | `test-verification` → `rd-execute` | 产物未满足验收判据（可复现反例） | 交开发修复 |
| 原型→设计 | `ux-prototype-designer` → `design-reviewer` | 判据不可实现 / 与目标端平台冲突 | 复核判据 |
| 运营→判据源 | 复盘 → 各评审 | 新故障模式 | 回灌为判据条目 |

## 四、独立评审的通用契约（每个评审角色都要满足）

1. **盲审隔离**：先读**判据源**形成"应该是什么样"，再看被审物；**不采信生产者自辩**（"这个没人用"必须给 grep 证据）。
2. **独立上下文**：以 sub-agent 执行，主 Agent 只回收摘要（结论 + 依据 + 未决项）。
3. **判据外部化**：每条结论必须指到**判据编号**；指不到的一律降级为「建议」并标注"无判据，属个人偏好"。
4. **只回流不代改**：不出稿、不改码、不改被审物。
5. **报告可机检**：落盘 + 机器可读头（阻塞 / 重要计数）+ 项目侧 commit 凭证或 CI 规则。

> 第 5 条是把"评审过了吗"从自觉变成事实的关键：**机器读不到评审质量，但能读到报告落盘并进了 git**。

## 五、分级与短路（避免门禁被关掉）

| 级别 | 判定 | 路径 |
|---|---|---|
| L0 | 微改动（≤5 行、单文件、纯文案/纯配置值） | 免评审，走豁免标记 |
| L1 | 小改动（单模块、无契约变更） | 生产者自查 + 完成验证门 |
| L2 | 中改动（契约 / 接口变更） | 全链 + 契约评审 |
| L3 | 大改动（跨模块 / 跨端 / 数据迁移 / 发布） | 全链 + 4 个人审节点 + 发布评审 |

两条纪律：

- **豁免口径必须一致**：同一种「微调豁免」语义要在所有机器检查里同时生效，否则"记了豁免还报错"会成为新的摩擦源。
- **作用域按改动面收窄**：纯文档 / 无关脚本改动应零摩擦。**摩擦过大的门禁最终会被关掉，等于没做。**

## 六、项目可选装配的评审角色

以下角色为**通用契约 + 项目判据**结构：角色协议（独立性机制 / 报告格式 / 回流边）是通用的，
**判据源必须由项目提供**（判据随领域而变）。项目未装配时，Hub 对应分支不生效，不视为未定义分派。

| 角色 | 领域 | 项目需提供 |
|---|---|---|
| `design-reviewer` | 视觉交互设计 | 设计基线条目（本 kit 提供方法与清单骨架，项目填判据） |
| `release-reviewer` | 发布与环境 | 发布判据清单（运行面 / 配置面 / 数据面 / 前端面 / 特殊通道） |
| `contract-reviewer` | 跨端/跨服务契约 | 契约登记（接口 / 事件 / 工具 / 权限码 / 路由）+ 消费方清单 |
| `code-reviewer` | 代码质量（独立于实现者自查） | 项目代码红线清单 |

> 装配方式：把角色技能放进项目的运行源，并把**判据源**落为项目文档；再在项目侧登记机器检查
> （凭证 trailer / CI 规则），使其"可机检"而不只是"有约定"。

## 七、与交付门禁的关系

评审链是**质量门**，交付门禁是**准入项**（见 SKILL.md「交付门禁」）：前者判"做得对不对"，后者判"该有的产物有没有"。
两者都不豁免「**交付物定义 + 验证判据先行**」这一开工前置不变量——判据先行才有资格当 stop condition。
