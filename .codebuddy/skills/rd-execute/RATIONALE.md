# rd-execute 设计理由（人面 · L2）

> 本文件不在 AI 执行路径上：AI 默认不加载，只在判断「能否绕过入口门禁 / 完成验证门是否可豁免」时按需跟随。
> 改 `SKILL.md` 必须 bump `version` 并同步本文件 `reviewed-at-version`，否则 CI 失败（`eval-gate.yml` S8-2）。
> 分层规范见 `references/dual-audience-design.md`。

## §1 为什么入口门禁卡这四项

准入项 = **计划（TODO 每项绑 V#）+ 方案 + 验证判据表 + 原型稿状态**。每一项对应一个「一旦跳过就无法低成本回头」的点：

| 准入项 | 缺失后会发生什么 |
|---|---|
| 计划 + 方案 | 执行侧自行决定做什么，需求方在设计确认后失去一次纠偏机会 |
| 验证判据表 | 交付标准由结果倒推——先实现再补判据，判据就失去 stop condition 的资格 |
| 原型稿状态 | 交互问题被压到实现后暴露，返工成本最高 |

**「判据缺失不是边写边补」**是最容易被协商掉的一条。它不是流程洁癖：判据一旦可以在实现后补，它就从「验收标准」降级成「验收记录」，设计与交付的同构随之失效（详见 `skills/rd-plan/RATIONALE.md` §1 的实测失效形态）。

**为什么原型稿「有没有」由 `rd-plan` 判定、execute 只校验**：该不该有原型稿是设计决策（用户拍板），execute 无从判断，只能校验 rd-plan 写入 TODO 的状态位。让执行侧判断「这次要不要原型」等于让实现方决定要不要被确认。

**小改动的判据最小形态**：简化为 1–2 条 V# 写进计划即可，**不可为空**。分级压缩的是数量与仪式，不是存在性。

## §2 为什么完成验证门必须对照同一份 V#

**异化形态（真实发生过的）**：交付时另拟一份「检查清单」勾核——看起来也逐条打勾，但与设计侧的 V# 无编号对应，于是「漏了一项」变成不可判定的状态。编号是唯一能让「漏」这个状态可观测的机制。

**为什么部分达成必须显式列出、不许静默**：无业务定义的路径自行兜底 = 发明行为，属红线（见 `AGENT.md` 兜底条目）。验证门要求「未达成项显式列出并已告知用户」，是把红线变成一道可勾核的工序。

**「用计划中的行为冒充已验证的行为」为什么单列为反模式**：混淆了「设计上会这样」与「跑出来是这样」，是设计与交付同构失效最隐蔽的形式——两份清单都写着同一句话，但一句是承诺、一句是结果。

## §3 为什么不主动 commit

commit 是对外不可逆动作，落在人审节点（见 `rules/general/02-human-in-loop.md`，交付前审查）。执行侧提示可提交、由人拍板——不是权限问题，是**责任归属**问题：谁承担「这批改动进入历史」的后果，谁按确认键。

## §4 反模式清单的出处

`SKILL.md` 的反模式不是凭空列举，每一条都对应一次实际返工，**新增反模式须附真实案例，否则不许入库**：

| 反模式 | 出处 |
|---|---|
| 「我修改了 X，现在应该没问题了」 | 完成声明无证据——红线机器化（eval-gate）之前的主要失效形态 |
| 只跑一个测试宣称全绿 | 抽样偏差：单测通过被当作整体验证通过 |
| 判据部分达成时宣称「完成」 | 静默降级，掩盖未达成项 |
| 用计划中的行为冒充已验证的行为 | 承诺与结果混写（见 §2） |
| 跳过 V#、改用临时清单勾核 | 编号契约失效，漏项不可判定 |

## §5 已知缺口

- 完成验证门的「lint / 类型检查通过」是通用要求，不区分技术栈；宿主项目需自行实例化具体命令。
- 子代理调度表（并行 / 团队模式）依赖宿主环境是否提供 `Task` 工具，环境不支持时应退化为串行执行，不视为违反工作流。
