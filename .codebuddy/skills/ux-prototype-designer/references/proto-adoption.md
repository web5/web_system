# 可并入性（一份稿怎么活下来、怎么被复用）

> 加载时机：出稿前定目录、出稿后自检、以及「要不要新开一份稿」这个念头出现时。
> 本文只讲**稿的工程形态**（能不能被整合/复用），不讲视觉与交互设计（那是 `prototype-common.md`）。

---

## 一、为什么这件事值得单独一章

原型最贵的失败不是「做得丑」，是**做完之后没人能用**：

| 症状 | 真实成本 |
|---|---|
| 稿写在应用代码目录（`apps/*/prototype/`） | 整合脚本只扫一个目录 → 抽不到 → 整合稿里永远是占位，等于白做 |
| 同一模块 v5…v14 平级堆放 | 评审不知道该看哪份；开发照着 v9 实现了 v14 已经否掉的设计 |
| 稿自带壳、自带路由 | 并进整合作品后两套壳、两套路由互相覆盖/劫持 |
| 类名用 `.btn/.card` 且不做作用域 | 并进去第一个症状就是「样式全乱」 |

共同点：**都不是写稿时的错，是「稿被当成一次性文件」的错**。
一份稿要被复用（整合进总稿、被别人接着改、被开发当对照源），就必须满足几条工程约束。

---

## 二、两条硬规则

### 2.1 一份稿只有一个家

- 落在项目约定的**统一原型目录**，且该目录必须是自动化整合的扫描根。
- ❌ 不新建 `apps/*/prototype/`、`src/prototypes/` 之类的第二目录。
  即使它看起来「离代码更近、更方便改」，也会让脚本与人对稿的认知分叉。
- 路径一旦定下就不要挪。要挪就一次挪干净（连同引用它的文档、注册表、脚本），
  否则会出现「注册表指向旧路径 → build 直接崩」或更糟的「注册表指向一个已废弃的副本」。

### 2.2 多版本不平级堆放

- **目录里只留当前有效版**；旧版进 `_archive/`（或同等语义的子目录）。
- 判断「当前版」的依据按优先级：① 注册表/索引里被引用 ② 文件名版本号 ③ 最近修改时间。
  只有 ③ 是不够的 —— 有人打开旧版看一眼就会更新 mtime。
- 归档不等于删除：设计决策的过程有追溯价值，但**不能和当前版平级**。

## 三、九个坑（写稿时就避开，比事后改造便宜十倍）

| # | 坑 | 判定 | 正确做法 |
|---|---|---|---|
| 1 | 自带整页壳 | 稿里有侧边栏/顶栏/面包屑 | 壳归**壳单源**（项目里通常有一份 shell 模块对齐真实前端布局）。稿只写内容区；整合时壳由宿主提供 |
| 2 | 自带 hash 路由 | `location.hash =` / `hashchange` 监听 | 整合宿主通常也用自己的 hash 路由，两者互斥（切一次就互相踢回默认屏）。要么把路由段标记成可整段丢弃，要么改成可注入的回调 |
| 3 | 评审台与产品代码混在一起 | 演示控件（场景包/角色/数据态）的 JS 直接跑在主逻辑里 | 控件是**独立打开时**的评审台，整合时必须能整段丢弃。用标记段（`// DEMO-PANEL-START/END`）包起来，且所有调用点加 `typeof` 守卫 —— 守卫是为了「整合稿里没有它也不报错」，不是为了「藏起来」 |
| 4 | 图标 sprite 放在内容区之外 | `<svg><symbol id="...">` 在 body 顶层 | 只抽内容区会把图标库丢掉 → 整稿图标全空（DOM 里 `<use href="#i-x">` 还在，所以不报错、只是空白）。图标库要单独声明抽取，且 id 加前缀防撞 |
| 5 | 屏容器类名与宿主撞名 | 稿用 `.screen`、宿主也用 `.screen` | 切屏按 **id 精确操作**，不要用类选择器遍历；宿主侧也把选择器收紧成「带数据属性的屏」 |
| 6 | 裸通用类名不做隔离 | `.btn/.card/.table/.modal/.drawer/.tag/.chip` 等大面积使用 | 二选一：**scope**（给每条规则加作用域前缀）或 **白名单**（只取带私有前缀的规则，如 `.st-*`）。谁都不做 = 样式污染，这是最高频事故 |
| 7 | 内容区外的弹层被漏掉 | drawer / mask / toast 写在内容区之后 | 单独声明「尾随片段」一起抽取；否则症状是「点新增 → 找不到抽屉」 |
| 8 | 跨屏跳转被拆散 | 模块内 A 页 JS 跳 B 页（B 属于另一个菜单项） | **这一条决定装配方式**（见 §四）。拆了就会「点了什么也不发生」 |
| 9 | 屏名/菜单 key 各说各话 | 稿的 section id ≠ 宿主菜单的 screen key | 装配时显式写映射表（`宿主屏 key → 稿内 section/根键`），并让脚本校验映射值都在菜单里 |

## 四、按屏拆 vs 整块搬：唯一判据是「有没有跨屏跳转」

| 情况 | 装配方式 | 理由 |
|---|---|---|
| 多屏之间**不互相跳**，只是同一个模块的并列页 | **按屏拆**（一屏一份 DOM，共用一份 CSS/JS） | 每屏只装自己那份，页面更轻 |
| 多屏之间有**跨页跳转**（详情页「去成文页查看」、空态「前往配置页」） | **整块搬**（DOM 不拆，切屏时把整块移到当前屏） | 拆开后目标 section 落在被隐藏的屏里，跳转静默失效 |

判据只有这一条。**不要在没确认是否有跨页跳转前就按屏拆** —— 这是最贵的返工点：
拆完才发现要跳转，等于把装配方式推倒重来。

无论哪种，**CSS/JS 只注入一次**。注入 N 次 = N 份状态机互相打架，症状是「改了一处，另一处跟着变」。

## 五、出稿后自检（10 分钟，能省一轮返工）

1. **位置**：稿在统一原型目录里吗？是整合脚本的扫描根吗？
2. **壳**：稿里有壳吗？有的话，抽取起点是否已在内容区内（壳没被抽到），或已声明丢弃？
3. **路由**：有 `location.hash` 赋值吗？它落在「可整段丢弃」的区间里吗？
4. **评审台**：控件 JS 有标记段吗？所有调用点有 `typeof` 守卫吗？
5. **图标**：有 `<symbol>` 吗？它会被抽到吗？
6. **类名**：裸通用类名超过 3 种吗？做了 scope 或白名单吗？
7. **弹层**：drawer/mask/toast 在内容区内还是外？声明尾随片段了吗？
8. **跳转**：稿内有 `go('x')` 且目标不是当前屏吗？→ 用「整块搬」
9. **映射**：宿主菜单的屏 key 与稿的 section/根键对得上吗？映射表写了吗？
10. **记录**：有没有同名设计决策记录？遗留项登记了吗？

> 项目里若有对应的静态检查脚本（如 web_system 的 `scripts/check-proto-adopt.mjs`），
> **直接跑它**，不要靠人眼过这 10 条。脚本能判的和人能判的，永远选脚本 ——
> 人会漏，而且漏了不自知。
> 同理：目录级「有没有散落稿 / 有没有多版本堆叠」也该由脚本守（如 `scripts/audit-proto-registry.mjs`），
> 而不是靠定期人工整理。

## 六、反模式

| 反模式 | 为什么错 |
|---|---|
| 「先做出来再说，整合的时候再改」 | 改造要动 CSS 作用域、JS 命名空间、DOM 结构，等于重写。**写的时候多花 10 分钟，整合省 1 小时** |
| 「留一份旧的做备份，以防万一」 | 版本管理就是备份。平级堆放只会让人照旧稿实现 |
| 「多个模块合成一份大稿更省事」 | 一份稿只能有一个主目标端与一套壳。合稿后任一模块改版都要重排整稿 |
| 「控件藏起来就等于整合好了」 | 藏 DOM 不断 JS：`location.hash` 还在跑、`body` 属性还在改。必须整段丢弃或守卫 |
| 「机检过了就没事了」 | 机检只验静态结构。样式是否串、图标是否空、跳转是否通，必须真开浏览器看一眼 |
