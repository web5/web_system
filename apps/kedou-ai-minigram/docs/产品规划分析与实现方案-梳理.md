## 0. 一句话结论

- **规划侧已经闭环**：原型 + 4 篇方案文档把「做什么、放哪层、改哪些文件、怎么验」都写完了，不需要重写。
- **代码侧停在「高保真 UI 骨架」**：28 个页面里新骨架 11 页全是假数据，唯一真链路是合同评估的 `services/contract-api.ts`（881 行，真 SSE）。
- **三个断点**：① 骨架没按原型收敛（tabBar / 导航主题 / 首页）；② 翻译链路是空实现（`const res = null`）；③ 后端意图路由**零行代码**。
- **建议节奏**：前端 M0→M2 可立刻开工（不依赖后端）；后端 M3→M4 是两段独立工作，其中 M4 有硬前置（6 个 agent 必须先配好）。

## 2. 产品定位：从单点工具到通用助手（规划共识）

| 维度 | 变更前（`mini-contract`） | 变更后（`kedou-ai-minigram`） |
|---|---|---|
| 定位 | 合同翻译官（单点工具） | 科豆 AI（通用对话助手 + 能力市场） |
| 一级入口 | 翻译 / 合同评估 / 我的 | **对话 / 发现 / 我的** |
| 翻译、合同评估 | 占一级 tab | 降级为「发现」页的能力卡（用完即走） |
| 首屏 | 品牌头 + 两个入口卡 | Hello. + 今日一句 + 开始对话（首条消息与对话页同文案） |
| 意图来源 | 前端写死 `contract-risk` | 对话 tab 未知（后端路由）／发现 tab 已知（显式 `agentId`） |
| 后端改动 | — | 几乎零改动（发现页）；需新增意图路由（对话 tab） |

**核心架构判断（已定，不再讨论）**：两条入口共用同一条执行链路（`POST /api/ai-agent/agent/run` + SSE + 会话 + 埋点），差别只在「agentId 由谁决定」。因此**发现页可以先上线、不依赖意图识别**，意图路由是给对话 tab 的增强。

## 5. 实现方案（M0–M4，按依赖排序）

### M0 · 骨架收口（前端，0.5–1 人日，无后端依赖）

| 动作 | 文件 |
|---|---|
| tabBar 换 对话 / 发现 / 我的；导航栏去蓝改白；`selectedColor` 用 `#C2410C`（对比度 5.4:1，纯品牌橙 2.9:1 不达标） | `app.json` |
| 新建通用对话页（抄 `pages/contract/chat/`，删「合同上下文」提示条，首条注入今日一句） | `pages/chat/index/index.*` |
| 新建发现页（翻译官 / 合同评估两张能力卡，`navigateTo` 到既有页） | `pages/discover/index/index.*` |
| 改写欢迎页为 Hello. + 今日一句 + 开始对话（`switchTab` 进对话） | `pages/welcome/index/index.*` |
| 我的页三条并列设置 → 收敛为「应用设置」分组 | `pages/mine/index/index.*` |

**验收**：启动进 welcome → 开始对话 `switchTab` 不可后退；三 tab 可切；发现页两入口可达；无硬编码 `#F97316`/`#1E6FFF` 残留；`tsc --noEmit` 零错误。

### M1 · 翻译链路打通（前端 + 后端，1–2 人日）

两条路，需拍板（§6-Q2）：

- **方案 A（推荐）：复用 `agent/run`** —— 配一个 `translate` agent，前端把 `contract-api.ts` 抽成工厂 `createAgentApi(agentId)`（`services/agent-stream.ts`），翻译 = `createAgentApi('translate')`。**收益**：SSE / 会话 / 埋点 / 重试全复用，后端零新增接口；翻译可进「我的翻译」历史（依赖 M4 的 `agent_id`）。
- **方案 B：新增 `POST /api/translate`（SSE）** —— 语义更直白，但要新写接口 + 网关路由 + 会话存储，且与 agent 体系并行两套。**不建议**。

**验收**：输入→流式出结果→结果页展示真实译文；断网/超时有明确失败态；不发版即可改 prompt。

### M2 · 合同评估链路接真（前端，1 人日）

- `pages/assess/index` 的 `takePhoto/chooseAlbum/chooseFile` 接 `services/ocr-api.ts`，`start()` 假的 800ms 进度换成真实 SSE 进度（复用 M1 抽出的工厂，`agentId='contract-risk'`）。
- `pages/assess/result` 渲染真实 `ContractReport`（替换硬编码示例）。
- **收口 `pages/contract/*` 与 `pages/assess/*` 双份实现**（建议留 `assess` 三页 + 把 `contract/chat` 的能力并入 `assess/result` 追问，`contract/*` 其余下架）。

**验收**：真上传→OCR→评估→报告全链路可跑；`contract-risk` 老链路行为不回归。

### M3 · 发现页数据驱动（后端 + 前端，1 人日）

- migration：`agent_definitions` 加 `entry JSON`（visible/icon/title/desc/category/sort/ui/route/suggestions/inputMode）。
- 新增 `GET /ai/agents`（ai-service，C 端只读，字段白名单，**绝不返回 systemPrompt**），只出 `enabled=1 AND status='published' AND entry.visible=1`。
- 前端发现页改 `GET /ai/agents` 渲染，`ui='custom'` 跳专属页、`ui='chat'` 跳通用壳。

**验收**：后台新增一个 agent 并勾 visible → 小程序刷新即出现（不发版）；接口无 prompt 字段。

> 注：M3 不是 M0 的前置 —— 发现页可先写死两张卡上线，M3 再改成数据驱动，避免被后端阻塞。

### M4 · 主对话意图路由（后端，2–3 人日 + agent 内容工作）

按 `意图识别-实现方案.md` 执行（含 §4 的 6 处修正）：

1. `packages/agent-core`：新增 `core/intent-classifier.ts`；`StreamEventType` 加 `'intent'`
2. `servers/ai-agent`：`intent/intent.service.ts`（会话锁定 + 切换检测）、`AgentRunDto.agentId` 加 `@IsOptional()`、`agent.controller.ts` 在 stream 前解析意图并先推 `intent` 事件
3. migration：`agent_conversations` 加 `agent_id` + `intent_history` + 索引
4. 开关 `INTENT_ROUTING_ENABLED` 默认 **关**；开之前必须已配好 6 个 agent

**验收**：省略 `agentId` 时 SSE 首个事件是 `intent`；同 `conversationId` 追问 `via='locked'` 不切换；`agent_log.agent_id` 是具体 agent 而非 `auto`；关开关行为与改动前完全一致。

### 依赖关系

M3 ──┘            M4（需先配 6 个 agent；与 M3 用同一份 entry 元数据）
