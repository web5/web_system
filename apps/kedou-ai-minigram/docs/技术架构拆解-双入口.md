# 技术架构拆解：主对话 与 发现

> 科豆 AI 小程序 · 2026-09-15
> 代码基线 `~/web_system_release`（servers/ai-agent 运行面 · servers/ai-service 配置面 · packages/agent-core · servers/mcp-gateway）
> 配套：多 Agent 意图路由架构设计 · 意图识别实现方案


## 服务职责边界（重要修正）

后端**不是**一个 ai-service，而是「配置面 / 运行面」两个服务分工：

| | **ai-service**（3003） | **ai-agent**（6010） |
|---|---|---|
| 角色 | **配置面 + 数据面** | **运行面** |
| 网关前缀 | `/api/ai/*` · `/api/agent-defs/*` · `/api/agent-runs/*` | `/api/ai-agent/*` |
| 管什么 | agent 定义（systemPrompt / capabilities / version）、skill 正文、run 记录落库、通用 chat/image/tts | **agent 执行（SSE）**、会话存储、MCP 客户端、skill provider、合同工具、权限 broker、OCR、模型目录 |
| 关键接口 | `GET /internal/agent-definitions`（供拉取）、`POST /internal/agent-runs`（收埋点）、`@Controller('admin/agent-defs')` | `POST /agent/run`、`GET /agent/conversations`、`POST /agent/permission/:id` |

**数据流**：ai-service 存定义 → ai-agent 定时轮询（agent-def-sync，约 30s）拉 published+enabled →
本地 `AgentRegistry.upsert()` 热更新 → 执行 → run 记录 push 回 ai-service 落库。

> ⚠️ 由此修正三处（此前文档写在了 ai-service 上，是错的）：
> 1. **意图识别与 IntentService 落在 ai-agent**（运行面），不是 ai-service
> 2. **会话锁定的表是 ai-agent 侧的 `agent_conversations`**，不是 ai-service 的 `conversations`
> 3. C 端应用清单接口加在 **ai-service**（配置面出清单），执行仍走 ai-agent —— 两者由网关分流，不冲突

## 0. 一句话结论

两个入口**共用同一条执行链路**（同一个接口、同一套 agent 引擎、同一套 SSE 与会话），差别只在**「agentId 由谁决定」**这一点上：

- **发现** = 用户点卡片，意图**已知** → 前端显式传 `agentId`，后端零分类、零延迟
- **主对话** = 只有一个输入框，意图**未知** → 后端加一层意图识别，先路由再执行

**所以「发现」是可以先上线、且不依赖意图识别的完整多 agent 架构**；意图识别只为主对话服务，两者并行不阻塞。

## 1. 两个入口的本质差异

| 维度 | 主对话（Chat tab） | 发现（Discover tab） |
|---|---|---|
| **意图来源** | 未知 —— 用户只给一句话 | 已知 —— 用户点了某张应用卡 |
| **agentId 谁定** | 后端分类（`auto`） | 前端显式传值 |
| **路由开销** | 0–400ms（规则层约 0，LLM 层 150–400ms） | **0** —— 天然绕过分类 |
| **是否需要兜底** | 需要，`general` 是 P0 安全阀 | 不需要 —— 用户已明确选择 |
| **会话内能否切 agent** | 能，且**应该**切（话题变了） | **不应**切（用户就在这个应用里） |
| **UI 形态** | 单一通用对话壳 | 可通用壳，也可专属 UI（翻译双语卡 / 合同报告） |
| **依赖后端改动** | 需新建 IntentService + 分类器 + migration | 几乎**零后端改动**，只缺一个应用清单接口 |
| **可独立上线** | 否，依赖 agent 全配好 | **是** —— 配一个 agent 就能上一个应用 |

> ⚠️ **一个反直觉的点：两条链路的「会话切换策略」是相反的**
>
> 主对话要做**切换检测**（话题变了要换 agent），发现页要做**切换免疫**。
> 举例：在翻译应用里说「再正式一点」——这句话本身像通用改写请求，若走切换检测会被判到 `general`，翻译官就「丢了」。
> 所以发现页进入的会话必须**锁定 agentId 且关闭意图重分类**，只有用户显式 `@其它应用` 才切。
> 这个对称性不提前设计，上线后必然出 bug。

## 2. 全景分层架构

```
入口层  小程序     对话 tab（通用输入框·意图未知）  发现 tab（应用卡片·意图已知）  我的 tab
网关层  gateway     /api/ai-agent/* → ai-agent(6010) 运行面    /api/agent-defs/* · /api/agent-runs/* → ai-service(3003) 配置面
路由层             [新] IntentService（落 ai-agent，仅主对话经过）   AgentRunDto.agentId（显式值直接命中）
执行层  agent-core AgentRegistry（DB 热同步）  AgentRunner（SSE·多步·记忆）  CapabilityResolver
能力层             内置 tools    skills（skill-loader）   MCP（mcp-gateway）   LLM（ClientRegistry）
数据层             agent_definitions(ai-service)    agent_conversations(ai-agent)    agent_runs(ai-service)
```

## 3. 两条链路并排时序

### 链路 A · 主对话（隐式路由）

1. 用户在输入框说话，前端不传 `agentId`（或传 `'auto'`），带上 `conversationId`
2. **后端 IntentService 解析意图**：显式 > 会话锁定 > 关键词规则 > 小模型分类 > `general` 兜底
3. SSE 先推 `{type:'intent',agentId,confidence,via}` —— 必须在第一个 token 之前
4. AgentRegistry 取定义 → AgentRunner 执行 → token 流
5. `final` 带 conversationId；`agent_id` 与判定流水写回会话

**新增成本**：分类延迟 0–400ms · 约 100–200 token/次（flash 档）· 需 migration · 需 general 兜底

### 链路 B · 发现（显式直达）

1. 前端从应用清单拿到 `agentId`，进入应用页（通用壳或专属 UI）
2. **跳过分类** —— 请求体里直接带 `agentId:'translate'`，后端老行为完全不变
3. 可选推 `{type:'intent',via:'explicit'}`，仅用于前端显示徽标，非必需
4. AgentRegistry 取定义 → AgentRunner 执行 → token 流（**与 A 完全同一条**）
5. `final` 带 conversationId；会话锁定该 agent，**关闭意图重分类**

**新增成本**：0 延迟 · 0 token · 后端几乎零改动（只缺一个 C 端清单接口）

## 4. 共享什么、各改什么

| 模块 | 状态 | 说明 |
|---|---|---|
| `POST /ai/agent/run` | 共用 | 唯一入口，两条链路都走它。`agentId` 本来就是入参，显式传值 = 零改动 |
| AgentRegistry | 共用 | DB 热同步，后台 publish 即生效 |
| AgentRunner / SSE | 共用 | 流式、多步、工具调用、记忆压缩，全部复用 |
| CapabilityResolver | 共用 | tool / mcp / skill 三类能力统一解析 |
| 会话与记忆 | 共用 | `conversationId` 持久化 + compaction |
| 埋点与计费 | 共用 | `agent_runs` 落库，结构一致 |
| **IntentService + 分类器** | **主对话专用** | 新增 `intent-classifier.ts` + `intent.service.ts`。发现页**不需要** |
| `StreamEventType:'intent'` | 主对话必需 | 发现页可选复用（显示徽标），不影响主流程 |
| `agent_conversations.agent_id` | **两条都要** | 主对话用于锁定；发现页用于切换免疫 + 按应用筛选历史 |
| **C 端应用清单接口** | **发现页专用** | **当前不存在** —— `admin/agent-defs` 是管理端，C 端调不了 |
| **agent 展示元数据** | **发现页专用** | **当前不存在** —— 表里没有 icon / 描述 / 分类 / 排序 / 是否上架 |
| 应用前端页面 | 发现页专用 | 通用对话壳（0 成本）或专属 UI（每个应用单独开发） |

## 5. 数据模型：两个必须加的字段

### 5.1 `agent_definitions.entry` —— 发现页的应用卡片元数据

现在这张表只有**运行**需要的字段（prompt / model / capabilities），**完全没有展示**需要的字段。
发现页要「数据驱动渲染」而不是写死卡片，就必须补一列：

```sql
-- migrations/0010（与本轮会话锁定同一条，尚未上线，可合并）
ALTER TABLE agent_definitions
  ADD COLUMN entry JSON NULL COMMENT '发现页展示元数据' AFTER enabled;

/*
  entry 结构：
  {
    "visible": true,              // 是否在发现页展示
    "icon": "translate",          // 图标 key，前端映射
    "title": "语言翻译官",
    "desc": "中英日德，给你得体表达",
    "category": "tool",           // 分组：chat/tool/life/knowledge
    "sort": 10,
    "ui": "custom",               // 'chat' 通用对话壳 | 'custom' 专属 UI
    "route": "pages/translate/index/index",   // ui=custom 时的页面路径
    "suggestions": ["把这段翻译成商务英语", "..."],  // 开场示例问题
    "inputMode": ["text", "image"]            // 支持的输入形态
  }
*/
```

> **为什么用 JSON 而不是加 8 个列**：展示元数据会持续变（以后加「是否会员专属」「是否需要联网」……），
> 加列每次都要出 migration；`JSON` 一列解决，且和表上已有的 `capabilities` / `skills` / `memory` 写法一致。

### 5.2 `agent_conversations.agent_id` + `intent_history`

```sql
-- 主对话：会话锁定（避免每轮重分类导致人格割裂）
ALTER TABLE agent_conversations
  ADD COLUMN agent_id VARCHAR(64) NULL COMMENT '锁定的 agent',
  ADD COLUMN intent_history JSON NULL COMMENT '判定流水，可回溯误判',
  ADD INDEX idx_conv_agent (agent_id);
```

发现页同样受益：带了 `agent_id` 才能做「我的翻译 128 条」这种按应用筛选的历史列表
（原型里 `p-mine` 已经有这个入口，现在后端撑不起来）。

## 6. 需要新增的接口

| 接口 | 优先级 | 说明 |
|---|---|---|
| `GET /ai/agents` | P0 | **新增** C 端只读应用清单。只返回 `enabled=1 AND status='published' AND entry->>'$.visible'=1`，字段仅限展示用（id/title/desc/icon/category/sort/ui/suggestions），**绝不返回 systemPrompt** |
| `GET /agent/conversations?agentId=` | P1 | 现有接口加可选筛选参数，撑起「我的翻译 / 我的合同」这类按应用的历史 |
| `POST /ai/agent/run` 兼容 | P0 | 只需给 `AgentRunDto.agentId` 加 `@IsOptional()`，显式传值的老调用一行都不用改 |

> ⚠️ **别让 C 端复用 admin/agent-defs**
> `servers/ai-service/src/agent-def/agent-def.controller.ts:21` 的 `@Controller('admin/agent-defs')`
> 是管理端域，带权限校验且返回全量字段（**含 systemPrompt**）。
> 让小程序直接调 = 提示词泄露。`GET /ai/agents` 必须是独立接口 + 字段白名单。

## 7. 关键决策：应用用「通用壳」还是「专属 UI」

| 形态 | 做法 | 成本 | 适合 |
|---|---|---|---|
| **通用对话壳** `entry.ui='chat'` | 所有应用共用一个聊天页，只换 agentId、标题、图标、开场示例 | **0 前端成本** —— 配一个 agent 就上一个应用 | 情感陪聊、百科科普、性格星座时运 |
| **专属 UI** `entry.ui='custom'` | 独立页面 + 定制输入输出（翻译的双语对照卡、合同的评估报告） | 每个应用 1–3 人日 | 语言翻译、合同评估（**已有现成页面**） |

> **建议：默认通用壳，只对「输出有结构」的应用做专属 UI**
> 判断标准：**如果答案是一段话，用通用壳；如果答案是一张卡/一份报告，做专属 UI。**
> 现有 `pages/translate/index/index` 和 `pages/contract/chat/chat` 已经是 custom 形态，直接挂上去即可。
> 新配的 4 个 agent（陪聊 / 百科 / 星座 / 工具）全部走通用壳，**当天就能上线**。

## 8. 小程序前端结构

```
tabBar（三 tab）
├── 对话  pages/chat/index/index        ← 通用壳，agentId 不传 / 'auto'
├── 发现  pages/discover/index/index    ← GET /ai/agents 驱动渲染
│         ├── ui='chat'   → navigateTo(pages/chat, { agentId, title })
│         └── ui='custom' → navigateTo(entry.route, { agentId })
└── 我的  pages/mine/index/index        ← 设置 · 历史 · 会员
```

```js
// 发现页渲染逻辑（伪代码）
onShow() {
  const apps = await getAgents();              // GET /ai/agents
  this.setData({ groups: groupBy(apps, 'category') });
}

onTapApp(e) {
  const { agentId, ui, route, title } = e.currentTarget.dataset;
  if (ui === 'custom') {
    wx.navigateTo({ url: `${route}?agentId=${agentId}&title=${title}` });
  } else {
    wx.navigateTo({ url: `/pages/chat/index/index?agentId=${agentId}&title=${title}` });
  }
}
```

要点：

- **发现页不写死卡片** —— 后台新增一个 agent 并勾 `visible`，小程序刷新即出现，不用发版
- **通用壳复用同一个页面** —— `pages/chat` 用 `options.agentId` 区分是「主对话」还是「某应用」，有值 = 显式模式（锁 agent、不重分类），无值 = 主对话模式（走意图路由）
- **专属 UI 页面也复用同一条请求管线** —— 只是 UI 不同，底层都是 `agent/run` + SSE

## 9. 会话归属与隔离（⚠️ 需拍板）

加了 `agent_id` 之后，一个现实问题：用户在「语言翻译官」里的 128 条记录，要不要出现在主对话的历史列表里？

| 方案 | 行为 | 取舍 |
|---|---|---|
| **A 完全隔离**（推荐） | 发现页的应用会话进「我的 → 各应用历史」，主对话列表只显示经由主对话产生的会话 | 心智最清晰：应用是工具，对话是聊天。缺点是同一话题的记录分两处 |
| **B 全合并** | 所有会话进同一个列表，用 agent 徽标区分 | 实现最省事，但主对话会被工具性记录淹没 |
| **C 合并 + 筛选** | 默认显示主对话，顶部提供「全部 / 翻译 / 合同」筛选 | 折中，需多做一套筛选 UI |

> ⚠️ **需要拍板**：倾向 **A**，原型里「我的」页已经把「我的翻译 128 条」单独列出来了，
> 说明心智本来就是隔离的。但这条影响列表接口和 UI，定了才能写死。

## 10. 落地拆分：两条线可并行

| # | 任务 | 依赖 | 产出 |
|---|---|---|---|
| 1 | 后台配 6 个 agent（含 `general` 兜底） | 无 | DB 记录 + systemPrompt + capabilities |
| 2 | `agent_definitions.entry` 字段 + migration 0010 | 无 | 应用可配置展示元数据 |
| 3 | `GET /ai/agents` C 端清单接口 | 2 | 发现页数据来源 |
| 4 | **发现页上线**（清单渲染 + 通用壳 + 挂现有两个专属页） | 1,3 | **可独立交付**，4 个新应用零前端成本 |
| 5 | `AgentRunDto.agentId` 加 `@IsOptional()` | 无 | 为 auto 铺路（一行） |
| 6 | IntentService + 分类器 + `'intent'` 事件 | 1,5 | 主对话具备路由能力 |
| 7 | `agent_conversations.agent_id` + 会话锁定 + 切换免疫 | 6 | 主对话人格稳定；发现页不串味 |
| 8 | **主对话灰度上线**（`INTENT_ROUTING_ENABLED` 默认关） | 6,7 | 配好后开开关 |

> **排期上的好消息**：第 1–4 步是一条完整可交付的线（发现页多应用），完全不依赖第 6–8 步的意图识别。
> 即使意图识别延后，**「发现」这一半的多 agent 架构也能先跑起来、先验证**。
> 反过来不成立 —— 主对话必须等 agent 全配好才能开灰度。
