设计决策记录

  • 为什么放基座而不是子模块：法定要求「网站所有页面」可及。基座是唯一全路由公共层， portal / admin 各自实现既重复又容易漏（历史上 portal 换血升级就漏过一次，见 d1d27b7）。
  • 为什么用 fixed 而非内容流：模块布局普遍 height: 100% 占满视口， 内容流 footer 会掉到视口之外，必须滚动才看得到，等于没有。
  • z-index 900：低于环境切换挂件（1080），dev 下挂件浮在条之上，互不遮挡主体功能。
  • 高度 30px + 半透明：尽量少占视口；模块贴底操作区需自留安全区（本稿 .mock-tail 已示意）。
  • 避让机制（2026-09-28 补）：fixed 条必然压住模块底部。首版未做避让， portal 开始页 / 对话页的左栏底部能力面板、admin sider 底部均被压 30px。 修法：基座在 :root 公开 --site-beian-bar-h， 各模块根容器高度由 100vh 改为 calc(100vh - var(--site-beian-bar-h, 0px))。 模块单独运行（无该变量）时回落 0，布局与改造前一致 —— 不产生基座强耦合。

未登录路由交接（登录页归属）

交接流程

未登录访问 /portal/chat → 基座守卫判定首段归属 portal → 跳 /portal/login?redirect=/portal/chat → portal 模块登录页（账密 + 微信扫码 + 注册）→ 登录成功写 user-store → 回跳 redirect。

改前：基座守卫无条件 next('/login') → 落在基座老登录页 （纯账密 + alert + 整页刷新），模块登录页永远进不去，扫码登录不可用。

设计决策记录（登录交接）

  • 为什么不让基座全拦：portal / admin 各自带 requiresAuth 守卫与自己的登录页， 基座登录页是更早的一份实现。全拦等于让全站登录体验退化到最早版本。
  • 为什么模块名取自 manifest：byEnv[env] 与 modules[] 是模块真身清单， 不硬编码 ['portal','admin'] —— 新增模块自动生效。
  • 为什么保留基座 /login：模块判定不出来（根路径 / 非法路径）时必须有兜底，不能白屏。
  • 判定口径统一（auth-storage）：模块登录后只写自己的 pinia persist key user-store，基座若只读历史 token 会误判未登录 → 登录死循环。 故 readToken/readRefreshToken 以 user-store 为准，无记录才回落旧 key。
  • 死锁规避：next() 到当前同址会无限触发 beforeEach， 「已在模块登录页」必须直接放行。
