#### 第二轮事故（同一模块二次走查，PR #381）——v2 也有没拦住的

补齐第一轮三项后用户再走查，仍翻车。这轮根因**全变了**，说明「发布漏项」之外还有**设计期缺陷**与**跨服务常量依赖**：

| 症状 | 真根因 | 为什么第一轮没暴露 | v2 为何没拦住 |
|---|---|---|---|
| dev 采集源页仍报「服务器错误」 | **跨 controller 路由抢匹配**：两个 controller 前缀同为 `api/content`，module 注册顺序 `[ContentController, ContentQualityController]`，`GET sources/last-collect` 被前者的 `@Get('sources/:id')` 先吞 → `Number('last-collect')=NaN` → TypeORM 把 `NaN` 当列名 → `Unknown column 'NaN'` 500 | 页面用 `Promise.all([listSources(), lastCollect()])`，**辅助接口 500 拖垮整页**，掩盖了「列表数据其实一直是好的」 | 方案设计只有「接口清单」，没有**接口设计约束**（静态路径与参数路径共存时的匹配顺序、路径参数强校验）→ 已补 **§2.9** |

**共同病根（第二轮）**：发布清单能兜住「漏发」，但兜不住**设计期缺陷**（路由冲突）和**跨服务代码依赖**（常量在别的服务里）。v2.1 新增 §2.9 接口设计约束、订正 §5 阶段2、新增附录 C 排查手法。

| 字典/枚举 | 数据源类型、质量状态 | 代码常量 | — | 随代码 |

**边界判定（三问法）**：
1. 是运行时业务数据、缺了功能空转？→ **是 = 初始化数据**
2. 是代码声明（router / 常量 / 配置）？→ **否**，归 2.2 / 2.5 / 2.8；但**生效同步**必须进发布清单
3. 存 DB 且需手工预置？→ **是 = 初始化数据**（含 DB 存储的菜单树、权限项、角色映射）

> ⚠️ 权限与菜单在 web_system 是**代码声明**（权限常量启动自动 seed、菜单在 router），故不算初始化数据；
> 但**权限需重启 user-service 同步、菜单需前端模块发布**，二者「生效」都是发布阶段必勾项。

### 2.8 权限模型 🆕
| 权限项 | 授予角色 | 门控什么 | 定义位置 | 生效方式 |
|---|---|---|---|---|
| `content:view` | admin/super_admin | 菜单与列表可见 | `packages/types` 常量（**由 user-service 消费并 seed**） | 🔴 见下方订正 |
| `content:manage` | admin/super_admin | 新建/编辑/重发 | 同上 | 同上 |

> 🔴 **订正（第二轮事故实证）**：「重启即生效」**只在常量已存在于运行版本时成立**。
> 权限常量**首次引入**时，必须先发版**定义/消费方服务**（`user-service`），否则重启只是重跑旧 seed。
> 发布前判据：`git show <线上版本>:packages/types/src/index.ts | grep '<权限前缀>:'` → **为空则必须发版**。
> 验证：发版后查 DB 权限项是否存在 + 目标角色权限总数是否 +N（prod 实测 26 → 27）。

### 2.9 接口设计约束 🆕（第二轮事故补齐）

设计阶段必查三项，**都是「能跑通但线上必炸」的类型**：

**① 静态路径与参数路径共存 → 检查匹配顺序**
多个 controller 前缀相同时，路由按 **module 里 `controllers: []` 的注册顺序**匹配，先注册的赢。
```
反例：controllers: [ContentController, ContentQualityController]
      ContentController      @Get('sources/:id')          ← 先注册，抢匹配
      ContentQualityController @Get('sources/last-collect') ← 永远进不来
      → Number('last-collect') = NaN → SQL Unknown column 'NaN' → 500
```
判据：新增静态子路径（如 `xxx/last`、`xxx/stats`）时，**必须确认同前缀下不存在会吃掉它的 `:param` 路由**；有冲突则改名（改静态路径，别改 param 路径）。

**② 路径参数必须强校验 → 非法一律 400**
禁止 `Number(id)` 直接进 ORM。`NaN` 进 TypeORM 不会报错在参数位，而是被当**列名**拼进 SQL，错误信息 `Unknown column 'NaN' in 'where clause'` **看不出是哪个接口**。
做法：统一 helper（如 `parseId()`），非数字抛 `BadRequestException`，所有 `:id` 路由走它。

**③ 前端并发聚合 → 辅助接口不得拖垮主流程**
`Promise.all([关键接口, 辅助接口])` 中任一失败会**整页崩**，用户看到的是「页面报错」而掩盖真实故障点。
判据：列表页的**装饰性数据**（最近采集时间、统计数）应允许失败降级（`.catch(() => null)`），不参与 `Promise.all` 的主链路。

- [ ] 网关路由比对：目标环境 gateway 版本是否已含新路径
- [ ] **初始化数据确认**：目标环境业务表是否已有 seed 数据（如 `content_sources` 行数）
- [ ] **跨服务常量比对** 🆕：新增的权限/枚举常量，检查**定义方与消费方服务**线上版本是否已含
      `git show <线上版本>:packages/types/src/index.ts | grep '<常量前缀>:'` → 为空则**该服务必须发版**（重启无用）
- [ ] **路由冲突自查** 🆕：新增静态子路径时，确认同前缀 controller 里没有 `:param` 路由会抢匹配（§2.9①）

### 阶段 1 · 后端（按 moduleKey 逐个发）
- [ ] `content-hub`、`gateway` 等提交流水线，**`--commit <sha>` 显式指定**
- [ ] dev/prod 都会停在 `awaiting-approval`，需 approve（prod 另需 `confirm:true`）

### 阶段 2 · 表结构 + 初始化数据 + 权限同步 🔴
- [ ] DDL：`CREATE TABLE IF NOT EXISTS` / 查 `information_schema` 后 `ALTER`
- [ ] **业务 seed 脚本执行**（幂等；prod 必跑，否则功能空壳）
- [ ] **权限同步** 🔴：先判「目标环境运行版本是否已含该常量」
      - **不含** → 发版 `user-service`（**这是 prod 无菜单的真根因，重启无效**）
      - 已含 → 重启 `user-service` 让 seed 生效即可
      - 验证：DB 权限项存在 + 目标角色权限总数增量正确（实测 admin 26 → 27）
      - **注意**：本阶段要在**前端发布之前**完成，否则菜单被门控过滤，用户看到「发完了却没菜单」

### 阶段 3 · 前端
- [ ] admin / portal 模块发布（构建 → 上传 → 切指针）
- [ ] 校验产物 HTTP 可达：`GET /static/modules/admin/<env>/<commit>/index.js` → 200

### 阶段 4 · 验证
- [ ] 按 §4.3 用例矩阵逐条走查（**dev + prod 都要**）
- [ ] 接口探活、回滚预案就绪

> **顺序铁律**：后端 → 数据 → 前端指针（颠倒会导致 404 白屏）。

## 附录 C · 排查手法速查（第二轮事故实战沉淀）

### C1 · 接口探活的状态码判据
| 码 | 含义 | 处置 |
|---|---|---|
| **401** | 路由已命中、被 auth guard 拦 | ✅ 路由存在（发布到位） |
| **404** | 路由不存在 | 后端/gateway 未发或路径错 |
| **400** | 命中且参数校验生效（如 `parseId` 兜底） | ✅ 防御生效 |
| **500** | 后端异常 | 查日志，见 C3 |

> 无 token 时 guard 先返 401，所以**用「401 vs 404」判断路由是否存在**比判断 200 更可靠。

### C2 · 前端产物是否真到位（别只看版本表）
- ⚠️ **`versions` 读的版本表对前端滞后**（曾显示 `005256fd` 但指针已是 `3a22972c`）。
- 判据：**指针 + 产物 HTTP 200** 才算数。
- prod 静态根（实测）：`/data/web_system_static/public/static/modules/<module>/<env>/<commit>/`
  —— **不是** `/data/web_system/public/...`（那是后端产物）
- dev 静态根不同，用 `find /data /home /root -maxdepth 9 -type d -name '<commit>'` 定位。
- 在线校验：`curl -o /dev/null -w '%{http_code}' https://kedouai.com/static/modules/admin/prod/<commit>/index.js` → 200。

### C3 · 后端 500 定位
```bash
ssh kedou-dev "pm2 logs content-hub --lines 600 --nostream > /tmp/ch-log.txt"
scp kedou-dev:/tmp/ch-log.txt /tmp/ch-log.txt   # 拉回本地精读
```
⚠️ 驱动层错误（`QueryFailedError: Unknown column 'NaN'`）**堆栈不含业务行号**，只能从代码反推：
优先查「把变量送进列名位置」的地方（未校验的路径参数、动态字段拼接）。

### C4 · 跨 controller 路由冲突排查
```bash
grep -n "controllers:" <module>.module.ts        # 1) 注册顺序 = 匹配优先级
grep -rn "@Controller(" <该 module 目录下>        # 2) 找同前缀 controller
git show <线上版本>:<controller 文件>             # 3) 确认线上是否已是修复版
```

### C5 · CI 与本地工具的坑
- **CI `build/test` 会卡死 40 分钟且无法 rerun**（runner 侧问题，非脚本）→ 解法：
  `git commit --amend --no-edit --date="$(date -u +%Y-%m-%dT%H:%M:%SZ)"` 改 sha 触发**全新 run**（正常 2m30s）。
- ~~**本机跑红线扫描必超时（>170s）**~~ → **已过期**：PR #384 把行级判定改 bash 内建后，
  `bash scripts/redline/scan-rules.sh diff HEAD~2..HEAD` 本机实测 **2 秒**，可直接本机跑。
- **验证红线规则有效性**用 `/tmp` 沙箱仓库构造受控场景（不污染真实仓库）。两个坑：
  - 沙箱**首 commit 用 `HEAD~1..HEAD` 无效**（无父节点）→ 会误判「规则没触发」
  - 挑历史 commit 做负向测试前**先查 body 是否带 `Micro-exempt`**——合法豁免会被正确跳过，容易误判规则是死代码
- ⚠️ **本机 bash `grep` 存在假阴性**（同一命令两次结果不同），排查规则/代码是否存在时用检索工具复核，别信一次 grep 的空结果。
