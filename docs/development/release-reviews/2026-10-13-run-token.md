## 重要项（不阻塞）

### Ⅰ. `fetch-config.sh` 的文案改动不会随本 PR 自动上线

- **情形**：仓库 `scripts/pipeline/fetch-config.sh` 改了 401 报错文案（新增"先看令牌是不是 `rt1_` 开头"的提示）。
- **实际**：流水线真正执行的动作脚本正文存在 DB `deploy_pipeline_actions`；console 代码内检索不到 `fetch-config` 字样，说明它**不属于 console 内置脚本**（内置脚本是"改代码 + 重启自动同步"，见 `pipeline-step-command.service.ts:248` 的报错文案）。仓库里的 `.sh` 是**模板副本**，供 `pipeline-lint` 体检与人工参考。
- **期望**：要么线上正文保持旧文案（功能不受影响），要么单独同步一次。
- **影响**：**仅排障提示，不影响功能** —— 服务端按令牌前缀自行判定两种凭据，旧文案的脚本照样能跑通新令牌（脚本侧零改造正是本次设计目标）。
- **判据**：A 类「改的东西真的会被加载吗」精神延伸；无既有编号，标"无判据"降级处理。
- **后续动作**：部署 dev 后核对 DB 中该动作正文；若需同步，走流水线动作编辑页手工更新（本次不阻塞合并）。

**未端到端验证的一项**：「run 结束后同一枚令牌回调应 401」。原因：撤销表在 console
进程内存中，外部脚本无法向进程内登记 jti，只有真实 run 的 `finally` 能触发；而 dev 上
所有流水线都是真实应用发布（git pull + build + restart），为验证凭据去跑一次真实发布，
风险与收益不成比例。该函数路径由单测覆盖（`run-token.spec` 的 revoked 用例 +
`issueScriptToken` 登记/撤销用例），接线点（3 行）经 `tsc` 与全量测试确认。
**顺验时机**：下次真正发布 deploy-console 自身时，在动作脚本里加一行
`curl -o /dev/null -w "%{http_code}" -H "x-internal-key: $CONSOLE_TOKEN" $CONSOLE_API/...`
即可——run 结束后由平台自己（而非脚本）再打一次，得 401 即证明撤销生效。

## 补记（同日）：`WS_INTERNAL_KEY` 这处僵尸凭据

核对部署产物时发现，引擎**有两套**变量组装，我只收口了其中一套：

- `resolveStageVars()` → 注入 `CONSOLE_TOKEN`（编排模式，现网脚本在用）—— 已在 #333 收口；
- `runStageCommand()` → 注入 `WS_INTERNAL_KEY = INTERNAL_API_KEY`（旧版 4 节点模板遗留）—— **漏了**。

dev DB 全表检索：`deploy_pipeline_actions` 中引用 `WS_INTERNAL_KEY` / `WS_PLATFORM_API`
的脚本均为 **0 条**，即这是一个**没人用但每次 run 都把长期 key 塞进脚本进程**的注入点
（`set -x` 或 `env` 一打印就泄露；新脚本照抄旧模板即回到老路）。

处置：改为复用 `issueScriptToken()`，**不删除** —— prod 库未逐条核过脚本正文，删除属
破坏性变更，换令牌则校验端按前缀自动识别、完全兼容。下期确认两端无引用后连
`WS_PLATFORM_API` 整块摘掉。
