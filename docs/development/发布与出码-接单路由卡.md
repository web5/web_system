## §0.5 · 接单 30 秒三问（顺序不可跳）

```
Q1 判链：命中 §0 哪一行？未命中/链档判不准/模块或环境缺失 → 停下来问人，不猜、不默认走任一通道。
Q2 定第一命令：查 §1/§2 决策表须唯一命中一行；命中多行或出现「或」→ 回 Q1 问人。
   取该行动作 + 真源绝对路径，并显式声明不用的通道。
Q3 核前置与停手：先过「动手前核对」(链A 4 项 / 链B 通用前置)，不过不执行；命中停止信号即停手问人。
```

**完成判据**

- 链 A = 出码前后三层校验一致 + 码可扫（3 finder + 1 alignment）+ 旧码标失效 +（若推送）`chatName` 精确匹配唯一会话且 `ok:true`
- 链 B = `verify_release` 的 `verdict == verified`（🔴 `status=succeeded` **不算生效**）

**停止信号（命中即停手问人）**

判不准链/模块/环境 · dev 副本 `.source-sha` ≠ 目标 commit · devtools 注册目录 ≠ 主目录或同 appid 多 worktree · prod 闸门 `closed` · `verdict ≠ verified` · 出码报错超出错误码表。

## §1 · 链 A · 小程序开发版预览码

真源：`~/skills/mp-preview/SKILL.md`（执行细节）· **命令真源：`~/workspace/web_system/docs/miniprogram/release-runbook.md` §零速查 + `apps/<app>/scripts/publish.js`**

> 🔴 **出码唯一主通道 = 本地 devtools CLI 三步**；`preview.mjs` 仅在 C2 全绿时可用，**当前 C2 关闭**。
> 判断不靠「要不要验改动」这种主观意图，靠可机判开关 `D`：
> `D = (ssh <dev 主机别名> cat ~/dachengzi-minigram-master/.source-sha) == 目标 commit` **且** dev 副本目标文件 sha256 == 本地产物 sha256。
> **当前盘面**：`D` = `30a0c4df`（#8916 未闭环）≠ 目标 commit → **C2 关闭**；11-18/11-19 四次实测（`21`→`25`→`31`→`34`）全部 C1。

| # | 条件 | 唯一动作 | 禁止 |
|---|---|---|---|
| **C1（默认）** | `D` 不一致 / 缺失 / 未核 / 要验当前改动 / **任何不确定** | 按 `release-runbook.md` §零速查「**本地 devtools CLI 三步**」条执行 → A3 推送 | ❌ 用 `preview.mjs` 出码做验收 ❌ 本机 `miniprogram-ci`（必报 `invalid ip`）❌ 只跑 `npm run publish -- preview` 而跳过前两步 |
| **C2（受控例外，非默认）** | 不验当前改动 **且** `D` 全绿 **且** 已整目录 rsync 并回写 `.source-sha` | `node ~/skills/mp-preview/scripts/preview.mjs --json '{"version":"<版本>"}'` → A3 推送 | 任一前置不成立 → **落 C1** |
| **A0（横切）** | 任何出码 | 先过「动手前 4 项核对」，不过不执行 | ❌ 跳过核对直接出码 |
| **A3** | 拿到码要推企微，**且 `sessions list` 按 `chatName`+`chatType` 精确匹配到唯一会话（空名群不发）、已确认文案** | `mp-preview/SKILL.md` §编排 ③ 推送：`wecom-push.mjs`（`filePath` / `text` / `chatName` 三字段，会话名现查不写死） | ❌ 手搓 `wecom-cli` / 自定三路兜底 / 群名空擅自发群 |
| **A4** | 码过期（TTL 25min）**或** 用户说「重新发下 / 没看到企微的二维码 / 出码」 | **重跑 C1 + A3**（唯一）；旧码全部标失效；不主动定时重出 | ❌ 续期 / 旧码当有效 / 只重出不推送 |

**C1 三步（只给命令名，全文见 `release-runbook.md` §零速查 / §8.1）**

`cli open` → `cli cache --clean compile` → `cli preview`（顺序不可省）。

> 🔴 **封装边界（2026-11-20 核实 `publish.js:307-308`、`:386`）**：`npm run publish -- preview` 的 cli 模式**只调第三步 `cli preview`**，不代做 `cli open` 与清编译缓存。漏前两步 = 扫码看到改动前代码（11-19 实测两轮返工）。三步全文、占位符、产物路径一律以 `release-runbook.md` 为准，本卡不复制。

**动手前 4 项核对**（缺一不执行；仅做前 3 项 git 核对仍会踩同 appid 覆盖）：

1. 该目录 `git rev-parse --short HEAD` == 目标 commit
2. `git status --porcelain` 为空
3. 目标文件 sha256 与改动后一致
4. 🔴 **目录环境 + 同 appid**：devtools `reduxPersist:projectList` 注册目录 == 主目录；本机 10+ 个 worktree 的 `appid` 全为 `wxd7a8a53e09dd20cc`，旧 worktree 会覆盖主目录 → 必须 `cli open` 显式切 + `cli cache --clean compile` 清编译缓存

- CLI **不支持 pageQuery** → 扫码进默认首页，须手动切目标页并开「开发调试」
- 「两原子拆用」写死：出码走 CLI 三步，**推送仍走 `wecom-push.mjs`**，不因出码通道改变
- 出码报错 → 只查 `mp-preview/SKILL.md` §失败解释口径（错误码表），不翻历史日志

## §2 · 链 B · 服务发布 → skill `web-system-deploy`

真源：`~/skills/web-system-deploy/SKILL.md` · 🔴 **唯一通道 = deploy-console MCP 流水线**

> **两跳：先判环境 → 再判调用方式。** 两种调用方式对后端 10 服务与前端 `admin`/`portal` **均可用**；前端常用 `tools/call` 是偏好、不是唯一（禁按模块二分）。

| # | 条件 | 唯一动作 | 硬判据 |
|---|---|---|---|
| **B0** | 目标是 `deploy-console` 自身 | `scripts/release-deploy-console.sh`（**永远手动**） | `enabled=0`，自部署会杀掉执行者；**先过 B0 再落 B1** |
| **B1** | 判不准发哪个模块 / 哪个环境 | `list_modules`；**环境缺失必须问人** | 禁猜模块名、禁猜环境 |
| **B2'** | **发 dev（任意模块）** | `bash ~/skills/web-system-deploy/scripts/publish.sh dev <svc...>` → 跟单遇 `awaiting-approval` **必须 approve** → 收尾按 B5 | ❌ 提交完即宣称已发布 ❌ 自起后台轮询 |
| **B3'** | **发 prod（publish.sh 方式）** | `publish.sh prod <svc...>` **提交即返回、停下来交人审批**；审批通过后另起 `publish.sh watch <jobId> --env prod --service <svc>` → 收尾按 B5 | 提交与审批都要 `confirm:true`；**agent 无权批 prod**；不轮询、不自动点审批 |
| **B4'** | **任一环境但走 MCP `tools/call` 方式** | `release_plan` → `publish_pipeline` → `get_job_status` → `verify_release` | `versionTag` 必传；prod 带 `confirm:true`；灰度 `grayscaleRule` 传对象 |
| **B5** | **横切判据，适用 B2'–B4' 全部** | `verify_release` 看 `verdict == verified` | 🔴 `status=succeeded` **不算生效**；verify 不传 `versionTag` = 恒通过的假验证 |
| **B6a** | 回滚（写） | `publish.sh rollback`（prod 需 `--yes` + **用户同意**） | 只切产物不重建；目标 `dist` 不在盘上直接 ABORT |
| **B6b** | 查状态 / 查版本 / 只读探测 | `publish.sh plan\|releases\|status\|versions\|gates` | 只读预演只认 `plan` / `release_plan`；`POST /pipeline` **无 dry-run** |

**B 通用前置（顺序不能反）**：

1. 代码已合 `origin/master`（dev 与 prod 发布源唯一，未合入**发不了任何环境**）
2. 本地已 commit & push
3. ②' **先 `git fetch origin master` 刷新本地 ref**（`publish.sh` 默认取本地 `origin/master` 的 ref，非实时远端，漏这步会发旧 commit）
4. **dev / prod 都会停在 `awaiting-approval`，均须 approve**
5. prod 首次发布或改过生产 `.env` 后，先 `publish.sh capture <svc>` 重捕检查点；闸门默认 `closed`，发前 `publish.sh gates` 且 `PROD_RUNTIME_ROLLOUT_RUN_ID` 必须 = 本次 jobId
6. 改过 prod `.env` 后重发同一 commit 必撞 `Immutable runtime version already exists with different content` → **先清两处目录**，配置对齐**早于**建单
7. prod 五步顺序「捕获 → 建单 → 绑 run → 人工审批 → 跟单」不可反

**禁止**：❌ 自签 JWT 打 `/api/pipelines`（会卡 `awaiting-approval` 403）❌ SSH scp 手工发 ❌ 直改 `deploy_*` 表 ❌ 按模块把 A/B 二分 ❌ 自行决定回滚生产。
