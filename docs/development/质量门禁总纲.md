# 质量门禁总纲（Gate Handbook）

> 版本 v1 · 2026-10-22 · 维护者：研发流程 owner
> **定位**：全仓门禁的**唯一索引与判定规则**。回答四个问题：有哪些门、在哪层拦、什么级别、怎么绕。
> **不定位**：不复述每条规则的业务理由。判据源仍是各 spec / checklist，本文只引用（见附录 B）。
> **维护纪律**：增删任何门禁，必须同 PR 更新本文 §4 与附录 A；否则视为门禁变更未完成。

## 0 一页速览

```
写代码 ──▶ L1 编辑器层（IDE hook，只拦 AI）
            │
            ▼
         git commit ──▶ L2 本地 git 层（仅 commit-msg；pre-commit 缺失，见 §8）
            │
            ▼
         PR ──▶ L3 CI 层（quality-gate.yml 4 个 job）  ← 唯一硬门
            │
            ▼
         发布 ──▶ L4 发布层（release.yml + release_plan 不变量）
```

| 数字 | 值 |
|---|---|
| 门禁编号总数 | 20（R1–R18 + R2b/R9b/R11b 三个变体，R7 空缺、R6 不在红线脚本内） |
| **实际机制** | **5 类**（行级 / 结构 / 凭证 / 构建测试 / 发布） |
| 真正会**阻断**的 | **13**（R1 R2 R2b R3 R4 R11 · B6 · L1 L5 L9 · D1 D2 D3） |
| 只**提示**不阻断的 | **13**（R3 弱占位 R5 R8 R9 R9b R10 R13 R14 R15 R16 R17 R18 · L6） |
| 仍**失效**的 | **1**（R11b 默认 off；原「L2 未启用」「D3 关闭」已于 2026-10-22 修复） |

> 计数口径：按「检查项」计，B6 含「生成物一致性」一步故不再单列 D4。
> **信度**：上一版（同日）是 12 / 13 / 3。同日加固后 L2 本地 git 层启用、ESLint 门开启，故 13 / 13 / 1。
> 一句话结论：**门禁不缺，缺的是「分层」和「级别纪律」**。27 个检查项里只有 13 个真能拦住人，13 个在 PR 上恒绿——它们不是门禁，是**体检项**。本文的核心工作就是把这两类分开说清楚，并且以后只用「门禁」称呼前者。

### 1.2 六个结构性病症（都有实证，不是印象）

| # | 病症 | 实证 | 代价 |
|---|---|---|---|
| 1 | **编号是长出来的，不是设计的** | 无 R7；R6 不在 `scan-rules.sh` 而在 `scripts/ci/changed-packages.sh`；R3 一号两义（TODO/FIXME=error，TEMP/TBD=warn）；R4 一号两义（`@ts-ignore` 与 `: any`） | 报错说「R4 违规」，人得先猜是哪一类 |
| 2 | **同一机制被写成 7 条规则** | R10/R11/R13/R14/R15/R17/R18 共用 `_trailer_check_one`，语义完全一致：`<Key>: pass` 或 `<Key>: <报告路径>` + 报告存在 + `阻塞: N`=0 + `Micro-exempt` 豁免 | 学习成本 ×7，实际机制只有 1 个 |
| 3 | **默认不阻断，但都叫「门禁」** | CI 调用不带 `--strict`，13 条 warning 恒绿；`gate-observation-log.md` 明确写着"四个评审门当前全是 warning（只报不拦）" | 「门禁通过」这句话失去信息量 |
| 4 | **开关与实现脱节** | ① `eslint.config.mjs` 10-10 已提交，quality-gate 的 `--lint` 自 09-22 关到现在；② `.githooks/` 只有 `commit-msg`，**没有 `pre-commit`**，但 `install-git-hooks.sh` 仍打印「pre-commit = 红线扫描」；③ 本机 `core.hooksPath` **未设置** | 文档承诺的拦截点，实际不存在 |
| 5 | **观察期机制已停摆** | `gate-observation-log.md` 唯一采集点停在 2026-09-25，升 error 需「≥20 commit 且 ≥5 命中」，一个月零采集 | warn→error 永远走不到，warning 事实永久化 |
| 6 | **判据源散在 7 份文档** | R9/R10→`kit-sop-enforcement`；R11/R13/R14/R15/R17/R18→`rd-process-model` + 3 份 checklist + 规范 v2；R2→`security-baseline`；L*→`specs/ci-cd`；proto→skill `ux-prototype-designer` | 查一条门禁要翻 7 处，且各处口径可能已过期（如规范 v2 附录 B 仍写「待落地」，实际 R17/R18 已上线） |

**重写原则**：编号不动（动编号会毁掉历史 commit 里的凭证语义），改为「**机制优先、编号降级为索引**」。以后新人只需记住 5 类机制，查具体实现再看附录 A。

## 2 四层模型：每一层到底拦得住谁

| 层 | 载体 | 时机 | 拦得住 | 拦不住 | 可信度 |
|---|---|---|---|---|---|
| **L1 编辑器层** | `.codebuddy/settings.json` 的 4 个 PreToolUse hook + 2 个 SessionStart + 1 个 PostToolUse | AI 每次写文件 / 执行命令**之前** | 只有 AI 的写入与命令 | 人手动编辑、人手动执行、其他 IDE | 对 AI **高**；对人 **零** |
| **L2 本地 git 层** | `.githooks/`（`core.hooksPath` 指向） | `git commit` | 所有本地提交（含 AI 提交） | `--no-verify`、`UI_GATE=off` | **已启用（2026-10-22 补齐 pre-commit）** |
| **L3 PR CI 层** | `quality-gate.yml` 4 个 job | 每次 PR 更新 | 所有进 master 的改动（前提：分支保护要求该 workflow 通过） | Admin merge、直推 master | **唯一硬门**，但仅 8 项阻断 |
| **L4 发布层** | `release.yml` + deploy-console `release_plan` / `release-verify` | 发布动作 | 发布流水线本身 | 手工 SSH 上机、绕过流水线改文件 | 中（不变量校验，非内容校验） |

> **设计含义**：L1 是"越早越便宜"的反馈，不是安全边界；L2 是快反馈（可被 `--no-verify` 绕过）；**L3 是唯一契约**。
> 「本地会拦住」只在「没加 --no-verify」的前提下成立——所以本地绿灯不等于可合并，CI 绿灯才是。

### 2.1 L1 的四道 hook 分别管什么

| hook | 触发 | 作用 | 拒绝后怎么办 |
|---|---|---|---|
| `hook-ui-prototype-gate.py` | AI 写文件前 | 未确认原型就写 UI 源码 → deny | 先出原型 → 用户确认 → 再写码 |
| `hook-shell-ui-gate.py` | AI 执行命令前 | 命令里含 UI 源码写入/生成 → deny | 同上 |
| `hook-worktree-gate.py` / `hook-worktree-shell-gate.py` | AI 写文件 / 执行命令前 | 非 worktree、非规范分支上的危险动作 → deny | 按 `docs/development/dev-workflow.md` 建 worktree |
| `hook-mark-proto-touched.py` | AI 写完文件后 | 标记本轮碰过原型，供后续判定 | 无（只做标记） |

### 2.2 L3 的两个隐藏契约（改 CI 前必读）

这两条都不写在任何 workflow 文件里，但违反了就会让门禁**静默失效**——CI 页面全绿，PR 却合不进去，或者反过来。

| 契约 | 表现 | 怎么发现的 | 正确做法 |
|---|---|---|---|
| **job `name` 就是分支保护 required check 的键** | 把 `改动包 build/test` 改成 `改动包 build/test/lint` 后，四个 job 全 `pass`，PR 依然 `BLOCKED`，`gh pr merge` 只说「加 --auto」；GitHub **不提示缺哪个 check** | 2026-10-22 实测：改回原名后同一 PR 立刻 `BLOCKED → CLEAN` | 改 job name 必须同步改 Settings → Branches → required checks；或干脆不改名（把新步骤塞进旧 job） |
| **workflow 必须真被 branch protection 引用** | 新增了 workflow / job，但它不在 required 列表里 → 红了也能合 | `quality-gate.yml` 头部注释「启用要求：master 分支保护开启，要求本 workflow 通过才可 merge」 | 新增 job 时确认它进 required 列表，否则它只是"参考信息" |

> 这两条合起来说明一件事：**L3 的强制力来自分支保护配置，不是来自 workflow 文件本身**。
> 所以「我加了 CI 检查」不等于「门禁生效」——必须验证一次「故意让它红，能不能拦住合并」。

## 3 五类机制（用机制替掉 20 个编号）

### 3.1 A 类 · 行级静态规则（逐行扫**新增行**）

共同约定：
- **只看新增/变更行**，存量违规不背锅（这是全仓门禁的第一原则）
- 注释行跳过（`//` `#` `/*` `*` `<!--`）——但 R3 占位规则**不跳**，因为 TODO 常写在注释里
- 豁免目录（R1 专用）：`scripts/*.mjs|cjs`、`apps/*/scripts/*`、`archive/migrations/*.mjs|cjs`、`.codebuddy/[agent-kit/]skills/*/scripts/*`
  → 判据是**「脚本的 stdout 就是产品输出」**，不是「这个目录比较特殊」

| 机制 | 编号 | 级别 | 判什么 |
|---|---|---|---|
| A1 调试残留 | R1 | error | `console.log` / `console.debug(` / `debugger` |
| A2 硬编码凭据 | R2b | error | `password\|secret\|api_key\|token\|private_key` 后跟 8 位以上字面量 |
| A3 敏感文件入库 | R2 | error | `*.pem` / `*.key` / `.env*`（`.env.example` 除外） |
| A4 占位残留 | R3 / R3b | error / warn | TODO·FIXME（error）；TEMP·TBD·HACK·XXX（warn） |
| A5 TS 铁律 | R4 | error | `@ts-ignore` / `@ts-nocheck`；`: any` 类型标注 |
| A6 CORS | R5 | warn | `enableCors()` 无参 / `origin: '*'` |
| A7 全局异常过滤器 | R8 | warn | `main.ts` 有 `enableCors` 却无 `useGlobalFilters` |

> **A5 的实现坑（已修，勿回退）**：`: any` 原字符类 `[[:space:],);\]}]` 在 POSIX 里 `\]` 不是转义 → 整类解析错 → `const a: any = 1` / `any[]` / `x: any;` 全部漏报。现用词界 `([^0-9A-Za-z_]|$)`。**禁止改回 `[[:alnum:]]`**：UTF-8 下汉字算字母，`中文TODO中文` 会漏报。

### 3.2 B 类 · 结构门（看「文件集合」而非单行）

| 机制 | 编号 | 级别 | 触发面 → 要求 |
|---|---|---|---|
| B1 新增页面须同行原型 | R9 | warn | diff 新增 `apps/*/pages/**` 或 `app.json` 的 pages/tabBar 变化 → 同 diff 须含 `apps/*/prototype/**` / `docs/ui/prototypes/**` / `specs/**/page-spec*.md` |
| B2 既有 UI 改动须同行原型 | R9b | warn | 改动既有 UI 源码且未同行改原型/规格 → 须 `Micro-exempt: <理由>` |
| B3 原型锚点漂移 | R11b | **off（默认）** | 原型与 page-spec 的 `data-dr` 锚点比对；`DESIGN_ANCHOR_MODE=warn/strict/scoped` 才生效 |
| B4 双源同源 | R12 | warn | `.codebuddy/agent-kit/skills` ↔ `.codebuddy/skills` 内容一致（项目专属技能与下游定制文件白名单跳过） |
| B5 SSE 契约一致 | R16 | warn | 消费方手写事件联合 ↔ `packages/agent-core` 的 `StreamEventType` 真相源（由 `check-sse-contract.py` 输出） |
| B6 原型体系静态三件套 | —（job: proto-static-check） | error | ① `build-agents-hub` 后生成物必须与提交一致；② 散落稿必须为 0 或已登记；③ 已并入稿的可并入性回归 |
| B7 流水线脚本静态体检 | L1/L5/L6/L9 | error / error / warn / error | L1 `bash -n`；L5 ssh 行尾缺续行符；L6 危险命令提示；L9 调 `$CONSOLE_API` 的 curl 缺 `-f` |

> B6 的判据源不在本文，在 skill `ux-prototype-designer/references/proto-adoption.md`。本文只保证「散落 = 0」这个不变量被 CI 守住。

### 3.3 C 类 · 凭证门（commit message trailer）

**这是全仓最容易被误认为「7 个门」的地方。实际是 1 个机制 + 7 个触发面。**

统一语义（实现：`_trailer_check_one`）：

```
命中触发面的 commit → message 必须含
    <Key>: pass                  ← 声明「本 commit 已过该评审」
  或 <Key>: <报告路径>            ← 指向报告，且报告须存在、头部 `阻塞: N` 为 0
否则 warning。统一豁免：Micro-exempt: <理由>
```

| 门 | Key | 触发面（可枚举，非语义判断） | 级别 |
|---|---|---|---|
| C1 原型确认 | `Proto` | commit 含 UI 源码 → 须指向**已落库且在本 commit 祖先链上**的原型 commit sha（四条校验） | warn |
| C2 设计评审 | `Design` | commit 含 UI 源码 / 原型规格 → `Design: pass`，且报告 `阻塞: 0` | **error** |
| C3 契约与数据 | `Contract` | `archive/migrations/*` · `packages/types/*` · `packages/agent-core/src/interfaces/*` · `servers/mcp-gateway/src/*/tools/*` · `servers/*/src/*/*.controller.ts`（另有行数阈值） | warn |
| C4 发布与环境 | `Release` | `ecosystem.config.**` · `servers/*/.env*` · `scripts/pipeline/*` · `scripts/{publish,deploy}-*.sh` · `servers/deploy-console/src/pipeline/*` · `.github/workflows/*` | warn |
| C5 独立代码评审 | `Code` | **新增** `*.controller.ts` 文件 | warn |
| C6 测试用例 | `Test` | **新增** `servers/*/src` · `apps/*/src` 下的非测试源码 | warn |
| C7 研发方案与发布清单 | `Plan` | **新增** service / controller / 前端 view（功能级改动） | warn |

**设计取向（务必保留）**：C5/C6/C7 的触发面刻意取窄（只认「新增」）。原因是这三条主观性最强、成本最高，宽触发面必然被 `Micro-exempt` 淹掉——**门禁一旦被批量豁免，就等于不存在**。

**C1 的特殊约束**：`Proto` 不是自由文本，是 sha。校验四条：非空 → 该 commit 存在 → 是 HEAD 的祖先 → 指向的 commit 含原型/规格文件。混合提交（UI 源码 + 原型同 commit）直接 error，因为那正是绕过「用户确认原型」节点的形态。

### 3.4 D 类 · 构建与测试门

| 机制 | 实现 | 级别 | 说明 |
|---|---|---|---|
| D1 类型检查 / build | `scripts/ci/changed-packages.sh` | error | 从改动路径反推子包；**先按拓扑序构建其工作区依赖**（`<name>^...`），否则 CI 全新 checkout 必报 `TS2307` |
| D2 单元测试 | 同上（有 `test` 脚本的包跑 `jest --runInBand`） | error | `set -e`，任何包非零即整体失败 |
| D3 ESLint | 两道：`changed-packages --lint`（拦 error）+ 根 `pnpm lint:ci`（warning 水位 328） | error | 2026-10-22 开启。子包 lint:ci 只拦 error；warning 用**总量水位**（只降不升），因为 ESLint 不提供「只报新增行」，按文件判会误伤存量大户 |
| D4 生成物一致性 | proto-static-check 第一步 | error | build 后 `git diff --quiet` 校验，防「改了源稿没重跑 build」与「手改生成物」 |

### 3.5 E 类 · 发布门

| 机制 | 载体 | 校验什么 |
|---|---|---|
| E1 发布流水线 | `.github/workflows/release.yml` | 只在发布源分支触发；master 合并不自动发布 |
| E2 发布方案不变量 | deploy-console `release_plan`（L1 只读 dry-run） | 模块在册 / **目标产物存在** / 发布锁空闲 / 环境健康 / 回滚点存在 |
| E3 发布后验证 | deploy-console `release-verify` | 按用例矩阵自动验证，替代人工点 |

> E2 的「目标产物存在」是唯一能抓住「流水线成功但前端产物没投递」的检查——2026-09 的事故正是这一类。这也是为什么 C7（`Plan` 凭证）必须存在：`release_plan` 只验不变量，不验「方案里到底写没写发布清单」。

## 5 阻断力真相：哪些门其实不拦

这一节存在的唯一目的：**让「全部检查通过」这句话重新有信息量。**

| 门 | 名义 | 实际（CI 不带 `--strict`） | 想让它真拦，需要 |
|---|---|---|---|

## 6 豁免与降级（五类出口）

| 出口 | 用法 | 影响范围 | 正规场景 | 滥用判据 |
|---|---|---|---|---|
| `Micro-exempt: <理由>` | commit message trailer | R9b / R10 / R11 / R13 / R14 / R15 / R17 / R18（同口径） | 纯文案、纯样式微调 | 同一理由一周出现 ≥3 次 → 说明触发面画错了，改触发面而不是继续豁免 |
| `UI_GATE=off` | 环境变量 | L1 的 UI hook + L2 的 commit-msg | 批量机械改动、紧急修复 | 出现在 CI 日志或日常提交里（应只出现在事故处置） |
| `git commit --no-verify` | git 参数 | 绕过 L2 全部 | 不应存在 | CI 仍跑 R1–R18，所以它只绕过"本地快反馈"，不绕过契约 |
| `DESIGN_ANCHOR_MODE=off\|warn\|strict\|scoped` | 环境变量 | R11b | `off`=存量回填前；`scoped`=分批推进 | 长期停在 `off` 且无人跟进回填 |
| 不传 `--strict` | 调用方式 | 全部 warning | 现状默认 | 见 §5：这是事实上的「全 warning 不阻断」开关，必须被显式认知 |

**统一原则**：豁免必须写在 commit message 里（可审计），不许写在代码注释或口头约定里。`hook-mark-proto-touched.py` 之类的状态文件不算豁免。

## 7 升级路径：warn → error 的三条件

一条 warning 门要升 error，必须**同时**满足：

1. **数据**：`docs/development/gate-observation-log.md` 累计 ≥20 个 commit、≥5 条真实命中、误报率可算出
2. **误报率 < 30%**：超过说明触发面画宽了，先收窄再谈升级
3. **豁免频次未走高**：`Micro-exempt` 使用率随门禁上线没有明显上升（这是"门禁被绕开"的头号前兆指标）

**现状（2026-10-23 更新）**：观察期已恢复采集，但**条件 1 仍未满足**。

| 门 | 近窗（`master~20..master`，20 commit） | 对照窗（`master~40..master~20`） | 条件 1 要求 ≥5 命中 |
|---|---|---|---|
| R13 契约面 | 6 | 8 | ✅ 已够 |
| R14 发布面 | 3 | 7 | ⏳ 未够 |
| R15 独立代码评审 | 0 | 1 | ❌ 差得远 |
| R17 测试用例 | 3 | 6 | ⏳ 未够 |
| R18 研发方案清单 | 2 | 2 | ❌ 差得远 |

`Micro-exempt` 豁免 1 → 2（20 commit 粒度），**未出现豁免暴增**，条件 3 暂无风险信号。
但 **条件 2（误报率 < 30%）一次都没算过**——它需要对每条命中人工判"这是真缺失还是触发面画宽了"，而当前数据里 R13 的 6 条命中还没逐条看过。

**所以：R13 是唯一"数据接近够用"的门，其余四条都不够。不要因为「采集恢复了」就以为可以升 error。**

**恢复动作（见 §8 P1-2）**：不要求每天采，改为「每合入一个含契约/发布面改动的 PR，跑一次 `collect-gate-observations.sh` 追加一行」。零命中也要记，因为"零命中"本身就是判断触发面是否画准的数据。

## 9 新增门禁准入标准（防再臃肿）

下一次想加门禁时，按顺序过这 7 条。**任何一条不过，就不许加。**

| # | 准入条件 | 反面例子（真实发生过的） |
|---|---|---|
| 1 | **能用现有 5 类机制表达就不许写新脚本** | 新增一个 `check-xxx.mjs` 去做"commit 须带某某 trailer"，而 `_trailer_check_one` 已经能做 |
| 2 | **必须默认 warning，且带观察期落点** | R11 直接上 error（可接受，因为它拦的是"绕过用户确认节点"，属零容忍；但不能成为惯例） |
| 3 | **触发面必须可枚举** | 写"检测架构是否合理"这类语义判断——机器判不了，最终靠人，必然误报泛滥；或用目录通配糊过去（`packages/ui/*` 把 package.json 也当 UI 源码，改个 lint 脚本就被要求设计评审，2026-10-22 实测） |
| 4 | **必须声明豁免方式 + 滥用判据** | 只给 `--no-verify`，没有可审计的豁免通道 → 人会直接跳过整个流程 |
| 5 | **至少在一层真正阻断，否则只能叫「体检项」** | 上线 5 条 warning 门后宣称"门禁已覆盖"，实际一条没拦 |
| 6 | **判据源必须单一**：本文只索引不复述 | 同一个要求在 3 份文档各写一遍，改一处漏两处（当前 7 份判据源就是这么来的） |
| 7 | **同 PR 更新本文 §4 与附录 A** | 加了规则但总表没有 → 半年后没人知道它存在 |

> 补充一条软约束：**新增门禁前先问「能不能不加」**。当前 20 个编号里，真正需要的是 13 个阻断项 + C 类凭证的 7 个触发面。再加之前，先确认它不属于"已有机制的又一个触发面"。
