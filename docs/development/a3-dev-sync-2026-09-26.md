## 4 拉齐过程中发现并修掉的问题

### 4.1 【仓库级 bug】`EmailVerificationCodeEntity` 漏登记 → 邮箱验证码全环境不可用

**现象**（dev 拉齐后实测）：
```
POST /internal/users/email/verify 带正确 x-internal-key → 500
EntityMetadataNotFoundError: No metadata for "EmailVerificationCodeEntity" was found.
    at email.service.ts:137 → Repository.findOne
```

**根因**：`servers/user-service/src/app.module.ts` 的 TypeOrmModule 用**手写 entities 清单**，`EmailModule` 已引入、`forFeature` 已注册，但根 DataSource 的数组漏了该类。

**危害面**：编译能过、单测能过，只有真调接口才暴露；**所有环境（含 prod）都不可用**。

**修复**：commit `0927d43`，补 import + 补进 entities 数组 + 加警示注释。

**全仓排查**（monorepo 铁律）：
- glob 自动登记（无漏登记风险）：ai-agent / ai-service / auth-service / deploy-console / system-service
- 手写清单（已逐一核对）：content-hub(9/9) / gateway(5/5) / knowledge-service(3/3) / mcp-gateway(3/3) / user-service(9/9 ← 修复后)
- **仅 user-service 存在漏登记，已修。**

### 4.2 `NODE_ENV=production` + `synchronize: false` → 新表不会自动建

`user-service` 的 synchronize 判定是 `NODE_ENV !== 'production'`，dev 上 `NODE_ENV=production`，故
`email_verification_codes` 表不会自动创建 → 需手工执行 `migrations/0014_mp_account_phone_email.sql`。

执行前已做前置检查：**`dup_phone = 0`**（无重复手机号），故 `ADD UNIQUE KEY uk_users_phone` 可安全执行。
执行时去掉了 `COLLATE=utf8mb4_0900_ai_ci`（见 §5 待办 I-3）。

### 4.3 pm2 命名不一致（已确证，属 A2 范畴）

dev 的 `ecosystem.config.cjs` 定义的是 `web-*`（web-gateway / web-auth …），但**实际 pm2 进程是短名**
（gateway / auth-service …）。`pm2 restart web-gateway` 会失败，必须用短名。
另：ecosystem 写 `web-auth PORT=6101`，**dev 实际 auth-service 跑在 6001**（`6101` 是本机值）——
即 dev 上端口由各服务 `.env` 决定，ecosystem 的 PORT 未被采用。

### 4.4 `INTERNAL_API_KEY` 缺口

dev 上缺该键的服务：gateway / auth-service / todo-service / content-hub。
其中**只有 auth-service 是真实缺口**（它调 `user-service /internal/users/email/verify`，
而 user-service 的 `InternalGuard` 在 `expected` 非空时要求严格匹配）→ 已补。
gateway / todo-service / content-hub **不是 outbound 调用方，当前无影响**（代码里无 `x-internal-key` 调用点）。

## 8 补记：F4 共享实体登记（2026-09-26 晚，commit `3b40fa4`）

承接 §5 的 I-2/I-3（0014_mp 迁移改造），评审提出的 F4：迁移建的 `merged_to` 列与
`uk_users_phone` 唯一索引**不在任何实体里**，会被 synchronize 反向 DROP。

### 影响面：比评审估计的更大

`user-service`（手写 entities 清单）/ `auth-service`、`todo-service`（glob 扫描
`**/*.entity{.ts,.js}`）三者的 `src/user*.entity.ts` 都只是
`export { User } from '@web-system/shared'` 的转发文件 → **三个服务都会对 users 表做 synchronize**。

| 环境 | NODE_ENV | 后果 |
|---|---|---|
| dev / prod | production | synchronize=false，**不受影响**（列由迁移提供） |
| 本机 | development | 此前 users 表**一直缺**这两项（实测 `has_merged_to=0` / `has_uk=0`），修复后 synchronize 自动补齐 |

### 实证（本机 MySQL + TypeORM schema builder dry-run）

| 实体版本 | synchronize 将要执行的 UP 语句 |
|---|---|
| 改前 | **2 条**：`DROP INDEX uk_users_phone ON users`、`ALTER TABLE users DROP COLUMN merged_to` |
| 改后 | **0 条**（实体与库 schema 完全一致） |

反证的意义：UP=0 本身不能证明脚本有效，回到改前版本跑出 2 条 DROP，才说明验证是有效的。

### 一个易踩的细节

索引**必须具名** `@Index('uk_users_phone', ['phone'], { unique: true })`。若改用
`@Column({ unique: true })`，TypeORM 会另起哈希名 `IDX_xxx`，与迁移建的 `uk_users_phone`
判定为不匹配 → 反复 DROP/BUILD 抖动。

### 部署注意

`@web-system/shared` 的 `main` 指向 **dist 产物** → 改源码后必须 `tsc` 重建 shared，
再重建依赖它的三个服务，否则运行时仍是旧元数据。dev 端已按此顺序执行并重启验证通过。
