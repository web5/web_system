## 1 门禁总表（按研发环节 S0–S9）

与 `specs/rd-process-model/design.md` §3.1 的环节编号一一对应。**这一列的意义**：告诉你在流程的哪一步该主动满足哪条门，而不是等 CI 报错再补。

| 环节 | 产出 | 该主动满足 | 谁拦 | 级别 |
|---|---|---|---|---|
| S0 需求转换 | 需求 spec（EARS + 反例） | — | — | — |
| S1 方案 + 交付清单 | 方案 / 验证判据 V1…Vn | **C7 `Plan:`** 在此产出方案后即可写 | CI | warn |
| S2/S3 原型出稿 | 原型 HTML + page-spec | **L1 hook**（未确认原型不许写码） | IDE | error(deny) |
| S3.2 D2 设计评审 | 设计评审报告（`阻塞: N`） | **C2 `Design:`** | CI | **error** |
| ◆③ 原型确认 | 用户确认 | **C1 `Proto: <sha>`** | CI | warn |
| S4.2 契约评审 | 契约评审报告 | **C3 `Contract:`** | CI | warn |
| S5 代码实现 | 代码 + 迁移 + 配置 | **A1–A7** 全程生效 | 本地+CI | error/warn |
| S5.2 独立代码评审 | 代码评审报告 | **C5 `Code:`**（仅新增 controller） | CI | warn |
| S6 D3 一致性评审 | 一致性报告 | **B3 R11b**（当前 off） | CI | off |
| S7 测试盲测 | 盲测报告 | **C6 `Test:`** | CI | warn |
| S8 交付发布 | 发布单 / 回滚方案 | **C4 `Release:`** + **E2 不变量** | CI+平台 | warn / error |
| S9 运营观测 | 指标 + 故障模式 | 回灌判据源（无机器门） | — | — |

**与环节无关的两条**（任何阶段改动都可能触发，故不占表中某一行）：

- **B4 R12**：`.codebuddy/` 双源不一致 → 谁碰到 skill 目录谁负责
- **B5 R16**：SSE 游标/事件联合改动 → 改 `packages/agent-core` 或消费方任一侧都触发

## 2 阻断力真相：哪些门其实不拦

这一节存在的唯一目的：**让「全部检查通过」这句话重新有信息量。**

| 门 | 名义 | 实际（CI 不带 `--strict`） | 想让它真拦，需要 |
|---|---|---|---|
| R1 R2 R2b R3 R4 | error | **阻断** | — |
| R11 | error | **阻断** | — |
| B6 原型三件套（含生成物一致性） | error | **阻断** | — |
| L1 L5 L9 | error | **阻断** | — |
| D1 类型检查 / build、D2 测试、D3 ESLint | error | **阻断** | — |
| R3 弱占位（TEMP/TBD/HACK/XXX） | warn | 只打印 | 有意不阻断：这类词常出现在文档与命名里 |
| R5 R8 | warn | 只打印 | `--strict`（不建议：CORS 形态多，易误报） |
| R9 R9b | warn | 只打印 | 先补观察期数据 |
| R10 | warn | 只打印 | 有 R11 兜底，可长期保持 warn |
| R13 R14 R15 R17 R18 | warn | 只打印 | 见 [02-机制原理.md](02-机制原理.md) §升级路径 |
| R16 | warn | 只打印 | 一旦 SSE 有第二消费方即升 error |
| L6 | warn | 只打印 | 永久 warn（危险命令本身合法） |
| R11b | **off** | 完全不跑 | 存量锚点回填完再 `scoped` |

> **L2 与 D3 已不在失效区（2026-10-22）**：L2（pre-commit）执行的就是 A 类规则，不单独计项；
> D3 已列入上方阻断区。此前它们一个「未启用」一个「关闭」，是 v1 记录的最严重两处失真。

**唯一不需要讨论的**：R1–R4、R11、B6、L1/L5/L9、D1/D2/D3。这 13 项是「错了就是错的」，其余全部是「值得提醒」。文档、周会、PR 模板里不要再把它们混称"门禁"。

## 3 豁免与降级（五类出口）

| 出口 | 用法 | 影响范围 | 正规场景 | 滥用判据 |
|---|---|---|---|---|
| `Micro-exempt: <理由>` | commit message trailer | R9b / R10 / R11 / R13 / R14 / R15 / R17 / R18（同口径） | 纯文案、纯样式微调 | 同一理由一周出现 ≥3 次 → 说明触发面画错了，改触发面而不是继续豁免 |
| `UI_GATE=off` | 环境变量 | L1 的 UI hook + L2 的 commit-msg | 批量机械改动、紧急修复 | 出现在 CI 日志或日常提交里（应只出现在事故处置） |
| `git commit --no-verify` | git 参数 | 绕过 L2 全部 | 不应存在 | CI 仍跑 R1–R18，所以它只绕过"本地快反馈"，不绕过契约 |
| `DESIGN_ANCHOR_MODE=off\|warn\|strict\|scoped` | 环境变量 | R11b | `off`=存量回填前；`scoped`=分批推进 | 长期停在 `off` 且无人跟进回填 |
| 不传 `--strict` | 调用方式 | 全部 warning | 现状默认 | 这是事实上的「全 warning 不阻断」开关，必须被显式认知 |

**统一原则**：豁免必须写在 commit message 里（可审计），不许写在代码注释或口头约定里。`hook-mark-proto-touched.py` 之类的状态文件不算豁免。
