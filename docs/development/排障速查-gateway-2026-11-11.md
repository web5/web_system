# 排障速查 · Gateway shell defaultEnv 与 HTML 缓存

> 规范真源：`~/AiWorkspace/20-私域资产/排障速查规范.md`。
> 本文只收「遇到 X → 查 Y」的可复用判据；单次事故时间线不展开。
> 默认讨论 NEW 域（站点 `defaultEnv` + `deploy_app_env_versions` 指针）；`DEPLOY_LEGACY_READ=1` 的应急通道另见各条适用范围。

## 命令约定

以下变量先按被测环境赋值，之后各段命令可直接复制执行。尖括号只是占位符，执行前必须替换；不要填入真实密码、Token 或数据库凭据。

```bash
GATEWAY_ORIGIN='http://127.0.0.1:6000' # 其他场景直连单个 gateway 进程，末尾不带 /；不要指向负载均衡入口
FORWARD_GATEWAY_ORIGIN='<FORWARD_GATEWAY_ORIGIN>' # 场景一冷启动实例 A，如 http://127.0.0.1:16001
REVERSE_GATEWAY_ORIGIN='<REVERSE_GATEWAY_ORIGIN>' # 场景一另一冷启动实例 B，如 http://127.0.0.1:16002
PROD_HOST='<PROD_HOST>'                 # Host 命中 defaultEnv=prod 的站点，不含 scheme
DEV_HOST='<DEV_HOST>'                   # Host 命中 defaultEnv=dev 的站点，不含 scheme
SHELL_ROUTE='/'                         # 任意由 gateway 返回 shell HTML 的 GET 路由
HTML_MARKER_RE='<HTML_MARKER_RE>'       # 能区分两份 HTML 的 ERE，见下方说明
PROD_HTML='<PROD_HTML>'                 # prod 当前指针实际指向的 index.html 绝对路径
DEV_HTML='<DEV_HTML>'                   # dev 当前指针实际指向的 index.html 绝对路径
PUBLIC_ROOT='<PUBLIC_ROOT>'             # 被测 gateway 进程实际静态根，不要仅凭 .env 猜测
```

- `HTML_MARKER_RE` 可使用测试 HTML 中各自唯一的标记，例如 `PROD_SHELL_HTML|DEV_SHELL_HTML`；真实产物可匹配版本唯一的 shell 资源 hash。两份产物的 marker 必须预先确认不同。
- HTTP 命令需要 `curl`、`jq`；`.data // .` 同时兼容统一响应 envelope 与未包装响应。
- `FORWARD_GATEWAY_ORIGIN` 与 `REVERSE_GATEWAY_ORIGIN` 必须是两个**同版本、新启动、互不复用缓存**的 gateway 进程，推荐监听两个不同隔离端口；每个方向开始前，对应实例不得已有 shell HTML 请求。
- 修改 mtime 的命令**只用于隔离测试环境或测试 worktree**，不得在共享 dev/prod 产物上执行。

### 场景一：站点 defaultEnv 已正确，但 HTML 与 manifest 环境不一致

**判据**：每个方向都在同一个 gateway 进程内按两个 Host 顺序请求，但 `prod→dev` 与 `dev→prod` 必须分别使用新启动的实例，保证两个方向各自从冷 HTML 缓存开始。每份响应同时核对 HTML marker、`manifest.defaultEnv`、`__version__` 的 shell 环境/版本路径；两份 HTML 必须同 mtime，排除 mtime 不同碰巧绕过缓存。

先读取两份实际 HTML，确认路径和 marker 都有区分度：

```bash
python3 - "$PROD_HTML" "$DEV_HTML" <<'PY'
import os
import sys

for path in sys.argv[1:]:
    stat = os.stat(path)
    print(path, 'mtime_ns=', stat.st_mtime_ns, 'size=', stat.st_size)
PY
```

仅在隔离测试环境把两份文件设为同一 mtime，并确认设置生效：

```bash
python3 - "$PROD_HTML" "$DEV_HTML" <<'PY'
import os
import sys

fixed_ns = 1704067200000000000
for path in sys.argv[1:]:
    os.utime(path, ns=(fixed_ns, fixed_ns))
    print(path, 'mtime_ns=', os.stat(path).st_mtime_ns)
PY
```

定义探针。冷启动实例 A 只跑 `prod→dev`；另一个冷启动实例 B 只跑 `dev→prod`。每个方向内部的两 Host 必须落到同一进程，两个方向之间不得复用已经预热的实例：

```bash
probe_shell() {
  label="$1"
  origin="$2"
  host="$3"
  html="$(curl --noproxy '*' -fsS -H "Host: $host" "$origin$SHELL_ROUTE")"
  printf '\n[%s]\nHTML markers:\n' "$label"
  printf '%s' "$html" | grep -oE "$HTML_MARKER_RE" | sort -u
  printf 'manifest: '
  curl --noproxy '*' -fsS -H "Host: $host" "$origin/__manifest__" \
    | jq -c '.data // . | {site,defaultEnv,source}'
  printf 'shell version: '
  curl --noproxy '*' -fsS -H "Host: $host" "$origin/__version__?module=shell" \
    | jq -c '.data // . | {env,version:(.version // null),entry,assetsBase}'
}

# 实例 A：此前不得有 shell HTML 请求
probe_shell '冷启动 A / prod→dev / prod' "$FORWARD_GATEWAY_ORIGIN" "$PROD_HOST"
probe_shell '冷启动 A / prod→dev / dev'  "$FORWARD_GATEWAY_ORIGIN" "$DEV_HOST"

# 实例 B：与 A 同版本但缓存独立，此前不得有 shell HTML 请求
probe_shell '冷启动 B / dev→prod / dev'  "$REVERSE_GATEWAY_ORIGIN" "$DEV_HOST"
probe_shell '冷启动 B / dev→prod / prod' "$REVERSE_GATEWAY_ORIGIN" "$PROD_HOST"
```

通过条件：

1. 每个 Host 的 HTML 只含本环境 marker，不含同一冷启动方向中上一个 Host 的 marker。
2. `manifest.defaultEnv` 与 `__version__.env` 分别等于该站点的 `defaultEnv`。
3. NEW 域默认资源模式下，shell `entry`/`assetsBase` 包含 `/shell/<expectedEnv>/<expectedVersion>/`；CDN 模式至少保证 `env`、`version` 和版本化 URL 同源。
4. `prod→dev` 在冷启动实例 A 通过，`dev→prod` 在另一个冷启动实例 B 通过，且两个方向都满足同 mtime；只绿一个方向，或反向仅在已预热实例上复测，均不算双向独立证据。

**易误判点**：

- `manifest.defaultEnv` 正确只说明 manifest 按 Host 解析正确，不能证明 HTML 缓存也按 Host/实际路径隔离。
- 单 Host、单方向、不同 mtime 的测试均可能假绿；旧缓存键常在同 mtime 的第二站请求才暴露。
- 在同一进程连续跑完 `prod→dev` 再跑 `dev→prod` 时，两个路径可能都已预热；后一组只是预热后的反向请求，**不是反向冷启动反例**，即使全绿也不能替代独立证据。
- 每个方向内部若经负载均衡落到不同进程，无法验证该方向的进程内缓存串用；必须直连该方向的同一实例。两个方向之间则必须使用缓存独立的冷启动实例。
- HTML 中的兼容字段 `manifest.env` 可能仍表示进程配置缺省值，本站判断以 `defaultEnv` 为准，不要拿它替代 `defaultEnv`。

**适用范围**：web_system gateway 微前端 shell，NEW 域、按 Host 匹配站点且两个站点指向不同 shell 产物。本地/隔离环境可用两个不同端口的新进程；发布后可用两个同版本且缓存独立的实例，或由场景三单元测试覆盖反向冷启动。单元测试须为每个方向新建 service，或在反向前显式执行 `(svc as any).htmlCache.clear()`。真实共享/prod 不得为测试重启进程或执行 mtime 修改段；若只有一个已预热实例，HTTP 结果只能算该方向的补充证据，反向独立证据由合格单测提供。

### 场景二：已改 req/Host 路径解析，需要判断 HTML 缓存键是否完整

**判据**：路径解析修对以后，继续检查 `readHtml`/`htmlCache`，不能只验收 `resolveShellHtmlFile(req)` 的返回值。

```bash
REPO_ROOT='<REPO_ROOT>' # web_system 被测 worktree 绝对路径
cd "$REPO_ROOT"
git grep -n -A 22 -B 4 'private async readHtml' -- \
  servers/gateway/src/deploy-version/index-html.service.ts
```

合格实现必须同时满足：

1. 先把本次 req/Host 解析出的 `requested` 归一化为实际文件路径，例如 `const file = resolve(requested)`（`resolve` 即 `path.resolve`）。
2. `htmlCache.get(...)` 与 `htmlCache.set(...)` 的键至少包含这个实际文件路径；等价复合键也可以，但不能只按 `pub`、`envId` 或 `pub + mtime`。
3. 保留 `stat + mtime` 作为**同一路径内容变化的失效条件**；mtime 是有效性元数据，不能代替路径维度。
4. 静态检查后再跑场景一的双向同 mtime 探针，以及场景三的缓存复用/切版计数，避免只看代码形状。

**易误判点**：

- `resolveShellHtmlFile(req)` 已返回不同路径，不代表 `readHtml` 使用了该路径作缓存键；路径解析和缓存索引是两道独立检查。
- `pub + mtime` 在不同文件同 mtime 时仍发生碰撞；把 mtime 加进键不等于完整隔离。
- 单 Host 测试绿不等于跨 Host 隔离；禁用缓存也可能让内容测试全绿，但会破坏同路径复用。
- 只检查 `get` 不检查 `set`，可能漏掉读写键不一致造成的永不命中或错误复用。

**适用范围**：所有由 `IndexHtmlService.readHtml` 读取并按请求解析路径的 shell HTML；对固定 `pub` 的 console HTML 不涉及跨 Host 路径选择，但同样可复用路径键与 mtime 失效判据。

### 场景三：内容测试全绿，需要区分「禁用缓存假绿」与「有效缓存」

**判据**：在 `readFileSync` 可计数的单元测试中同时锁以下四类行为；只有内容断言、没有读取次数断言不算验证缓存。

在包含对应回归断言的 web_system 分支执行：

```bash
REPO_ROOT='<REPO_ROOT>' # 被测 worktree 绝对路径
cd "$REPO_ROOT"
pnpm --filter @web-system/gateway test -- --runInBand \
  src/deploy-version/index-html.service.spec.ts \
  -t '同一实际 HTML 路径|shell 指针切版后|同 mtime 的不同 Host'
```

核对选中测试的断言，而不是只看进程退出码：

| 操作序列 | 必须断言的结果 |
|---|---|
| 同一实际路径、同 mtime，连续 render 两次 | 两次内容一致，累计 `readFileSync=1`；证明缓存仍有效 |
| 同一实际路径，mtime 从 1 变为 2 后再 render | 返回新 marker，累计 `readFileSync=2`；证明 mtime 失效仍有效 |
| shell 指针从旧版切到新版，新旧 HTML 同 mtime | 清版本缓存或等其 TTL 后，读取新版实际路径并返回新 marker，累计读取次数增加；不得复用旧路径内容 |
| 两个 Host 指向不同实际路径且同 mtime，双向 render | 每个方向分别新建 service，或在反向前显式清空 `htmlCache`；各自只返回本环境 marker，两个实际路径都被读取 |

自写等价测试时，至少 mock `statSync(...).mtimeMs`、`readFileSync(path)` 和 shell 指针；`readFileSync` 应按传入路径返回不同 marker，并对调用次数及最终路径作断言。双向用例必须让每个方向从冷 `htmlCache` 开始，不得在同一个已预热 service 上连续跑两个方向。切版用例若存在版本指针 TTL，必须显式清缓存或控制时间，避免把旧指针误认为 HTML 缓存缺陷。

**易误判点**：

- 禁用 HTML 缓存后，所有内容测试都可能变绿，但同路径重复 render 会变成 `readFileSync=2`；这不是有效缓存。
- 只测「同路径=1、mtime 变化=2」仍可能漏掉「不同路径同 mtime」碰撞；切版与跨 Host 用例不可省。
- 切版后仍读旧路径，先区分版本指针 TTL/失效与 HTML 缓存；不要通过改 HTML 内容去掩盖指针未更新。
- Jest 没有匹配到任何测试时也可能退出成功；输出必须显示上述用例实际运行并通过。

**适用范围**：`IndexHtmlService` 的进程内 HTML 缓存及其单元测试；不用于推断浏览器、CDN 或 nginx 缓存行为。旧分支若没有这些断言，只能记为「未覆盖」，不能记为 PASS。

### 场景四：需要区分「无指针固定目录回落」与「错误跨站复用」

**判据**：先查 shell 指针与实际文件，再解释 HTML 相同/不同；不要仅凭两个 Host 的页面内容下结论。

```bash
shell_pointer() {
  host="$1"
  curl --noproxy '*' -fsS -H "Host: $host" "$GATEWAY_ORIGIN/__version__?module=shell" \
    | jq -c '.data // . | {env,version:(.version // null),entry,assetsBase,source}'
}

printf 'prod pointer: '; shell_pointer "$PROD_HOST"
printf 'dev pointer:  '; shell_pointer "$DEV_HOST"
printf 'prod manifest: '
curl --noproxy '*' -fsS -H "Host: $PROD_HOST" "$GATEWAY_ORIGIN/__manifest__" \
  | jq -c '.data // . | {site,defaultEnv,source}'
printf 'dev manifest:  '
curl --noproxy '*' -fsS -H "Host: $DEV_HOST" "$GATEWAY_ORIGIN/__manifest__" \
  | jq -c '.data // . | {site,defaultEnv,source}'

for file in "$PROD_HTML" "$DEV_HTML" "$PUBLIC_ROOT/shell/index.html"; do
  if [ -f "$file" ]; then printf 'exists: %s\n' "$file"; else printf 'missing: %s\n' "$file"; fi
done
```

按下表分类：

| 观测组合 | 判定 |
|---|---|
| 各 Host 的 `manifest.defaultEnv` 与 `__version__.env` 正确，`version=null`、`entry=null`，固定 `shell/index.html` 存在 | 无指针固定目录回落。两个 Host 返回相同固定目录 HTML 是设计行为，不是跨站串缓存 |
| 指针存在，但版本目录/`index.html` 缺失，最终读固定目录 | 版本目录缺失回落；与「无指针」分开记录，先查产物投递完整性 |
| 指针存在且本环境版本化 HTML 文件存在，但响应 HTML 带另一 Host 的 marker；交换请求顺序后串用方向随之变化 | 错误跨站复用。继续按场景一固定同 mtime 复现，并按场景二检查缓存键 |
| `defaultEnv` 或 `__version__.env` 已落到另一环境 | 先查站点 Host 匹配/defaultEnv/请求透传；这不是单靠 HTML 缓存键可以解释的现象 |

固定目录回落与错误跨站复用的关键区别是：**前者没有可用的版本化指针/目录，后者有可用且不同的实际版本化文件，却返回了另一站内容。**

**易误判点**：

- 两个 Host HTML 相同不一定是 bug；共同回落固定目录时本来就相同。
- 固定目录里的旧版本号或旧 marker 不等于缓存串站；先看指针是否存在、版本目录是否可用。
- 两个 Host HTML 不同也不证明缓存正确；不同 mtime 或禁用缓存都能制造表面正确。
- 只看 HTML 不看 `__version__`，会把「无指针」「目录缺失」「指针 TTL」「缓存串用」混为一类。
- 未匹配站点（IP/localhost）会走进程配置环境，不应用已注册站点的预期强行判定。

**适用范围**：NEW 域默认读取模式的 shell HTML 与 `/__version__?module=shell`。`DEPLOY_LEGACY_READ=1` 使用配置环境和旧表扁平路径，不走站点 `defaultEnv`，不能直接套用此表。

## 容量边界（不是已复现故障）

按实际文件路径作键能隔离不同版本内容，但不会主动删除旧路径条目；高基数频繁切版时，旧缓存可能存续到进程结束。当前案例未做高基数、长时间 RSS 压测，因此不能据此声明存在或排除内存容量问题。需要评估时，至少同时记录不同实际 HTML 路径数、切版频率与进程 RSS 曲线，再决定是否需要容量上限或 TTL。
