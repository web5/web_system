# Issue 工作流：issue 是任务载体，不是聊天入口

> **v1.0 · 2026-10-23 建立**
> 定位：让每个「有复现路径的坏行为 / 有设计决策的需求 / 有证据的整改」都有一条可回溯的记录，
> 并把 `需求 → 分支 → PR → 发布 → 验收` 串成一条线。
> 关联：[协作指令速查](../协作指令速查.md)（动代码前的门）· [质量门禁总纲](质量门禁总纲.md)（门禁全景）·
> [开发流程：三区分离](dev-workflow.md)（分支命名原有约定）

## 0 为什么建（先看现状事实，不看愿望）

| 事实 | 数据 | 后果 |
|---|---|---|
| issue 实际未使用 | 仓库至今 **390 个 PR、1 个 issue**（#356，已关闭） | 需求只活在会话里，换会话即失忆 |
| 「为什么改」只留在 commit message | 一次改动压缩成一行标题 | 回溯要翻 `git log` 才拼得出动机 |
| 门禁总纲的 S0 需求转换环节**产出为空** | [gates/01-日常使用.md](gates/01-日常使用.md) §1 的 S0 行「产出」= `—`、级别表全 `—` | 流程图上 S0 是个洞，方案九子项的第一项没有载体 |
| 规范 §8 追溯矩阵第一列「需求」无稳定锚点 | 总控《研发方案与发布规范 v2.2》§8 | 矩阵能填满，但「哪个需求」靠人记编号 |

**所以 issue 在这里不承担协作功能**（单人 + 多 AI 会话，没有第二个人要分派），
它承担两件别的东西：**任务的上下文载体**（断点续接）和**追溯键**（编号贯穿全链路）。

## 1 一句话判据

> **会不会需要第二次回来读它？会 → 开 issue；不会 → 直接 PR。**

| 情形 | 开吗 | 用哪个模板 | 理由 |
|---|---|---|---|
| 单文件笔误、文案、依赖小版本 | ❌ | — | PR body 写「无 issue：单点修改」即可，走 §4 |
| 能复现的坏行为 | ✅ | 缺陷 `bug` | 复现步骤 + 实证 + 回归用例必须留痕 |
| 新功能 / 新接口 / 新页面 | ✅ | 需求 `feature` | 影响面决定过哪道门，验收标准决定发布粒度 |
| 技术债、门禁增删、脚本与配置治理 | ✅ | 任务 `task` | 完成判据要能被别人复现 |
| 事故复盘里的整改项 | ✅ | 任务 `task` + 标签 `回归` | 对应复盘文档里的 TC 用例编号 |
| 探索性调研 | ❌ | — | 结论不成型前进 issue 只会变成半截草稿，落 `docs/` |

判断的边界：**「十分钟内说完 + 一次改完 + 不需要发布方案」三条全中，才可以不开。**

## 2 编号 = 追溯键（全链路长这样）

```
        ① 开 issue          →  #123  （标题带 fix:/feat:/chore: 前缀，模板已预填）
             │
        ② 分支名带编号       →  fix/123-admin-token-guard
             │
        ③ push 自动建 PR     →  body 首行自动写入 Closes #123（auto-pr.yml 从分支名解析）
             │
        ④ commit 说明         →  正文可写「见 #123」，非强制
             │
        ⑤ 发布清单            →  §5 每项标注 #123
             │
        ⑥ 验收回到 issue      →  一条 comment：可见结果 + 证据 → 然后关单
```

规则：**只认 `#` + 数字这一个形式**，不要发明 `ISSUE-123` / `[123]` 之类变体——
`Closes #123` 是 GitHub 能自动关单的唯一语法，变体写法的后果是 PR 合并了 issue 还开着，
然后没人记得它到底做完了没有。

## 3 三张模板的硬字段（以及为什么硬）

模板在 [`.github/ISSUE_TEMPLATE/`](../../.github/ISSUE_TEMPLATE/)。**必填字段不是形式主义，每条都对应一次踩过的坑。**

| 模板 | 硬字段 | 为什么必填 |
|---|---|---|
| 缺陷 `bug` | **实证**（日志/响应/运行版本） | 10-23 事故里，`pm2 logs` 路径中的 `.../1e946126/...` 一眼排除了「发布没生效」这个错误方向。没有实证时，同一症状会被当成发布问题多查两小时 |
| 缺陷 `bug` | **回归用例** | 它同时是 R17 `Test:` 的依据。写「已修复」没有信息量，写「断言 SQL 括号配平，负向改回错误写法必须红」才有 |
| 缺陷 `bug` | 已排除的假设 | 避免下一个会话重走同一条死路 |
| 需求 `feature` | **范围外** | 空着必然被追加需求，然后从半天变成一周 |
| 需求 `feature` | **验收标准（可判定）** | 「体验良好」不是判据，走查会退化成点两下看着像就行 |
| 需求 `feature` | 影响面 + 发布顺序 | 决定过哪几道门，以及会不会踩「功能发了但菜单看不见」 |
| 任务 `task` | **证据**（路径+行号/命令输出） | 没有证据的整改项就是个人偏好 |
| 任务 `task` | **完成判据** | 最好是「一条命令」或「故意让它红的负向验证」 |

> 🔴 **本仓库是 PUBLIC**：issue 正文、模板回复、截图里都**不得出现**凭证、内网 IP、服务器绝对路径、
> 真实用户数据、数据库连接串。要贴配置就贴字段名，不贴值。

空白 issue 已关闭（[`config.yml`](../../.github/ISSUE_TEMPLATE/config.yml)：`blank_issues_enabled: false`）。
理由很直接：一句话愿望没有实证和验收标准，后续谁接都得重新问一遍当初为什么——等于没登记。

## 4 分支命名与 PR 自动关联

沿用 [dev-workflow.md](dev-workflow.md) §2 的前缀规则（`auto-pr.yml` 只对 `feature/*`、`fix/*` 自动建 PR），
**只在 slug 前多插一个 issue 编号**：

```bash
git checkout -B fix/123-admin-token-guard master      # ✅ 缺陷
git checkout -B feature/128-content-source-filter master  # ✅ 需求
git checkout -B fix/admin-token-guard master          # ⚠️ 允许，但 PR body 要写「无 issue + 理由」
```

| 分支名形态 | auto-pr 行为 |
|---|---|
| `fix/123-xxx`、`feature/123-xxx` | 建 PR，body 首行自动写 `Closes #123`（并校验 issue 存在） |
| `fix/xxx`（无编号） | 建 PR，**不写 Closes**；PR 模板「关联 Issue」一栏需填「无 + 理由」 |
| `chore/*`、`docs/*`、`refactor/*` | 不自动建 PR，需手动 `gh pr create`（原规则不变） |

其余分支规则不变：小写 + 数字 + 连字符；`feature/test` 等长期集成分支仍被排除（避免巨型残影 PR）。

## 5 标签与优先级（最小集，别扩）

| 轴 | 标签 | 谁打 | 判据 |
|---|---|---|---|
| 类型 | `bug` / `enhancement` / `chore` / `documentation` | 模板自动 | 一张 issue 只属于一类，混了就拆 |
| 优先级 | `P0-阻断` / `P1-重要` / `P2-待排期` | 建时默认 P2，人工上调 | 见下表 |
| 来源 | `回归` | 从事故复盘派生的整改项 | 需要带 TC 用例编号 |

| 优先级 | 判据（可判定，不是感觉） |
|---|---|
| `P0-阻断` | 线上不可用 / 数据错 / 门禁失效（承诺的拦截点实际不存在）/ 安全 |
| `P1-重要` | 功能残缺但有绕路 / 同一坑第二次踩 / 门禁恒绿无信息量 |
| `P2-待排期` | 体验、性能、技术债、文档治理 |

一次性建标签（幂等，已存在不会报错）：

```bash
gh label create "P0-阻断"     --color B60205 --description "线上不可用/数据错/门禁失效，插队处理"
gh label create "P1-重要"     --color D93F0B --description "功能残缺但有绕路，或同一坑第二次踩"
gh label create "P2-待排期"   --color FBCA04 --description "体验/性能/技术债，按窗口排"
gh label create "chore"       --color C5DEF5 --description "重构/治理/门禁/脚本，不改用户可见行为"
gh label create "回归"         --color 5319E7 --description "事故复盘派生的整改项，需带 TC 用例"
```

> 🔴 **前置条件：token 必须给 `Issues: Read and write`**
> 实测（2026-10-23，issue #401）：fine-grained PAT 没这条权限时，`gh issue create --label` **照样返回成功 URL，但标签被静默丢弃**；
> 且**改正文 / 加标签 / 评论 / 手工关单全部 403** —— 三个环节（标签、验收 comment、关单）同时失效，却一条报错都没有。
> 判据只能是回查 `gh issue view <N> --json labels`，不能看命令是否成功。
> `scripts/issue/new.sh` 已内置回查，缺权限时**exit 4** 并列出被丢的标签。
> 修法：Settings → Developer settings → Fine-grained tokens → 该 token → Permissions → **Issues: Read and write**。

### 5.1 权限改完不等于立刻可用（自查顺序，2026-10-23 实测踩过）

改完权限后仍会连续 403 **约 10 分钟**才生效（平台侧传播/缓存，不是改错了）。
这段时间里最容易犯的错是「判定用户没改对」，然后让用户反复确认 —— 顺序错了。

| 步骤 | 动作 | 说明 |
|---|---|---|
| 1 | 等 10 分钟再测 | 别在第 1 分钟下结论 |
| 2 | 用**已有 issue** 探针：`gh api -X POST repos/{o}/{r}/issues/<N>/labels -f 'labels[]=bug'` | 200 = 通了；403 = 还没通 |
| 3 | 判断是「只有 issues 不通」还是「全部写不通」 | `gh api -X POST repos/{o}/{r}/git/refs -f ref=refs/heads/probe -f sha=000…0`：**422 = contents 写通**（仅参数错），403 = 全只读 |

> ⚠️ **不要用「建 issue」当权限探针**：`POST /issues` 传空标题会返回 **422**（参数校验先于权限校验），
> 看起来「能建」，实际下一步打标签就 403 —— 这个假信号 2026-10-23 骗过一次排查。
> 可靠的判据只有两种：给已有 issue 打标签、关单。

## 6 与发布、验收、关单的衔接

1. **方案落 `docs/`，issue 只放链接**。issue 正文写方案 = 方案改一版要同步两处 = 必然漂移。
2. **发布清单标注编号**：总控《研发方案与发布规范 v2.2》§5 的每个阶段项后面标 `#123`，
   这样「这条发布项在为谁服务」是查得到的。
3. **验收回 issue**：关单前必须有一条 comment，写**可见结果 + 证据**（截图 / 状态码 / 相对路径），
   而不是「已发布」。「已发布」和「能用」是两件事——10-22 那次三轮走查翻车就是两者的差值。
4. **自动关单只发生在 PR 写了 `Closes #N` 时**。没写就手工关，并补验收 comment。
5. **一个 issue 一次生命**：需求变更导致没做完的，继续留着并更新验收标准；
   已经做完但发现新问题的，**开新 issue 并互相引用**，不要复活旧的。

## 7 多 AI 会话：issue 就是断点续接的载体

| 时机 | 动作 |
|---|---|
| 开会话 | `gh issue list --label P0-阻断` 定优先级；`gh issue view 123` 拿上下文，不要让人重述需求 |
| 中途被打断 | 在 issue 追一条 comment：**做到哪 / 下一步 / 卡在哪**。下个会话从这条接，不重读整段对话 |
| 收尾 | 验收 comment + 关单 + 分支删除 |

反面：把 issue 当聊天记录，几十条碎 comment 里夹着结论——等于把「需要重读」的成本转移给了下一个人（很可能是两周后的自己）。

## 8 自测发现的问题怎么记（低摩擦入口）

> 这一节的唯一目标：**别让「记一下」这件事本身成为成本**。
> 自测时注意力在测、不在流程；任何需要离开当前操作 15 秒以上的记录方式，最后都不会被用
> ——仓库 390 个 PR 只有 1 个 issue，就是「回头再补录」从来没真正发生过的证明。
>
> 所以要纠正一个常见目标错位：**该第一时间留下的不是 issue，而是「带证据的一句话」**。
> 格式化和开单交给 AI 或脚本，你只负责说话。

### 8.1 两个入口，按手上几秒选

| 场景 | 入口 | 耗时 | 字段谁填 |
|---|---|---|---|
| 正在跟 AI 对话（最常见） | 直接说：**「记一下：<一句话症状>」** | 3 秒 | AI 调 `scripts/issue/new.sh` 代填 |
| 手机上 / 真机自测，没有 AI 在手边 | GitHub 网页或 App → New issue → 选「缺陷」 | ~30 秒 | 你填三项，其余可留空 |

### 8.2 什么值得单开，什么该攒批次

一轮自测通常发现 5–15 个问题。**逐条单开会把 P0 淹掉**，但也**不能全攒成一条**（关不掉，追溯矩阵填不实）。

| 类型 | 怎么记 | 理由 |
|---|---|---|
| 有复现路径、修完要防复发（报错、数据不对、逻辑错、状态不同步） | **单开一条 `bug`** | 需要「实证 + 回归用例」两栏，混在一起必然写不清 |
| 同类视觉微调（文案错字、间距、图标位置、颜色不统一） | **合成一条 `task`，正文用清单**，每条写「页面 + 期望 / 实际」 | 修法同源（同一批 UI 提交）、验收方式相同（截图对比），拆开是纯负担 |
| 你还不确定是不是 bug 的观感问题 | 先挂到批次那条的「待确认」小节 | 不当场判性质，避免为它单开又关不掉 |

批次那条的验收标准写成「清单逐条验完」，且**每条粒度必须可判定**：
「按钮间距不对」不合格，「列表行高 48px，设计稿 40px」合格。

### 8.3 AI 代开时的最小字段：只有三项是硬的

1. **一句话症状** —— 讲「在哪、点了什么、看到什么」
2. **环境** —— dev / prod / 本地
3. **实证** —— 至少一条：原始报错 / 接口响应 / 截图（截图里有 host、IP 的**先裁掉**）

其余（根因假设、已排除假设、回归用例、影响面）**允许留 `TODO` 空着**。
理由：你当时只说了 3 秒的话，编不出来的字段不要编 —— 空着比瞎填好，后面补。
但 **根因 + 回归用例这两栏必须在动手修之前补齐**，否则这条 issue 只算「线索」，不算「登记」。

```bash
# 最省事：只说症状，环境默认 dev
scripts/issue/new.sh bug "采集明细整页 500，列表数据其实是好的"

# 带实证（实证里有引号时用单引号包住）
scripts/issue/new.sh bug "来源筛选选完不生效" --env dev \
  --evidence "content/sources?enabled=true 返回 200 但列表没变"

# 自测批次（同类微调合并成一条）
scripts/issue/new.sh task "admin 自测视觉微调批次（10-23）" --p1 \
  --evidence "采集明细行高 48px，设计稿 40px" --evidence "来源筛选下拉未对齐"

# 先看要建什么，不建（dry-run，无副作用）
scripts/issue/new.sh bug "..." --dry-run

# 提醒：AI 建完把 issue 编号贴回来，分支名就能带编号（§4）
```

### 8.4 明确不做：本地「收件箱」/ 批量补录

不建 `自测速记.md` 之类的本地收集箱，也不做「先记下来，一周后批量转成 issue」。三条理由：

- 两份清单必然只维护一份，而被放弃的一定是后转的那份；
- 「批量转」没有截止点，第 6 条永远转不到；
- 手机端用模板填本来只要 30 秒，为省这 30 秒去造一套收集箱，代价更大。

### 8.5 🔴 自测截图 / 日志的红线（本仓库 PUBLIC）

自测时最自然的证据恰恰最危险：截图带着内网地址、admin 页面带着真实手机号、日志带着连接串。
**贴之前先裁、先脱敏**：要贴配置就贴字段名不贴值；要贴日志就贴报错行，不贴它上下的路径与凭据。

## 9 反模式（明确禁止）

| 反模式 | 后果 |
|---|---|
| issue 正文贴整篇方案 | 与 `docs/` 双真源，改一处漏一处 |
| 一个 issue 混多个无关主题 | 关不掉（一半做完一半没做），追溯矩阵填不实 |
| 改完不写验收就 close | 下次看到同样症状，无法判断是否同一个问题 |
| 把 `master-todo-*.md` 里的条目逐条搬成 issue | 两份清单，必然只维护一份。todo 文档管「窗口内排期」，issue 管「单件事的完整生命周期」，不要互相替代 |
| 用 issue 记「想法」 | 无实证无验收，等同于空 issue |
| 自测问题先记到本地清单，等有空批量转 | 收集箱一定烂尾；且批量转没有截止点（§8.4） |
| 自测截图/日志不脱敏直接贴 | 仓库 PUBLIC，贴出即泄露，删掉后仍留在 fork 与缓存里（§8.5） |
