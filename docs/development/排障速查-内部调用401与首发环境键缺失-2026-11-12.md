### 场景 1：服务间内部调用报 401 / 调用方把错误包成「XX 服务不可用」

判据（按序，1 分钟定位）：

```bash
# ① 先查调用方 .env 里键「存不存在」（缺失 → 代码 fallback 空串 → 恒 401）
grep -c '^INTERNAL_API_KEY=' /data/web_system/servers/<调用方>/.env    # 0 = 没配，就是根因
# ② 存在才比对值是否一致（只看哈希，不回显明文）
grep '^INTERNAL_API_KEY=' /data/web_system/servers/<a>/.env | sha256sum
grep '^INTERNAL_API_KEY=' /data/web_system/servers/<b>/.env | sha256sum
# ③ 时间戳对撞：被调方 err 日志 401（invalid internal key）与调用方 5xx 同秒出现 = 实锤
pm2 logs <被调方> --nostream --lines 200 | grep 'invalid internal key'
```

易误判：
- 🔴 **以为是「密钥不一致」去轮换密钥**——多数情况是调用方**根本没配这个键**（`configService.get('X') || ''` 静默 fallback 空串），先查存在性再查一致性。
- 以为 401 是鉴权 bug 去改 guard——guard 是对的，是配置缺失。

适用：web_system 全环境（dev/prod），所有带 InternalGuard 的 `/internal/*` 链路。

### 场景 2：gateway 503「认证状态暂不可用」——不一定是 Redis/认证服务挂

判据：

```bash
# 文案出自 auth-service auth.service.ts（Redis 黑名单查询失败）或
# gateway token-blacklist.guard.ts（fail-closed：token-status 非 200 一律抛 503）。
# 区分手法：看 auth-service 同秒有没有 401 invalid internal key
pm2 logs auth-service --nostream --err --lines 100 | grep -E '401|invalid internal key'
# 有 401 → 是「场景 1」的密钥问题；没有任何 auth 侧新日志 → 才查 Redis
redis-cli -u <url> ping
```

易误判：文案字面指向「认证/Redis 暂不可用」，实际可能是**配置错误（401）被 fail-closed 吞成 503**。
（待办：guard 应区分 401 配置错误与 5xx/超时，避免误导排障——尚未立项。）

适用：web_system dev/prod。

### 场景 3：新功能首发 prod， dev 全绿但 prod 连环报错

判据：**dev 绿 ≠ prod 配置齐**。凡依赖「环境变量键」的功能，首发前核对链路上**每个服务**的键存在性：

```bash
# 例：邮箱绑定链 = user-service(SMTP_*) + auth-service(INTERNAL_API_KEY) + gateway(INTERNAL_API_KEY)
for svc in user-service auth-service gateway mcp-gateway content-hub todo-service; do
  printf '%-14s INTERNAL_API_KEY=%s\n' "$svc" \
    "$(grep -c '^INTERNAL_API_KEY=' /data/web_system/servers/$svc/.env 2>/dev/null)"
done
grep -c '^SMTP_' /data/web_system/servers/user-service/.env    # 邮件类功能 ≥5
```

易误判：
- 🔴 只验「被改的服务」——配置缺失会沿调用链**逐环暴露**（本次：修一环才暴露下一环，用户在真机上连撞三次）。
- 以 ecosystem.config.js 里有同名键当「已配」——先确认那段 env 块**归属哪个 app**（prod ecosystem 里的 SMTP_* 属 mcp-gateway，不属 user-service）。

适用：web_system 首发/新键引入。

### 场景 4：往 `.env` 追加配置

判据：追加前必须确认末行有换行，否则新行与最后一行粘连、污染最后一个键：

```bash
tail -c 1 /data/web_system/servers/<svc>/.env | od -c   # 输出应含 \n；没有则先 echo >> 补空行
```

易误判：追加后服务起来但某个「不相干」功能坏了（本次疑似 Redis 故障，实为假想——但粘连模式真实存在，先查再说）。

适用：全环境所有手工改 .env 的场景。
