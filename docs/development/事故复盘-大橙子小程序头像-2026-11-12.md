## 一、事故概述

「我的」页头像/昵称不显示（台账 #8707）。表面单一症状，实际**三个独立缺陷叠加**，
历经多轮「修复」未愈，2026-11-11 晚至 11-12 晨全链路实证排障后彻底闭环。

## 二、三个真根因（全部已修复上线）

| # | 根因 | 修复 commit | 教训关键词 |
|---|---|---|---|
| R1 | upload-service 返回完整 URL，小程序原样 PUT 落库 → DB 写侧污染（违反 D1） | `stripPublicBaseUrl` 写侧净化（a69a94c2 / PR #623） | 读侧修复前先查写侧 |
| R2 | **onShow 第一句** `setTabBarSelected` 内 `getTabBar()` 脱离实例调用（严格模式 this=undefined）+ 无防御 → `__treeManager__` TypeError 穿透 onShow → `fetchProfile` 永不执行 | `getTabBar.call(page)` + try/catch（b95e7579 / PR #630） | 工具函数崩溃半径 = 整个 onShow |

## 三、为什么反复修不好（六条归因）

1. **复合缺陷当单 bug 修**：每层修复都「对症」但不完整，症状不变 ⇒ 观感「反复修」。
2. **修复后无端到端实证**：以「代码逻辑应该对」收尾，未做 DB→API→网络→渲染逐环取证。
3. **第一现场证据被跳过**：Console 的 `__treeManager__` 报错一直在，但没人把「tabBar 报错」
   与「头像不显示」建立因果（需同时看 Console + onShow 代码顺序）。
4. **测试盲区结构性存在**：单测 259/259 绿，但「onShow 内工具函数抛异常后页面数据加载
   是否存活」属组件时序交互，单测天然覆盖不到；getTabBar 脱离实例调用是微信运行时行为。
5. **环境噪音淹没信号**：4 个同名小程序实例 / appid 41002 中间态 / node_modules 断链 /
   头像本体是黑底圆环图（长得像「没加载」）——每个噪音都制造假线索。
6. **排障无显式留痕**：同一嫌疑（域名白名单）被反复提起放下；改「每层定罪/排除出表」后才收敛。

## 四、正确的排障过程（今后强制执行）

```
① 分层取证：DB 存什么 → API 返回什么 → 公网通不通 → 页面渲染什么（每层一条实证命令）
② Console/Network 是第一现场，先于代码审计
③ 修复必须带端到端验证证据才能标绿
④ 环境先对齐：哪个目录 / 哪个 appid / 连哪个环境（多 checkout 并行时先钉死）
```
