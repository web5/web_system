# auth-service 账号合并 bug 修复方案（#10 邮箱绑定「已注册→合并」失败）

> 类型：缺陷修复（后端）
> 关联需求：#10 大橙子个人助理小程序 · 账号合并
> 负责人：engineer-merge-fix
> 定位：rd-debugger（诊断）→ engineer-merge-fix（编码）
> 分支：`master`（待提交后回报 commitId）

---

## 1. 背景与目标

- **问题**：用户绑定邮箱/手机号命中「已注册」目标账号时，前端带 `confirmMerge=true` 二次请求，后端仍返回 `{ conflict: true }`，控制器抛 409，前端显示「合并失败」。**账号合并（邮箱 + 手机号共用一条链路）整体无法完成。**
- **验收目标**：确认合并（`confirmMerge=true`）命中冲突目标时，转入 `mergeInto(...)` 完成数据迁移 + 凭证重签，返回 `{ conflict: false, merged: true, accessToken, ... }`；phone / email 两条链路同时覆盖。
- **Non-goals**：
  - 不改合并迁移表清单 `MERGE_TABLES`；
  - 不改 `mergeInto` 的幂等/异常语义；
  - 不新增接口、不改前端、不改 DDL。

## 2. 根因

`servers/auth-service/src/account/account.service.ts` 的 `bindByValue`：

```ts
if (existing?.length) {
  ...
  if (allowPending) await this.savePending(...);
  return { conflict: true, canMerge: true, ... };   // ← 无条件 return conflict
}
const merged = allowPending ? false : true;         // ← 死逻辑
if (!merged) { /* 首次绑定直接落库 */ }
return this.mergeInto(...);                         // ← 只在「无冲突」时可达，业务上不可能
```

- `allowPending` 语义：`true` = 首次绑定（命中冲突→暂存 pending→返回 conflict）；`false` = 二次确认合并（应直接 `mergeInto`）。
- 冲突分支**无条件 `return conflict`**，导致 `false`（确认合并）路径永远到不了 `mergeInto`；`mergeInto` 成为死代码。

## 3. 方案设计

修改 `bindByValue` 冲突分支，按 `allowPending` 分流：

| 分支 | 行为 |
|---|---|
| 命中冲突 + `allowPending=true`（首次） | 暂存 pending → 返回 `{ conflict: true, canMerge: true, ... }` |
| 命中冲突 + `allowPending=false`（确认合并） | `return this.mergeInto(userId, source, value)` |
| 无冲突 | 直接 `UPDATE users SET {column} = ?` 落库（含「确认合并时目标已释放该值」的兜底） |

- 清理 `merged` 变量死逻辑；
- phone / email 共用 `bindByValue`/`mergeInto`，一处修复两条链路同时覆盖。
