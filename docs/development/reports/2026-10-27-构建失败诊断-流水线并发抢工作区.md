### 为什么准入锁没拦住

`submission-admission` 的互斥粒度是 **(module_key, env)**：同模块同环境的 pending/running 会 409。但 dev 与 prod 是不同 env → 两条都放行；而两者共享同一个构建工作区（workspace 按模块不按 env），直接相撞。

**进一步**：工作区其实按「后端模块共用一个 checkout」组织（`servers/<mod>/` 多模块同仓），不同模块的 git reset 也存在并发风险——只是这次撞的是同模块 dev/prod 的 dist。

### 与 prebuild 的关系

无关。prebuild 步骤执行正常（isStale 扫 8 包全跳过），失败在下一动作。本次不改 prebuild 任何东西。

## 3. 修复方案（待拍板）

| 方案 | 内容 | 覆盖面 | 改动量 | 评价 |
|---|---|---|---|---|
| **A. 准入锁抬粒度** | submission-admission 互斥从 (module_key, env) → **module_key**（或 workspace 路径）：同模块任一 env 发布互斥 | 同模块 dev/prod 互撞 ✅；跨模块 git/build 互撞 ❌ | 小（admission where 条件 + 测试） | 快，但不覆盖跨模块 |
| **B. 工作区文件锁（推荐）** | 各 run 在进入「git→prebuild→build→package」工作区临界区前抢 `RELEASE_DIR` 上的 flock（mkdir/lockfile 原子锁，同 prebuild 脚本 withBuildLock 风格），抢不到则排队或显式失败 | 同模块异 env ✅ + 跨模块 ✅（git reset 也护住） | 中（执行层 1 处 + 测试） | 治本 |
| **C. A+B** | 准入快速拒绝 + 文件锁兜底 | 全 | 中 | 最稳 |
| **D. 仅打磨** | package 动作 cpSync 后校验 `bundle/dist/main.js` 必须存在，否则报「构建产物被并发替换」清晰错误 | 不防撞，只把裸 ENOENT 变成可读错误 | 极小 | 可作为 B 的顺带项 |

**推荐：B + D**（文件锁治本 + 校验信息顺带加固）；若要发布体验更顺可加 A（提交时直接 409 而不是跑一半失败）。

**P0 止血（现在就能做，不动代码）**：等当前无并发运行时再发 dev；同一时刻只发一条后端流水线。
