# 技术方案 · prebuild 改「可选普通步骤」（待确认稿）

> 状态：**已拍板（2026-10-27）**：Q1=A / Q2=不留 / Q3=是 / Q4=去掉 / Q5=按建议。实施走 A 案（纯脚本节点，完全去内置），A 案落点差异见 §9。
> 背景：PR #459 已把 prebuild 硬编码进 PIPELINE_STAGES（9→10 阶段，所有流水线强制执行）。用户反对：「你内置了，但是有些流水线不一定需要的呀，还是改成普通步骤，然后在流水线的步骤里面加一个步骤」。本方案重新梳理挂接方式。
> 出品：研发部 rd-product（2026-10-27）。

---

## 1. 机制澄清：「流水线的步骤」在代码里到底是什么

| 机制 | 位置 | 语义 | 与「加步骤」的关系 |
|---|---|---|---|
| `PIPELINE_STAGES` | `deploy-pipeline.entity.ts` | **legacy 全量默认清单**（9 阶段固定序）。只在 `p.nodes=null 且 p.steps=null` 时兜底 | ❌ 不是「加步骤」的入口——它是硬编码全量，这正是用户反对点 |
| `resolveRunStages(p)` | `pipeline.service.ts:172` | 执行计划解析：`p.nodes` 非空 → 节点 keys（v5）；否则 `p.steps ?? PIPELINE_STAGES`（legacy） | 节点/步骤出现在执行计划里才会跑——**opt-in 的天然载体** |
| v5 `TemplateNode` | `template-node.ts` | 终态节点模型：`shell`（跑命令，可增删拖拽）+ `approval`。`platform`/`script` 仅读取兼容 | ✅ **「加一个步骤」的正确入口 = 模板 nodes 数组里加一个 shell 节点** |
| step-registry | `steps/step-registry.ts` | 内置步骤执行体注册表（category/commandMode/skip/run） | prebuild 的平台托管能力放这里；v5 路径走 `planNodeExec` |
| 节点命令 | `deploy_pipeline_step_commands` | v5 节点脚本真相源（R6） | 节点脚本在 PipelineEdit 右侧抽屉配置 |

**v5 节点执行分派**（`planNodeExec`，`node-exec-plan.ts`）：
- `key=git` → DB 脚本优先 + 内置 PullExecutor 回退（`how:'git'`）
- `key=check` → 内置安全基线恒跑 + 命令叠加（`how:'check-base'`）
- 其余 shell 节点 → 纯命令驱动（`how:'script'`）：配了脚本跑脚本，没配按 `optional` 跳过或 fail-fast

**结论**：「在流水线的步骤里面加一个步骤」= **在 PipelineEdit 流程编排画布「+ 添加节点」加一个 shell 节点**。prebuild 从 PIPELINE_STAGES 硬编码清单里拿掉，变成画布上按需添加的节点。这与 git（拉取代码）的模式一致——git 就是「普通 shell 节点 + 内置兜底」。

**当前 PR 的隐藏缺陷（顺带修）**：`legacyStepsToNodes` 的 `BUILTIN_SCRIPT_KEYS` 不含 prebuild——legacy 模板转存 nodes 时 prebuild 节点被静默丢弃。

## 2. 方案选项

### 方案 A：纯脚本 shell 节点（完全去内置）

prebuild 不再有平台执行体。用户「+ 添加节点」加任意 shell 节点，自己配脚本 `node scripts/prebuild-workspace-deps.mjs`。

| 维度 | 表现 |
|---|---|
| 「普通步骤」语义 | ✅ 最纯粹，与自定义节点完全同构 |
| 用户操作成本 | ❌ 要手写脚本路径，不知道有这个脚本就永远不会用 |
| 平台托管价值 | ❌ 丢失（isStale/目录锁/幂等封装在脚本里，但要用户自己发现并正确调用） |
| 与 git 模式一致性 | ❌ 不统一 |
| 工作量 | 后端小 / 前端零 |

### 方案 B：内置能力 shell 节点（key=prebuild，可脚本覆盖）

prebuild 保留 PrebuildExecutor 作为内置执行体，不再进 PIPELINE_STAGES。节点 key=`prebuild` 时：配了节点脚本 → 脚本覆盖；没配 → 跑内置。

| 维度 | 表现 |
|---|---|
| 「普通步骤」语义 | ✅ 画布可增删拖拽，不进默认全量 |
| 用户操作成本 | ⚠️ 要知道 key 得叫 `prebuild`（key 约定脆弱） |
| 平台托管价值 | ✅ 保留 |
| 与 git 模式一致性 | ✅ 完全同构 |
| 工作量 | 后端中 / 前端零~小 |

### 方案 C：内置能力节点 + 「加步骤」内置步骤目录（推荐 ★）

执行语义同 B。差异在 UI：「+ 添加节点」弹出**步骤目录**：

```
┌─────────────────────────┐
│  ＋ 添加步骤              │
│  ─────────────────────  │
│  ○ 空白节点（自定义脚本） │
│  ● 预构建（内置）         │  ← 点击插入 key=prebuild 节点
│     workspace 依赖预构建，  │     label=预构建，无需配脚本
│     陈旧即重建，防吃旧 dist │
└─────────────────────────┘
```

选「预构建」→ 画布插入 `{ kind:'shell', key:'prebuild', label:'预构建', optional:false }`，自动选中并打开抽屉（展示内置说明，可选配自定义脚本覆盖）。用户全程不需要知道 key 约定。

| 维度 | 表现 |
|---|---|
| 「普通步骤」语义 | ✅ 同 B |
| 用户操作成本 | ✅ 最低，点目录项即完成 |
| 平台托管价值 | ✅ 同 B |
| 工作量 | 后端中 / 前端小-中（约 1 个组件 + PipelineEdit 局部改动） |
| 扩展性 | ✅ 目录可收纳后续内置能力（探活/清理等） |

### 对比总表

| | A 纯脚本 | B 内置+key 约定 | C 内置+步骤目录 ★ |
|---|---|---|---|
| opt-in（不强制） | ✅ | ✅ | ✅ |
| 零配置可用 | ❌ 要写脚本 | ✅ | ✅ |
| 无 key 约定脆弱性 | ✅ | ❌ | ✅ |
| 与 git 模式一致 | ❌ | ✅ | ✅ |
| 后端改动 | 小 | 中 | 中 |
| 前端改动 | 无 | 无~小 | 小-中 |
| 覆盖 legacy 转存缺陷 | 不涉及 | ✅ | ✅ |

**推荐方案 C**：① 步骤目录是「在流水线的步骤里面加一个步骤」最直接的兑现；② 预构建有 isStale/锁/幂等设计，不该让用户手写命令行；③ 与 git 节点「shell + 内置回退」同构；④ 比 A 多的前端成本有限。压成本可退 **B**（执行层完全一致，仅少目录 UI）。A 不推荐。

## 4. 用户操作面

**v5 节点画布（主路径）**：
1. 流水线中心 → 编辑流水线 → 流程编排 tab
2. 「+ 添加节点」（方案 C 弹步骤目录）→ 选「预构建（内置）」
3. 拖拽到「拉取代码」之后、「构建」之前
4. 保存 → 该流水线发布时执行预构建；不加则不执行

**三层编排画布（orchestration 模式）**：添加步骤/动作，脚本填 `node scripts/prebuild-workspace-deps.mjs`（该模式本就全脚本化，无内置兜底）。

**建议默认（Q3）**：新建后端模块流水线默认节点序列自动含「预构建」（可删）；前端/小程序模板默认不含。

### afterSync 兜底（Q2，默认建议保留全局）

| 选项 | 行为 | ✅ | ❌ |
|---|---|---|---|
| **① 保留全局兜底（默认）** | 所有流水线 pull 后跑（isStale 幂等，开销≈0） | 防 #270 回归 | 不需要的流水线也在跑（成本可忽略） |
