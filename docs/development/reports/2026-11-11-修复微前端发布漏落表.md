## 1. 背景与目标

### 1.1 问题陈述

deploy-console 新版发布流水线（2026-11-02 起的 `release` / `gc-runtime` 阶段）对**微前端模块（admin / portal）**发布时，只写了「磁盘指针 + `deploy_versions`（版本记录）」，**没有落 `deploy_app_env_versions` 表（gateway 前端唯一读取源），也没有落 `deploy_deployments` 表（legacy 指针）**。结果 prod 出现「半发布」：盘上产物/指针切到新版本，但 gateway 实际读的表还停在旧版本 → 客户端加载错版前端、旧 API 路径 404 / 挂起。11-07、11-09 两单流水线均显示 `succeeded` 却漏落表。

### 1.2 目标用户与场景

- **直接受影响**：prod 环境访问 admin / portal 的最终用户（加载错版前端、接口 404/挂起）。
- **操作者**：通过 deploy-console 发布流水线发版 admin / portal 的研发/运维。

### 1.3 验收目标

1. 微前端（admin / portal）经 `release` / `gc-runtime` 流水线发布后，`deploy_app_env_versions` 与 `deploy_deployments` 两张表都落上 `current_version = 新版本`，且 prod 云库镜像同步完成。
2. 落表失败（本地写失败 / 云库镜像失败 / 应用未登记）时，流水线**必须 failed**，不再静默 `succeeded`。
3. 与 MCP `publish_version` 走同一套落表逻辑，行为一致。

### 1.4 Non-goals（明确不做）

- 不改 gateway 的读取源逻辑（gateway 读 `deploy_app_env_versions` 的现状不变）。
- 不改 DDL / 表结构（`deploy_app_env_versions`、`deploy_deployments`、`deploy_versions` 结构均不动）。
- 不新增对外接口、不改前端、不改权限模型。
- 不回溯历史两单已错版的 prod 数据（数据修复另行评估，见 §6.3）。

## 2. 方案设计（技术方案九子项）

### 2.1 架构与数据流

**现状（正确闭环，MCP `publish_version` 走的路）**：

```
startPublishVersion(DeployService)
  ├─ 写 legacy deploy_deployments（指针）
  ├─ mirrorLegacyPointer（prod → 云库，应急读取源）
  └─ syncAppEnvPointer → deploy_app_env_versions + mirrorPointer（prod → 云库，STRICT）
```

**现状（有问题路径，`release`/`gc-runtime` 阶段的 pointer 步骤 + 编排收尾）**：

```
PipelineSucceeded（非 backend）→ registry.setPointer
  ├─ 写 legacy deploy_deployments          ✅
  ├─ mirrorLegacyPointer（云库，写失败不阻断） ✅
  └─ syncAppEnvPointerInner（双写 deploy_app_env_versions）
       ├─ app 未登记 → 静默 return         ❌ 漏落表
       ├─ 本地写失败 → warn + return        ❌ 漏落表却 succeeded
       └─ 本地成功 + 云库失败 → throw        ✅（仅此一处严格）
```

**修复后（目标）**：`pointer` 步骤对前端应用改走 `switchVersion → setAppEnvPointer`（strict），`setPointer` 内嵌双写的本地失败改为 throw；与 `publish_version` / `internal/release/pointer` / UI 切换同一套落表逻辑。

数据流向不变：`deploy_app_env_versions` 仍是 gateway `byEnv` / 基座 shell 的唯一读取源，`deploy_deployments`（legacy）仅用于应急开关 `DEPLOY_LEGACY_READ=1` 与排障比对。

### 2.2 页面清单（含菜单）

**无 UI 改动。** 本次为后端服务（deploy-console）内部发布语义修复，不涉及任何页面/组件/菜单。

### 2.3 接口清单

**无新增对外接口。** 现有内部接口契约不变：

| 方法 | 路径 | 变化 |
|---|---|---|
| POST | `/api/internal/release/pointer` | 契约不变；其 env-dir 分支已正确走 `switchVersion → setAppEnvPointer`，作为修复的参考实现 |
| POST | `/api/internal/release/versions` | 不变 |

> 本次改动在**服务内部方法调用**（`PointerExecutor.run`、`ReleaseRegistryService.syncAppEnvPointerInner`），不暴露新端点。

### 2.4 数据结构

**无 DDL。** 涉及三张表现状（只读引用，不改结构）：

| 表 | 角色 | 本次 |
|---|---|---|
| `deploy_app_env_versions` | 前端 env-dir/site-version 指针，gateway **唯一读取源** | 修复落表 + 失败抛出 |
| `deploy_deployments` | legacy 指针（应急开关 + 排障比对） | 继续双写 |
| `deploy_versions` | 版本发布记录 | 不变（`version` 步骤已写） |

关键列（`deploy_app_env_versions`）：`appKey` + `envId`（唯一）、`currentVersion`、`previousVersion`（回滚目标）、`status`、`deployedAt`、`deployedBy`、`taskId`。无需 DDL 发布。

**无新增配置。** 沿用现有：

| 配置项 | 改动 | 说明 |
|---|---|---|
| `CDN_LAYOUT_MODE` | 沿用 | CDN 去指针化模式，`switchVersion` 内部已按此判断是否写磁盘指针 |
| `RELEASE_WORKSPACE` / `DEPLOY_LEGACY_READ` | 沿用 | legacy 应急开关语义不变 |
| 云库连接（`EnvSplitWriterService`） | 沿用 | prod 指针镜像到云库 |

### 2.6 依赖系统或接口

| 依赖对象 | 类型 | 强/弱 | 缺失后果 | 发布关联 |
|---|---|---|---|---|
| `EnvSplitWriterService.mirrorPointer`（prod → 云库） | 内部 | **强** | prod gateway 读不到新指针（半发布） | 阶段 4 验证 |
| `EnvSplitWriterService.mirrorLegacyPointer` | 内部 | 弱 | 应急开关/排障缺比对数据 | 阶段 4 验证 |
| `ReleaseLockService`（发布锁） | 内部 | 强 | 并发发布交叉覆盖 | 无新增 |

**无。** 本次不新增运行时业务数据，不改 `deploy_apps` 种子。admin / portal 在 `deploy_apps` 中的登记（`deploy_mode='env-dir'`）为既有数据，仅作为落表判据使用。

### 2.8 权限模型

**无变更。** 内部接口鉴权仍走 `InternalGuardService`（`x-internal-key` + 限流 + 来源白名单 + 审计），服务内部方法调用不涉及用户权限。

### 2.9 接口设计约束（本次核心）

#### ① 落表顺序（必须保持，不得交换）

对前端 env-dir / site-version 应用，落表顺序固定为：

1. **先落 `deploy_app_env_versions`（gateway 唯一读取源）**——`setAppEnvPointer` 内部含 CAS + previousVersion 维护 + 云库镜像（STRICT）。
2. **再写磁盘入口指针**（`env-dir` 且非 CDN 布局时）——写失败则回滚第 1 步（`revertAppEnvPointer`）。
3. **legacy `deploy_deployments` 双写**——维持应急开关与排障可比对（见 §2.9③）。

> 顺序铁律与 §5 发布清单「后端 → 数据 → 前端指针」一致；先写 gateway 真相源，避免「DB 说新版、盘还指旧版」的撕裂态。

#### ② 失败语义（本次修复的核心，对应 2 个红灯用例）

- `deploy_app_env_versions` **本地写失败 → 必须 throw**（不再 `warn + return`）。
- prod **云库镜像失败 → 必须 throw**（已有语义，保持不变）。
- 应用未登记于 `deploy_apps`（前端类）→ `setAppEnvPointer` 抛 `NotFoundException`（不再静默空转）。

> 语义对齐 2026-09-30 基座事故口径：**宁可发布红掉，也不静默不一致**。

#### ③ legacy 指针是否继续双写（待确认，见 §9）

`setAppEnvPointer` 只写 `deploy_app_env_versions`；`setPointer` 写两处。修复需明确前端 env-dir 是否继续写 legacy `deploy_deployments`。当前 gateway 已停用 legacy 读取源，写它只为应急开关 + 排障。

#### ④ 幂等

目标版本 == 当前版本时，`setAppEnvPointer` 不写库也不镜像（`unchanged=true`），避免两库 `deployed_at/deployed_by` 漂移；`switchVersion` 对此返回 `unchanged`，pointer 步骤按此短路。

## 3. 方案对比

### 3.1 方案 A（推荐）：pointer 步骤改走 strict 单入口 + setPointer 双写失败抛出

- **改动 1**：`PointerExecutor.run`（`pipeline/steps/pointer.executor.ts`）非灰度分支，对前端应用（`deploy_apps.deploy_mode ∈ {env-dir, site-version}`）改走 `AppsService.switchVersion`（内部 `setAppEnvPointer` strict + 磁盘指针 + gateway 缓存通知），与 `internal/release/pointer` / `publish_version` / UI 切换**同一入口**；后端/未登记仍走 `registry.setPointer`（legacy）。
- **改动 2**：`ReleaseRegistryService.syncAppEnvPointerInner`（`registry/release-registry.service.ts`）本地 `deploy_app_env_versions` 写失败由「warn + return」改为「throw」，覆盖 `setPointer` 双写这条路径的静默失败（对应 2 个红灯用例）。

✅ 与 `publish_version` 完全同套落表逻辑，语义收敛到 `setAppEnvPointer` 单入口
✅ 覆盖所有 `setPointer` 调用方（pointer 步骤 + 编排收尾 + deployVersion/rollback/switchPointer/promote）
✅ 落表失败一律 failed，彻底消灭「静默半发布」
❌ 改动面稍大（2 个文件），需确认 `PointerExecutor` 注入 `AppsService` 无循环依赖
❌ 需明确 legacy 指针是否继续双写

### 3.2 方案 B（最小）：只改 setPointer 双写失败语义

- 仅改 `syncAppEnvPointerInner` 本地写失败为 throw；`PointerExecutor` 仍走 `registry.setPointer`。

✅ 改动面最小（1 个文件），风险最低
✅ 同样能通过 2 个红灯用例，消灭静默半发布
✅ legacy 双写天然保留（`setPointer` 本来就写两处）
❌ 仍保留「setPointer 附赠同步」这条独立路径，与 `switchVersion` 仍是两套逻辑（未来仍有漂移风险）
❌ 不满足「与 publish_version 同一套落表逻辑」的结构对齐目标

### 3.3 方案 C（仅 DB 模板层，不推荐单用）

- 在 DB 模板把 release/gc-runtime 阶段的 pointer 动作改为引用 `switch-pointer` service action（已有能力），不改代码。

✅ 数据层即可改行为
❌ 无法解决 `setPointer` 内嵌双写「本地失败静默」的根因（红灯用例仍失败）
❌ 依赖 DB 模板现状（需先取证确认模板实际内容），无法作为唯一手段

**结论**：推荐 **方案 A**；若评估后认为结构对齐非必需，可退 **方案 B**。二者都以「改动 2（失败抛出）」为必做项。

## 4. 详细设计

### 4.1 改动文件与方法

| 文件 | 方法 | 改动 |
|---|---|---|
| `servers/deploy-console/src/registry/release-registry.service.ts` | `syncAppEnvPointerInner`（:227） | 本地写失败 `warn + return` → `throw` |
| `servers/deploy-console/src/pipeline/steps/pointer.executor.ts` | `PointerExecutor.run`（:50） | 前端应用改走 `switchVersion`（strict） |

### 4.2 落表顺序与云库镜像时机（方案 A）

```
PointerExecutor.run（非灰度）
  ├─ assertCdnReady（CDN 硬门禁，先于切指针）
  └─ 查 deploy_apps.deploy_mode
       ├─ env-dir / site-version（前端）
       │    AppsService.switchVersion(moduleKey, env, versionTag, operator, lockOwner)
       │      ├─ 产物存在性校验（index.js / index.html）
       │      ├─ 1) setAppEnvPointer（deploy_app_env_versions + 云库镜像 STRICT）
       │      │      ├─ 本地写失败 → throw
       │      │      ├─ app 未登记 → throw NotFound
       │      │      └─ prod 云库失败 → throw
       │      ├─ 2) 写磁盘入口指针（env-dir 且非 CDN）；失败回滚第 1 步
       │      └─ 3) gateway 缓存失效通知（best-effort）
       └─ 其余（后端/未登记）
            registry.setPointer（legacy deploy_deployments + 双写 + 云库镜像）
```

云库镜像时机：**在本地 `deploy_app_env_versions` 写成功之后**、磁盘指针之前（`setAppEnvPointer` 内部），失败即抛。

### 4.3 与 2 个红灯用例的对应

rd-engineer 已在 `release-registry.service.spec.ts` 新增 2 个失败用例，均针对 `setPointer` 双写失败语义：

1. `setPointer 双写：新表（deploy_app_env_versions）写失败 → 抛出，不静默「半发布」`（:189）
2. `分流：本地 deploy_app_env_versions 写失败 → 抛出且不镜像（不留「半发布」）`（:211）

两者都要求 `appVersionRepo.save` reject 时 `setPointer` **rejects** 且不调用 `mirrorPointer`。当前 `syncAppEnvPointerInner` 的 `catch → warn + return` 使它们失败 → 改动 2 让其转绿。

### 5.2 兼容性

- **后端服务发布**：零影响。`pointer` 步骤对 `moduleType='backend'` 本就 `skip`；`setPointer` 对后端（`appRepo.findOne` 返回 null）仍走「只写 legacy、不写新表、不镜像」原路径，不触发新 throw。

**不灰度。** 本次是缺陷修复，落表失败即 failed 是期望行为（对齐「宁可红掉不静默」口径），无需灰度开关。

## 10. 风险与排期

| 风险 | 等级 | 缓解 |
|---|---|---|
| `setPointer` 失败语义收紧影响其他调用方（deployVersion/rollback/promote） | 中 | 只影响前端落表失败场景；后端路径不触发新 throw；单测 + 回归覆盖 |
| `PointerExecutor` 注入 `AppsService` 引入循环依赖 | 低 | 单向依赖（AppsService 不依赖 PointerExecutor）；若遇 DI 循环则改方案 B |
| prod 云库镜像更严格导致发布偶发失败 | 低 | 已是既有 STRICT 语义；失败可见可重试 |

**排期**：单文件核心改动（改动 2）+ 结构对齐（改动 1），预计 0.5 人日编码 + 0.5 人日测试回归；不含历史数据修复。
