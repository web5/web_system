# 台账 #9027 · 版本指针写入端归一（纯 commit）

> 类型：bug 修复（无 UI 变化）
> 影响面：`deploy_app_env_versions.current_version` / `previous_version` 两列的**新写入值**
> 关联回执：`~/AiWorkspace/30-任务产物/2026-11-26-台账9027-版本前缀/01-诊断与修复回执.md`

## 问题

`portal` 应用 `prod` 环境的版本指针为 `portal/b6ec9950`（带模板前缀），而列契约是纯短哈希。
gateway 读取时靠 `toCommitId()` 取末段兜底，才没有 404 —— 属于「靠读取端容错活着」。

## 根因链路

| # | 位置 | 行为 |
|---|---|---|
| 1 | `pipeline/git-identity.ts:10` `buildVersionRef()` | 生成版本身份 `<templateKey>/<commit>` |
| 2 | `pipeline/pipeline.service.ts:2546` | 回填 `versionTag = portal/b6ec9950` |
| 3 | `pipeline/steps/check.executor.ts:51` | 复用产物时再次写完整引用 |
| 4 | `pipeline/steps/pointer.executor.ts:61` | 把 `versionTag` 当版本值传给 `switchVersion` |
| 5 | `apps/apps.service.ts:573` | 透传 `currentVersion` 给 `setAppEnvPointer` |
| 6 | `registry/release-registry.service.ts:313` / `cloud-db/env-split-writer.service.ts:74` | 原样落库（本地 + prod 云库） |

结论：前缀来自 `templateKey`（经 `versionTag` 透传），**写入端没有任何一处按列契约收敛**。

## 改动方案

写入端归一，不动读端：

- 复用/补齐 `pipeline/release-paths.ts` 的 `normalizeCommitRef()`：整串按 `/` 切开取**最后一段**
  （覆盖 `portal/b6ec9950`、`portal/prod/b6ec9950`、前后空格、空值）。
- `ReleaseRegistryService` 两个写入 `deploy_app_env_versions` 的入口
  （`setAppEnvPointerInner`、`syncAppEnvPointerInner`）在比较/写库前归一 `currentVersion`，
  `previous_version` 同口径归一；镜像给云库的入参也归一。
- `EnvSplitWriterService.mirrorPointer()` 作为云库镜像的最后一道，再归一次（含云库历史脏值的
  `previous_version` 取值），保证任何调用方都写不出带前缀的值。
- **不改** `toCommitId()`：它是产物目录引用（`version` 允许含 `/`）的宽松解析口径，
  与列的格式契约是两件事（见该函数 JSDoc 的对比说明）。

## 改动面与风险

- 只影响 `deploy_app_env_versions` 两列的新写入值；`deploy_deployments`（legacy）
  与 `deploy_versions`（发布记录）不做改动。
- legacy 后端服务（content-hub 等）不写 `deploy_app_env_versions`，不受影响。
- 存量脏值不靠本次代码自愈，单独给出数据修正 SQL（回执 ⑥），由发布运维执行。

## 验证方式

- 单测：`normalizeCommitRef` 7 类边界；写入点断言落库值为纯 commit；云库镜像参数为纯 commit。
- 数据修正后期望：manifest `byEnv.prod.portal.version === 'b6ec9950'`；
  `curl -I https://<prod>/portal/` = 200；磁盘 shim / CDN 指向同一 commit 目录。

## 第五轮补充（2026-11-26）：回滚目标的**返回契约**改为原样返回（方案 A″）

第一轮把「返回值必须是纯 commit」也一起改了（`resolveRollbackTarget` 三个分支都归一后返回），
这是错的 —— 与「归一发生在写列处」的原则冲突，且打断了两类消费者：

| 消费者 | 需要的形态 | 归一后为什么坏 |
|---|---|---|
| app / env-dir（`env-artifact.service.ts` 的 `hasVersion` / `writePointer`） | 原始引用即可 | 本就是「原始值优先、归一值兜底」，归一反而丢掉 `portal/<commit>` 的命中 |
| 后端（`deploy.service.ts` 的 `applyBackendVersion`） | **必须**原始引用 | `path.join(ws,'servers',dir,versionTag)`，`runtime-checkpoint/<id>` 是磁盘上真实一级目录，剥前缀指向不存在路径 |

**现约定**：`resolveRollbackTarget` 只回答「回滚到哪个版本**引用**」，三个分支（`explicit` /
`previous_version` / 历史表 `versionTag`）都原样返回来源值；纯 commit 契约由
`setAppEnvPointerInner` / `syncAppEnvPointerInner` / `mirrorPointer` 三处在写列时保证。
归一**比对**仍留在函数内（只用于判断「是不是同一个版本」），否则历史脏值
`portal/b6ec9950` 与当前值 `b6ec9950` 会被判为不同版本 → 把当前版本选成回滚目标 →
下游 `from === currentVersion` → `unchanged: true` 静默 no-op（P1 回归）。

配套两处守卫：

- `explicit` 分支**保留** `requireCommitRef` 校验（归一失败 → 400），但返回值不取归一结果
  —— 该分支没有回落路径，非法值直穿 `path.join` 就是路径穿越；
  另加「归一后等于 current → 400」，堵住「回滚到当前版本」被静默吃掉。
- `previous_version` 分支加 `prevRef !== fromCommit`：`previous == current` 是「同一 commit
  连续发布两次」的**合法状态**（prod shell 的 `a82270f9` 于 10-10 14:23 / 14:33 各发一次），
  视同无 previous 回落历史表，而不是抛错（抛错会把可自救变不可自救）。

回归证据：本改动同时修掉 master 上 `src/deploy/rollback-pointer.spec.ts` 的红灯 ——
该用例断言后端回滚时 `setPointer` / `mirrorLegacyPointer` 收到的
`currentVersion` 是 `runtime-checkpoint/todo-prod-1792396360725`，round-1 归一后变成
`todo-prod-1792396360725`，CI「改动包 build/test」因此一直 fail。
