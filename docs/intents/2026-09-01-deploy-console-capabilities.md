## 一、背景与动机（解决什么）

Deploy-Console 当前是发布控制台的「单一入口」，但能力仍偏薄：

1. **监控盲区**：现有监控全部走 SSH 远端执行（`monitor.service.ts` 的 `execSsh`），对 deploy-console 自身运行主机（本机）实际运行的 pm2 进程、端口存活、日志毫无感知。运维排障时「控制台看到的」与「本机真实跑的」是两套。
2. **模块管理形态落后**：模块注册表（backend / frontend / micro-frontend / mini-app 四类）仍以「单表格 + 类型下拉筛选」呈现，类型越多越难用。
3. **发布可靠性缺口**（playbook 现状盘点 + 生产踩坑）：回滚只切版本表指针不重建后端、发布后无健康探针、verify 失败不回滚、DB Migration 未纳入发布、密钥/环境变量无法页面配置、缺审批/通知/审计/可观测等。

## 二、面向谁

- 平台运维人员（日常发布、监控、排障、配置）
- 研发负责人（审批、审计、发布度量）

## 三、范围

- **本期明确需求（用户指定）**：① 本地服务监控（新增，本机 pm2/探活/日志）；② 模块管理 tab 化（改为按类型分 tab + 计数）。
- **全量规划**：在生产必补（P0）+ 一致性（P1）+ 可观测（P2）三个层级补齐共 19 项能力（含上述①②），**分批实现**（批 1 已启动编码，批 2/批 3 待做）。
- **实现方式**：在现有「九阶段发布流水线 + Hook + MCP + Agent」架构上**增量扩展**，不推倒重来；监控/审批/通知等以独立模块接入，发布核心流程保持稳定。

## 四、成功标准

1. 控制台可监控本机真实 pm2 进程（CPU/内存/端口/重启次数）与健康探活，与远程 dev/prod 并列切换。
2. 模块管理按类型 tab 分组并实时计数，保留新建/详情/编辑/删除。
3. 发布具备「探针 + 失败回滚 + 迁移 + 并发锁 + 配置中心 + 审批门禁 + 通知 + 审计」可靠性闭环。
4. 所有新增/修改均通过子代理独立技术评审，铁律级问题（安全/CORS/异常过滤器/类型）清零。

## 五、不在范围（哪些不做）

- 不重写发布核心流水线（保持九阶段模型）。
- 不引入新的消息队列/调度框架（复用现有 pipeline + Hook）。
- 密钥库本期用「服务侧主密钥 AES 加密存 DB」方案，不对接 Vault（列为后续增强）。
- 线上监控自动回灌（playbook 缺口⑥）暂缓。
