## 1. 三条主线与边界

| 主线 | 已核实的开发状态 | 尚缺的交付闭环 |
|---|---|---|
| Console 重构 | 核心改造已有多批实现与分项验证，含自举、凭据、投递边界、事实巡检、发布前提案与发布后验证 | 统一范围基线、dev 整体回归、失败与回滚演练、生产适用性核查及验收报告 |
| Content-hub 内容质量工程 | M1 数据底座及一批后端能力已随 PR #353 合并；Admin 五屏有原型 | M1 部署与真实采集验收、M2 接口与页面闭环、M3 校准、M4 统计 |
| AI Agent 整体架构改造 | 方案与 B0–B5 路线图已出；未发现整体改造启动证据 | 从 B0/B1 开始实施，再按依赖推进 B2–B5 |

Console 的本轮重构收尾不等于完整 Agent-Native DevOps 目标完成。Runner 拉模式、prod 入站 SSH 部署下线、自动验证回滚等单列为后续建设，不塞入本轮验收。

Content-hub 的内容质量字段不等于 Agent 的运行归因；内容中枢不自动等于研发助手知识库，两条数据链分别验收。

## 2. 执行顺序与规模

按单执行人、串行推进估算。人日是初步工作量，不是承诺日期；环境访问、用户评审及采样观察时间另计。

| 批次 | 任务 | 粗估 | 启动条件 | 出口 |
|---|---|---|---|---|
| S0 | Console 范围与运行基线盘点 | 0.5–1 人日 | 收到执行指令 | C0 范围清单和验收矩阵 |
| S1 | Console 整体验收及阻塞缺陷修复 | 2–4 人日 | C0 完成、dev 可用 | C1–C3 证据齐全；生产未验部分显式列出 |
| S2 | Content-hub M1 实际交付闭环 | 1–2 人日 | Console 对应部署通道已验证，或已确认独立发布路径 | H1 真实采集闭环 |
| S3 | Agent B0 + B1 | 3–4 人日 | S2 收口后启动；技术上不依赖 H1 | A0/A1 运行归因与链路回归通过 |
| S4 | Content-hub M2 | 3–5 人日 | H1 通过；原型、权限和接口缺口确认 | H2 五屏真实业务闭环 |
| S5 | Content-hub M3/M4 + Agent B2/B3/B4 | 二次估算 | 分别满足 H2、A0 及各专项前置 | 校准统计、模型成本、调参与检索各自验收 |
| S6 | Agent B5 多 Agent 首例 | 原路线图约 3 人日，启动前复估 | A0 + B4 内容补齐及召回抽查通过 | 研发助手多集合检索汇总闭环 |

S0–S4 初估约 9.5–16 人日。若 Console 暴露结构性问题，先重估，不用无限追加功能冒充“验收修复”。本计划不默认启用多会话或并行代理。

## 3. Console：先完成本轮重构验收

### C0. 固定范围与基线

- 对照现有方案、最近提交和旧任务表，逐项标明已实现、已部署、已验收、未做、后续目标。
- 记录待验 commit、Console 版本、dev/prod 环境、模块/主机配置、迁移状态及回退点；采集结果脱敏。
- 产出验收矩阵，至少覆盖微前端、shell 和后端三种产物；不适用项写明原因，不能计为通过。

### C1. dev 正向全链路

- 验证自举与配置加载、权限、流水线配置读取、构建、投递、版本记录、指针切换、重启及探活的实际顺序。
- 每类产物验证发布前提案、现有发布入口和发布后验证；记录当前能力之间是否真正串联，不假设已实现强制 planId 提交流程。
- 除流水线状态外，独立核对目标机产物、指针、进程、端口及真实 HTTP；前端补关键资源与浏览器主路径检查。
- `verify_release` 现有能力不包含真实 HTTP 探测，因此在本轮用独立检查补证，不将“扩展验证工具”设为默认前置。

### C2. dev 失败与回滚

- 用隔离模块或可恢复测试目标验证：构建失败、缺产物、配置缺失、投递失败、无权限、同模块同环境并发、重复请求。
- 核对失败不误切指针、不误报成功；未实现的幂等或锁行为如实记缺口，根据风险决定修复或阻塞，不预设通过。
- 做一次真实版本回退，验证产物、指针及服务响应一致，并在结束后恢复测试环境。
- 不对生产注入故障，不把 prod 数据和服务作为破坏性演练目标。

### C3. 生产适用性与验收结论

- 先只读核对 prod 与 dev 的差异、权限、目标机、配置、静态根、版本和回退点。
- 生产发布与回退验证单独确认窗口后执行；未获确认时标记“dev 已验收 / prod 待验证”，不能宣称全环境完成。
- 交付统一报告：每个用例含版本、环境、步骤、预期、实际、脱敏证据、缺陷及复测结果。
- 退出标准：约定范围内阻塞缺陷为零；其它缺陷有明确处置；未验项不混入通过率。

## 4. Content-hub：从 M1 到可用产品

### H0. 对齐方案与事实

- 开始前取得并核对资料库的 05/06/07 版方案，按 M1–M4 映射任务，不凭摘要补造需求。
- 复查 M1 迁移、服务代码、种子及部署状态；现有“数据库已迁移、服务尚未部署”的记录只作为待验证基线。

### H1. M1 真实采集闭环

- 按既有发布路径部署已合并版本；迁移先检查状态，不盲目重跑，并验证直连与导出路径的重复执行行为。
- 分别验证龙虎榜、快讯、论文摘要链路，串起来源、批次日志、入库条目、质量状态与阶段、错误原因。
- 覆盖正常、重复、空结果、上游失败和摘要 fallback；人工核对席位打标、摘要与原文、prompt_version 及重复入库行为。
- 外部源无数据时区分“本次确实为空”和“采集失败”；受控样本只作补充，不能替代真实采集证据。
- 退出标准：每条链路有可追溯结果和失败语义；未跑通的源明确列阻塞，不以表存在或接口 200 代替验收。

### H2. M2 接口与 Admin 五屏

- 逐字段对拍原型与实际接口，补齐已约定的接口缺口，特别是席位新增/停用、分页筛选及采集触发。
- 核实 content:view/content:manage 的登记及服务端权限执行；不能只靠前端菜单控制授权。
- 完成采集总览、内容条目、条目详情、龙虎榜、席位库五屏，并覆盖加载、空、错、无权限和提交中状态。
- 沿用既有原型评审与契约门，原型确认后再改业务页面；真实接口联调后做浏览器验收。
- 退出标准：只读用户无法触发写操作；管理操作有真实结果及错误反馈；五屏不依赖原型假数据。

### H3/H4. 校准与统计

- H1 跑通即开始积累可追溯样本；阈值、采样量和观察窗口以正式方案为准，未定义的启动前确认。
- 区分采集、去重、LLM、fallback 等阶段，分别统计覆盖、失败、重复与质量；缺数据不能按零失败处理。
- 固定来源、原文、prompt 版本和模型等可比条件，按方案完成质量抽查/校准，再生成统计结论。
- 不在缺样本时宣布质量提升，不先扩展更多采集源掩盖已有链路问题。

## 5. AI Agent：按既有路线图启动，不重新发明方案

| 编号 | 任务范围 | 验收重点 |
|---|---|---|
| A0 / B0 | outcome/fail_stage 及定义、落库、回填策略 | 成功、模型失败、工具失败、超时/取消等结果按既定语义记录；历史未知结果不伪造；runId 能串起定位证据 |
| A1 / B1 | 心跳、C 端高危工具服务端过滤、runId、Admin intent、拒绝后结束 | PC/小程序流式回归；长任务不断联；拒绝不挂起；requiresConfirm 工具不会装配到 C 端 |
| A2 / B2 | thinking 计价与模型链路统一 | 成本口径可追溯，缺计价数据显式标记；模型选择、配置与既有业务回归通过 |
| A3 / B3 | temperature/maxTokens/topP/thinking/max_steps 最小调参集 | 先核实 C7 等前置是否合入；仅超管可改，服务端鉴权与审计生效，合法的 0 不被默认值吞掉 |
| A4 / B4 | 内部研发知识库内容补齐与召回抽查 | 各集合有实际可用内容；真实问题可追到来源；无证据时不编造结论；不扩建重型评测平台 |
| A5 / B5 | Agent-as-Tool 与研发助手多集合汇总 | 复用方案四道护栏及预算、深度等约束，验证失败传递、权限和成本归因；与单 Agent 基线比较价值 |

B0 验收后再启动 B2/B3/B4；B1 无技术前置，但本计划按单执行人安排与 B0 同批、串行实施。B5 必须等 B0 和 B4 通过，不能因为编排代码写完就提前验收。

## 6. 执行与记账规则

- 每批启动先核实现有代码与远端合并状态，避免重复实现；代码工作按仓库既有 worktree/评审规则执行。
- 每项任务记录四种状态：方案、代码、部署、验收；状态必须附版本、环境、日期和证据路径。
- 测试从改动范围开始，再做服务回归与端到端验证；不相关缺陷单列，不顺带扩改。
- 每批独立交付与独立回退；涉及生产写入、迁移风险或范围变化时先确认，不用本计划代替操作授权。
- 本计划作为三主线入口，专项方案继续维护技术细节；旧总表后续指向这里，不整体重写历史记录。
