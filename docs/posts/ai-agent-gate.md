# 让 AI 无法跳过流程：用 Hook + git 凭证给编程助手装上「动作门」

## 一、引子：一个修不好的「记性问题」

我们的项目里有一条 SOP：改 UI 前先改原型稿，用户确认后才落码。写进了常驻文档，写进了项目规则，写进了技能描述。

然后它还是被跳过了。典型场景是我随口说一句「输入框换行间距高了」——AI 二话不说打开 `index.wxss` 就改。

第一反应是「它没记住」，于是补提示词、加触发词、在规则里再写一遍。没用。**第二版甚至专门给技能的 `description` 加了「间距 / 太丑 / 隐藏 / 挪 / 颜色 / 字号」这些词**，仍然会漏——因为用户的措辞空间是无限的，而你能枚举的触发词是有限的。

真正的转折点是停止问「怎么让它记住」，改问「它为什么能做到」。盘点后是四个结构性断点：

| # | 断点 | 证据 |
|---|---|---|
| 1 | 常驻层只做**索引**，不做动作门 | 常驻文档写的是「需要的技能从这里找」——被动取用语义；含动作门的那份文档根本不在常驻加载列表里 |
| 2 | **规则真空** | 已有 UI 规则首行就声明「品牌端不适用」→ 小程序改动无任何项目级规则兜底 |
| 3 | **触发词失配**（最隐蔽） | 技能触发词是「原型稿生成 / 交互怎么设计」，用户真实措辞是「间距高了」「tabBar 隐藏」——零命中，技能压根不加载 |
| 4 | **无机器检查** | 红线扫描只管代码红线、结构守护只管目录漂移，没人管「UI 改动是否走过原型」 |

断点 3 判了「补触发词」这条路的死刑，断点 1、2 说明软约束靠不住，断点 4 说明硬约束是缺失项。

结论只有一个：**把 SOP 从「提示」降层为「拦截」。**

## 二、判据挂在哪里，决定了门禁成不成立

整套机制最关键的一个设计决策，是**判定条件从「用户说了什么」换成「这次要写的是哪个文件」**。

- 用户措辞：无限集，「间距高了 / 太丑 / 挪一下 / 换个色」……永远补不完；
- 改动对象路径：有限集，且可靠。

于是所有机器层统一按一个判据工作：**这次要写的是不是 UI 源码文件**。

```python
# 受门禁约束（UI 源码）
apps/*/pages/**          # wxml / wxss / ts / json
apps/*/src/**/*.vue      # admin 系微前端
apps/*/components/**
packages/ui/**
app.json                 # 信息架构：pages / tabBar

# 通行证路径（原型与规格）
apps/*/prototype/**
docs/ui/prototypes/**
specs/**/page-spec*.md
```

这一步换轨之后，「用户怎么说」彻底不重要了。说「间距高了」和说「帮我重做这个页面」，走的是同一条判据、同一道门。

## 三、第一道门：在工具调用层硬阻断

CodeBuddy 的 Hook 机制提供了 `PreToolUse` 事件，命中后可以返回 `permissionDecision: "deny"`，直接否决这次工具调用。这是真强制：不是 AI「选择遵守」，是它调用不成功。

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "write_to_file|replace_in_file|Write|Edit|MultiEdit",
        "hooks": [{ "type": "command",
                    "command": "python3 scripts/redline/hook-ui-prototype-gate.py",
                    "timeout": 10 }] },
      { "matcher": "execute_command|Bash",
        "hooks": [{ "type": "command",
                    "command": "python3 scripts/redline/hook-shell-ui-gate.py",
                    "timeout": 10 }] }
    ],
    "PostToolUse": [
      { "matcher": "write_to_file|replace_in_file|Write|Edit|MultiEdit",
        "hooks": [{ "type": "command",
                    "command": "python3 scripts/redline/hook-mark-proto-touched.py",
                    "timeout": 10 }] }
    ]
  }
}
```

- **gate**：写 UI 源码前，检查本会话有没有改过原型/规格（per-session 通行证 + 4 小时 TTL + 跨端校验），没有就 deny；
- **mark**：改原型/规格后写通行证；
- **放行时也要说话**：不是静默放行，而是回一段 `additionalContext`——「你正在改 UI 源码 X，通行证来自原型 Y；若形态未在原型中体现请先更新原型；纯视觉微调请记一行『微调豁免』」。约束的是下一步意图，不是这次调用。

三个必须做的工程细节：

1. **`tool_name` 有双风格**。IDE 是 `write_to_file` / `replace_in_file` / `execute_command`，CLI 是 `Write` / `Edit` / `Bash`；`tool_input` 字段名也可能是 `filePath` 或 `file_path`。脚本内禁止硬编码单一风格，matcher 写双值。
2. **失败一律 fail-open**（`exit 0`）。门禁脚本自己崩了不能让 IDE 会话卡死，这是底线。
3. **零摩擦边界要主动验证**。非 UI 文件必须完全无输出——自检里有专门的断言。

配合三层文本约束（常驻动作门 / 端规则 / CI 红线 R9），第一版看起来闭环了。**然后上线第一天就被打脸。**

## 四、上线后实测的四个漏口

把门禁交给真实会话跑一天，暴露出四条缝隙，且每条都能定位到具体代码行：

| # | 漏口 | 说明 |
|---|---|---|
| P0 | **只拦编辑工具，不拦 shell** | matcher 只覆盖了 `write_to_file` 类；`sed -i`、`cat >`、`git apply`、`cp` 全部绕行 |
| P1 | **通行证是全局的，不区分端** | 改 A 端原型 → 8 小时内 B 端任意页面随便写 |
| P2 | **无「用户确认」信号** | hook 只能证明「原型被改过」，不能证明「人点头了」 |
| P3 | **fail-open 且无审计** | 放行/拒绝都无日志，静默失效无法发现，摩擦也无法度量 |

前三条是设计时就留下的缺口，第四条让它们变得不可观测。

### P0 的补丁：shell 通道的双命中判定

shell 没有结构化文件路径，只能对命令文本做判定。做法是**双命中**——UI 路径特征 ∩ 写操作符特征，白名单兜底：

```python
UI_PATH_PAT = ...   # .wxss/.wxml/.vue、apps/*/pages|components/、packages/ui/、app.json
WRITE_OP_PAT = ...  # sed -i / perl -i / tee / cp|mv|rm / git apply / git checkout -- / patch /
                    # python -c / node -e / writeFile( / open(...'w') / <<EOF
```

实跑中暴露两个缺陷，都很典型：

- **白名单前置导致绕过**：`echo x > a.wxss` 因为 `echo ` 在白名单里被放过。修法是判定顺序改为「UI 路径命中 → 再看写语义 → 白名单最后兜底」，白名单不赦免写语义。
- **临时目录误伤**：在 `/tmp` 里 init 一个 demo repo 的脚手架命令被拦。补了 `within_repo` 判定——路径按 `cwd` 归一后必须在项目根下。

第二个尤其值得记：**误伤是「摩擦导致门禁被关掉」的头号诱因**。门禁死于误报，而不是死于漏报。

### P1/P3 的补丁

通行证细粒度化为 per-session 文件（记录 `apps` 集合 + 原型文件 + sha256），跨端改动直接 deny；新增 `SessionStart` 注入动作门摘要；所有决策追加审计日志 `{ts, session_id, tool_name, path, decision}`；新增自检脚本把判据断言化，一条命令验证门禁还活着。

## 五、语义缺口：机器读不到「人点头了」

P2 是最难的一条。hook 能把「先原型」变成物理顺序约束，但**它证明不了用户确认过**——这是语义缺口，不是工程缺口。

我们的办法是**不试图读取「点头」，而是把点头物化成一条 git 记录**。三个候选：

| 方案 | 验证力 | 伪造成本 | 摩擦 |
|---|---|---|---|
| A 人签通行证脚本 | 中 | **低**：AI 也能调用那个脚本 | 低 |
| **B git 凭证（选此）** | 高：凭证进 git 历史，可回到任意 PR 复验 | 高：需伪造 commit 历史或 `--no-verify` | 中（两条 commit 纪律） |
| C B + 人签 + PR 模板勾选 | 最高 | 最高 | **高**：易触发「把门禁关掉」 |

B 的关键在于**凭证落在既有的 review 面上**——PR diff 里就能看见，不引入任何外部系统。两条铁律：

```
① 改原型/规格 → 过质检 → 用户确认 → 单独 commit（不得与 UI 源码混入）→ 记下 sha
② 改 UI 源码 → 该 commit 的 message 必须带一行 trailer：Proto: <sha>
```

强制点必须在 `commit-msg` hook 而不是 `pre-commit`（后者拿不到 commit message）。四档判定：

| staged 构成 | 判定 |
|---|---|
| 不含 UI 源码 | 与本门无关，放行 |
| 含 UI 源码 **且** 含原型/规格（混合提交） | **error**：同一 commit 内「改原型 + 落码」正是绕过形态，提示拆两个 commit |
| 只含原型/规格 | 这是 Proto 起点 commit，放行 |
| 含 UI 源码 | 须同时满足：① 带 `Proto: <sha>`；② `git cat-file -e` 存在；③ `git merge-base --is-ancestor`；④ 该 sha 的变更文件含原型/规格路径 |

第 ④ 条是方案 B 与旧标记机制的本质差异：**工作区改过的原型没有进 review 面，指向它不算数**，必须指向一个已落库的祖先 commit。

本地 hook 是防呆不是防线（`--no-verify` 能绕），所以 CI 侧加了 R10 兜底：遍历 PR range，凡含 UI 源码的 commit 必须带凭证。

## 六、第二个语义缺口：质量无人把关

流程强制住之后，下一个问题立刻出现：**强制「有」，不强制「好」**。

体系里有一个明显的不对称——测试侧有 `test-verification`（盲测：隔离实现思路，按需求判据打产物），**设计侧没有对应的第三方**：原型是 `ux-prototype-designer` 出稿、自己过自己的质检清单，等价于开发自证。长期下来，评审成本全部压到用户一个人身上。

于是补了一个独立评审角色 `design-reviewer`，定位是**设计挑刺者，不是帮忙画图的人**。它的成败全在三条独立性机制上：

| 机制 | 做法 | 防的是什么 |
|---|---|---|
| ① 盲审隔离 | 先读判据源形成「应该长什么样」，**再看被审物**；**禁止读**出稿方的「设计决策记录·为什么这么设计」自辩段 | 被生产者思路带偏 |
| ② 独立上下文 | 以 sub-agent 执行评审，主 Agent 只回收报告摘要 | 主上下文里已有的出稿意图污染评审 |
| ③ 判据外部化 | 每条结论必须指到判据编号；**指不到的一律降级为「建议」并标注「无判据，属个人偏好」** | 主观否定 |

第 ③ 条尤其重要。评审最容易退化成「感觉不太对」，而一旦允许这种表达，评审就变成了噪音。规则是：**写不出判据编号的意见，默认不阻塞，并且必须显式承认自己是偏好。**

配套还有三件事：

1. **补单一真相源** `docs/ui/design-system.md`（层级 / 密度 / 间距 / 色彩语义 / 状态矩阵 / 文案 / 端差异 / 反模式）。评审判据不落盘，评审必然退化为主观判断。注意它**不复制数值**，数值仍以 tokens 为唯一事实源——防漂移。
2. **三关口**：D1 设计输入评审 → D2 原型规格评审（交人确认前）→ D3 实现一致性评审（落码后）。D2 是独立复审，不替代出稿方的自检下限，正如完成验证门不替代独立验证。
3. **D3 分层**：机检层做锚点比对——原型关键元素打 `data-dr="<key>"`，实现同名打点，CI 比对锚点集合差异（缺 / 新增 / 改名），结构化漂移即刻可见；视觉并置层才交给 AI 判。分层是为了不让最贵的一关沦为不可回归的主观比对。

### 把「评审过了吗」也物化

沿用同一套思路：**机器读不到评审质量，但能读到「报告落盘并进了 git」**。

评审报告固定带两行机器可读头：

```
阻塞: N
重要: N
```

CI 规则 R11（**error 级**）：含 UI 源码的 commit 缺 `Design:` trailer → 报错；报告头部 `阻塞: N` 且 N>0 → 报错。

这里有个必然的连带问题：锚点要回填存量页面（三端上百个界面文件），回填完成前就让锚点比对达到 error 级，会让存量页面的任何改动全线红。所以拆成两条判据、两种节奏：

| 判据 | 生效时机 | 级别 |
|---|---|---|
| R11-a trailer 与阻塞清零 | 落码即生效，存量新增一视同仁 | error |
| R11-b 锚点集合比对 | 三档开关 `off → warn → strict`，随回填批次推进 | 初始 off |

并且**只当原型侧与实现侧都声明了锚点清单时才比对**——「尚未回填」不等于「已漂移」。这条防误报约定是 R11 能直接上 error 的前提。

## 七、门禁的门禁

最有意思的一条规则是最后加的。

上游 `ai-agent-kit` 通过 sync 只写能力源（`.codebuddy/agent-kit/`），而 IDE 实际加载的是运行源（`.codebuddy/skills/`），中间缺一步 apply。结果上游合并了「Hub 接入 design-reviewer 分派」和「扩充 UI 微调触发词」两件事，能力源更新了，**运行源没动——Hub 根本不认识新角色，触发词也还是旧的**。

也就是说：**门禁自己被同步机制绕过了。**

于是补了 R12 同源守门：比对两处应同源的路径，以源为准，目标缺失即「未同步」、内容不同即「漂移」，报警自带修复命令（`cp` 一行）。并用一份**保护清单**跳过项目专属只存在于运行源的技能，避免误报。

它复用了和 R9/R10/R11 同一套通用骨架 `check_sync_pair`。这条规则的价值不在代码量，而在提醒：**任何依赖同步的机制，都需要一个守着同步本身的检查**。

## 九、摩擦控制：门禁最大的死因是被关掉

这一节的优先级高于前面所有设计。门禁不是越严越好——**摩擦过大的 hook 最终会被关掉，等于没做**。所以每一条硬规则都必须配一个零摩擦或低摩擦出口：

| 出口 | 用法 | 适用 |
|---|---|---|
| 记一行「微调豁免」 | 在原型/规格写：`<!-- 微调豁免: 仅调输入框行距 -->` | 纯视觉微调 |
| `Micro-exempt: <理由>` | commit trailer | 同一语义在 CI 侧的表达 |
| `UI_GATE=off` | 环境变量 | 批量机械改动、紧急修复 |
| 通行证过期 | per-session + 4h TTL + `SessionStart` 重置 | 防跨会话误放行 |

以及三条纪律：

1. **豁免口径必须一致**。同一种「微调豁免」语义，在 R9b / R10 / R11 里必须同时生效。否则「记了豁免还报错」会成为新的摩擦源——这类不一致比规则本身更消耗信任。
2. **作用域收窄**。所有 CI 规则只在 diff 含 UI 源码时触发，纯后端 / 文档 / 脚本 PR 完全零摩擦。自检里有专门的零摩擦断言。
3. **不叠加 deny**。设计评审只走 trailer + CI，不在 `PreToolUse` 再加一层阻断——UI gate 已经 deny 一次，再加一次会显著推高摩擦。

设计取舍写成一句话：**宁可偶尔多一次豁免记录，也不要让 hook 变成日常噪音。**

## 十、可复用的七条

如果你也想给自己的 AI 工作流加门禁：

1. **判据挂在改动对象，不挂用户措辞**。措辞是无限集，路径是有限集。这是整套机制的地基。
2. **先补真相源，再补角色**。评审判据不落盘，评审必然退化成主观判断；判据文档不要抄数值，数值留在 tokens/代码里。
3. **强制点选在工具调用层**（`PreToolUse` deny），文本层只做第一道。
4. **写完立刻做攻击性测试**：换通道（shell）、换端（跨 app）、换会话（过期标记）、关掉配置（自检脚本）。我们四个漏口全是这么找出来的，不是想出来的。
5. **机器读不到的东西，就把它物化成 git 记录**。用户确认、评审质量——都能用 commit trailer + 报告头两行转成可机检的事实。
6. **给每一条硬规则配豁免出口，并保证口径一致**。
7. **加一条守着门禁自身的检查**（同源守门 / 自检脚本）。门禁会漂移、会被同步机制绕过、会静默失效。

最后一条体会：这套东西真正的价值不是「拦住了 24 次」，而是**把「先原型、后代码、有人审」从口头共识变成了可回归的事实**——任何人打开任意一个 PR，都能看到原型 commit、评审报告、凭证 trailer 三件套。流程不再依赖谁记得。
