# T11 Agent 开发技术架构 · 技能思维导图

> 视角：以 T11 架构师的第一性原理看 Agent 开发——**把承重层做稳、可换层做松、易变层做便宜**。
> 模型层（能力、价格、可用模型）动得越快，越要这样分层。每个技术节点拆三件事：
> **价值**（为什么是架构级决策，错判的代价）/ **技术原理**（它到底在解决什么）/ **技术实现方案**（怎么落，含你项目的落地信号）。

## 0. 总览（四层 + 业务透镜）

```
                 T11 Agent 开发技术架构
        ┌──────────┬──────────┬──────────┬──────────┐
        │ 承重层   │ 可换层   │ 易变层   │ 业务透镜 │
        │ 伤筋动骨 │ 可插拔   │ 便宜迭代 │ 翻译业务 │
        └──────────┴──────────┴──────────┴──────────┘
```

- **承重层**（优先锁死）：架构范式 / 控制流所有权 / 状态与记忆 / 安全边界 / 质量与评测
- **可换层**（设计为可插拔）：模型解耦 / 工具契约 / KB 与检索 / 评测体系
- **易变层**（配置化，每周能改）：提示词 / 模型选型 / 调参
- **业务透镜**（把技术翻译成决策）：成本 / 风险 / 杠杆 / 度量

> 使用方式：从任一层挑一个节点说"拆 X"，即按下面三段展开。

## 1. 承重层（改一次伤筋动骨）

### 1.1 架构范式
- **价值**：决定引擎形态，事后改要推倒重写。多 Agent 编排 vs 单 Agent 闭环、自主循环(ReAct) vs 确定性图(LangGraph 式) 一旦选定，工具/状态/HITL 接口都受其约束。
- **技术原理**：自主循环 = 模型每步采样决定下一步，灵活但不可控；确定性图 = 代码控制流转，可预测但丧失涌现。本质是"在哪划不确定性的边界"。
- **技术实现方案**：先按任务确定性选基线（确定性任务用图，探索性任务用循环）；多 Agent 用 supervisor/黑板模式，避免网状互调。你项目：`agent-core` 已是契约面，范式基本定了，但**多 Agent 编排尚未铺开**——扩之前先预留子 Agent 注册与消息总线接口。

### 1.2 控制流所有权
- **价值**：模型驱动还是代码驱动，定了它引擎形态就定型。错判→要么失控不可控，要么丧失 Agent 灵活性。
- **技术原理**："下一步做什么"的来源。代码驱动=确定性状态机；模型驱动=LLM 输出动作。混合态=代码定骨架、模型填叶子。
- **技术实现方案**：以"人类可审批节点"为锚点划分——审批前代码驱动保可控，审批后模型驱动保灵活。你项目：`agent-engine.ts` 是驱动核心、`RunInput.model` 单次覆盖，目前代码驱动为主、模型采样为辅，符合"骨架代码定、叶子模型填"。

### 1.3 状态与记忆边界
- **价值**：决定长对话能否不崩、成本是否爆炸、中断能否续跑。错判→上下文溢出或重复计算。
- **技术原理**：context 窗口有限，需压缩/摘要/检索平衡；long-term 记忆要解决"存什么、怎么取、何时忘"；checkpoint 解决可恢复性。
- **技术实现方案**：短期上下文用滑动窗口+关键摘要；长期用向量库+结构化记忆；每步写 checkpoint 支持断点续跑。你项目：`agent_definitions.memory` 字段已在，但压缩/恢复策略未体系化，建议补"上下文管理策略"配置项。

### 1.4 安全边界（爆炸半径 + 认知安全）
- **价值**：Agent 能碰什么（工具/数据/外部调用）决定出错影响面；认知安全（grounding/抗幻觉）决定敢说什么。错判→越权、数据泄露、资损、编造答案客诉。
- **技术原理**：最小权限原则 + 工具权限收敛；grounding = 答案必须可溯源到给定上下文，无据则拒答。
- **技术实现方案**：工具按风险分级（只读/写/外部），Agent 实例按角色授权；输出层加引用校验与置信度门。你项目：`InternalGuard`/权限码体系在，但 **Agent 自主调用时的权限收敛还需明确**（见 §1.5 grounding 护栏）。

### 1.5 质量与评测（成功标准设计 + grounding 护栏）⭐ 新增承重决策
- **价值**：定义"完成/准确"即定义优化目标（Goodhart：指标塑造优化方向）；grounding 是认知安全边界。错判→优化错方向、答不对留不住人（直接挂钩营收）。这是被遗漏的一整块，现升级为承重层一等决策。
- **技术原理**：成功标准设计（过程跑通 vs 答案正确 vs 用户满意）决定你卷什么；grounding 把"模型自信但错误"挡在门外；评测体系把"感觉变好"变成可量化。
- **技术实现方案（落地方案 —— `agent_runs` 加 outcome + 业务线 eval 集）**：
  1. **`agent_runs` 加字段**：`outcome`(enum: success/partial/fail)、`fail_stage`(enum: retrieval/推理/工具/其他)、`score`(0-100 可选)、`graded_by`(enum: auto_llm_judge/human/rule)、`graded_at`。写入点：引擎结束判 success/partial/fail；`fail_stage` 在编排各阶段埋点（检索失败/推理失败/工具失败）。
  2. **成本→质量双归因**：现有 `DictPricingProvider` 读字典价写 `agent_runs.cost`，加 `outcome` 后升级为"质量+成本"双维度复盘。
  3. **业务线 golden 集**：每日论文 / 财经聚合 / 变变 / 科豆 各建 20~50 条，含 `input` + 期望 success 判据 + 评分 rubric。
  4. **离线 eval**：脚本对 golden 跑 agent，LLM-as-judge 判 `outcome`，输出完成率 + 分项失败率。
  5. **线上监控**：`agent_runs.outcome` 分布曲线 + 人工抽检；`fail_stage` 分布决定改 **KB / prompt / 编排**。
  6. **KB 侧优先测检索召回率**（当前性价比最高的质量杠杆，比调 prompt 有效得多）。

## 2. 可换层（设计为可插拔）

### 2.1 模型解耦层（多级回落）
- **价值**：模型层一动（涨价/停服/出新模型）不伤结构，护住议价权与抗断供能力。错判→绑死单一供应商，定价权不在手。
- **技术原理**：抽象 `ChatClient` 接口，注册多实现；按 DB 字典 → env → 代码 三级回落选择。
- **技术实现方案**：你项目 **ai-agent 已做三级回落**（DB `llm_models` → `TOKENHUB_MODELS`(env) → 代码内置）；**ai-service 仍硬编码 `Hy3Client` + `TokenHubClient('deepseek-v4-flash')`**——这是最该先补齐的可换层缺口（落地方案见 `agent-def-detail-v2.md` §11.3，过契约评审门）。

### 2.2 工具契约（schema 版本化）
- **价值**：工具 schema 是模型**直接消费**的接口，版本化错了→模型调不动工具或升级 breaking。
- **技术原理**：工具描述/参数 schema 是 prompt 的一部分，影响模型的函数调用准确率；需语义化版本（breaking/feat/fix）。
- **技术实现方案**：工具定义集中登记，变更走版本号 + 兼容策略；契约登记进 `contracts.md`（你项目已有"MCP 工具"契约类）。新增/改工具须过契约评审。

### 2.3 知识库与检索（KB & RAG）
- **价值**：短期质量主因。召回率上不来，模型再强也答不对（KB 准确率被 recall 卡死）。
- **技术原理**：chunking 决定粒度，embedding 决定语义召回，rerank/混合检索提升精度，时效与冲突消解决定正确性。
- **技术实现方案**：按业务切分策略（论文按章节、财经按标的）；embedding + 向量库 + BM25 混合；rerank 模型兜底；知识更新走增量。你项目：每日论文/财经聚合强依赖 KB，知识库沉淀腾讯 ima——先测检索召回率再谈其他优化。

### 2.4 评测体系（离线 golden + 线上监控）
- **价值**：换模型/prompt 用数据说话，而非赌。错判→越改越差不知道。
- **技术原理**：离线 golden 集 + LLM-as-judge 判分 + 线上完成率监控 + 人工抽检，构成"改之前有基线、改之后有对比"。
- **技术实现方案**：与 §1.5 共用——golden 集与 `agent_runs.outcome` 是同一套数据资产的两端：离线定基线，线上看分布。建议新建 `scripts/agent-eval/` 跑 golden，结果落 `agent_runs`。

## 3. 易变层（低成本快速迭代 · 必须配置化）

### 3.1 提示词
- **价值**：调对了收益大、成本低，但它是易变层——每周都能改，不该进代码评审重流程。
- **技术原理**：指令遵循、角色设定、少样本、结构约束，共同决定输出形态。
- **技术实现方案**：提示词模板化 + 版本化存配置/DB，支持 A/B；与具体模型共同调（换模型常需重写 prompt）。你项目：prompt 管理应纳入配置面，避免散落代码。

### 3.2 模型选型
- **价值**：影响成本/延迟/能力天花板，但属易变层——应能通过配置切换，不应发版。
- **技术原理**：不同模型在指令遵循、长上下文、工具调用、价格上各有取舍。
- **技术实现方案**：与 §2.1 解耦层配合——`agent_definitions.model` 字段 + DB 字典即可切模型，不发版。`RunInput.model` 支持单次覆盖做实验。

### 3.3 调参（temperature / maxTokens / topP / thinking）
- **价值**：压住输出分布方差到系统可承受范围；但必须配置化（见上轮讨论）。
- **技术原理**：temperature 控随机性、maxTokens 防截断、topP 控长尾、thinking 控推理深度（hidden cost 大头）。
- **技术实现方案**：把 `maxTokens/topP/thinking` 补进 `agent_definitions`（现状只暴露 `model/temperature/maxSteps/streaming/memory`，另三个透传断在 `agent-engine.ts`）→ 配置化后线上出问题有止血手段，不用发版。参考 `CLASSIFY_MAX_TOKENS=256` + `thinking:disabled` 的教训（思考吃光输出→100% 兜底）。

## 4. 业务透镜（翻译为业务决策）

### 4.1 成本
- **价值**：决定定价/毛利/能否养免费试用。错判→按 token 粗算，thinking+多步重算吃穿毛利。
- **技术原理**：成本 = input + output + thinking 三块，thinking 常是隐形大头；多步 Agent = 单步 × 步数；缓存命中率决定毛利。
- **技术实现方案**：`agent_runs.cost` 已做单 run 归因；补 `outcome` 后做"质量×成本"矩阵，识别高成本低质量路径。定价模型基于实测单任务成本而非标称 token 价。

### 4.2 风险
- **价值**：决定哪些功能敢写进卖点/SLA。错判→"模型变傻"投诉，翻日志才发现是配额。
- **技术原理**：幻觉/长文丢失/工具不稳是概率性能力；版本升级、供应商换底层会让"昨天好的今天挂"。
- **技术实现方案**：把旋钮配置化（§3.3）作为止血手段；关键路径加 fallback 与兜底分支；对外承诺只对确定性能力下保证。

### 4.3 杠杆
- **价值**：决定议价权/抗断供/技术债。错判→供应商一涨价核心体验跟着挂。
- **技术原理**：多模型可切换 = 不被单一供应商绑架；model-agnostic 架构让"今天补的后处理，下月模型可能原生支持"。
- **技术实现方案**：优先做 §2.1（ai-service 解绑）；架构保持 model-agnostic，避免把后处理写死成某模型特化逻辑。

### 4.4 度量
- **价值**：决定"到底有没有变好 / 该不该换模型"。错判→凭感觉迭代。
- **技术原理**：通用 benchmark ≠ 你的业务效果；要自建 eval 集对齐转化率/人工接管率等业务指标。
- **技术实现方案**：即 §2.4 + §1.5 的 eval 体系；以业务指标（完单率、接管率）为目标函数，而非模型榜单分数。
