# 系统优化计划

> 基于 2026-08-14 ~ 15 MCP 平台开发全流程 Review，梳理效率瓶颈与优化方向

---

## 一、部署流程（最大效率瓶颈）

### 现状问题

1. **deploy.sh 缺失 mcp-gateway 和 finnews**
   - 脚本只覆盖 gateway/auth/system/portal/admin/mcp-admin/seed
   - 这两个服务每次部署都是手工 `tar → scp → ssh pm2 delete+start`
   - 反复踩坑：macOS tar 带 `._` 文件、`-h` 只跟一层 symlink 缺传递依赖、pnpm deploy 生成 162M 自包含目录

2. **服务器代码与 git 脱节**
   - 服务器 git 停在 `8339ab9` 且有本地改动，不能 `git pull`
   - 新依赖（如 nodemailer）不会安装，需手动 tar node_modules
   - ecosystem.config.js 改动需手动同步

3. **PM2 env 更新不可靠**
   - `pm2 restart --update-env` 不刷新 env block
   - 必须 `pm2 delete` + `pm2 start ecosystem.config.js --only xxx`

4. **health_check 端口过期**
   - deploy.sh 的 health_check 里还是旧端口 3000/3001/3004，需更新到 6000/6001/6004

### 优化措施

| # | 优化项 | 具体措施 | 优先级 | 工作量 |
|---|--------|---------|--------|--------|
| 1.1 | **补全 deploy.sh** | 加 `mcp-gateway`/`finnews` 部署函数（build → tar dist → scp → pm2 delete+start），复用 auth/system 模板 | P0 | 0.5h |
| 1.2 | **修复 health_check** | 端口 3000→6000、3001→6001、3004→6004，加 6006/6007 检查 | P0 | 0.2h |
| 1.3 | **PM2 封装** | deploy.sh 统一用 `pm2 delete <name> && pm2 start ecosystem.config.js --only <name>` 替代 `pm2 restart` | P0 | 0.3h |
| 1.4 | **服务器 git 拉通** | 处理服务器本地改动（stash 或 commit）→ `git pull` → `pnpm install` → `pnpm build`，后续部署走 git | P1 | 1h |
| 1.5 | **统一部署方式** | 放弃 tar-dist 模式，改为服务器端 `git pull + pnpm build`，deploy.sh 只负责触发 | P1 | 2h |

### 预期收益
- mcp-gateway/finnews 部署从 15 分钟手工操作 → 1 条命令
- 消除 tar 路径/symlink/AppleDouble 等反复踩的坑

## 二、环境一致性（DEV/PROD 分裂）

### 现状问题

1. **PROD gateway 是旧版**
   - 无 mcpProxy/mcp-admin，导致申请页和管理台走 DEV
   - SSL 层 nginx 路由分散：`/mcp`→PROD(246), `/api/mcp`→PROD(246), `/mcp-admin`→DEV(123)

2. **DB 版本不同**
   - DEV MySQL 8.0 vs PROD MySQL 5.7
   - collation `utf8mb4_0900_ai_ci` 不兼容，每次导入需 sed 替换为 `utf8mb4_general_ci`

3. **key 库分裂**（已修复但根因仍在）
   - 申请写 DEV 库，验证查 PROD 库 → 401
   - 根因：环境分裂，API 端点和后端不在同一环境

4. **nginx 配置全手动**
   - SSL 层每次改动都是手动 SSH + python 脚本插入
   - 多个 `.bak-*` 备份文件，没有版本管理

### 优化措施

| # | 优化项 | 具体措施 | 优先级 | 工作量 |
|---|--------|---------|--------|--------|
| 2.1 | **PROD gateway 升级** | 把 DEV gateway 最新代码部署到 PROD(246)，让 PROD 也有 mcpProxy/mcp-admin | P0 | 1h |
| 2.2 | **nginx 配置版本管理** | SSL 层 nginx conf 放进仓库 `nginx/` 目录，改动走 git，部署用 `scp + nginx -t && reload` | P1 | 1h |
| 2.3 | **DB 迁移机制** | 用 TypeORM migrations 替代 `synchronize:false` + 手动 SQL，每次 schema 变更生成 migration 文件 | P1 | 3h |
| 2.4 | **DB 版本统一** | PROD MySQL 5.7 升级到 8.0，或统一降级到 5.7 | P2 | 2h |
| 2.5 | **SSL 层路由统一** | PROD gateway 升级后，`/api/mcp` 和 `/mcp-admin` 全部切 PROD，消除跨环境调用 | P0 | 0.5h |

### 预期收益
- 消除"DEV 能跑 PROD 不能"的调试时间（两天里约 40% 时间花在这上面）
- nginx 变更有 git 历史，不再靠 `.bak` 文件追溯

## 三、密钥与配置管理

### 现状问题

1. **密钥分散在 5+ 位置**
   - `~/env_config/smtp.env`
   - `~/.workbuddy/mcp.json`（WorkBuddy 连接配置）
   - 服务器 `/data/web_system/.env.production`
   - `ecosystem.config.js`（部分重复定义）
   - 本地各服务 `.env`

2. **key 笔误排查成本高**
   - `~/.workbuddy/mcp.json` 里 key 多一个 `f`（`a45bf3` vs `a45b3`），排查了很久

3. **ecosystem.config.js 与 .env.production 重复**
   - ecosystem 读 `process.env`，但部分 key 在 ecosystem env 段又写了一遍

### 优化措施

| # | 优化项 | 具体措施 | 优先级 | 工作量 |
|---|--------|---------|--------|--------|
| 3.1 | **.env.production 唯一源** | ecosystem.config.js 只读 `process.env`，不在 env 段重复定义 | P1 | 0.5h |
| 3.2 | **密钥同步脚本** | `scripts/sync-env.sh`：从 `~/env_config/` 读取 → 写入 DEV/PROD 服务器 `.env.production` → pm2 restart | P1 | 1h |
| 3.3 | **.env.example 完整化** | 所有新增环境变量（MCP_ADMIN_KEY/SMTP_*/FINNEWS_SERVICE_KEY 等）补到各服务 `.env.example` | P0 | 0.3h |

### 密钥清单（当前）

| 密钥 | 用途 | 存储位置 |
|------|------|---------|
| `MCP_CLIENT_KEY` | WorkBuddy → mcp-gateway 遗留共享鉴权 | .env.production |
| `MCP_ADMIN_KEY` | /api/keys 管理接口保护（X-Admin-Key） | .env.production |
| `FINNEWS_SERVICE_KEY` | mcp-gateway → gateway 服务间鉴权 | .env.production |
| `SMTP_PASS` | 验证码邮件发送（腾讯企业邮箱客户端专用密码） | .env.production + ~/env_config/smtp.env |
| `JWT_SECRET` | 用户认证 | .env.production |
| `DB_PASSWORD` | 数据库 | .env.production |

## 四、代码架构改进

### 现状问题

1. **seed 逻辑脆弱**
   - `onModuleInit` seed finnews 模块"已存在则跳过"导致 base_url 不更新
   - 后改为"已存在但不一致则同步"，但仍是运行时隐式逻辑

2. **TypeORM `string | null` 反复踩坑**
   - 被推断为 `Object`（DataTypeNotSupportedError），需显式 `type: 'varchar'`

3. **MCP transport 无 TTL**
   - 每 session 独立 buildServerFromDb，创建后无超时清理
   - 长时间运行会内存泄漏

4. **deploy.sh 未覆盖 mcp-gateway/finnews 的依赖安装**
   - tar-dist 模式不同步 node_modules，新依赖（nodemailer）需手动处理

### 优化措施

| # | 优化项 | 具体措施 | 优先级 | 工作量 |
|---|--------|---------|--------|--------|
| 4.1 | **seed 逻辑独立** | 改为 `scripts/seed-mcp-modules.ts`，部署时显式执行，不在运行时自动 seed | P1 | 1h |
| 4.2 | **Nullable 类型封装** | 封装 helper 或用 `type: 'varchar' as const`，避免重复踩坑 | P2 | 0.3h |
| 4.3 | **MCP session 清理** | 加 session 超时（如 30 分钟无活动自动 disconnect + GC） | P2 | 1h |
| 4.4 | **FINNEWS_HTTP_TOOLS 声明式化** | finnews 工具声明硬编码在 mcp.service.ts，考虑移到配置或 DB | P2 | 2h |

## 五、测试与质量保障

### 现状问题

1. **无自动化测试**
   - 只有 `test/e2e-keys.sh` 手动脚本
   - 每次改动都手工 curl 验证，容易遗漏回归

2. **部署后健康检查不完整**
   - health_check 端口过期
   - 不检查 /mcp、/api/modules 等关键端点

### 优化措施

| # | 优化项 | 具体措施 | 优先级 | 工作量 |
|---|--------|---------|--------|--------|
| 5.1 | **关键路径集成测试** | mcp-gateway 的 /mcp 端点 + key 申请/验证流程写成 Jest 集成测试 | P1 | 3h |
| 5.2 | **部署后自动验证** | deploy.sh 末尾自动 curl 关键端点（/health、/mcp initialize、/api/modules），失败即报警 | P0 | 0.5h |
| 5.3 | **E2E 脚本完善** | e2e-keys.sh 补全 finnews 工具调用验证（6 个工具全覆盖） | P1 | 1h |
