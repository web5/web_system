## 阻塞（必须解决，未清零不得交人确认）

- [ ] [S7] 禁用态的「原因」实际不可见 —— 原生 `disabled` 让 `title` 在 Chromium 桌面浏览器不触发，键盘也到不了，落到 S7 反例「无声禁用」
  - 反例（情形 → 实际 vs 期望）：
    - 情形 A：Chrome / Edge（桌面）打开对话页，鼠标悬停到那条淡掉的「朗读」按钮 → **实际**：无任何浮层，用户只看到「朗读」两字变淡，不知道为什么不能点 → **期望**（S7）：浮出「朗读能力未配置（服务端 TTS 凭据缺失）」。
    - 情形 B：键盘用户 Tab 遍历 → **实际**：`disabled` 按钮被移出 Tab 序列且无 `aria-disabled` / `aria-describedby`，原因永远读不到 → **期望**（J 维 + S7）：可到达且能获得原因。
    - 情形 C：对话操作条 `.acts` 常态 `opacity:0`（index.html:231），只在 `.mrow:hover` 时显形（232）——**该按钮唯一的可见时机就是 hover，而 hover 恰恰是 title 不触发的时机**，禁用信号在它唯一能被看到的瞬间仍然是哑的。
    - 加重项：禁用态按钮文案与启用态**完全相同**（都叫「朗读」，index.html:757/842/1135 vs readBtn 输出 1259），去掉 tooltip 后，用户拿到的信息量 = 0。
  - 判据：[S7]（design-system §4 状态矩阵：禁用态 →「禁用时 tooltip 说明原因」，反例形态「无声禁用」）+ [P3]（§1 状态必须可见：请求失败静默、按钮点了没反应均属不合格）+ [J] 可访问性基线（可点击元素键盘可达）
  - 严重级：阻塞 ｜ 是否阻塞交用户确认：**是**
  - 说明：本次改动的全部价值 =「把不可用前移到点击之前 + 说明原因」。原因的**唯一载体**就是这个 tooltip；载体不触发 = 改动一半失效，交到人面前会被确认成一个「信号不可见」的设计。
  - 建议改法（不代改，供 ux-prototype-designer 选用）：① 用 `aria-disabled="true"` 代替 `disabled` 属性 + 在 click 处理器里拦截，保留可聚焦与鼠标事件；或 ② 按钮外包一层 `<span title="…" tabindex="0">` 承载 title 与焦点；禁用视觉改由 class 表达，不用 `disabled` 属性。

- [ ] [X1] 对话内嵌翻译卡的「朗读」未接入 `readBtn` —— 覆盖范围内仍可点，事故形态原样复现
  - 反例：打开控制条「TTS 未配置」→ 进入一段被识别为**翻译**的 AI 回答 → **实际**：`msgAi` 因 `hasCard` 为真不渲染操作条朗读（index.html:757），而卡内朗读（index.html:703）是硬编码按钮、未走 `readBtn`，点了弹「朗读：请稍候…」然后无下文 → 整条回答在「TTS 未配置」下**没有任何禁用信号**，且点击后仍是「点了才知道」→ **期望**：该入口同为禁用态 + 原因说明。
  - 判据：[X1]（§7 反模式：只画主路径，异常分支全缺）+ [P3]（§1 状态必须可见）+ [P2]（§1 一致性优先于个性化：同端同类元素形态一致——同为「朗读」按钮，两处禁用一处不禁用）
  - 严重级：阻塞 ｜ 是否阻塞交用户确认：**是**
  - 说明：page-spec §1 把 `AiChat.vue` 列为改动组件，卡内朗读渲染在 AiChat 内（`renderBlocks`），属覆盖范围内的漏项；而它恰好是含卡片回答的**唯一**朗读入口——漏一个 = 该场景整条防线失效。

## 重要（建议解决，不阻塞交人）

- [ ] [P2] 三处接入形态不一致：翻译卡的「朗读」在禁用态凭空多出一个喇叭图标
  - 反例：控制条开关关→开，翻译卡操作行「朗读」按钮（index.html:842 vs readBtn 1259）**多出** `SVG(I.vol)` 图标，而启用态（842）及同行的「收藏」「更多」均无图标 → 禁用态比启用态视觉更重、更抢眼（禁用本应更弱）；同一按钮两态形态不一致。对话条（757）与生词本（1135）启用态带图标、禁用态也带图标，与翻译卡三者互不对齐。
  - 判据：[P2]（§1：同端同类元素形态一致；反例「同一系统里两种主操作样式并存」）
  - 严重级：重要 ｜ 是否阻塞：否（不影响「能不能用」的判断，但会让禁用态在视觉上被误读为「更重要的那个」）

- [ ] [S5] 不可用态只有「出了什么问题」，没有「怎么办」与唯一出路
  - 反例：tooltip 文案「朗读能力未配置（服务端 TTS 凭据缺失）」（index.html:1258）→ 用户看完无任何可行动作：无重试入口、无「稍后再来」、无反馈通道；运维补上凭据后，因 page-spec §2.4「结果存模块级变量」，用户必须**整页刷新**才可能恢复 → 而用户无从得知「可以刷新试试」。
  - 判据：[S5]（§4：无权限态须「显式说明 + 唯一出路」，反例「按钮消失但无说明」——本稿说明了原因，但出路仍缺）+ [H4]（§5：错误文案 = 出了什么问题 + **怎么办**）
  - 严重级：重要 ｜ 是否阻塞：否（服务端故障场景下「出路」是否必须有，需人裁决，见文末）

- [ ] [P6] health「拉取中」态未定义、原型也未演示
  - 反例：page-spec §2.4 只写了「进入页面时拉一次、结果存模块级变量」，未定义**请求在飞期间按钮长什么样**；原型控制条（index.html:449）只有「TTS 未配置」一个开关，没有「health 拉取中」「health 拉取失败」两态的演示入口 → 评审与用户都无法看到这两种形态，默认实现大概率是「先按可用渲染、拉回来再翻成禁用」，即按钮状态中途跳变。
  - 判据：[S1]（§4：加载中可见）+ [P6]（§1：未定义不脑补——规格未定义即须显式标注待确认）
  - 严重级：重要 ｜ 是否阻塞：否
  - 注：page-spec §2.5 已定义「拉取失败 → 视为可用」，**该条有定义、属可辩护取舍**（见「待用户裁决」）；缺的是「拉取中」。

- [ ] [P4] 禁用按钮仍响应 hover，视觉上「看着能点」
  - 反例：`.acts button:hover{background:var(--page-bg);color:var(--brand-strong)}`（index.html:234-235）与 `.btn.ghost:hover`（150）均未排除 `:disabled` → 鼠标移到禁用的「朗读」上，背景变浅、文字变品牌橙 → **实际**：强化「可点」暗示 → **期望**：禁用态不产生 hover 反馈。本次改动的目的是消除「点了才知道」，而 hover 变品牌色正在把用户往「点一下」引导。
  - 判据：[P4]（§1：操作必须可预期，用户点之前能预判后果）
  - 严重级：重要 ｜ 是否阻塞：否

- [ ] [P2][G3] 禁用视觉用 inline `opacity:.45`，与既有 disabled 阶梯不一致，且把文案对比度压到 AA 以下
  - 反例：新增行内样式 `opacity:.45;cursor:not-allowed`（index.html:1259）覆盖了既有 `.btn:disabled{opacity:.5;cursor:not-allowed}`（151）→ 同为 disabled 按钮，本系统里出现 .5 与 .45 两套值，且 .45 是阶外自定义值；对话操作条那处 `cls=''` 无 `.btn` class，`.btn:disabled` 根本不生效，禁用视觉完全靠这段 inline 兜底 → 三处禁用态不同源。对比度上：`.acts button` 文字 `--t3 #6B6560`（约 4.9:1）经 .45 后有效色约 #B0ABA7 ≈ **1.9:1**；`.btn.ghost` `--t2 #57534E` ≈ **2.6:1**，均跌破 4.5:1。
  - 判据：[P2]（同类元素形态一致）+ [G3]（§2.4：正文对比度 ≥ 4.5:1）
  - 严重级：重要 ｜ 是否阻塞：否
  - 注：WCAG 1.4.3 对 inactive 控件有豁免，是否把禁用按钮纳入 G3 校验 → 见「待用户裁决」。另：page-spec §4 声明「禁用态沿用各组件既有 disabled 样式，不新增裸色值」，与原型实际（新增 inline .45）不一致，规格需同步。

## 建议（无判据的个人偏好，可驳回）

- 控制条「TTS 未配置」开关未在说明区（index.html:453-465）登记一行含义，后续评审/用户看说明区不知道这个开关是什么 —— **无判据编号，属个人偏好，可驳回**。
