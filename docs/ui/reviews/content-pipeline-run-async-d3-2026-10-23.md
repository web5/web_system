# 管线手动运行改异步 · D3 实现一致性评审

阻塞: 0

## 起因（不是设计偏好，是缺陷修复）

「立即运行」上线后点下去弹「网络错误，请检查网络连接」。查证链路，**后端其实跑成功了**
（dev 库 21:30:51 入库 5 条条目、21:30:55 公众号草稿 #21 已建）——只是前端在 10 秒时自己
cancel 了，没拿到结果。链路上三道超时依次是：

| 层 | 超时 | 位置 |
|---|---|---|
| 前端 axios | **10s** | `packages/shared/src/api.ts` `API_TIMEOUT.DEFAULT`（元凶，最先断） |
| 网关 content-admin 通道 | 30s | `servers/gateway/src/proxy/proxy.service.ts:189` 硬编码 |
| nginx `/api` | 60s（默认） | `/etc/nginx/sites-enabled/web-system` 该 location 未设 `proxy_read_timeout` |

所以**只改前端超时没用**——网关 30s 会接着掐断，返回 504。而实测一次运行 30 秒起步
（多源采集 + 逐条 LLM 摘要）。

更糟的是失败形态：请求被掐断 ≠ 任务没跑。用户看到「网络错误」会以为没跑成，于是再点一次，
草稿箱里就多一条重复内容（本次 dev 上 21:27 与 21:30 两次草稿即由此而来）。

## 方案选择

| 方案 | 代价 | 为什么没选 |
|---|---|---|
| 同步 + 三处调长超时 | 改前端 + 网关代码（要发 gateway）+ nginx 配置（要 reload） | 改三个服务、用户干等 30–60 秒转圈、仍无法区分"在跑"和"卡死" |
| **受理即返回 + 轮询（选它）** | 只改 content-hub + admin | — |

异步化后请求毫秒级返回，**不触碰网关与 nginx**，顺带得到两个此前没有的性质：
同管线重复点击可判定复用（不再重复投递）、在途任务有可见状态。

## 范围与证据

依据原型 `docs/ui/prototypes/admin-media-ops.html` 管线屏（本次同步改为异步形态）：
- 点击「立即运行」→ 二次确认 → 按钮变「运行中…」+ 其余按钮禁用 + 顶部进度条走秒
- 完成后弹「运行完成（Ns）：采集 N · 新入库 N · 发布 N · 失败 N」

核对对象：`ContentPipelines.vue`、`api/content.ts`、
后端 `pipeline-run.service.ts` / `pipeline-run.entity.ts` / `content.controller.ts` / 迁移 `0017`。

## 检查结果

| 判据 | 结果与反例 |
|---|---|
| 与原型同形 | 按钮运行态文案「运行中…」、顶部 `a-alert` 进度条走秒、完成弹四数——与原型一致；原型进度条用 `run-banner`（info 底色 + 呼吸点），实现用 antd `a-alert banner` 同语义 |
| 真发布仍须二次确认 | `a-popconfirm` 文案不变，仍明写「会按发布目标真实投递内容」 |
| 重复点击不重复投递 | 后端同管线已有 `running` 记录则复用并返回 `reused: true`，前端弹「本次复用了它 —— 不会重复投递内容」；前端另有 `runningCode` 单飞 |
| 长任务有反馈 | 进度条显示「已运行 Ns」，来源是后端 `elapsed_ms`，不是前端自嗨计时 |
| 超时不谎报 | 轮询 180s 未终态时，如实提示「仍在运行（已 Ns），后台会跑完 —— 稍后到发布记录看结果」；既不假成功也不假失败 |
| 失败可见 | `status=failed` 弹「运行失败：<error_msg>」，错误来自后端真实异常 |
| 重启不留死任务 | `onModuleInit` 把遗留 `running` 判死并写原因「服务重启，本次运行中断」——否则前端会一直轮询永不终态的任务 |
| 组件卸载即停轮询 | `onBeforeUnmount` 置 `pollCancelled`，避免在已销毁组件上写 ref |
| 空体请求不踩 #428 | `runPipeline` 仍传 `{}` 而非 `null`（axios 把 null 序列化成裸 `null`，网关 strict 模式 400） |
| 权限收窄 | 运行按钮仅 `content:manage` 可见，未变 |
| 无裸色值 / 无 emoji / 无红线词 | 沿用 antd token；新增 `.run-tip` 只给下边距；无 R3 红线词 |

## 未覆盖（须人工复验）

- 真实运行耗时：本次只证伪了「10s 超时」，未测出端到端精确耗时（dev 上观察到从提交到入库约 30s）
- 轮询期间的体感：进度条每 2 秒跳一次，是否够用需 dev 上实际点一次
- 服务重启回收逻辑：`onModuleInit` 的批量 UPDATE 只在真实重启路径触发，本次未在生产触发过
- `run/recent` 接口已提供但前端未使用（页面暂无"最近运行"列表），留待后续接入

## 原型 → 实现的已知偏差

| 偏差 | 原因 | 处置 |
|---|---|---|
| 原型 6 秒给终态，实现按真实轮询 | 原型是演示节奏，真实运行 30 秒起步 | 接受：原型表达形态，实现表达事实 |
| 实现多了 `run/recent` 接口 | 为后续"最近运行"列表预留 | 前端暂不消费，无副作用 |
