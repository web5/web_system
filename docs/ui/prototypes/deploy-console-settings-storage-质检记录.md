## 一、设计决策记录

| 项 | 结论 |
|---|---|
| **目标端** | **桌面 Web**（deploy-console 深色控制台壳，1280×820）。非多端，无需分区 |
| 对齐对象 | 信息架构 + 交互细节（**高保真**）：真实文案、真实路径样例、可点击跳转与模拟时序 |
| 本次范围 | ① 把「系统设置」从**占位 generic 屏**升级为真实屏（顺带修掉与代码的漂移）；② 新增「存储配置」区块 |
| 与落地对齐 | 「通知与审批」字段按 `apps/deploy-console/src/views/SystemSettings.vue` 现有内容还原（通用 Webhook / 企业微信 Webhook / 需审批环境） |
| 主操作 | 每个卡片各 1 个主操作用各自的保存按钮；「存储配置」的保存为 **primary**，「通知与审批」的保存为次要按钮（避免同屏 2 个 primary 打架） |
| 双值语义 | 「**当前生效目录**」= upload-service 启动时采纳的内存值（`GET /internal/storage/path` on 6008）；「**待生效目录**」= 权威配置值（`GET /api/admin/settings/storage`）。两者不同 → 徽标「待重启生效」+ warn 条，说清「重启生效、不做热切换」 |
| 选择方式 | **目录树为主 + 文本输入兜底**（design §1.4 已定）：树选择需 `storage:browse`（仅 super_admin）；非超管或 `storage.browse_enabled=0` 时树按钮**禁用并说明原因**，自动落回文本输入 |
| 校验前置 | 保存按钮**默认禁用**，需先「校验」通过（文案随状态变化）。越界 / 不可写 / 非目录 → 禁止保存；**「目录不存在」允许保存**（PUT 会自动 `mkdir -p`），文案显式说明 —— 与后端实现一致 |
| 目录树约束的可见化 | 只列目录不列文件、截断提示（前 200 项）、「解链后越界的符号链接会被跳过」写在树脚注，避免评审以为能当文件浏览器用 |
| 状态演示条 | 右上 `[原型] 状态演示`（9 态）**是原型工具，不是产品功能**：用于走查状态矩阵（真实产品里不存在这个控件） |
| Token 纪律 | 本区块新增样式**全部引 `--ws-*` 变量**，变量名/值对齐 `packages/ui/src/tokens.ts` 的 **`roles.light`**；文件里旧稿的裸 hex 属历史遗留，按需分批迁移（未在本次一次性重写） |

### 本轮修正记录（两处自查发现）

1. **配色口径修正（原误用深色 token）**：A6 首次落地时把 `--ws-*` 取成了 `roles.dark`，渲染出来是「白页面里几张黑卡」。
   排查后确认：**本原型自 #107（`65c00a9`）起整稿亮色** —— 文件第二个 `<style>` 块里就有一段
   「亮色主题覆盖（原深色硬编码 → 对齐 admin 浅色体系）」，把 console 壳与公共组件统一覆盖为浅色。
   已改为 `roles.light`，并把「白底上的橙色文本」改用 `--ws-brand-600`（`#EA580C`，满足 design-system G4：
   纯品牌橙 `#F97316` 在白底对比度不足，不得作正文/链接色），primary 按钮文字用 `--ws-on-brand`。
2. **撤掉重复的覆盖层**：修正过程中曾顺手加了一段「内容区亮色」覆盖，与 #107 的既有覆盖**重复**
   （同权重时后置样式块本来就会赢），已删除，避免出现第三套覆盖层。

### 与落地的一处口径差异（记为后续巡检项，不阻塞 A6）

- **落地** deploy-console（`apps/deploy-console/src/style.scss`，2026-09-03 裁决）：**外壳固定深色反白面板** + 内容区随 antd 主题（默认 light）。
- **本原型**：自 #107 起**整稿亮色**（含侧栏/顶栏）。
- 即：评审看稿时「外壳颜色」与落地不同。这是原型侧的历史口径/有意简化（评审关注信息架构与交互），
  若要严格对齐，需另立一轮「原型外壳配色巡检」（全稿级改动），**不属 A6 范围**。

### 另：admin 侧「存储配置」的去留（用户 2026-09-22 决策）

`apps/admin` 的「系统设置」里有一个 **`storage` tab（存储配置）**：存储方式（本地/OSS）、Bucket、Region、
AccessKey/SecretKey、上传大小限制。核查结论 —— 它是**未接线的空壳**：

| 核查项 | 结果 |
|---|---|
| 后端是否读取它写的键（`storage_type` / `storage_bucket` / `storage_region` / `storage_access_key*` / `storage_max_upload_mb`） | **零引用**（全仓 `servers/`、`packages/` 均无命中） |
| 配置表里是否有这些键的值 | **零条**（`web_system.system_configs` 里仅有 A2 写入的 `storage.upload_dir`） |
| 实际生效的上传限制 | upload-service 的 `CATEGORIES` 代码常量（2/5/10MB），与这个 tab 无关 |

→ **用户决定：去掉 admin 侧的「存储配置」**，真正生效的「上传根目录」统一放在 deploy-console 系统设置。
落地范围与注意事项见 `specs/backend-consolidation/page-spec-storage-config.md` §admin 侧处理。
