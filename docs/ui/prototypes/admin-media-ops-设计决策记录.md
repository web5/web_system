## 二、本次原型要确认什么

对应用户三条需求：

1. **触发采集结果不友好**（截图：弹窗里吐原始 JSON `{"status":"unknown","reason":"未注册采集器类型: arxiv"}`，看不出成没成功）→ 原型 S2 触发弹窗改造
2. **缺少「明细」与「公众号成文」两个确认交付的视图** → 原型新增采集明细（S4/S5）、公众号成文（S6）
3. **菜单按功能拆二级、编辑开新页面** → 原型侧边栏重组（S1 所在模块）与编辑页（S3/S8）

**追加需求（14:20）**：编辑采集源页加「测试采集」——试采数据当前流程可见，**不入库**真实采集记录 → 原型 S3 编辑页新增试采面板（D8/D9）

## 三、信息架构（页面清单 + 跳转）

```
侧边栏「自媒体运营」sub-menu（替换原单页「内容采集源」，风格对齐 Agents sub-menu）
│
├── 采集源管理        /content/sources          列表；行内 触发(弹窗)/编辑(→新页)/删除(二次确认)
│    └─ 编辑/新建      /content/sources/new|:id/edit   新页面（原弹窗改为整页）
├── 采集明细 ★新      /content/items            筛选 + 质量归因列表
│    └─ 明细详情 ★新   /content/items/:id        质量归因流程条 + 摘要 + meta + 发布记录
├── 公众号成文 ★新    /content/publications     发布记录列表 + 成文预览抽屉
├── 发布管线          /content/pipelines        列表；编辑/新建为新页面（原 Tab 改独立页）
└── 采集监控          /content/runs             健康度 + 批次记录（原「采集记录」Tab）
```

跳转闭环：每个列表页都有返回路径（面包屑 / 返回按钮）；触发结果卡内嵌「查看采集明细」「前往发布管线」等下一步入口；详情页发布记录可跳转成文列表。

## 四、关键设计决策与取舍

| # | 决策 | 理由 | 备选 |
|---|---|---|---|
| D1 | 模块改名「自媒体运营」，五功能平铺为二级菜单 | 原单页三 Tab 已装不下新功能；与 Agents sub-menu 风格一致；「采集源」只是功能之一，叫模块名以偏概全 | 保留「内容采集源」为组名 —— 若用户偏好原名可回退 |
| D2 | 触发保留弹窗，结果区友好化 | 触发是动作不是表单，弹窗内就地看结果最顺；编辑才是表单，按用户要求改新页面 | 触发也改新页面（信息密度低，不推荐） |
| D3 | 结果卡五态：成功 / 类型未接入 / 空结果 / 失败 / 运行中 | 直接覆盖截图的 unknown 与真实世界的失败/空/并发态；技术原文折叠进「技术详情」不丢 | 只显示成功失败两态（丢失可定位性，否） |
| D4 | 明细质量列展示 `ok/partial/fail/skip` + 归因阶段子标签 | 复用 content_items 已有的 quality_status/quality_stage 字段，让「卡在哪一步」一眼可见 | 只显示 status 状态机（信息不足） |
| D5 | 成文预览用右侧抽屉（只读） | 预览是查看不是编辑，抽屉不丢列表上下文；成文正文按公众号文章样式渲染 | 预览也开新页面 |
| D6 | 采集源列表新增「最近采集」列 | 直接回答「这源还活着吗」；arxiv 行演示失败态（08-24 网络故障实况） | 不放列表，去监控页看（多一跳） |
| D7 | 采集明细统计行（今日新增/去重/质量异常/进入成文） | 让明细页自带概览，不用先看监控页 | 无统计行 |
| D8 | 编辑页「测试采集」：结果面板内嵌表单下方（非弹窗/抽屉） | 试采要与 config 对照着看，同屏不丢上下文；面板带「仅预览 · 未入库」徽章常驻提醒 | 结果也开抽屉（多一层关闭成本） |
| D9 | 试采测的是**当前表单配置**（含未保存修改） | 「先测后存」是自然工作流；若只测已存配置，用户得先保存再测，失败配置已被落库 | 只测已存配置 |

## 七、独立交互质检结论（ux-review-checklist）

**通过**：
- A 信息架构：8 屏齐全，入口/返回路径完整，无死链；层级 ≤3

## 十、并入 admin 整合稿（2026-10-22）

> 背景（产品意见）：「设计出来的原型需要统一融合进 admin 的原型稿里，目前是散落的」。
> 此前本稿落在 `apps/admin/prototype/` 下，与整合稿 `admin-agents-hub.html` 互不相通 ——
> 评审要看两份稿，改一处要记得改两处。

### 10.1 三条硬约束（决定了技术上必须这么做）

| # | 约束 | 后果 |
|---|---|---|
| C1 | **不能按菜单页拆 DOM** | 模块内二级页之间有跨根键跳转：明细详情 →「去『公众号成文』查看」、成文空态 →「前往发布管线」。拆成 5 份后，目标 `section` 在别的屏里、被 hub 隐藏，点了什么也不会发生 |
| C2 | **不能带自己的评审台进 hub** | 控件写 `location.hash = '#s=<key>'`，而 hub 的 hash 是它自己的路由（`#/content/items`）——切一次场景包，hub 就被踢回默认屏 |
| C3 | **不能带自己的壳进 hub** | 壳与菜单的唯一真相源是 `BasicLayout.vue` → `proto-shell.mjs`；第二份壳 = 第二真相源（2026-10-15 已裁决过同型问题） |

### 10.2 落地方式：`mount` 源（一份 DOM 服务 5 页）

| 项 | 做法 |
|---|---|
| 稿的位置 | `docs/ui/prototypes/admin-media-ops.html`（与其它原型同目录；`PROTO_DIR` 只认这一个目录） |
| 注册表登记 | `scripts/lib/proto-registry.mjs` → `SRC_MEDIA`，`mount.screens` 把 5 个 hub 屏映射到模块根键：`content-sources→sources` / `content-items→items` / `content-publications→publications` / `content-pipelines→pipelines` / `content-monitor→runs` |
| DOM | **整块一份**，容器 `data-zm-module`；切菜单时 hub 把这块 `appendChild` 到当前屏，再调 `ZM.go(根键)` |
| 状态机 | 一份（IIFE + `ns:'ZM'`，inline handler 改写为 `ZM.xxx()`） |
| CSS | 作用域隔离到 `.zm-scope`（本稿类名是裸通用名且与 hub 大面积重叠：`.btn/.card/.page-head/.screen`…）；`:root` 私有 token 转成 `.zm-scope{…}`，**不并进整合稿全局** |
| 弹层 | `trails` 多段抽取：手动触发弹窗 + 成文预览抽屉 + `#toast`（这三块挂在 `.content` 之外） |
| 图标库 | `sprite`：`<svg><symbol id="i-*">` 在 body 顶层，不抽就是整稿图标全空 |
| 评审台 | `jsDrop` 按 `DEMO-PANEL-START/END` 整段丢弃；本稿对它的两处调用都做了 `typeof` 守卫（独立打开照常生效） |
| 模块内跳转 | `go()` 末尾调 `window.zmSync(key)` → hub 换屏 + 菜单高亮 + 地址栏同步（子页映射到父屏，如 `item-detail → content-items`） |
| 屏容器命名 | **保留 `.screen`**，但 `go()` 改成按 id 精确操作（`SCREENS[k].el`）—— hub 的屏容器也叫 `.screen`，用类选择器会互相误伤；hub 侧也把 `qsa('.screen')` 收紧成 `qsa('.screen[data-screen]')` |
