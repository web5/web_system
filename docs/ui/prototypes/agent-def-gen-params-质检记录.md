## 0. 先回答四个指定问题（结论先行）

### Q1 状态矩阵覆盖情况

| 状态（规格 §3） | 覆盖 | 说明 |
|---|---|---|
| 默认（未配置，null=沿用默认） | **部分** | 列表第 3 行有「全部沿用默认（未配置）」，但**弹窗里没有对应的全 null 视图**；且 inTemp/inMax 清空后因无 placeholder 反而看不出「未配置」（见 #4、#9） |
| 已配置 | 是 | 0.7 / 2048 / 思考沿用，回填正确（`?? 0.7` 已修） |
| 互斥禁用 | **部分** | 视觉置灰有，但**值未清空且不可见**，见 #1 |
| 思考=开启展开 budget | 是（仅展开） | extra 不联动、预算值域说明缺，见 #6、#8 |
| 校验失败 | **不合规** | 只有 2.6s toast + 前端自造文案，无字段级错误态、未演示后端原文，见 #3 |
| 保存中 | **缺失** | 无 loading、无重复提交锁，规格明确要求却没做，见 #2 |

**遗漏的格子**：保存中（规格内）、加载中/回填失败（规格外但属 B 类异常分支）、保存失败(网络/500)、无权限只读、模型不支持 thinking 的禁用态、"有未保存改动就关闭"的二次确认、以及与 C7-c 相关的「thinking null 实际落到 env/客户端推断」这一语义分支。

### Q2 「Temperature / Top P 二选一」是否真能防住（逐路径推演）

脚本三段相关：`toggle()` 只做 3 件事——切 `.off` 类、`input.disabled`、换 extra 文案，**从不碰 `input.value`**；`saveBtn` 里有 `if (t && p)` 兜底。

| 路径 | 结果 |
|---|---|
| 默认 Temperature 态直接保存 | ✅ 通过（t=0.7, p=''） |
| 切到 Top P 后只填 Top P，保存 | ❌ 拦下。但 t 仍是被隐藏的 0.7 → 报错文案不指名字段，且**唯一解法是去点一个看起来被禁用控件上的「清空」** |
| 切到 Top P 后**什么都不填**就保存 | ⚠️ **静默成功但不符合用户意图**：用户以为自己在配 Top P（界面把 Temperature 灰掉了），实际落库仍是 `temperature=0.7, topP=null` |
| 填了 A → 切到 B → 再切回 A 改值 → 保存 | ❌ 拦下，同样不知道该清哪个 |
| Temperature 填 0.8 → 套预设（写 inTemp / 清 inTopP）→ 切 Top P → 填 Top P → 保存 | ❌ 拦下，形成最坏组合 |

**结论：后端语义没被绕过**（`if (t && p)` 无论 disabled 与否都读到残留值），所以不会出现"后端拒绝、前端显示成功"。真正的问题不是被绕过，而是**「冲突源不可见」+「报错不给解法」**：这是用户侧的事实性失败。#1 定阻塞。

### Q3 「清空 = 沿用默认」语义用户看得懂吗

**看不懂，而且漏了最关键的一帧**：`inTemp`、`inMax` 这两个 input **根本没写 placeholder**（只有 `inTopP` 有）。点「清空」后变成完全空白的输入框，用户无法区分"没填/会存成 0"还是"沿用模型默认"。按钮词「清空」也只描述动作不描述后果。建议改成「沿用默认」+ 清空后**动态补 placeholder / 显示灰字 chip**，并把 extra 翻成确认句。详见 #4。

另注意：`null` 在 thinking 上并不等于"模型默认"——按 C7-c 实际落到 `env TOKENHUB_THINKING` 或客户端按模型推断。所以「沿用模型默认 / 沿用客户端默认 / 沿用默认」三种叫法不是笔误，是语义不统一，必须先定口径（#7）。

### Q4 预设套用的反馈够不够

**不够**：select 选完立即 `value=''`，只剩 2.6s toast；没有留存痕迹、不能重复确认、**不能撤销**、覆盖已有配置无二次确认。而且预设无视当前采样模式，一律写 `inTemp` 并清 `inTopP`——在 Top P 模式下套用会把值写进那个灰掉看不见的框。详见 #5。

## 一、阻塞（必须修完才能交确认）

### B1 · 互斥切换后残留值不可见，报错无解法 —— 用户侧「拦得住修不了」

- **位置**：`admin-agents.html:494-515`（seg + 两个 ctrl）、`toggle()` `:577-580`、save 校验 `:615-621`
- **现象**
  1. `toggle()` 从不触碰 `input.value`：从 Temperature 切到 Top P，`inTemp` 被 disable 但值 `0.7` 保留；
  2. 该值用 `.ctrl.off` → `color: var(--ws-text-disabled)` = `#D4D4D4`，底 `--ws-bg-subtle` = `#F2F2F2`，**对比度约 1.3:1，肉眼基本看不见**；
  3. 用户在 Top P 里填 0.9 后保存 → `if (t && p)` 触发 toast「Temperature 与 Top P 只能填其一」，但文案**不指名字段、不给解法**；用户看遍全屏找不到那个冲突值；
  4. 唯一解除手段是点 `.ctrl.off` 上那个「清空」——而父级 `cursor:not-allowed` 与 `.clear{cursor:pointer}` 自相矛盾，且并无任何提示告诉用户可以这么干；
  5. 若在切到 Top P 后**什么都不填**直接保存 → toast「已保存」成功，实际落库 `temperature=0.7, topP=null`，与用户"我要配 Top P"的意图相反（Q2 第 3 行）。
- **建议修法**（三选一，推荐①）
  - ① **切换即置 null**：切到 B 时把 A 的 value 清空 + 动态加 placeholder「沿用模型默认」，并在 extra 回显「已清空 Temperature（与 Top P 互斥，只保留其一）」；
  - ② 若坚持保留可回滚，则禁用态必须用**可读配色**（≥ `--ws-text-secondary`，对比度达标）+ 明确占位提示；报错必须落到**字段级**（红边 + 行内文案写清字段名与当前值）+ 报错条上给「清空 Temperature」的一键按钮；同时统一 disabled 项下「清空」的可点性与 cursor；
  - ③ **规格补一条**（比 UI 更硬）：切换采样策略时另一项必须置 null，提交前按 mode 裁剪 payload，避免实现时被 `v-model` 的 disabled 值偷带走。

### B2 · 「保存中」态缺失，重复提交未锁

- **位置**：`#saveBtn` `:615-621`；规格 §3「保存中：按钮 loading，防重复提交」
- **现象**：点击后立刻弹成功 toast，按钮无 loading、无 disabled；连点 N 次 = N 次提交 + N 条相同 toast（成功 toast 与错误 toast 视觉几乎一样）。D 类「重复提交被锁」不合格。
- **建议修法**：保存 → 按钮 `disabled` + 文案「保存中…」，模拟 ~800ms；顺带演示一次「保存失败」（toast 用错误样式 + 后端中文原文），让三条分支（成功/校验失败/网络失败）在主路径上都能点到。

### B3 · 校验失败的呈现违反规格 §3/§4，且剿了后端的判据权

- **位置**：`:615-621`、`:623-629`；规格 §3 校验失败行、§4 前后端分工
- **现象**
  1. 前端自己判了值域（1–32768）并**自撰文案**「输出上限须为 1–32768 的整数」——规格明确要求「**前端只做预防性禁填，报错文案一律用后端返回的中文**」，这里属于在前端重造判据（原型一旦这么演示，实现极易照抄）；
  2. 全表单**没有任何字段级错误态**（无红边、无行内红字），只有整屏 2.6s 后自动消失的 toast；
  3. 成功/错误仅靠 6px 圆点颜色区分（白字深底同一种样式）——**纯颜色编码**，F 类不合格；toast 无 `role="alert"`，读屏不播报。
- **建议修法**：① 原型里的值域自判要么删掉，要么就地标注「仅演示，实现以 `assertTuningParams()` 返回为准」；② 演示一条**后端中文原文**的落地形态（`message.error` + 字段红边 + 行内文案常驻到用户改值为止）；③ toast 加图标 + 前缀区分（「保存失败：…」/「已保存：…」）+ `role="alert" aria-live="assertive"`。

## 二、重要

### I1 · 「清空」后的空框没有任何语义提示（Q3）

- **位置**：`:503 / :511 / :523` 清空按钮、`:592-594` handler
- **现象**：`inTemp`、`inMax` 无 placeholder，清空后是彻底空白的输入框；用户无法判断"这算没填还是会用默认值"。`inTopP` 有 placeholder，三者口径又不统一。
- **建议修法**：清空时动态写入 placeholder「沿用模型默认」（或在控件内渲染灰字 chip）；按钮文案从「清空」改为「沿用默认」+ `title="清空该值 = 保存为 null，运行时由模型侧默认值决定"`；清空后 extra 翻为确认句「已设为沿用模型默认：具体值由模型/服务端决定，不在后台锁死」。

### I2 · 预设套用：无留存反馈、无撤销、会写穿禁用控件（Q4）

- **位置**：`:605-613`
- **现象**
  1. `e.target.value = ''` 让 select 回到「— 选择 —」，toast 2.6s 即逝 → **用户无法回头确认刚才套的是哪个档位**；
  2. 覆盖已有自配值前**无二次确认、无撤销**，且 preset 控件放在分组标题右侧（误触风险位）；
  3. 无视当前采样模式，**一律写 `inTemp` 并清 `inTopP`** —— Top P 模式下套预设，值被塞进那个灰掉看不见的 Temperature 框，界面仍显示"我在配 Top P"，与 B1 叠加成最坏情况；
  4. 所有档位都不喂 `topP`，但 §7.4 里"创意/文案"明文写的是「或改 topP 0.95」→ Top P 控件在预设路径上永远够不着。
- **建议修法**：① select 保留选中值，或在该区显示常驻 chip「已套用：对话 · temp 0.7 / max 2000 / 思考沿用」+「撤销套用」；② 目标字段非空且与预设不同 → 二次确认「将覆盖 Temperature=0.8 / 输出上限=2048」；③ 写值时跟随当前采样模式（Top P 模式就写 topP），并给「创意」档提供 topP 0.95。

### I3 · 思考三态的 extra 不联动，且暴露实现字段

- **位置**：`:529-535`、`:583-589`（脚本只切 `budgetRow.hidden`，不动 `#exThink`）
- **现象**：`#exThink` 恒定显示「type=disabled / enabled 由后端下发，null = 沿用客户端默认」，选「关闭」「开启并限预算」都不变。`type=disabled/enabled` 是实现字段名，不是用户语言；用户也无从知道「关闭」= 无思维链直接作答。
- **建议修法**：三态各配 extra——沿用默认 / 关闭「不产出思维链，直接作答（省 token、降延迟）」/ 开启「先消耗思考预算再出正文，与输出上限共享预算」。

### I4 · 「沿用模型默认 / 沿用客户端默认 / 沿用默认」三个口径并存

- **位置**：`:505 / :513 / :525 / :534` extra、`:530` 思考按钮「沿用默认」、`:443` 列表「全部沿用默认（未配置）」
- **现象**：同一个 null 语义三种叫法；更麻烦的是**它们也不真的是同一个语义**——按 C7-c，thinking 的 null 落到 `env TOKENHUB_THINKING` 或客户端按模型推断，并非"模型默认"。所以这是语义不统一，不是错别字。
- **建议修法**：先拍一个口径（建议统一「沿用默认」，悬停/问号解释：temperature/topP/maxTokens → 模型侧默认值；thinking → 由服务端环境或客户端按模型推断，见 C7-c）。若业务上确实两个来源，就在 UI 里显式标注来源，不要让用户自己悟。全文（列表 chips、extra、radio 文案）同步。

### I5 · 思考预算行：隐藏≠清空，且缺失值域/清空入口

- **位置**：`:537-545`
- **现象**：与 B1 同类 bug——`budgetRow` 只是 `display:none`，`inBudget` 的 `1024` 仍在 DOM/模型里；思考三态切回「沿用默认」后这个值如果随 payload 提交，就变成 `type:'inherit' + budget_tokens:1024`，正好是后端会拒的组合。此外该控件没有「清空」（与另外三个数值控件不一致），extra 只有共享预算警示，**没有值域、没有"留空=沿用默认"**。
- **建议修法**：切换三态时对 budget 做 null 化（或提交前按 thinking 类型裁剪）；补齐 extra「整数 N–M；留空 = 沿用默认」；与其它数值控件保持一致的清空入口；补一条校验演示：`budget_tokens` ≥ maxTokens 时展示后端报错原文。

### I6 · 「默认（未配置）」这一格没有演示，也没有整组重置

- **位置**：整个生成参数区（`:476-550`）vs 列表 `:443`
- **现象**：列表第 3 行写着「全部沿用默认（未配置）」，但弹窗唯一示例开局就是 `temp 0.7 / max 2048 / 思考沿用` 全填满——「全 null 的弹窗长什么样」没有 Corresponding 视图；而要把一组从已配置改回未配置，得逐个点 4 次清空。
- **建议修法**：加一组视图切换（未配置 / 已配置 两份快照），或在分组标题右侧加「全部恢复默认」入口（带二次确认）。

## 三、建议

- **S1 · 未定义项未标注（清单 I，静默发明）**：① thinking 是否按所选模型动态禁用（规格 §5.1 待澄清；第 3 行就是 hy3）—— 原型里三态对所有模型一律可点，应在控件旁打 ⚠ 标注；② 列表 chips 超宽是否截断为「+N」（规格 §5.3）未标注；③ 成功 toast「已保存（草稿），发布后运行时生效」凭空引入了「草稿/发布」概念，全稿无此流程，属自行发明的降级行为——要么删，要么标注待确认。
- **S2 · 提交内容完全不可见**：整份原型没有"这次到底提交了什么"的展示。建议加一块 **payload 预览**（`{ temperature: 0.7, topP: null, maxTokens: 2048, thinking: { type: 'inherit' } }`），随操作实时更新——一次性解决 B1/I1/I5 的可验证性，也是给 rd-execute 的验收锚点。
- **S3 · 值域/步长提示不全**：Temperature 只有控件内「0–2」且无 step；Top P **完全没有值域标识**（选中后 extra 只说"建议 0.9–0.95"）；maxTokens 有范围但没说整数。规格 §1 要求 0–2/step .1、0–1/step .05、整数 1–32768，建议统一进 extra。另 §7.4 的**推理模型例外**（思考模式下 temperature 不生效、top_p 被钳在 0.95~1.0）在 UI 任何处都没提示，建议在「note」或 Temperature extra 补一句。
- **S4 · 视觉一致性**：① 同弹窗内两个 radio group 选中态不一致（采样=品牌橙 `.on` vs 思考=灰底 `.on.plain`），规格 §2 说选中态走 `--ws-brand-500/600` → 建议统一；② 屏②用 `✕ ▾ ●` 文本符号，屏①用内联 SVG，同文件两套语言；③ **裸值出现在 `:root` 之外**（清单 E 不合格）：`.toast{color:#fff}`、`.btn.primary:hover{color:#fff}`、`.avatar.ai{color:#fff}`、`.mask{rgba(23,23,23,.45)}`、`.ad-desktop{rgba(20,30,50,.14)}`、`.toast box-shadow{rgba(0,0,0,.18)}` → 建议补 `--ws-overlay` 并复用 `--ws-on-brand`；④ `.extra/.chip/.clear` 的 11.5px 低于 12px 基值；`--ws-text-tertiary #A3A3A3` 在白底约 2.6:1，小字辅助文案不达标（token 层问题，会波及全库）。
- **S5 · 键盘/语义基线（清单 F，原型阶段可仅标注）**：「清空」用 `<span>` 不可 Tab 到达；`.seg` 无 `role="radiogroup"` / `aria-checked`；toast 无 `role="alert"`；preset select 无 `aria-label`。
- **S6 · 退路缺失（清单 A 无死链）**：弹窗 `✕` 与「取消」按钮绑定了 `cursor:pointer` 但**无任何行为**，列表三行「编辑」也不可点。建议至少做成「无改动直接关 / 有改动走二次确认（后果写明：将丢失本次生成参数改动）」，或就地标注为静态占位，避免评审时被当成真 bug。

## 四、总结

这份稿的**方向与信息架构是对的**：分组位置、字段粒度、列表 chips、档位参考都与规格和 C7 契约对齐，`?? 0.7` 的违规回填也确实修掉了。但作为交互稿它现在输在一个点上——**「看不见的状态」太多**：

互斥切换后残留的值看不见、清空后的空框没有语义、预设套用过后的痕迹看不见、隐藏的思考预算值还在、null 到底"沿用谁的默认"三处口径不一致。这些都不是视觉问题，是用户会在真实操作里踩进去的坑；其中 B1 尤其危险，因为它在质检意义上"后端不会被绕过"，却在体验上等于**拦住了但修不了**，还有一条静默成功路径（什么都不填就保存）。

另外两条是硬伤：规格明确要求的「保存中 loading + 防重复提交」没做；校验失败落的却是前端自造文案与自造判据，直接违反规格 §4「不许在前端重造判据、报错一律用后端中文原文」。

**修完 B1–B3 + I1/I2/I5 即可复检**；S2（payload 预览）强烈建议一并加，它是把 B1/I1/I5 从"纸面对齐"变成"可验证"的最低成本办法。剩余建议项不阻断交用户确认，但应在稿上显式标注后再呈递。
