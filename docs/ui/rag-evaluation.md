# AI 文档读取架构决策 · 是否需要自建 RAG

> 版本：v0.1（草稿）｜ 日期：2026-09-03 ｜ 状态：已定（不建，触发条件重估）
> 场景：docs/ui 规范文档 + 加载链（RULE.mdc / CODEBUDDY.md / skill）持续增长时，AI 如何高效读取。
> 关联：`README.md`（读取地图 = 现采用的确定性入口方案）。

## 1. 结论

**现阶段不需要自建 RAG**。以"读取地图 + 按需最小集 + AI 原生检索"替代，成本近零且足够。

## 2. 判断依据（RAG 前提 vs 本项目事实）

| 维度 | RAG 的前提假设 | 本项目事实（2026-09-03） |
|---|---|---|
| 文档量级 | 上千份、无法穷举入口 | docs/ui 现 7+2 份，全读 ≈ 1-2 万 token |
| 入口是否可枚举 | 开放问答，不知道对应哪份 | 可枚举：任务 4-5 类，README §2 一张表穷尽 |
| 检索手段 | 需外部向量库 | CodeBuddy AI 原生 `read_file` / `search_content`（对仓库文件即精确检索器） |

## 3. RAG 解决 / 不解决的问题

- ✅ 解决：跨海量文档的**语义相关度召回**（"不知道知识在哪"）。
- ❌ 不解决本项目真正痛点：
  1. **执行一致性**（找到规范不遵守）→ 靠动作门 + 规则 + 走查清单（`design.md` §0/§5）；
  2. **文档间漂移**（两份说了不算话）→ 靠单事实源 + 同步责任表（`README.md` §3）。

## 4. 替代方案（现采用，按性价比排序）

1. **README 读取地图**：确定性入口，一张表穷尽任务 × 最小文档集（已建）。
2. **AI 原生检索**：跨文档找细节用 `search_content` 定向 grep（如 hover 色 → `grep --ws-bg-*`）。
3. **文档收敛优先于检索**：历史任务文档归档（`archive/`）、重复内容去重——整理永远比检索便宜。
4. **用户裁决沉淀**：CodeBuddy Memory / 评审回流（`geist-token-评审记录.md`），而非外部 RAG。

## 5. 何时重估（满足 ≥2 条再议 RAG）

- [ ] 规范文档 > 30 份且跨多个独立主题域（UI/后端/安全/业务规则混合），规则文件无法穷举入口
- [ ] 提问模式为开放问答（"这个需求违反哪条规范？"），而非固定任务流
- [ ] 文档高度动态且需**全文语义**检索（路径/关键词定位不了）
- [ ] 已有现成 RAG 基建可接（不新建）

|---|---|---|---|
