## P0 · 尽快做（防止同类问题再炸）

### P0-1 环境配置治理 `[~]`

**问题**：
- 根 `.env.production` 与各 `servers/*/.env` 多份配置，变量名不一致（`MYSQL_*` vs `DB_*`、`AUTH_SERVICE_URL` 端口 3001/6001 混用）
- 新增配置项（`INTERNAL_API_KEY`/`USER_SERVICE_URL`/`MYSQL_USER`/`DEPLOY_*`）无人同步到 dev/prod → 静默配错
- `ConfigModule` 不覆盖 process.env 已有变量，空值/错值会污染

**动作**：
- [x] 生成根 `.env.example` 全量变量模板（含用途注释、适用服务、示例）
- [ ] 各服务生成 `.env.example`（从现有 `.env` 提取变量名）
- [x] `scripts/check-env.sh`：对比 dev/prod 关键变量差异 + 空值检测
- [ ] 服务启动时 ConfigModule validation（缺必需变量直接启动失败，不再静默）

### P0-2 双库 Schema 同步 `[ ]`

**问题**：dev 本机 MySQL 与 prod 腾讯云 MySQL 两套库，schema 变更常漏（users/conversations/mcp_* 表补列反复发生）。

**动作**：
- [x] 把 08-21 所有手工 `ALTER TABLE` 汇总成 `scripts/sync-schema.sh`（幂等，dev/prod 已执行对齐）
- [x] `scripts/sync-schema.sh <dev|prod>`：对两库执行同一份 SQL（已实际执行，dev 补齐缺口）
- [ ] 新增迁移必须同时落到 dev/prod（写进部署 checklist）

### P0-3 一键部署脚本 `[ ]`

**问题**：prod 手动部署（非 git），build→打包→上传→依赖安装→pm2 reload 全手工，依赖缺失反复。

**动作**：
- [x] `scripts/deploy.sh <env> <service>`：build → 打包 → 上传 → 依赖修复 → pm2 reload（DRY_RUN 预览）
- [ ] 依赖完整性校验：检查 `@web-system/*` 链接、关键 node_modules 存在性
- [x] `scripts/health-check.sh`：端口/接口/MCP/进程巡检（dev/prod 实测通过）
