# 合同翻译官 · 护城河与重点建设指南

> 版本：v1.0 · 2026-08-26
> 定位：作为产品的**战略建设指南**，明确什么值得投入、什么是护城河、按什么优先级建设。

---

## 一、产品定位一句话

> **签字前的 AI 翻译官** —— 只解读、不推荐。
> 把"律师/理财师才看得懂"的合同翻译成大白话，用**法定标准（尺子）**识别"可主张权益"，告诉用户能要回什么、怎么做。

## 二、护城河的本质判断

**最容易被做成的样子**：一个"套壳 LLM 的合同翻译器"——那没有任何护城河，任何有 API key 的人都能做。

**真正的护城河**：**不来自大模型**，而来自三样"模型做不了、也抄不走"的东西。

| 层面 | 是什么 | 抄得走吗 | 依赖 |
|------|--------|---------|------|
| 大模型（DeepSeek/混元） | 翻译、定位条款 | ⚠️ 任何人都有，非护城河 | 现有 ai-service ClientRegistry |
| **法定标准库（尺子）** | 利率上限/砍头息/违约金30%/定金20%/犹豫期/免责提示/强制搭售/自动续费 | ❌ 难抄，需持续跟进监管与司法口径 | 内容工程 + 监管知识 |
| **精确计算模块（IRR）** | 真实年化利率、费用测算 | ❌ 必须 100% 准，纯规则实现 | 数学 + 严格测试 |
| **内容资产（话术库）** | "条款→大白话"映射 | ❌ 核心积累，靠逐条打磨 | 文案 + 判例对照 |
| **数据飞轮** | 历史合同标注、命中率反馈 | ❌ 越用越准、越用越贵 | 用户反馈 + 标注体系 |

> 一句话总结护城河：
> **护城河 = 一本"能算准的尺子书"（标准库）+ 一本"说人话的话术库"（内容映射）+ 一个"越用越准的反馈飞轮"（数据标注）。**

## 三、核心难点与重点（按优先级排列）

### 🥇 难点 1：把"专业条款"翻译成"看得懂、算得出"的大白话 —— 内容资产
**最核心、最难、最护城河**的部分，也最容易做浅。

- **难在**：一个条款（如"利息不得预先扣除"）有**多个可感知变体**（砍头息、服务费前置、保证金抵扣…），要让 AI 全部识别出来，靠的不是一个 prompt，而是一套**结构化标准库 + 判定规则 + 话术模板**。
- **护城河**：这套映射库是**逐条打磨 + 对照司法判例**沉淀出来的，竞品难以在短时间内达到同等覆盖度与准确率。
- **建设重点**：`contract-standards` 标准库，每个标准 = `{ 识别特征(规则/正则), 法定依据(条文), 用户话术模板, 严重度, 3步操作 }`。

### 🥈 难点 2：IRR 等金融计算的"100% 准确"
**能用规则算的绝不用 AI 算**，成本测算必须 100% 正确。

- **难在**：现金流复杂度（先息后本/等额本息/砍头息/提前还款违约金/逾期罚息叠加），IRR 牛顿迭代必须收敛正确，且处理边界（0 期、多解、提前终止）。
- **护城河**：**数字可信是生命线**。一旦算错一次，信任崩塌，比"翻译错"严重得多。
- **建设重点**：独立 `irr.ts` 纯函数模块 + 严格单测（**唯一必须 TDD 的模块**）。

### 🥉 难点 3：OCR 对"长合同、多页、拍照歪斜"的稳定性
保险条款、贷款合同多为 PDF 或多页拍照，识别质量决定后续所有环节。

- **难在**：微信 OCR 免费额度有限、适合短文本；长合同需腾讯云 OCR + 文档/拍照分场景调度 + 置信度处理。
- **建设重点**：OCR 分层（微信端轻量预识别 → 后端腾讯云精识别）+ 图片预处理。

### 难点 4：场景识别与"标准库"的正确匹配
先判断"消费贷还是购车贷款"，选错标准库则整个报告错误。

- **难在**：合同类型混装（一个文件既有借款又有担保），需**先分类、再按类套尺子**，并允许用户手动改场景兜底。

### 难点 5：合规红线在"产品机制"层面做好，而非靠人审
"只解读不推荐"是生存底线（金融牌照边界）。

- **难在**：AI 输出极易滑向"该不该买/哪个好"。需**在系统层约束输出边界**（Prompt 约束 + 后置规则过滤敏感表述）。
- **建设重点**：输出护栏 + 全程免责声明。

## 四、交互设计（已确认：方案 A+B）

> 已确认用户交互方案，原型见：`合同翻译官_原型_v3_风险信号.html`

**核心设计原则**：用户**不需要理解任何专业问题**，只看到"我的风险是什么、多严重、能要回什么、怎么做"。

1. **首页**：一键上传（不强迫选场景），下方"能查什么"科普卡
2. **上传页**：拍照/相册/文件 + 示例样本
3. **解读中**：4 步进度
4. **结果页 - 结论屏**：健康指数分 + 一句话大白话结论 + 可争取金额 + 最该注意的点
5. **结果页 - 风险信号列表**：按严重度排序，每条用"用户可感知现象 + 具体数字"命名（非专业条款名），点开下钻法律依据 + 3 步操作 + 术语解释
6. 底部 Tab：首页 / 历史 / 我的

**关键转换**：从"专业问题列表"→"风险信号列表"（用户视角的信号词）：

| 旧做法（专业问题） | 新做法（风险信号） |
|---|---|
| "是否构成砍头息？" | "借 10 万，到手仅 9.5 万" |
| "利率是否超 LPR 4 倍？" | "实际年化 36%，远超 24% 红线" |
| "违约金是否过高？" | "提前还款收 3% 违约金" |

## 五、护城河建设路线图

### 阶段一 · 地基（第 1-2 周）—— 先把"算得准"做扎实
- [ ] IRR 计算模块（100% 准，TDD 强测）
- [ ] 标准库 v1：覆盖 3 场景（消费贷/购车/医疗险）的 9 个核心尺子
  - 利率上限、砍头息、违约金30%、定金20%、犹豫期、免责提示、强制搭售、自动续费、格式条款

### 阶段二 · 内容护城河（第 3-4 周）—— 把"说人话"做厚
- [ ] 条款→话术映射库：每个尺子配套"风险信号命名 + 一句话大白话 + 3 步操作 + 术语解释"
- [ ] 输出护栏：Prompt 约束 + 后置过滤，锁死"只解读不推荐"

### 阶段三 · 数据飞轮（第 5-6 周起）—— 把"越用越准"做起来
- [ ] 用户确认机制：报告末尾"这条风险准不准？"反馈按钮 → 人工标注
- [ ] 命中率看板：统计每个尺子的识别准确率 → 回喂标准库

## 六、技术与合规红线（贯穿全程）

### 合规红线（文档要求，必须系统层实现）
- 全程声明"仅用于理解合同，不构成法律/理财/投资建议"
- 不做产品比较结论、不做"该不该买/哪个好"
- 出口引导"重大决策请咨询持牌专业人士"
- 数据加密存储、不入训练、可删除

### 技术铁律（遵循项目 CODEBUDDY.md）
- 标准库/常量收口到共享层，禁止各端拷贝
- AI 异步接口用 `API_TIMEOUT.AI_TASK`（180s）
- 所有输入用 class-validator DTO 校验
- 异常统一过滤器 + Logger，禁止 console.log
- TypeScript 严格模式，禁止 any
