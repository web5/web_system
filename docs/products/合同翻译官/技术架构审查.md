# 合同翻译官 · 技术架构审查报告

> 版本：v1.0 · 2026-08-26
> 审查对象：agent-core 三角色插件化演进 + 独立 ai-agent 服务

## 方案概述
> 将 AI 编排能力从 `ai-service` 抽离为独立 `ai-agent` 服务；`agent-core` 向 deepseek-harness 的"三角色能力（Definition/Provider/Consumer）+ 一切皆插件"演进，新增 MCP 远程 Provider；`ai-service` 瘦身为仅承载 harness 管理与业务。

## 审查依据（已确认现状）
- `ai-service`(3003) 现承载：AI 对话 chat / SSE 流式 / TTS / bianbian / artworks / agent(AgentModule)
- `agent-core`：`ToolDefinition` 接口统一、`ToolRegistry` 静态 Map、ReAct 循环、无 MCP 消费、已支持 OpenAI function calling
- `mcp-core` 基于 `@modelcontextprotocol/sdk`，是 MCP 服务端（无 client）
- gateway `/api/ai/*` → ai-service，SSE 需原生转发
- `shared` 已有标准库 + IRR 纯函数（阶段一地基）

---

## ⚠️ 风险项（必须解决）

### 风险1：存量 AI 能力的迁移边界未定义
"ai-service 不再承载 AI 相关能力"，但 ai-service 现有 chat / SSE 流式 / TTS / bianbian / artworks 大量存量 AI 能力。全部迁移是大手术，会动到全链路 + 部署。

**解决：阶段化拆分。** 新建 `ai-agent` 只承载新增 agent 编排能力（合同风险等增量场景）；存量 chat/TTS/bianbian 短期留在 ai-service，评估后再迁。

### 风险2：agent-core 改造的向后兼容
`agent-core` 被 `kedou-agent`（CLI）和 `ai-service`(AgentModule) 共同消费。ToolRegistry 静态 Map → 可插拔解析层，必须保证现有消费者不破。

**解决：** 抽象层做增量扩展而非重写，保持 `register/get/execute/toSchemas` 接口稳定，先加 `resolve()` 钩子。

### 风险3：三角色能力的过度设计
deepseek-harness 官方明确"不要预先拆分"。IRR/规则是纯本地能力，无本地↔远程切换需求，拆三角色是过度设计。

**解决：分层治理。** 纯本地确定性能力（IRR/规则）先用简单 Tool 封装；有本地↔远程切换诉求的能力（如 OCR）才做三角色；MCP 远程能力天然是 Provider。

### 风险4：MCP 桥接的客户端缺失
`mcp-core` 是 MCP 服务端，agent-core 要"消费 MCP"需要 MCP client（sdk 的 streamable-http client）。项目无现成 MCP client。

**解决：** 确认 agent-core 通过 `@modelcontextprotocol/sdk` 的 `Client` 以 streamable-http 连 mcp-gateway，或复用 `mcp-core` 的 `callApi` 走 REST。

### 风险5：独立服务的数据与部署成本
`ai-agent` 新建需补齐：独立 DB、docker-compose、Dockerfile、gateway 代理、健康检查、.env 模型密钥。

**解决：** `ai-agent` 用独立数据库（agent_runs/conversation），符合"每服务独享"规范；模型密钥与 ai-service 同步；gateway 新增 `/api/ai-agent/*` 代理 + SSE 原生转发。

### 风险6：MCP 调用的安全边界（prompt injection）
agent 通过 MCP 调用外部能力，若 prompt 被注入可能诱导调用危险工具或泄露数据。

**解决：** MCP Provider 增加工具白名单 + 鉴权 + 敏感操作确认（复用 agent-core 的 confirm 机制）。

---

## 💡 优化建议（建议采纳）

### 建议1：用"合同风险识别"作为 ai-agent 的第一个落地场景
跑通"独立服务 + agent 编排 + Tool 插件化"全链路，先证明架构，再横向铺开。

### 建议2：`shared` 标准库/IRR 直接封装成 agent-core 本地 Tool
不必等三角色，先把纯函数包成 `ContractRuleTool` / `ContractIrrTool`（implements ToolDefinition）。

### 建议3：MCP 桥接采用"适配器 + 按需拉起"
`McpToolAdapter` 把 mcp-gateway 工具转成 ToolDefinition，按 agent.tools 声明懒加载，减少启动开销。

### 建议4：预留 ai-agent 的 SSE 能力
agent 编排（合同风险）结果要流式返回进度，ai-agent 应提供 SSE 端点（复用 gateway stream 转发模式），前端小程序才能做"解读中 4 步进度"。

---

## ✅ 合理项（无需改动）
- 一切皆插件 + 三角色能力：方向与 deepseek-harness 对齐，ToolDefinition 统一契约是现成地基
- MCP 作为 Provider 来源而非全部 MCP 化：避免本地纯函数工具走 MCP 的自调用冗余
- 复用现有基础设施：shared（标准库/IRR）、agent-core（ReAct 引擎）、mcp-core（MCP 协议）、ClientRegistry（模型）
- 独立 ai-agent 服务：符合"每服务单一职责"规范

## 结论
⚠️ **有条件通过**

方向正确、基础设施充分，但必须阶段化落地：
1. 先新建 ai-agent 承载新增 agent 编排能力，不搬空 ai-service 存量（风险1）
2. agent-core 插件化做兼容扩展（风险2），IRR/规则先用简单 Tool（风险3）
3. 明确 MCP client 方案（风险4）+ 独立 DB + gateway 代理（风险5）+ 安全边界（风险6）
4. 用合同风险识别作为第一个落地场景验证骨架（建议1）
