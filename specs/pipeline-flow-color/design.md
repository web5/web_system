## 0 背景与目标

详情页「执行流程」连线着色（走过路径绿色高亮）此前没有整体定义过：规则散落在实现里，
2026-09-22 定过一条「分叉竖线：目标分支存在 skipped → 整段灰」，2026-09-23 又修过一次
「支线只排除 skipped → 未执行也提前变绿」。两次都是局部打补丁，缺一张完整的规则表，
导致连续两轮「看着不对」的反馈。本设计把规则整体定义 + 出可切换场景的原型演示，
确认后再一次性落码。

## 1 问题（真实实例）

| 实例 | 状态 | 现象 |
|---|---|---|
| #3373（成功） | 4-1 local 条件未命中 → 跳过；4-2 dev 成功 | v1 竖线规则「存在 skipped 分支 → 整段灰」→ **4-2 的成功路径入口是灰的**，用户反馈「4-2 执行成功了，怎么还是灰色」 |
| （运行中实例） | 停在「发布确认 · 待审批」 | v1 支线判据「非 skipped 即绿」→ 4-1/4-2 未执行却提前变绿（2026-09-23 已修，判据改为按数据状态） |

根因：规则从未被整体确认；「走过路径」在条件分叉场景下语义模糊（一条分支没走 = 整条路没走过？）。

## 2 规则 v2（提案 · 待拍板）

状态集沿用 `specs/pipeline-task-status/design.md` §2（任务级：succeeded / failed / running /
awaiting / skipped / cancelled / 未执行`''`）。步骤聚合规则不变（§4.2）。

| 连线元件 | 着色条件 | 颜色 |
|---|---|---|
| 主线横线 L1 | 进入侧（前一列）步骤聚合 = succeeded | 绿 `--ok`，否则灰 |
| 分叉竖线 L2 | 进入侧 succeeded 时**跟主路径分支（默认/无条件任务）的状态**（用户 2026-09-23 两轮反馈收敛：竖线 = 主路径分支自己的状态线） | 主路径 ok→绿 `--ok` / fail→红 `--danger` / run→品牌色 `--primary` / await→`--ws-warn` / skip·none→灰；进入侧未完成 → 灰 |
| 支线横线 L3 + 箭头 L4 | 跟**目标任务自身状态**：succeeded | 绿 `--ok` |
| | failed | 红 `--danger`（v1 为灰，提案升级，待拍板） |
| | running | 品牌色 `--primary`（沿用原型图例「执行中」的色，不新增 token） |
| | awaiting | `--ws-warn`（沿用原型图例「待审批」的色） |
| | skipped / cancelled / 未执行 | 灰 `--border` |

### 2.5 连线绘制定义（唯一判据源 · 2026-09-23）

之前只在「颜色」上打补丁，没有定义连线本身怎么画、每段归谁 —— 这是两轮反馈互相矛盾的根源。
定义如下（实现 = `ProgressFlow.vue drawWires()`，原型 = `deploy-console-domain-split.html`
屏 `dc-rundetail` 的同名函数）：

| 段 | 几何 | 归属（状态源） | 颜色 |
|---|---|---|---|
| L1 主线横线 | 进入侧列**首个任务卡**右侧中点 → 水平到分叉 X（mx = 两列中点） | 进入侧步骤的聚合状态 | 聚合完成 → 绿，否则灰 |
| L2 分叉竖线 | 目标列多任务时才有：mx 处，最高任务行中线 → 最低任务行中线 | **主路径分支**（无条件/默认任务；条件分支是旁路，不进主干） | 进入侧未完成 → 灰；否则跟主路径分支状态：ok→绿 / fail→红 / run→品牌色 / await→warn / skip·none→灰 |
| L3 支线横线 | mx → 每个目标任务卡左缘中点（每任务一条） | 目标任务自身 | 完成→绿 / 失败→红 / 执行中→品牌色 / 待审批→warn / 跳过·未执行→灰 |
| L4 箭头 | 支线末端 chevron，尖点落在任务卡左缘 | 同 L3 | 同 L3 |

规则与特例：

- **主路径分支的判定**：该列中 `condition` 为空（无条件）的任务；一列全为条件任务时取最后一个。
  （local 是条件分支 = 旁路，dev 是无条件分支 = 主干；旁路成败只影响自己的支线，不进主干。）
- **L2 竖线 = 主路径分支的状态线**（用户 2026-09-23 两轮反馈收敛）：进入侧完成时，竖线直接取
  主路径分支状态色（成功绿 / 执行中品牌色 / 失败红 / 跳过·未进入灰）；进入侧未完成 → 灰。
- **sameLine**：目标列单任务且与进入侧任务同高 → 无 L2/L3，L1 直接接到目标卡 + L4 箭头，色同 L1。
- **不画线**：任一侧无任务卡（该列没有渲染任务）。
- **线型**：一律实线 2.5px；虚线只用于任务卡边框表达「跳过」。
- **重绘时机**：实例数据更新 / 窗口 resize / 画布滚动后重新测量（DOM 测量式，不用估算坐标）。

任务的六种状态（`taskStates` 落库）：完成 / 失败 / 执行中 / 待审批 / 跳过（条件不满足等，
没有真正执行）/ 未执行（还没轮到，无记录）；另有已取消（按灰，待拍板）。

核心变化：

1. **竖线从「无 skipped 分支才绿」改为「存在执行并成功的分支才绿」** ——
   跳过的分支不拖灰成功分支（修「4-2 成功了还是灰」），但执行中/失败/全跳过也不给绿（修「没成功却绿」）。
2. **支线从「非 skipped 即绿」改为「按目标任务状态着色」** ——
   未执行/待审批不再提前变绿（2026-09-23 已先修），失败标红、执行中品牌色为提案新增。

## 3 场景矩阵（原型演示的四个场景）

| 场景 | 步骤/任务状态 | 期望着色 |
|---|---|---|
| S0 成功 · dev 跳过 | 前三步完成、4-1 local 完成、4-2 dev 跳过 | 主线 3→4 绿；**竖线灰**（主路径 dev 没走通）；4-1 支线绿；**4-2 支线灰** |
| S2 成功 · 命中 dev（= 真实 #3373） | 前三步完成、4-1 跳过、4-2 完成 | 主线 3→4 绿；**竖线绿**（主路径 dev 成功）；4-1 支线灰；4-2 支线绿 |
| S1 运行中 · 停在发布确认 | git 完成、build 完成、审批门禁 待审批、4-1/4-2 未执行 | 主线 1→2→3 绿；3→4 主线/竖线/支线全灰（未进入不提前绿） |
| S3 失败 · dev 动作失败 | 前三步完成、4-1 跳过、4-2 失败 | 主线 3→4 绿；**竖线红**（跟 dev 失败）；4-1 支线灰；**4-2 支线红** |
| S4 执行中 · dev 运行中 | 前三步完成、4-1 跳过、4-2 执行中 | 主线 3→4 绿；**竖线品牌色**（跟 dev 执行中）；4-1 支线灰；**4-2 支线品牌色** |

> S0 与 S2 是对称场景（一成一跳），竖线结果不同是**故意的**：竖线归主路径分支（dev），
> 不归「有没有分支成功」—— 这正是用户两次反馈（「4-2 成功了怎么还是灰」/「未执行时竖线要灰」）都能自洽的关键。

## 4 与 v1 的差异汇总

1. 竖线：`无 skipped 分支才绿` → `存在已执行（succeeded/failed）分支即绿`（修 S2 反馈）。
2. 支线：`非 skipped 即绿` → `按目标任务状态着色`（修运行中提前变绿，2026-09-23 已先修）。
3. 新增可选着色：failed 支线红、running 蓝、awaiting 橙（v1 全灰）。

## 5 拍板情况与待拍板项

已拍板（用户 2026-09-23）：
- **竖线规则**：进入侧完成 且 存在执行并成功的分支 → 绿；执行中 / 失败 / 全部跳过 / 未进入 → 灰。

待拍板：
1. failed 支线标红（信息量更高）还是保持灰？
2. running / awaiting 支线着色（S4 中支线品牌色）是否认可，还是一律灰（只有走过才上色）？
3. cancelled（取消）按灰处理是否可以？
4. 步骤标题卡跟随聚合状态着色边框（现状已如此，确认保留）？
