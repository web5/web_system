## 0 背景与目标

详情页「执行流程」连线着色（走过路径绿色高亮）此前没有整体定义过：规则散落在实现里，
2026-09-22 定过一条「分叉竖线：目标分支存在 skipped → 整段灰」，2026-09-23 又修过一次
「支线只排除 skipped → 未执行也提前变绿」。两次都是局部打补丁，缺一张完整的规则表，
导致连续两轮「看着不对」的反馈。本设计把规则整体定义 + 出可切换场景的原型演示，
确认后再一次性落码。

## 1 问题（真实实例）

| 实例 | 状态 | 现象 |
|---|---|---|
| #3373（成功） | 4-1 local 条件未命中 → 跳过；4-2 dev 成功 | v1 竖线规则「存在 skipped 分支 → 整段灰」→ **4-2 的成功路径入口是灰的**，用户反馈「4-2 执行成功了，怎么还是灰色」 |
| （运行中实例） | 停在「发布确认 · 待审批」 | v1 支线判据「非 skipped 即绿」→ 4-1/4-2 未执行却提前变绿（2026-09-23 已修，判据改为按数据状态） |

根因：规则从未被整体确认；「走过路径」在条件分叉场景下语义模糊（一条分支没走 = 整条路没走过？）。

## 2 规则 v2（提案 · 待拍板）

状态集沿用 `specs/pipeline-task-status/design.md` §2（任务级：succeeded / failed / running /
awaiting / skipped / cancelled / 未执行`''`）。步骤聚合规则不变（§4.2）。

| 连线元件 | 着色条件 | 颜色 |
|---|---|---|
| 主线横线 L1 | **目标列步骤的聚合状态**（该列所有分支的合并，有成功分支时成功覆盖；聚合规则与步骤卡边框同源）——用户 2026-09-23 定稿：「边的颜色 = 下一个节点的颜色」「成功的节点覆盖其他节点」 | 聚合：ok→绿 `--ok` / fail→红 `--danger` / run→品牌色 `--primary` / await→`--ws-warn` / skip·none→灰 `--border` |
| 分叉竖线 L2（**按转折点分段**） | 每段归**该段通往的目标任务**（用户 2026-09-23：「你需要计算转折点」） | 同 L3/L4：该段目标任务的自身状态色 |
| 支线横线 L3 + 箭头 L4 | 跟**目标任务自身状态**（每条分支各看各的） | 完成→绿 / 失败→红 / 执行中→品牌色 / 待审批→橙 / 跳过·未执行→灰 |

### 2.5 连线绘制定义（唯一判据源 · 2026-09-23）

之前只在「颜色」上打补丁，没有定义连线本身怎么画、每段归谁 —— 这是几轮反馈互相矛盾的根源。
定义如下（实现 = `ProgressFlow.vue drawWires()`，原型 = `deploy-console-domain-split.html`
屏 `dc-rundetail` 的同名函数）：

**总纲：一条边的颜色 = 目标（下一个）节点的颜色，与源节点无关**（用户 2026-09-23 定稿：
a→b 看 b、a→c 看 c；「如果有成功，成功的节点要覆盖其他节点」）。落到几何上分两层：

- **L1（出口横段）** = 目标列**步骤的聚合状态**色 —— 聚合规则与步骤卡边框同源
  （任一 failed → 红；任一 running → 品牌色；任一 awaiting → 橙；有 succeeded → 绿；全 skip/none → 灰）。
  「成功覆盖」由此自然成立。
- **L2（竖线）= 按转折点分段**：每个目标任务的行中线是一个转折点，第 k 段竖线
  （上一转折点 → 第 k 个任务行中线）属于第 k 条分支，颜色 = 该任务自身状态。
  于是「成功 + 跳过」时：L1 绿（成功覆盖）、竖线那一段（属跳过分支）灰、成功分支自己的支线绿 —— 各段各归各的。
- **L3/L4（支线与箭头）** = 各目标任务自身状态色。

| 段 | 几何 | 归属（状态源） | 颜色 |
|---|---|---|---|
| L1 主线横线 | 进入侧列**首个任务卡**右侧中点 → 水平到分叉 X（mx = 两列中点） | 目标列步骤的**聚合状态** | 聚合：ok→绿 / fail→红 / run→品牌色 / await→warn / skip·none→灰 |
| L2 分叉竖线 | mx 处**按转折点分段**：第 k 段 = 上一转折点 → 第 k 个任务行中线（n 个任务 → n−1 段，见兜底） | 该段通往的目标任务 | 同 L3：该任务自身状态色 |
| L3 支线横线 | mx → 每个目标任务卡左缘中点（每任务一条，从自己的转折点横出） | 目标任务自身 | 完成→绿 / 失败→红 / 执行中→品牌色 / 待审批→warn / 跳过·未执行→灰 |
| L4 箭头 | 支线末端 chevron，尖点落在任务卡左缘 | 同 L3 | 同 L3 |

规则与特例（完备性要求：任何状态组合都不得出现"画不出/画错"）：

- **聚合规则**：与步骤卡边框同源（failed > cancelled > running > awaiting > succeeded > skipped > none）。
  「成功覆盖跳过」= succeeded 优先级高于 skipped；failed 优先级最高（步骤确实断了，红最醒目，
  成功分支自己的支线仍绿）。
- **转折点兜底**：进入侧任务行低于目标列首行（f.cy < y1）→ 顶部补一段归第 1 个任务；
  进入侧任务行高于目标列末行（f.cy > yn）→ 末段补画并归最后一个任务；等长段（差值 ≤0.5px）不画。
- **sameLine**：目标列单任务且与进入侧任务同高 → 无 L2/L3，整条边直接接到目标卡 + L4 箭头，
  颜色 = 该目标任务状态（聚合 = 自身，天然一致）。
- **n ≥ 3 分支**：竖线切分成 n−1 段（段 k 归任务 k+1），第 1 个任务的支线直接从主线高度横出；
  已由 S6/S7 三分支场景验证。
- **不画线**：任一侧无任务卡（该列没有渲染任务）。
- **线型**：一律实线 2.5px；虚线只用于任务卡边框表达「跳过」。
- **重绘时机**：实例数据更新 / 窗口 resize / 画布滚动后重新测量（DOM 测量式，不用估算坐标）。

任务的六种状态（`taskStates` 落库）：完成 / 失败 / 执行中 / 待审批 / 跳过（条件不满足等，
没有真正执行）/ 未执行（还没轮到，无记录）；另有已取消（按灰，待拍板）。

核心变化（最终定稿 · 用户 2026-09-23「边的颜色 = 下一个节点的颜色」+「成功覆盖」）：

1. **连线颜色全部看目标端**：共享段（L1+L2）= 目标列步骤聚合色；支线（L3+L4）= 目标任务自身色。
   进入侧聚合、主路径分支特判都不再参与。
2. **支线从「非 skipped 即绿」改为「按目标任务状态着色」** ——
   未执行/待审批不再提前变绿，失败红、执行中品牌色。

| 场景 | 步骤/任务状态 | 期望着色（L1 / 竖线 / 支线） |
|---|---|---|
| S0 成功 · dev 跳过 | 4-1 local 完成、4-2 dev 跳过 | 绿（成功覆盖）/ **灰**（竖线属 4-2）/ 4-1 绿、4-2 灰 |
| S2 成功 · 命中 dev（= 真实 #3373） | 4-1 跳过、4-2 完成 | 绿 / 绿 / 4-1 灰、4-2 绿 |

| S3 失败 · dev 动作失败 | 4-1 跳过、4-2 失败 | 红 / 红 / 4-1 灰、4-2 红 |

| S6 三分支 · 成功/跳过/失败 | local 完成、dev 跳过、prod 失败 | L1 红（聚合 failed）/ 段1 灰、段2 红 / 支线 绿·灰·红 |
| S7 三分支 · 成功/跳过/执行中 | local 完成、dev 跳过、prod 执行中 | L1 品牌色（聚合 running）/ 段1 灰、段2 品牌色 / 支线 绿·灰·品牌色 |

> S0 与 S2 是对称场景（一成一跳），主干颜色相同（都绿）正是「成功覆盖」的体现；
> 主干与 4-2 支线颜色不同（S0 里主干绿、4-2 支线灰）也是故意的 —— 支线只代表各分支自己。
> 用户几轮反馈（「4-2 成功了怎么还是灰」/「未执行时竖线要灰」/「横线要跟 4-2 同色」/「成功要覆盖」）在此全部自洽。

## 4 与 v1 的差异汇总

1. 着色方向反转：`看源（进入侧聚合/skipped 排除）` → `看目标端`（用户定稿）。
2. 共享段（L1+L2）= 目标列**聚合**状态（成功覆盖）；支线 = 目标任务自身。
3. 支线：`非 skipped 即绿` → `按目标任务状态着色`（失败红、执行中品牌色、待审批橙）。

## 5 拍板情况与待拍板项

已拍板（用户 2026-09-23）：
- **边的颜色 = 下一个节点的颜色**（a→b 看 b、a→c 看 c）。
