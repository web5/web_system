## 2. 映射规则（按语义定档，禁止只按数值替换）

⚠️ **同一数值在不同语义下归一档会制造新的不一致**（如 `8px` 在标签上是 chip、在卡片上是 card）。判定顺序：先看元素**是什么**，再看数值是否接近当前端该档的值。

| 元素语义 | 目标档 | 说明 |
|---|---|---|
| 标签 / 徽标 / 小色块 / 微角 / 代码片段背景 | `--r-chip` | 点状、条状小元素 |
| 输入框 / 按钮 / 选择器 / 下拉 / 分段控件 / 日期选择 / 上传按钮 | `--r-control` | 可交互控件 |
| 卡片 / 面板 / 弹窗 / 抽屉 / 列表容器 / 表格容器 / 浮层 | `--r-card` | 容器类 |
| 胶囊按钮 / 开关（轨道 + 圆钮）/ 标签式筛选片 | `--r-pill` | 形状语义（R5：开关归 pill） |
| 头像 / 状态点 / 圆形图标 | `border-radius: 50%` | **不改**（R3 例外） |
| 气泡贴边角 / 贴边抽屉 | `border-radius: 0` | **不改**（R3 例外） |

**数值线索（仅用于定位候选，不直接决定归属）**：`≤4px` 多为 chip；`6–8px` 在 admin 为 control、在品牌端为 card/chip；`10–16px` 多为 card；`≥20px` / `999px` 多为 pill 或刻意大圆角。

**端内取值**（按各端 token 层，不跨端套用）：

| 档 | admin / console（px） | portal（px） | 小程序（rpx，1px≈2rpx） |
|---|---|---|---|
| chip | 4 | 4 | 8 |
| control | 6 | 6 | 12 |
| card | 8 | 8 | 16 |
| pill | 9999 | 9999 | 999rpx |

## 4.0 零变化原则（2026-09-23 实测后修订 · 重要）

**实测发现存量值与语义档并不匹配**：admin 大量「卡片」写的是 `4px`，而语义档 `--r-card` 是 `8px`；另有 `3px` / `10px` / `12px` 等阶外值。因此「收敛到语义档」**必然带来视觉变化**，与原 §5「柔和档逐处一致」直接冲突。

**修订口径**：本方案只做「**值匹配 + 语义匹配**」的零变化收敛：

| 现状值 | 目标档 | 附加判据（必须同时满足） |
|---|---|---|
| 4px | `var(--r-chip)` | 元素确实是标签 / 徽标 / 小方块 |
| 6px | `var(--r-control)` | 元素确实是可交互控件 |
| 8px | `var(--r-card)` | 元素确实是容器 / 卡片 |

- **阶外值一律不动**（`3px` / `10px` / `12px` / `14px` / `16px` / `20px` …）
- **值在档内但语义不符**的处（典型：`4px` 的卡片）**也不动** —— 强行归 card 会让卡片从 4px 变 8px
- 上述两类汇总为**待设计决策清单**：是「统一到语义档」（显式接受视觉变化、需单独批次）还是「维持现状」

理由：存量收敛的目标是**让新代码一致 + 让变更可控**，不是把历史值全改一遍换取大面积视觉回归。

## 4.5 执行口径（2026-09-23 决策：方案 B —— 全量统一，覆盖 §4.0）

负责人已选 **B：全量统一到语义档、接受视觉变化**（理由：避免留下"以后再分析一次"的尾巴）。故 §4.0「只做零变化收敛」的限定**作废**，改为：

**归档规则**（一律按元素语义定档，值由档决定）：

| 元素语义 | 目标档 | admin / console | portal | 小程序 |
|---|---|---|---|---|
| 标签 / 徽标 / 小色块 / 微角 | `--r-chip` | 4px | 4px | 8rpx |
| 控件（输入 / 按钮 / 选择器 / 分段 / 开关） | `--r-control` | 6px | 6px | 12rpx |
| 容器（卡片 / 面板 / 弹窗 / 抽屉 / 列表 / 表格） | `--r-card` | 8px | 8px | 16rpx |
| 胶囊 / 开关轨道 / 标签式筛选片 | `--r-pill` | 9999px | 9999px | 999rpx |
| 头像 / 状态点 / 圆形图标 | `50%` | 不改 | 不改 | 不改 |

**预期视觉变化（必须走查留证）**：
- admin：卡片 `4px → 8px`（更圆润）、`10/12px → 8px`；`3px → 4px`
- portal：卡片 `12–16px → 8px`（更锐）、`10/11px → 8px`
- 小程序：卡片 `24rpx → 16rpx`、`20rpx → 16rpx`；`40/48rpx` 视语义归 card 或 pill

**执行节奏**：以**文件**为单位 —— 读一次该文件的模板 + 样式，判定该文件全部处，再批量替换；每轮 3–4 文件（约 20–30 处）。91 文件预计 12–15 轮。

**辅助**：`/tmp/conv-*.json` 是按选择器名生成的建议表（实测自动判定率 58%，其余 42% 为 `.d1` / `.row` / `.li` 等无语义类名，需人工）；**建议仅作候选，最终以元素语义为准**。

**每批仍须**：柔和档与改前**逐处比对并记录变化**（B 的代价）、三档切换无异常、单批一个 commit（`Proto: <本条规格的 sha>` + `Design: pass`）。

## 4. 例外清单（一律不改）

- `border-radius: 50%`、`border-radius: 0`
- 刻意的大圆角：如小程序 `24rpx`（=12px）卡片、`999rpx` 胶囊 —— 若该端语义档已覆盖则归 card/pill，否则保留
- 非圆角来源的圆角：如 `overflow: hidden` 容器的临时值（需保留视觉，改 token 前先确认该处是"设计意图"还是"顺手写的值"）

## 4.6 扫描与替换口径（2026-09-23 实测踩坑，每批必读）

存量圆角有**五种形态**，只匹配「单值裸 px」会漏掉中间三种：

| 形态 | 示例 | 处理 |
|---|---|---|
| ① 单值裸值 | `border-radius: 6px;` | 直接换 token |
| ② **多值** | `border-radius: 0 0 6px 6px;`、`2px 0 0 2px` | **必须整串替换**。只替换首个数值会留下 `var(--r-chip) 0 0 2px` 这类混合值（实测踩到 2 处：`.task-node .seq`、`.orch-task .rseq`，已由 `ad06201` 修正） |
| ③ **模板内联 style** | `<pre style="...; border-radius: 4px; ...">` | deploy-console 有 9 处，须单独扫描 |
| ④ **跨行长规则** | 选择器与声明相邻 >25 行 | 按锚点向后搜索要留足窗口，否则漏改（实测漏 1 处 `.task-node`，已修正） |
| ⑤ 例外 | `border-radius: 50%` / `0` | 不改（R3） |

**复核方法（每批必跑，且不能用 grep 行级过滤）**：按「**声明**」粒度扫描 —— 判定条件不能是「整行不含 `var(--`」（同一行常有背景色等其它 token 变量，会把裸值行误排除，实测因此漏过一轮复核）。应截取 `border-radius:` 之后到 `;` 的那一段声明单独判断，抓两类残留：

1. **混合值**：该声明里同时出现 `var(--r-*)` 与数值
2. **未归档**：该声明里没有任何 `var(--r-*)`，且数值不是 `50%` / `0`

**另发现（观察项，非裸值）**：6 处写作 `var(--ws-radius-md, 8px)` 这类「尺寸档 + fallback」形式，fallback 值与尺寸档实际值不一致（md=6px 却写 8px），字面意图与实际渲染不符。因属尺寸档引用（口径允许）故未改动，列为观察项待确认。

**补档判据（2026-09-23 portal P3 实测补充，用于消除「归 chip 还是 pill」的反复）**：

1. **小内联元素**（标签 / 徽标 / 筛选片 / 口味片）：现状 radius **≥ 12px** 视为「已是胶囊」→ 归 `--r-pill`（元素高约 2×radius，视觉基本不变）；**< 12px** → 归 `--r-chip`。
2. **按钮**：现状 radius **≥ 20px** 视为胶囊 → `--r-pill`；**12–18px** → `--r-control`。
3. **容器**（卡片 / 面板 / 图块 / 画布 / 框 / 列表）：一律 `--r-card`，不受上述阈值影响（大容器 20px 半径仍是容器，不是胶囊）。
4. 圆形（`50%` / `999px`）：`50%` 不改；`999px` → `--r-pill`（等价，统一写法）。

## 5. 每批验收（缺一不可）

1. **计数**：该批文件的裸值计数归零，或仅剩 §4 例外；
2. **视觉一致**：柔和档下与改动前**逐处一致**（AC2 的局部版）——必要时用浏览器读 computed 抽样比对；
3. **切换可用**：三档切换下该页无异常（无负值、无角部撕裂）；
4. **提交**：每批一个 commit，message 带 `Proto: <sha>`（本文件的 commit）与 `Design: pass`；跨多端的机械批可走 `UI_GATE=off`。
