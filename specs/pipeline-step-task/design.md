## 1 需求与产品定位

### 1.1 旧模型的问题

| 问题 | 表现 |
|---|---|
| 步骤与执行体耦合 | 「步骤」直接挂脚本/条件/操作序列，改一个脚本能碰坏整条流水线 |
| 分支藏在脚本里 | 「按环境走不同脚本」拼在一个 case 里，页面上看不到跑的是哪个分支 |
| 编排不可读 | 节点横排 + 脚本内嵌逻辑，非配置人无法看懂一条流水线在干什么 |
| 多套真相源 | command 列 / actions[].code / 模板 nodes 三处都可能存执行体，改错地方不生效（已实际踩坑） |
| 平台能力耦合进节点 | write-version 等平台操作以 service action 内嵌在节点 actions 里，配置人看不见、也管不了 |

### 1.2 产品目标

一句话：**让一条发布流水线在画布上一眼读懂 —— 步骤讲"做什么事"，任务讲"在哪个条件下怎么做"，动作讲"按顺序跑哪些脚本"。**

- 运维只改**任务**的条件与**动作**的脚本，不动流程结构
- 任何环境差异（本机/远程、不同目标机）都落在任务的条件里，流程结构环境无关
- 审批也是任务（审核任务），与脚本任务混排，统一编排心智
- **动作一律是 shell 脚本**：调用平台能力（写版本记录等）= 脚本内调用平台接口，不存在"内置工具"执行实体（工具目录只是可复用脚本的模板库）

## 2 概念模型（三层实体）

```
流水线 pipeline（deploy_pipelines）
 └─ 步骤 step（deploy_pipeline_steps）          分组容器：名称 + 介绍，无脚本、无条件
     └─ 任务 task（deploy_pipeline_tasks）1:N    执行单元，同步骤内混排
         ├─ 脚本任务 kind=script：可选执行条件 + 任务级环境变量 + 1..N 动作（有序脚本）
         │    └─ 动作 action：{名称, 脚本}；按序执行；调平台能力=脚本调接口
         └─ 审核任务 kind=approval：审批人/超时动作/拒绝策略 —— 无动作
```

| 实体 | 职责 | 脚本 | 执行条件 | 环境变量 |
|---|---|---|---|---|
| 步骤 | 分组 + 人话介绍（纯展示，不参与执行） | ✗ | ✗ | ✗ |
| 脚本任务 | 条件命中才执行，串起 1..N 个动作 | — | ✓ 可选 | ✓ 任务级 |
| 动作 | 执行一段自包含 shell 脚本（含调平台接口的脚本，如 write-version） | ✓ | ✗（条件在任务上） | —（继承任务） |
| 审核任务 | 人工审批门禁 | ✗ | ✓ 可选 | ✗ |

**编号规则**（画布展示）：单任务步骤直接用步骤号（`1`）；多任务步骤用「步骤号-任务号」（`4-1`、`4-2`）。

## 3 执行语义

```
流水线执行 = 按 sort 顺序遍历步骤；
步骤内 = 处理该步骤下所有启用的任务：
  ├─ 任务无执行条件   → 恒执行（同步骤内多个无条件任务并行调度）
  ├─ 任务有执行条件   → 求值命中才执行，未命中跳过（日志记「条件不满足，已跳过」）
  ├─ 表达式非法       → 该任务失败（不静默放行）
  ├─ 脚本任务         → 命中后按序执行其动作（任一动作失败 → 任务失败，后续动作不再执行）
  └─ 审核任务         → 进入即挂起等人批；批准后步骤收尾，拒绝按 onReject 处置
步骤内任务全部结束（含跳过）后，进入下一个步骤。
```

- **条件表达式**（步骤任务共用 `steps/condition.ts` 引擎，已有 9 单测）：
  `KEY == 值` / `KEY != 值`，多条件 `&&`；变量 = 内置（`DEPLOY_ENV` / `MODULE_KEY` / `MODULE_TYPE` / `BRANCH` / `COMMIT_ID`…）+ 流水线变量 + 配置中心值。
- **多选一**（如发布：本机 cp / 远程 scp）用**互斥条件**表达（`DEPLOY_ENV == local` / `DEPLOY_ENV == dev`），不提供"默认任务兜底"——未命中任何任务时该步骤**失败**，强制显式配置（不静默猜）。
- **并行**只发生在同一步骤内、无依赖的无条件任务之间；跨步骤严格按 sort 顺序。需要顺序的操作拆成多个步骤或同一任务的多个动作。
- **动作序**：任务内动作严格按数组顺序串行（如 release：`发布文件到目标位置` → `write-version · 写版本记录`）；条件不命中跳过整个任务（含其全部动作），不会出现"任务被跳过但某个动作仍执行"。
- **平台能力调用**：write-version 等以脚本实现（`curl $CONSOLE_API/...`），平台向动作进程注入 `CONSOLE_API` / `CONSOLE_TOKEN` 等凭据变量——与其他脚本无差别，可读可改可审计。
- **变量注入优先级**：任务级 env > 流水线变量 > 配置中心 > 内置。

### 4.4 与旧表的关系（p16 迁移）

| 旧 | → 新 |
|---|---|
| `deploy_pipeline_step_commands`（节点命令：command/actions/condition） | 每个节点 → 一个步骤 + 其下任务 |
| 节点的 `command` / `actions[shell].code`（shell 执行体） | 任务下的**动作**（script） |
| 节点 `actions` 里 service 操作（write-version 等） | 任务下的**动作**（write-version 脚本：curl 平台接口写版本记录） |

| `deploy_pipeline_step_branches`（分支实体） | 同一发布步骤下的**互斥条件任务**（local / dev 各一，各带自己的动作序列） |
| 审批节点（模板 nodes 里 kind=approval） | 审核任务 |
| env_branches（已废弃 json 列） | 互斥条件任务 |

旧表本轮不删（读路径切换后，退役在 p17）。

## 5 接口设计

| 方法 | 路径 | 语义 |
|---|---|---|
| `GET` | `/api/pipelines/:id/steps` | 步骤列表（含各自任务与动作，一次取整树） |
| `PUT` | `/api/pipelines/:id/steps` | 步骤全量保存（名称/介绍/排序；空数组=清空） |
| `PUT` | `/api/pipelines/:id/steps/:stepId/tasks` | 该步骤任务全量保存（含各自 actions；逐条 `bash -n` + 条件校验；空数组=清空） |
| `DELETE` | `/api/pipelines/:id/steps/:stepId` | 删除步骤（级联任务与动作） |

保存前校验：步骤名非空且唯一；任务名组内唯一、动作名任务内唯一；脚本动作 `bash -n`；`kind=approval` 审批字段完整且**不携带 actions/env**；`managed=1` 的动作不允许删除/改名（平台托管）；条件表达式语法；审计日志记录前后 diff。

### 6.0 框架（全局）

- **亮色主题**为默认（token：主橙 `#F97316`、卡白底 `#E8EBF0` 边、文字三级 `#1A1F2E/#5B6372/#9AA1AD`）
- **顶部一级菜单 + 左侧二级菜单**：顶部横排域 tab（仪表盘/微前端/API 网关/流水线管理/基础设施），左侧只显示当前域的页面项；切域进组内首页，详情页跳转时顶部 tab 跟随所在域
- 其他模块页统一交互骨架：页头按钮组（取消 / 删除〔禁用态〕 / 保存）+ 工具栏（分段筛选+搜索+新建）+ 列表行操作

### 6.1 画布布局（三层：步骤 → 任务 → 动作）

```
 ①拉取代码            ②构建              ③发布确认           ④发布                ⑤通知
      │                   │                   │                  │                   │
  [1|任务|git] ▶＋▶ [2|任务|build] ▶＋▶ [3|任务|审批门禁] ─┬─▶ [4-1|任务|local·if] ─▶＋▶ [5|任务|notify·if]
   ┆校验代码来源与分支      ┆vite build·打包…                      │ ┆发布文件到目标位置    ┆curl·发布结果回调
   ┆检出目标分支并自证                                            │ ┆write-version·写版本记录
                                                                └──▶ [4-2|任务|dev·默认]
                                                                      ┆打包上传到远程主机
                                                                      ┆write-version·写版本记录
```

- **上行**：步骤标题框（名称 + 介绍），横向排开，**互不连线**
- **任务卡**（宽 ≥140px，等宽，左对齐，圆角 **2px**）：
  - 结构 = `序号竖条 | 「任务」标签 | [if 徽标 / 默认徽标] 任务名`；hover 右上角 ×（删除任务）
  - 编号：单任务步骤 `1`；多任务 `4-1`/`4-2`
- **动作块**（任务头下方**紧贴**，共享一个边框组，圆角 **2px**，内部以分隔线分行）：
  - 每行 = `[脚本] 动作名`（等宽字体），hover 高亮 + 右上角 ×（**删除动作在画布上**，不在抽屉）
  - 平台托管动作（git/build 下）：删除按钮禁用态 + tooltip「平台托管动作不可删除」
- **连线**（JS 测量节点坐标 + SVG 绘制，与布局解耦——定稿关键技术决策）：
  - 上一列主任务右缘 → 水平线 → 中点「＋」号（**添加步骤**）→ 下一列
  - 下一列单任务：直线 + 空心箭头（箭尖顶住任务左缘）
  - 下一列多任务：主线拐出分叉竖线，每任务一条水平线 + 箭头；**互斥分支不画汇出线**
  - 切换到流水线屏时重测重绘（隐藏态坐标为 0 的坑已踩过）
- **添加**：步骤 = 连线中间「＋」；任务 = 步骤内底部入口；动作 = 任务总览抽屉「＋ 添加动作」

### 6.2 抽屉（点任务头 / 点动作卡两种形态；**无保存按钮**）

| 点击对象 | 抽屉内容 |
|---|---|
| 步骤框 | 仅「名称 + 介绍」两字段 |
| 任务头 | 任务总览：任务名 + 动作列表（点行进入单动作）+「＋ 添加动作」；tab「高级」（执行条件）/「环境变量」 |
| 动作卡 | **只展示当前动作**：动作名 + 脚本正文（不展示同任务其他动作；无删除/返回按钮——删除在画布，切换靠重新点画布） |
| 审核任务 | 审批人 / 超时动作 / 拒绝策略（无动作、无高级） |

### 6.3 保存模型（页面级）

- 抽屉是**纯编辑面板**：改完即暂存到画布态，抽屉内无「保存/取消」
- 流水线页**标题栏右侧按钮组**：`取消`（放弃未保存修改）/ `删除`（禁用条件：存在进行中的运行，tooltip 说明）/ `保存`（保存整条流水线：步骤/任务/动作/条件/变量）

## 7 迁移（p16，幂等）

`scripts/migrations/p16-step-task.mjs`（DRY_RUN 支持，备份 `/tmp/p16-backup-<ts>.json`）：

以 `admin 发布` 为例的映射结果：

| 旧节点 | → 新步骤 | → 新任务 | → 新动作 |
|---|---|---|---|
| git | 步骤① 拉取代码 | 任务 git（managed） | 校验代码来源与分支；检出目标分支并自证 |
| build | 步骤② 构建 | 任务 build（managed） | vite build · 打包微模块产物 |
| 审批节点 | 步骤③ 发布确认 | 任务 审批门禁（approval） | —（审核任务无动作） |
| release（含 branches local/dev） | 步骤④ 发布 | 任务 local（`DEPLOY_ENV == local`）+ 任务 dev（默认） | local：发布文件到目标位置、write-version·写版本记录<br>dev：打包上传到远程主机、write-version·写版本记录 |
| notify | 步骤⑤ 通知 | 任务 notify（`DEPLOY_ENV == prod`） | curl · 发布结果回调 |

**write-version 动作脚本**（原 service 操作的脚本化）：

```bash
#!/usr/bin/env bash
# 写版本记录：脚本内调用平台接口（非内置工具）
curl -sf -X POST "${CONSOLE_API}/api/pipelines/versions" \
  -H "Content-Type: application/json" \
  -d '{"module":"${MODULE_KEY}","env":"${ENV_ID}","version":"${VER}"}'
```

其余 15 个模块按同规则批量迁移；迁移后执行引擎读新表，旧表冻结。

| 判据 | 方法 |
|---|---|
| V1 步骤纯分组 | 步骤抽屉/接口均无 actions/condition/env 字段 |

## 常见问题

**Q：为什么没有"内置工具"实体？（write-version 去哪了）**
A：平台能力一律以**脚本**呈现：write-version = 一段 curl 平台接口的 shell 脚本，和其他动作无差别——可读、可改、可审计，执行链路只有一种（跑脚本）。旧模型的 service action 内嵌在节点 actions 里，配置人不可见且执行链路分叉（已实际踩坑：改了 command 列不生效）。工具目录保留为**可复用脚本的模板库**（引用 = 把模板脚本拷入动作），不是执行实体。

**Q：为什么去掉"默认任务兜底"？**
A：兜底会让"未配置的环境"静默走某条路径，出问题难定位。互斥条件 + 未命中即失败，把配置缺口在发布时第一时间暴露（不静默猜）。

**Q：为什么抽屉里不放保存/删除？**
A：画布是唯一真相源：删除是**结构操作**（画布 hover × 所见即所得）；保存是**页面级动作**（标题栏按钮组一次保存整条流水线）。抽屉只做字段编辑，避免"抽屉里保存了一半"的中间态。

**Q：为什么连线用 JS 测量而不是 CSS 画？**
A：原型迭代中验证过：CSS 定位方案依赖大量 magic number，节点内容一变（字体/文字长度/任务数）全线错位。测量式方案（getBoundingClientRect + SVG）让布局与连线解耦，加删任务自动重算。注意：画布不在可视屏时坐标全 0，切屏后必须重绘（已踩坑）。

**Q：并行执行会不会乱？**
A：并行仅限同步骤内无依赖的无条件任务，日志按任务名归并；需要顺序的操作拆成多个步骤（步骤间严格按 sort）或同一任务的多个动作（动作间严格串行）。
