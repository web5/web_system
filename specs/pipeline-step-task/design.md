## 1 需求与产品定位

### 1.1 旧模型的问题

| 问题 | 表现 |
|---|---|
| 步骤与执行体耦合 | 「步骤」直接挂脚本/条件/操作序列，改一个脚本能碰坏整条流水线 |
| 分支藏在脚本里 | 「按环境走不同脚本」拼在一个 case 里，页面上看不到跑的是哪个分支 |
| 编排不可读 | 节点横排 + 脚本内嵌逻辑，非配置人无法看懂一条流水线在干什么 |
| 多套真相源 | command 列 / actions[].code / 模板 nodes 三处都可能存执行体，改错地方不生效（已实际踩坑） |

### 1.2 产品目标

一句话：**让一条发布流水线在画布上一眼读懂 —— 步骤讲"做什么事"，任务讲"具体怎么做"，工具讲"顺带调用什么平台能力"。**

- 运维只改**任务**的脚本与条件，不动流程结构
- 任何环境差异（本机/远程、不同目标机）都落在任务的条件与脚本里，流程结构环境无关
- 审批也是任务（审核任务），与脚本任务混排，统一编排心智

## 2 概念模型（四层实体）

```
流水线 pipeline（deploy_pipelines）
 └─ 步骤 step（deploy_pipeline_steps）          分组容器：名称 + 介绍，无脚本、无条件
     └─ 任务 task（deploy_pipeline_tasks）1:N    执行单元，同步骤内混排
         ├─ 脚本任务 kind=script：脚本 + 0..N 工具 + 可选执行条件 + 任务级环境变量
         └─ 审核任务 kind=approval：审批人/超时动作/拒绝策略 —— 不挂工具
              └─ 工具 tool（deploy_tool_catalog）：平台能力引用（写版本/重启/探活…）
```

| 实体 | 职责 | 脚本 | 工具 | 执行条件 | 环境变量 |
|---|---|---|---|---|---|
| 步骤 | 分组 + 人话介绍（纯展示，不参与执行） | ✗ | ✗ | ✗ | ✗ |
| 脚本任务 | 执行一段自包含脚本 | ✓ | ✓ 0..N | ✓ 可选 | ✓ 任务级 |
| 审核任务 | 人工审批门禁 | ✗ | ✗（明确不挂） | ✓ 可选 | ✗ |
| 工具 | 平台能力（引用 tool catalog） | — | — | — | — |

**编号规则**（画布展示）：单任务步骤直接用步骤号（`1`）；多任务步骤用「步骤号-任务号」（`4-1`、`4-2`）。

## 3 执行语义

```
流水线执行 = 按 sort 顺序遍历步骤；
步骤内 = 处理该步骤下所有启用的任务：
  ├─ 任务无执行条件   → 恒执行（同步骤内多个无条件任务并行调度）
  ├─ 任务有执行条件   → 求值命中才执行，未命中跳过（日志记「条件不满足，已跳过」）
  ├─ 表达式非法       → 该任务失败（不静默放行）
  └─ 审核任务         → 进入即挂起等人批；批准后步骤收尾，拒绝按 onReject 处置
步骤内任务全部结束（含跳过）后，进入下一个步骤。
```

- **条件表达式**（步骤任务共用 `steps/condition.ts` 引擎，已有 9 单测）：
  `KEY == 值` / `KEY != 值`，多条件 `&&`；变量 = 内置（`DEPLOY_ENV` / `MODULE_KEY` / `MODULE_TYPE` / `BRANCH` / `COMMIT_ID`…）+ 流水线变量 + 配置中心值。
- **多选一**（如发布：本机 cp / 远程 scp）用**互斥条件**表达（`DEPLOY_ENV == local` / `DEPLOY_ENV == dev`），不提供"默认任务兜底"——未命中任何任务时该步骤**失败**，强制显式配置（不静默猜）。
- **并行**只发生在同一步骤内、无依赖的无条件任务之间；跨步骤严格按 sort 顺序。需要顺序的操作拆成多个步骤。
- **变量注入优先级**：任务级 env > 流水线变量 > 配置中心 > 内置。
- 工具（如 write-version）在任务脚本执行**之后**按序调用，不因任务条件分支而被绕过。

## 4 数据模型

### 4.1 新表 `deploy_pipeline_steps`

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | |
| `pipeline_id` | varchar(64) | 流水线 ID（沿用历史列名 `template_id`） |
| `name` | varchar(64) | 步骤名 |
| `description` | varchar(255) NULL | 介绍（纯展示） |
| `sort` | int | 顺序 |
| `enabled` | tinyint | |
| 时间戳 / 编辑人 | | |

唯一键 `(pipeline_id, name)`。

### 4.2 新表 `deploy_pipeline_tasks`

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | |
| `step_id` | varchar(36) | 归属步骤（级联删除） |
| `kind` | varchar(16) | `script` / `approval` |
| `name` | varchar(64) | 任务名（同步骤内唯一） |
| `condition` | varchar(255) NULL | 执行条件；空 = 恒执行 |
| `script` | text NULL | 脚本任务的脚本正文（自包含） |
| `tools` | json NULL | 脚本任务挂的工具：`[{tool, args?}]`（审核任务恒 NULL） |
| `env` | json NULL | 任务级环境变量：`{KEY: value}` |
| `approval` | json NULL | 审核任务：`{approvers, timeoutSec, timeoutAction, onReject}` |
| `sort` | int | 同步骤内顺序 |
| `enabled` | tinyint | |
| 时间戳 / 编辑人 | | |

唯一键 `(step_id, name)`。校验：`script` 必填脚本 + `bash -n`；`approval` 必填审批字段；条件表达式语法校验。

### 4.3 与旧表的关系（p16 迁移）

| 旧 | → 新 |
|---|---|
| `deploy_pipeline_step_commands`（节点命令：command/actions/condition） | 每个节点 → 一个步骤 + 其下任务 |
| 节点的 `command` / `actions[shell].code` | 脚本任务的 `script` |
| 节点 `actions` 里 service 操作（write-version 等） | 该任务的 `tools` |
| 节点 `condition`（gate） | 任务的 `condition` |
| `deploy_pipeline_step_branches`（分支实体） | 同一发布步骤下的**互斥条件任务** |
| 审批节点（模板 nodes 里 kind=approval） | 审核任务 |

旧表本轮不删（读路径切换后，退役在 p17）。

## 5 接口设计

| 方法 | 路径 | 语义 |
|---|---|---|
| `GET` | `/api/pipelines/:id/steps` | 步骤列表（含各自任务，一次取整树） |
| `PUT` | `/api/pipelines/:id/steps` | 步骤全量保存（名称/介绍/排序；空数组=清空） |
| `PUT` | `/api/pipelines/:id/steps/:stepId/tasks` | 该步骤任务全量保存（逐条 bash -n + 条件校验；空数组=清空） |
| `DELETE` | `/api/pipelines/:id/steps/:stepId` | 删除步骤（级联任务） |

保存前校验：步骤名非空且唯一；任务名组内唯一；`kind=script` 脚本非空且 `bash -n`；`kind=approval` 审批字段完整且**不携带 tools/script/env**；条件表达式语法；审计日志记录前后 diff。

## 6 UI / 交互设计（与原型稿 v7 一致）

### 6.1 画布布局

```
 ①拉取代码         ②构建          ③发布确认        ④发布            ⑤通知     ← 步骤行（不连线）
      │                │               │               │                │
  [1|脚本|git] ▶＋▶ [2|脚本|build] ▶＋▶ [3|审核|审批门禁] ─┬─▶ [4-1|脚本|local] ─▶＋▶ [5|脚本|notify]
                                                          └──▶ [4-2|脚本|dev·默认]
```

- **上行**：步骤标题框（名称 + 介绍），横向排开，**互不连线**
- **下行**：任务节点（宽 ≥140px，等宽，内容左对齐）：
  - 结构 = `序号竖条 | 类型标签 | 任务名`；序号左侧背景块上下铺满节点、左缘贴合节点圆角；`脚本`（主橙）/ `审核`（绿）标签；条件任务带 `if` 徽标、无条件多任务标 `默认`
  - 主轴：每列**第一个任务**与其他列的任务严格同高（第一行对齐）
- **连线**（JS 测量节点坐标 + SVG 绘制，与布局解耦——这是定稿的关键技术决策）：
  - 上一列主任务右缘 → 水平线 → 中点「＋」号（**添加步骤**）→ 继续到下一列
  - 下一列单任务：直线 + 空心箭头（箭尖精确顶住任务左缘）
  - 下一列多任务：主线上拐出**分叉竖线**（覆盖各任务中线范围），每任务一条水平线 + 箭头
  - **互斥分支不画汇出线**（local→notify 一条主链表达流向，dev 不重复连线）
  - SVG 尺寸按画布**实际内容宽高**设置（防横向滚动溢出时线被裁）；load 后多次重绘吸收字体加载
- **删除**：步骤框 / 任务节点 hover 时右上角显示红色 × 图标（SVG）
- **添加**：步骤 = 连线中间「＋」；任务 = 步骤内底部虚线入口

### 6.2 抽屉（三种形态）

| 点击对象 | 抽屉内容 |
|---|---|
| 步骤 | 仅「名称 + 介绍」两字段 |
| 脚本任务 | Tab1 任务（任务名 + 脚本 + 工具列表）；Tab2 高级（执行条件，**无预置模板**，仅文档说明：语法/变量/示例）；Tab3 环境变量（任务级 key=value） |
| 审核任务 | 审批人 / 超时动作 / 拒绝策略（无脚本、无工具、无高级） |

## 8 验收

| 判据 | 方法 |
|---|---|
| V1 步骤纯分组 | 步骤抽屉/接口均无 script/condition/tools 字段 |
| V2 条件执行 | 单测：无条件恒执行、命中执行、未命中跳过、非法条件任务失败 |

## 常见问题

**Q：为什么去掉"默认任务兜底"？**
A：兜底会让"未配置的环境"静默走某条路径，出问题难定位。互斥条件 + 未命中即失败，把配置缺口在发布时第一时间暴露（不静默猜）。

**Q：为什么连线用 JS 测量而不是 CSS 画？**
A：原型迭代中验证过：CSS 定位方案依赖大量 magic number，节点内容一变（字体/文字长度/任务数）全线错位。测量式方案（getBoundingClientRect + SVG）让布局与连线解耦，加删任务自动重算，这是 v7 定稿的直接原因。

**Q：并行执行会不会乱？**
A：并行仅限同步骤内无依赖的无条件任务，日志按任务名归并；需要顺序的操作拆成多个步骤（步骤间严格按 sort）。
