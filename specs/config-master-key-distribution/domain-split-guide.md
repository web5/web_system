## 0. 一页速览

主密钥**跟着部署库实例走**（`design.md` §2）：库里 `is_secret=1` 的密文是用"该库所属域"的密钥加密的。
换库 = 换域 = 换钥，**旧域的密文不能直接搬到新域**（跨域解密必然 GCM 认证失败）。

| 情形 | 做法 | 是否用脚本 |
|---|---|---|
| **A 新库是空的**（推荐） | 在新库按需重新录入密钥项（用新钥加密），业务值从来源（第三方控制台 / 旧库控制台）重取 | ❌ 不需要 |
| **B 新库由旧库 dump 复制而来** | 密文必须**换钥重加密**后再入库 | ✅ `scripts/master-key-domain-split.mjs` |

> 首选 A：**少一次加密数据搬迁，就少一类事故**。只有"必须保留历史快照/审计连贯性、不想重录"时才走 B。

---

## 1. 触发判据（满足任一即需要本指南）

1. prod 拥有独立部署库实例（与 dev 不再是同一个 `web_system_deploy`）；
2. 本地开发库迁到另一台机器 / 另一实例；
3. 新增一个**独立部署库**（如新建 staging 环境库）；
4. 安全要求"某环境的密钥不得落到另一批机器上"（例如 prod 密钥不得出现在 dev 机器）。

---

## 2. 情形 A：新库为空（推荐路径）

| # | 步骤 | 校验 |
|---|---|---|
| 1 | 生成新域密钥并投递到该域所有机器（`provision-master-key.sh --domain <新域>`，0600 + 备份 + 指纹） | 各机指纹一致 |
| 2 | 在新库控制台**逐项录入**需要的 `is_secret` 项（值取自第三方控制台或旧库页面回显） | 录入后 `verify-config-master-key.mjs` 退出码 0 |
| 3 | 启动服务 → 启动自检通过；跑一次真实发布，确认下发文件里的凭据可用 | 自检日志 + 发布成功 + 下游调用 200 |
| 4 | 清理：新域机器上**不得残留旧域密钥**（含 `.env`、`.bak`、旧密钥文件） | `grep -r` 旧钥指纹无命中 |

**不需要**：迁移脚本、影子表、停机窗口。

## 3. 情形 B：从旧库 dump 复制（脚本路径）

### 3.1 前置

- 明确**源域**与**目标域**，两把密钥各自就位（源钥用于解密，目标钥用于加密）；
- **停掉目标域 console**（迁移写入期间），并停掉源域 console 的写入（或至少确认迁移期间无人改配置项）；
- 先在**本地/演练库**跑一遍全流程（含回退），再到域 C 执行。

### 3.2 命令

```bash
# 1) 空转（默认，只读；不改任何数据）
node scripts/master-key-domain-split.mjs \
  --src-env servers/deploy-console/.env \
  --dst-env /tmp/new-domain.env \
  --src-key-file /etc/web-system/config-master.key \
  --dst-key-file /etc/web-system/config-master.key.new \
  --key-id p1

# 2) 确认清单无误后落库
node scripts/master-key-domain-split.mjs ... --apply

# 3) 出问题时回退（用影子表恢复目标库两表）
node scripts/master-key-domain-split.mjs ... --rollback=<时间戳> --apply
```

| 参数 | 必填 | 含义 |
|---|---|---|
| `--src-env` / `--dst-env` | ✅ | 两个域各自的 env 文件（读 `MYSQL_HOST/PORT/USER/PASSWORD/DB`；兼容 `DB_*`） |
| `--src-key-file` / `--dst-key-file` | ✅ | 两把密钥**文件路径**（密钥值禁止走命令行，会进 shell 历史） |
| `--key-id` | — | 写入目标库的 keyId（默认 `p1`；建议与源域区分，便于审计辨识） |
| `--filter-env` | — | 只迁 `env_id=<值>` 的行（`global` 行总是包含；默认迁全部） |
| `--overwrite` | — | 目标库已存在同键行时覆盖（**默认跳过并报告**，避免悄悄盖掉目标域人工配置） |
| `--prune-src` | — | 迁移成功后删除源库对应密文行（**默认保留**；先保留一段时间更安全） |
| `--apply` | — | 真正写入。**不加此参数 = dry-run** |
| `--rollback=<ts>` | — | 从 `<表>_bak_domainsplit_<ts>` 恢复目标库 |
| `--sample=<n>` | — | 回读抽样校验条数（默认 10） |

### 3.3 脚本做什么（可审计的动作清单）

1. 读两个 env → 连库；**若源与目标指向同一实例则直接拒绝**（防误当跨库用）；
2. 打印两把钥的**指纹**（不一致才说明确实换域）；
3. 扫描源库：`is_secret=1` 行数、keyId 分布、`config_snapshots` 条数；
4. **用源钥逐行试解**（解不开 = 源钥不对，立即中止，绝不猜钥）；
5. dry-run 报告：将迁移 N 行 / M 个快照、目标库冲突清单；
6. `--apply`：先在目标库建影子表 `<表>_bak_domainsplit_<ts>`，再逐行「源钥解 → 目标钥加密（带新 keyId）」写入；快照 `payload` 内密文同样处理；
7. 回读目标库抽样解密校验；失败 → 退出码 2 并提示回退命令。

### 3.4 机器侧同步（与迁移同批完成）

| # | 动作 | 校验 |
|---|---|---|
| 1 | 新域所有机器 `provision-master-key.sh --domain <新域>`（写新钥） | 指纹一致 |
| 2 | **移除旧域钥**：旧密钥文件、`.bak`、`.env` 里的 `CONFIG_MASTER_KEY` 行、注入参数 | `verify` 只报新 keyId |
| 3 | 启动各机 console → 启动自检通过 | 日志 `active=<新 keyId>` |

## 4. 验收

| # | 判据 | 口径 |
|---|---|---|
| D1 | 目标域全库可解 | `verify-config-master-key.mjs` 退出码 0，且 keyId 分布**只有新 keyId** |
| D2 | 域确实分离 | 两域**指纹不同**；用源钥解目标库密文必然失败（可抽样验证一条） |
| D3 | 快照一起迁完 | 目标库 `config_snapshots` 数与源库一致（按 `env_id/module_key` 逐组比对） |
| D4 | 旧钥不残留 | 新域机器上无旧钥文件/文件内无旧钥指纹 |
| D5 | 业务可用 | 跑一次真实发布：下发 `.env.generated` 的凭据可用，下游调用成功 |
| D6 | 回退可用 | 演练中执行过一次 `--rollback`，目标库回到迁移前状态且服务可启动 |

## 5. 常见坑（全部会"看起来没事"）

| # | 坑 | 后果 | 规避 |
|---|---|---|---|
| 1 | 只迁 `env`/`module` 行，漏 `global` 行 | 新库解析时 global 层为空 → 缺配置项，报错点远离根因 | 脚本**恒包含 `scope='global'`**；验收比对行数 |
| 2 | 漏迁 `config_snapshots.payload` 密文 | 新库首次回滚写入不可解数据（故障延后引爆） | 脚本处理快照；验收 D3 |
| 3 | 目标库已有同键行被静默覆盖 | 目标域人工配置被旧库值盖掉，无人察觉 | 默认**跳过并报告**，`--overwrite` 才覆盖 |
| 4 | 源钥给错（拿了另一域的钥） | 迁移"成功"但写入一堆垃圾密文 | 脚本第 4 步**逐行试解**，失败即中止 |
| 5 | 迁移后源库继续当权威库用 | 两库分叉，配置漂移 | 迁移后明确**只保留一个权威库**；`--prune-src` 或立即下线旧库入口 |
| 6 | 旧钥残留在新域机器（含 `.bak`） | 域隔离形同虚设 | 验收 D4；`provision` 脚本打印指纹供比对 |
| 7 | 把脚本当"日常同步工具"反复跑 | 目标域被反复改写，审计混乱 | 脚本**一次性用途**；重复执行前先 dry-run 看冲突数 |
