## 背景与问题

deploy-console 是发布控制台单一入口，当前存在结构性缺陷：

1. **build 阶段硬编码**：流水线的 check/pull/upload/restart/verify/cleanup 各阶段都支持模块级 shell 脚本覆盖，**唯独 build 不支持**，构建命令写死为 `nest build`/`vite build`；改一条构建命令必须改 TS → 重建控制台 → 处理端口冲突。
2. **两套互斥机制**：`deploy_modules.buildCmd` 字段 与 `deploy_module_hooks` 的 build 阶段脚本并存，文档互相矛盾（`deploy-pipeline-dev.md:101` 称 buildCmd 已废弃，`release-system-design.md` 则列为模块字段），且都未真正落实。
3. **配置能力缺失**：环境变量/密钥无法页面配置；历史出现过 shell 全局写死 `PORT=6200` 导致端口污染。
4. **可靠性缺口**：回滚只切指针不重建进程、verify 仅查 pm2 status 无真实探活、verify 失败不回滚、无并发锁、DB Migration 未纳入、缺审批/通知/审计/度量。
5. **发布核心从未评审**：`pipeline.service.ts`（九阶段编排）从未被独立子代理评审，是缺陷未被拦截的直接原因。

## 目标用户

- 平台运维：日常发布、监控、排障、配置
- 研发负责人：审批、审计、发布度量

## 验收标准（EARS）

### L1 资源层

- 当 运维查看模块列表时，应能按类型（backend/frontend/micro-frontend/mini-app）分 tab 浏览并显示各类型计数
- 当 环境包含多台服务器时，应能按 serverName 服务器组管理，并将服务路由到指定组
- 当 模块被禁用时，应不出现在可发布清单

### L2 配置层（配置中心）

- 当 运维为「模块 × 环境」保存环境变量时，应落库并在发布/重启时注入进程
- 在 多作用域冲突时，当 执行注入时，应按 模块级 > 环境级 > 全局默认 合并并**强制覆盖**
- 当 保存密钥时，应 AES 加密存储，页面仅显示掩码，不支持读取明文
- 当 回滚到历史版本时，应同步回退该版本关联的配置快照
- 当 配置存在端口冲突/必填缺失/密钥格式错误时，应拒绝保存并提示原因
- 当 配置发生变更时，应记录审计（谁/何时/前后 diff），密钥不记明文

### L3 构建与发布层（命令驱动）

- 当 模块配置了某阶段命令时，pipeline 应在该阶段执行该 shell 命令
- 当 模块未配置可配置阶段（check/pull/build/upload/restart/cleanup）的命令时，pipeline 应在该阶段失败并明确报错，且**不回退任何内置技术栈命令**
- 当 阶段命令退出码非 0 时，应中断发布并将输出写入流水线日志
- 在 命令执行期间，当 超过 timeoutSec 时，应超时中断并标记该阶段失败
- 当 运维按模块类型一键填充默认模板时，应生成对应默认命令（backend 构建→tsc/nest build；前端→vite build）
- 当 发布历史版本且产物已存在时，应跳过 pull/build/upload 并秒级切指针
- 当 构建与上传完成后，应写入版本记录并切换环境指针（version/pointer 固定由流水线执行）

### L4 运行时层

- 当 后端模块发布时，应在目标服务器重建 pm2 进程（PID 变化或端口重新响应），而非仅切指针
- 当 进入 verify 阶段时，应做真实端口/HTTP 探活（非仅 pm2 status），结果写入发布记录与审计
- 当 探活失败时，应阻断发布

### L5 治理层

- 当 同一模块同一环境并发发布时，应串行化或拒绝重复提交，不互相覆盖指针
- 当 提交 prod 发布且未审批时，应被阻断并留审批记录
- 当 任意变更发生时，应可追溯到人/时间/前后 diff

### L6 可观测层

- 当 查看监控时，应能在本机与远程 dev/prod 之间切换，查看 pm2 进程（CPU/内存/端口/重启次数/存活）、探活与日志
- 当 查看发布度量时，应按环境/模块/时间筛选展示成功率与时长趋势

### L7 灰度与回滚

- 当 配置灰度规则（user-list/percent/header）并放量时，命中流量应加载 canary 版本，并支持一键全量/回滚
- 当 执行回滚时，目标进程应实际运行旧版本代码（探活确认）
- 在 verify 失败状态下，当 pipeline 捕获失败时，应自动回滚到上一稳定版本并留痕
- 当 执行版本清理时，应保留最近 N 个版本，被灰度规则引用的版本跳过

### L8 接入层

- 当 通过 MCP/发布 Agent 发布时，应支持按环境+模块+版本发布，prod 发布前必须二次确认
- 当 MCP 发起发布时，审计中的 operator 应为真实 ownerId，不得为 mcp/anonymous/unknown

### L3b 流水线模板与实例（S6 演进，模板=流程定义 / 实例=一次发布）

- 当 运维为模块创建多套流水线模板时，应能按模块浏览模板并创建/编辑/启停/复制默认，模板与模块基本信息、阶段命令相互独立
- 当 提交发布时指定模板，应生成一条引用该模板的实例；实例执行按**提交时模板快照**，模板后续修改/删除不影响已提交实例
- 当 模板启用「跳过 verify」时，该模板的实例应不执行探活验证阶段
- 当 模板审批策略为 always/never 时，应覆盖环境默认规则；为 inherit 时沿用环境规则（默认）
- 当 模板设置默认投递（local/remote）而提交未指定时，实例应使用模板默认
- 当 模块从未显式建模板时，应存在一条不可删除的默认模板，语义等同现状（全阶段 + 环境规则审批）
- 当 查看流水线记录/详情时，应能识别实例所用的模板名称
- 安全：模板管理仅控制台 JWT 可写，不暴露 MCP；MCP 提交不传模板时使用模块默认模板

## 约束

- **兼容**：不破坏现有微前端加载与灰度能力；批 1 已完成成果（本地监控、tab 化、四项 MUST 修复）保留并收编进本 spec
- **安全**：阶段命令与配置仅控制台 JWT 可写，不暴露 MCP；命令保存前 `bash -n` 语法校验
- **性能**：各阶段超时可配；并发发布串行化
- **合规**：密钥明文不落库、不回显、不记入审计
