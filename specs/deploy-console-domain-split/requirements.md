# 需求 spec · deploy-console 双域重构（微前端 / API 网关）

> 状态：**已评审确认 v1.1**（2026-09-18，第 1 轮需求评审通过，见 `review-01-requirements.md`）
> 决策依据：用户在 rd-brainstorm 阶段选定 **方案 B（彻底分家、全新设计）**，并确认 D1–D5 五项前提（见 §1.3）。
> 关联现状：`servers/deploy-console/src/entities/*`、`servers/gateway/src/proxy/proxy.controller.ts`、`servers/gateway/src/entities/gateway-route.entity.ts`、`apps/deploy-console/src/layouts/MainLayout.vue`
> 下游文档：`design.md`（数据模型 + 接口契约）→ 原型稿 `docs/ui/prototypes/`

---

## 0. 一句话背景

当前 deploy-console 用一张 `deploy_modules` 表 + 一根 `type` 字符串（`backend | frontend | micro-frontend | mini-app`）同时承载「前端产物」与「后端进程」两种语义完全不同的东西，导致 28 处 `type` 分支、字段稀疏（`pm2` 与 `publicPath/entry/externals` 互斥列平铺）、"服务"概念缺位（`/modules` 页面的组件名仍是 `ServiceManager.vue`），且环境模型已经出现裂缝（`deploy_environments` 是复合主键 `(module_key, id)`，而 `deploy_deployments.envId`、`deploy_env_service_routes.envId` 仍是扁平全局 env_id）。

本次把 console 拆成 **「微前端」** 与 **「API 网关」** 两大限界上下文，各自有独立的注册、环境、部署模型；流水线层保持不动，作为两域共用的编排器。

## 1. 目标与非目标

### 1.1 目标（做成 = 什么）

| # | 目标 | 可验证定义 |
|---|---|---|
| G1 | **双域分离** | console 存在「微前端」「API 网关」两个一级域，各自独立的应用/服务注册入口；两域的数据模型、环境模型、部署执行逻辑不再互相复用同一张表 |
| G2 | **应用按产品特性定义** | 「微前端 → 应用管理」中以产品视角管理 `portal` / `admin` / `shell`，未来可直接加入独立 PC 应用、小程序，或 portal/admin 拆出的子模块 |
| G3 | **后台叫服务管理** | 「API 网关 → 服务管理」中以服务视角管理 `auth` / `user` / `ai` / `system` … |
| G4 | **接口级粒度** | 服务下的「接口管理」粒度到 **HTTP 方法 + 路径**（如 `POST /api/auth/login`），而非现在 `gateway_routes` 的模块级前缀（`pathPrefix`） |
| G5 | **部署两套逻辑** | 应用部署 = 构建产物 → 静态目录 → 版本指针切换；服务部署 = 构建 → 进程/容器重启 → 健康检查 → 网关上游切换。共用流水线编排，执行层按域分派 |
| G6 | **流水线不动** | 用户对「流水线」的心智与操作方式不变；流水线内部通过统一的 `targetRef` 寻址到任一域的对象 |
| G7 | **环境可多建（并列）** | 同一站点（`dev`）下可建多个**并列环境**（`dev` / `1` / `2` …），每个环境是一个独立加载上下文与产物目录；envId 系统自增，请求未命中时回退 `dev` |

### 1.2 非目标（明确不做）

| # | 非目标 | 理由 |
|---|---|---|
| NG1 | 本次**不实现** docker 运行时 | 只把模型与运行时抽象留出来；pm2 仍是唯一实现（见 NFR-4） |
| NG2 | 本次**不重建**流水线模型（节点/变量/审批/远程执行） | 另有 `specs/pipeline-node-model/` 在推进，避免两个重构叠加 |
| NG3 | 本次**不做** portal/admin 的实际子模块拆分 | 只是让「子模块」在数据模型上可表达，实际拆分由后续需求驱动 |
| NG4 | 本次**不做**接口级鉴权策略的执行引擎 | 只登记 `authMode` / `permissionCode` 等元数据，网关执行侧仅做最小验证（`unknownPolicy` 放行模式），鉴权语义下沉由后续需求驱动 |
| NG5 | 本次**不改** distill Nginx 配置与 micro-frontend 加载协议 | 属于另一层（CDN/externals），不在本次范围 |

### 1.3 已确认前提（用户 2026-09-17 答复）

| # | 问题 | 用户答复 | 设计影响 |
|---|---|---|---|
| D1 | dev1/dev2 语义（**2026-09-18 修订**） | **多个并列环境**（不是同一环境的多实例）：每个 envId 是独立加载上下文与产物目录 | 无 slot 概念；`envId` 系统自增（内置保留字 `dev`/`local`/`prod`）；请求 envId 未命中时回退 `dev` |
| D2 | portal/admin 拆子模块 | **规划中**，按统一模块管理做平，不额外做两级结构 | 应用用**单表平铺** + 可选 `parentKey` 表达归属；子模块与顶层应用在模型上是同构的，不引入「应用→模块」强制层级 |
| D3 | 接口管理粒度 | **要接口级**；现有 `gateway_routes` 只是定义"接口所属模块名"的级别，不够 | 新建 `deploy_endpoints`（方法+路径+鉴权+限流+文档），与转发规则 `deploy_service_routes` 分层；`gateway_routes` 退役并迁移为两者 |
| D4 | 方案选择 | **方案 B，全部重新设计** | 新表全部新建（沿用 `deploy_` 前缀），旧 `deploy_modules` 走「新建 → 双读 → 迁移 → 退役」四阶段 |
| D5 | 允许重写实现 | 是 | 允许重建 Entity / Service / 前端页面，但**流水线表结构（`deploy_pipelines` / `deploy_pipeline_runs`）保持兼容**，只允许加列与兼容解析（见 FR-9.2） |

## 2. 角色与场景

| 角色 | 诉求 | 典型场景 |
|---|---|---|
| **发布操作员**（主要） | 快速找到要发的东西并发布 | "把 admin 发到 dev" / "把 auth 服务发到 prod" |
| **平台运维** | 管理应用/服务的注册、环境、网关路由 | 新增一个后端服务并在网关上暴露它的接口；在 dev 站点下新建一个环境（如「联调环境」）；在某环境详情里改后端服务指向 |
| **前端负责人** | 关心应用、路由挂载、版本灰度 | portal 拆出子模块后，给它配一条 shell 挂载路由 |
| **后端负责人** | 关心服务、接口清单、鉴权标记 | 给 `POST /api/pay/refund` 标上 `service_key` 鉴权模式 |

## 3. 术语表（本次确立，后续文档沿用）

| 术语 | 英文/字段 | 定义 | 对比旧概念 |
|---|---|---|---|
| **应用** | app | 微前端域的可发布构建单元，按产品特性定义（portal/admin/shell/独立 PC 应用/小程序） | 旧 `deploy_modules.type IN (frontend, micro-frontend, mini-app)` |
| **服务** | service | API 网关域的后端进程/容器，网关的前端转发对象 | 旧 `deploy_modules.type = 'backend'` |
| **接口** | endpoint | 服务对外暴露的一条 API（HTTP 方法 + 路径），带鉴权/限流/文档元数据 | 旧无此概念（`gateway_routes` 只有前缀级） |
| **网关路由** | route | 网关转发规则（路径前缀 → 上游服务 + 前缀剥离/重写/超时） | 旧 `gateway_routes`（不在 console 库内，且未被执行） |
| **环境** | env / `envId` | 微前端的**加载维度**：每个 envId 对应一个产物目录 `/static/modules/<appKey>/<envId>/`。内置保留字 `dev`（主开发，回退目标）/ `local` / `prod`（唯一）；用户创建的为**系统自增数字** | 旧 `deploy_environments`（模块私有复合主键，已废弃） |
| **站点** | site | 入口域名（`local` / `dev` / `prod`），决定该域名下可切换哪些环境（`switchable`） | 新增概念 |
| **环境指向** | service route | 某环境下某后端服务的上游地址（主机 + 端口 + 上游 URL），在**环境详情**内编辑 | 旧 `deploy_env_service_routes` |
| **主机** | host | 物理/虚拟部署节点（SSH 目标），带运行时类型 pm2/docker | 旧 `deploy_servers` |
| **目标引用** | targetRef | 跨域统一寻址串：`app:<key>` / `svc:<key>` | 旧 `moduleKey` + `moduleType` 二元组 |
| **域** | domain | `app`（微前端） / `svc`（API 网关） | 旧散落的 `type` 字符串 |

## 4. 功能需求（FR）与验收判据（EARS）

> 判据格式：当〈触发〉时，系统应〈行为〉，使得〈可观测结果〉。

### FR-1 微前端 · 应用管理

| # | 需求 | EARS 验收判据 |
|---|---|---|
| FR-1.1 | 应用列表 | 当用户进入「微前端 → 应用管理」时，系统应展示全部应用（`portal` / `admin` / `shell` 及后续新增），每行包含 key、名称、类型（`shell`/`micro-frontend`/`spa`/`mini-app`）、仓库目录、启用状态、各环境当前版本概览，使得用户无需进入详情页即可判定"该发哪个、现在发到哪了" |
| FR-1.2 | 新建应用 | 当用户提交新建应用表单（key、名称、类型、仓库目录）且 key 全局唯一时，系统应创建应用记录并自动为其创建默认初始化数据（一条 `default` 网关路由/挂载路由模板），使得新应用在保存后立即可被流水线选中 |
| FR-1.3 | key 唯一约束 | 当用户输入已存在的 key 时，系统应拒绝保存并返回明确冲突提示，**不得**产生第二条同 key 记录或静默覆盖 |
| FR-1.4 | 子模块平铺表达 | 当用户为某应用（`portal`）新增一个子模块时，系统应允许以**同构的应用记录**形式创建并可填 `parentKey=portal`，使得子模块无需新表、且其路由/环境/部署管理与顶层应用完全一致 |
| FR-1.5 | 类型即能力约束 | 当用户把某应用类型设为 `shell` 时，系统应在校验中限制其可被挂载的应用数量约束（同一非 shell 应用在同一环境下最多被一个 shell 挂载），使得不满足当前 shell 加载协议的配置不会被写入 |

### FR-2 微前端 · 路由管理

| # | 需求 | EARS 验收判据 |
|---|---|---|
| FR-2.1 | 挂载路由列表 | 当用户打开某应用的「路由」页签时，系统应列出其在 shell 中的挂载点（`mountPath` 如 `/admin`）、激活规则（`activeRule`）、是否需要鉴权、排序，使得 portal/admin 的入口挂载变化集中可查 |
| FR-2.2 | 路由冲突检测 | 当用户新增/修改一条挂载路由且其 `mountPath` 与同 shell 下已有路由重复时，系统应拒绝并提示冲突方，使得 shell 不会出现两条同挂载点的路由 |
| FR-2.3 | 路由变更不自动上线 | 当用户保存路由变更后，系统应**只更新配置数据**、不触发任何发布动作，使得"改路由"与"发布"是两个显式的独立动作 |

### FR-3 微前端 · 环境（**2026-09-18 按新模型重写**）

| # | 需求 | EARS 验收判据 |
|---|---|---|
| FR-3.1 | 环境列表 | 当用户进入「微前端 → 环境管理」时，系统应列出全部环境（`envId` / 名称 / 站点 / 类型 / 排序 / 内置 / 启用），并支持按站点筛选 + 关键字搜索 + 分页（每页 20），使得环境达几十个时仍可定位 |
| FR-3.2 | 新建环境 | 当用户新增环境时，系统应**由系统自增生成 envId**（用户不可填），只要求填写名称与归属站点，使得 envId 始终满足目录名安全要求 |
| FR-3.3 | envId 回退 | 当运行时传入的 envId 在环境表中不存在时，系统应回退到内置 `dev`，使得失效的本地选择不会导致页面白屏 |
| FR-3.4 | prod 唯一 | 当用户创建 `isProd=true` 的环境时，系统应保证全局至多一条，使得"生产只有一个环境"在数据层被强制 |
| FR-3.5 | 环境删除保护 | 当用户尝试删除某环境且该 envId 下仍存在有效部署记录（任意应用 `currentVersion` 非空）时，系统应拒绝删除并列出占用者 |
| FR-3.6 | 环境详情 · 后端服务指向 | 当用户打开某环境详情并进入「后端服务指向」时，系统应列出该环境下各服务的上游指向（主机 / 端口 / 上游地址 / 启用）并允许修改，使得"改某个环境的后端指向"只有唯一入口 |
| FR-3.7 | 指向校验 | 当用户保存某服务的指向且主机为空时，系统应拒绝保存（提示必填），**不得**静默回落到 localhost |
| FR-3.8 | 环境切换（产品页） | 当开发者在产品页挂件选择某环境时，系统应写入本地选择并**整页重载**，随后按该 envId 加载产物并解析该环境的后端指向，使得前端产物与后端指向同时切换 |

### FR-4 微前端 · 部署（应用侧）

| # | 需求 | EARS 验收判据 |
|---|---|---|
| FR-4.1 | 应用部署视图 | 当用户打开某应用的「部署」页签时，系统应**按环境逐行**展示当前版本、发布时间、发布人、状态与操作（部署 / 切换版本 / 回滚），使得应用侧看到的永远是"哪个环境跑着哪个版本" |
| FR-4.2 | 版本指针切换 | 当用户执行版本切换时，系统应先在弹窗中**选择目标版本**，确认后原子地改写该环境的指针并把旧值写入 `previousVersion`，使得下一次 `__manifest__` 读到新版本且可回滚 |
| FR-4.2b | 回滚 | 当用户执行回滚时，系统应在弹窗中**选择回滚到的版本**（默认预选上一版本），确认后把该环境入口指针指回所选版本 |
| FR-4.5 | 版本产物保留（Q105-B） | 当发布 / 切换 / 回滚发生时，系统应保留 `envId/<version>/` 下的历史产物（默认保留 5 版且不超过 7 天），并只改写 `envId/index.js` 入口指针，使得正在使用旧版本的浏览器不会因分包被删而 404 |
| FR-4.3 | 域名 homelessness 隔离 | 当用户对 `app:admin` 执行部署时，系统应**只**执行"构建产物 → 上传静态目录 → 切版本指针"的应用侧动作，**不得**触碰任何 pm2 进程或服务端口（详见 FR-6.4 分派约束），使得应用发布不会误重启后端服务 |
| FR-4.4 |Shell 特例收敛 | 当发布对象是 `kind=shell` 的应用时，系统应仍按应用侧流程执行（产物 + 版本指针），只是额外触发 gateway 静态资源刷新，**不得**复用"服务重启"流程 |

### FR-5 API 网关 · 服务管理

| # | 需求 | EARS 验收判据 |
|---|---|---|
| FR-5.1 | 服务列表 | 当用户进入「API 网关 → 服务管理」时，系统应列出全部后端服务（`auth`/`user`/`ai`/`system`/…含 `gateway` 自身），每行含 key、名称、类型、仓库目录、健康检查路径、默认端口、启用状态、各环境健康状态概览 |
| FR-5.2 | 新建服务 | 当用户新建服务并指定仓库目录（`servers/<dir>`）时，系统应在保存前校验该目录在发布工作区内存在，使得写错目录的服务不会被登记 |
| FR-5.3 | 服务退役保护 | 当用户尝试删除某服务且该服务仍有启用中的网关路由或接口时，系统应拒绝删除并列出引用者，使得网关不会出现指向不存在服务的路由 |

### FR-6 API 网关 · 接口管理（重点）

| # | 需求 | EARS 验收判据 |
|---|---|---|
| FR-6.1 | 接口级登记 | 当用户为某服务登记一条接口（HTTP 方法 + 路径模式 + 鉴权模式 + 可选权限码 + 摘要）时，系统应持久化该接口，使得粒度细于当前的「路径前缀（`pathPrefix`）」级别 |
| FR-6.2 | 路径模式 | 当接口路径含动态段（`/api/todo/:id`）时，系统应支持占位符登记并在匹配时把同层不同 id 归为同一条接口，使得接口清单不被数据 id 撑爆 |
| FR-6.3 | 方法区分 | 当用户登记 `GET /api/x` 后又登记 `POST /api/x` 时，系统应视为两条独立接口并允许不同鉴权模式，使得读写分离能配置不同策略 |
| FR-6.4 | 请求落未登记接口 | 当网关收到一条未登记接口的请求时，系统应按该服务的 `unknownPolicy`（默认 `allow`）决定是否放行，并在命中时记一条观测记录，使得"先接进来再补登记"的迁移期行为可控 |
| FR-6.5 | 批量导入 | 当用户以 OpenAPI/Swagger 或清单文件批量导入接口时，系统应 UPSERT（按 `serviceKey + method + pathPattern` 幂等），已存在的接口**只补全空字段、不覆盖已有人工配置**，使得重复导入不会冲掉手工调整 |
| FR-6.6 | 接口变更不影响转发 | 当用户修改某接口的鉴权模式或摘要时，系统应**只**更新接口元数据、不改变任何转发规则，使得"接口清单"与"转发行为"解耦 |

### FR-7 API 网关 · 网关路由

| # | 需求 | EARS 验收判据 |
|---|---|---|
| FR-7.1 | 路由列表 | 当用户打开某服务的「网关路由」时，系统应列出该服务在各环境下的转发规则（前缀、剥离规则、重写目标、超时、鉴权模式、优先级、启用），使得"一个请求怎么被转走"可查可改 |
| FR-7.2 | 优先级冲突提示 | 当同一环境下两条启用路由的前缀存在包含关系（如 `/api` 与 `/api/auth`）时，系统应展示提示（允许保存），并明确数值小者优先，使得用户能预判匹配结果而非靠猜 |
| FR-7.3 | 环境级覆盖 | 当用户为 `dev` 环境单独设置一条上游覆盖（指向另一台主机/端口）时，系统应只在 `dev` 生效且不影响 `prod` 同名路由 |
| FR-7.4 | 禁用生效 | 当用户禁用某条路由时，网关应在缓存 TTL（≤60s）内停止匹配该路由，使得禁用是即时可感知的运维动作 |

### FR-8 API 网关 · 服务环境与部署

| # | 需求 | EARS 验收判据 |
|---|---|---|
| FR-8.1 | 服务环境配置 | 当用户为 `(serviceKey, envId)` 配置目标主机、端口、副本数、运行时（pm2/docker）、健康检查路径时，系统应持久化并在部署时按此执行；**编辑入口为环境详情（FR-3.6），服务详情只读展示** |
| FR-8.2 | 健康检查 | 当服务部署完成后，系统应调用该服务的 `healthPath` 做探活并把结果写入部署记录；探活失败应使本次部署标记为失败（是否回滚由流水线模板的 `rollbackOnFailure` 决定），使得"上线成功"以真实可服务为准而非进程存在为准 |
| FR-8.3 | 服务侧隔离 | 当发布对象是 `svc:*` 时，系统应执行"构建 → 上传 → 进程/容器重启 → 探活 → 网关上游就绪"的服务侧动作，**不得**写 `deploy_app_env_versions` 的指针，使得服务发布不会污染前端 manifest |
| FR-8.4 | 环境数量（原「并行实例约束」作废） | 环境之间相互独立，**不限制同一站点下的环境数量**（D1 已修订为"并列环境"）；仅要求每个环境配置自己的端口与运行时，冲突时在环境详情给出提示 |

### FR-9 流水线跨域寻址（约束，非重做）

| # | 需求 | EARS 验收判据 |
|---|---|---|
| FR-9.1 | 目标引用 | 当流水线模板/运行实例引用一个发布对象时，系统应以 `targetRef`（`app:<key>` / `svc:<key>`）寻址，使得流水线层不需要知道对象属于哪个域 |
| FR-9.2 | 兼容旧数据 | 当流水线表读到历史 `moduleKey`（无前缀，如 `admin`）时，系统应按「先看 apps 后看 services」的顺序解析成 `targetRef`，使得**历史流水线与历史运行记录无需数据改造即可继续工作** |
| FR-9.3 | 不改流水线 UI | 当用户操作「流水线」菜单（列表/编辑/运行/灰度/诊断）时，其行为与本次重构前保持一致，使得本需求不引入流水线侧的操作习惯变更 |
| FR-9.4 | 工作目录推导 | 当执行器需要推导构建目录时，系统应按 `domain` 决定根目录（应用 → `apps/<dir>`，服务 → `servers/<dir>`），**不得**再依赖 `type === 'backend'` 之类的字符串判断 |

### FR-10 gateway 运行时消费

| # | 需求 | EARS 验收判据 |
|---|---|---|
| FR-10.1 | manifest 结构改造 | 当 gateway 生成 `__manifest__` 时，应返回该站点的 `{ site, defaultEnv, switchable, envs[], byEnv{} }`（由 Host 匹配站点、由 `deploy_app_env_versions` 取各环境入口），兼容期内保留旧字段用于回落，使得前端可按用户选择的环境加载对应目录产物 |
| FR-10.2 | 转发规则数据源切换 | 当 gateway 处理 `/api/*` 请求时，应优先从 `deploy_service_routes`（按 env + priority）匹配，匹配不到再回落到硬编码路由表，使得路由管理真正驱动运行时，而非只是静态登记 |
| FR-10.3 | 缓存与热更新 | 当网关加载上述配置时，应使用带 TTL 的本地缓存（≤60s）并提供手动刷新入口，使得改路由不必重启 gateway 且不会被 DB 拖慢 |

## 5. 边界与反例（必须在实现中被显式处理）

| # | 反例 / 边界 | 期望行为 |
|---|---|---|
| B1 | 用同一份表单同时填了 `publicPath`（应用字段）和 `pm2Name`（服务字段） | 不可能发生：两域是两张表的两个入口，字段不共存 |
| B2 | 用户在「应用管理」里修改了 `admin` 的 key，导致 gateway manifest 按旧 key 取不到版本 | 应用的 **key 创建后不可编辑**，只允许改名称/描述；确需改 key 必须走"新建 + 迁移" |
| B3 | 用户本地选择的环境（`localStorage`）已被删除 / 不在站点可切换列表中 | 回退到站点 `defaultEnv`（缺省 `dev`）并正常加载；**不得**报错或白屏（FR-3.3） |
| B4 | 某服务在 `dev` 未配置目标主机 | 部署时立即 fail-fast 并提示「未配置 dev 环境目标主机」，**不得**回落到 localhost 静默发到错机器 |
| B5 | 删除某应用后，其历史版本指针与流水线运行记录里仍有引用 | 采用**软删除**（`enabled=false` / `deletedAt`），历史记录继续可查；硬删除仅在无任何引用时允许 |
| B6 | 同一服务对象同时在「服务管理」和旧的「模块管理」里被登记 | 迁移期内以新表为准，旧表只读；切换后旧 `deploy_modules` 不参与任何运行时查询 |
| B7 | 接口导入时同一路径大小写不同（`/api/User` vs `/api/user`） | 按原样登记为**两条**，并在导入结果里标注"疑似重复"提示，由人决定合并，**不得**自动归一化（避免误改真实路由） |
| B8 | gateway 自身既是服务对象又在提供 manifest | `gateway` 作为普通服务登记；其版本/依赖采取独立托管策略（沿用 `specs/deploy-console/gateway-and-shell-versioned-release.md` 的约定），不因本次改造改变发布通道 |
| B9 | 绕过 UI 直接调接口创建 envId 含非法字符（`/`、`..`、空格）的环境 | 后端必须做**目录名安全校验**（数字或 `[a-z0-9_-]+`），不能只靠前端拦截（envId 会作为 URL 段与目录名） |

## 6. 非功能需求（NFR）

| # | 需求 | 判据 |
|---|---|---|
| NFR-1 | 可灰度切换 | 新旧两套数据源必须能共存运行 ≥1 个发布周期，支持按环境一键回落到旧逻辑 |
| NFR-2 | 数据可迁移 | 现有 16 个登记对象（12 backend + shell + portal + admin + mini-contract）必须能用幂等脚本一次性迁入新模型，且流水线历史记录零丢失 |
| NFR-3 | 迁移幂等 | 迁移脚本重复执行不产生重复数据（按业务主键 UPSERT） |
| NFR-4 | 运行时抽象 | 执行层对 pm2/docker 的差异收敛在一个策略接口后；本次只实现 pm2，但不得在业务代码里写死 `pm2 restart` |
| NFR-5 | 类型安全 | 全部 Entity/DTO 走 TS strict，禁止 `any`；跨域判断用联合类型 `AppKind | ServiceKind`，**不得**再出现裸字符串 `'micro-frontend'` 判断 |
| NFR-6 | 与流水线重构解耦 | 本需求不得改动 `deploy_pipelines` / `deploy_pipeline_runs` 的表结构；只允许「加列 + 兼容解析」（见 FR-9.2） |
| NFR-7 | 命名一致性 | 前端页面组件名必须与领域一致：`AppManager.vue` / `ServiceManager.vue`，杜绝 `/modules` 路由挂 `ServiceManager` 这类错位 |
