## 一、决策清单

| # | 决策 | 结论 | 替代方案与被否原因 |
|---|---|---|---|
| D1 | 通道形态 | **企微自建应用 + OAuth 免登 H5**（B） | A 签名链接：外泄即失控，prod 门禁变成"谁有链接谁能批"；C 企微 OA 审批：模板字段映射 + 审批人两处维护，单人公司收益不抵复杂度 |
| D2 | 身份存放 | **`users` 表加 `wecom_userid` + `unionid` 两列** | ①console 本地映射表：只对 console 有效，未来小程序要再打通一次；②独立 `user_external_identities` 表：与既有 `mp_openid`/`oa_openid` 形成双真源，且要迁存量 + 改 auth-service 登录链路 |
| D3 | 身份解析入口 | **user-service `POST /internal/identities/{resolve,bind,unbind}` 唯一契约** | 各服务直连 users 表：列名/合并/停用规则会在每个调用方复制一遍，必然漂移 |
| D4 | 解析失败的处理 | **fail-closed（403）** | 沿用既有 `ApproverService` 的"降级放行"：那条规则是历史宽松策略，用在新通道等于谁都能批 prod |
| D5 | 审批人数量 | 单人（你），不做或签 | 与拍板 #3 一致；列结构不限制后续加人 |
| D6 | 打包方式 | **两张卡**（身份层 1.5 日 / 审批通道 2 日） | 合并成一张 3.5 日：超「M ≤ 2 日」定义，且身份层可独立交付、独立回滚 |
| D7 | 审批单过期 | 不做 | 会改变既有语义（现在 pending 永不过期）；要做得另开卡，不要夹带 |
| D8 | 出站安全机制 | **企业可信IP = dev 固定出口 IP 一个**（`175.27.189.123`） | 期望"用可信域名替代 IP 加白"不成立：可信域名管入站、可信IP 管出站，二者正交；新应用不配可信IP 一律 60020 |
| D9 | 本地联调方式 | **不把本地动态 IP 加白**：mock 为主，真链路走 SSH 隧道 / dev 代理借 dev EIP | 临时加白本地公网 IP：动态 IP 易变、无过期机制、留审计债；仅极应急且用完必删 |

## 二、D2 的关键论据（这是本次最容易做错的一处）

### 事实（2026-11-04 13:50 只读核实）

| # | 事实 | 位置 |
|---|---|---|
| F1 | `users` 表**已有** `mp_openid`、`oa_openid`，且都带 `@Index()` | `packages/shared/src/entities/user.entity.ts:68-76` |
| F2 | 无 `unionid`、无企微 `userid` | 同文件全文 |
| F3 | 用户实体是 packages/shared 单一真源，多服务共用 | `:4-11` |
| F4 | 生产 `synchronize=false`，加列必须手写迁移 + 手工执行 DDL | `:124-132`、`:134-147` 注释 |
| F5 | `merged_to` 账号合并已存在，auth-service 裸 SQL 写 | `:82-103` |
| F6 | 登记进实体但漏写迁移 → synchronize 反向 DROP（本机 development 才会抖） | `:36-38` |

### 推理

1. **事实 F1 直接否掉独立表方案（短期）**：微信渠道的身份已经在 `users` 用列存了。再建一张表承接"渠道身份"，同一事实就有两处真源 —— 那么 `mp_openid` 到底还算不算数？任何"某处改了另一处没改"的场景都会变成线上 bug，且只在登录时暴露。
2. **D2 不是"偷懒不建表"，是"不为 3 个渠道建第 4 套抽象"**：渠道枚举就三个（wecom/mp/oa），加列即可穷举；真正的复用价值在**解析契约**（D3），不在表结构。
3. **D2 的代价被 F4 放大**：加列要动生产 DDL。所以卡① 的完成判据里必须包含"dev/prod 各执行一次 + `SHOW COLUMNS` 证据"（V15），否则代码绿、线上红。
4. **D2 的已知天花板**：`oa_openid` 单列天然只存一个公众号。这是**既有限制**，不是本次引入；一旦要支持"一人多公众号/多小程序"，必须升级为独立表 —— 升级路径见下，是可迁移的，不是推倒重来。

### 升级路径（真到那天按这个走，不要临时发明）

```
第 1 步：建 user_external_identities(user_id, channel, external_id, union_id, enabled)
第 2 步：把 users.mp_openid / oa_openid / wecom_userid 存量回填进去（一次性脚本）
第 3 步：identities/resolve 改读新表；users 三列**保留**但降级为「主账号绑定」只读取值
第 4 步：观察 2 个发布周期，确认无调用方读列后，再决定是否删列
```
关键：**第 3 步之前不要删列**，否则回滚无路。

## 三、D4 的现场依据

既有 `ApproverService.canApprove()`：

```ts
const { users, degraded, reason } = await this.list();
if (degraded) return { ok: true, degraded: true, reason }; // 降级放行
```

| 场景 | 既有通道 | 企微通道（本需求） |
|---|---|---|
| user-service 超时 | **放行** + 告警 | **拒绝**（403） |
| 可审批人清单为空 | **放行** + 告警 | **拒绝** |
| 理由 | 紧急回滚时不能被权限服务卡死（控制台本身要登录、有 JWT，风险可控） | 企微页面的**唯一**身份来源就是这条解析；放行 = 任何拿到链接的人都能批 prod |

> 结论：**同一个降级策略不能跨通道平移**。这条要写进代码注释，否则后人"统一一下"就把门拆了。
> 另：既有降级放行本身要不要收紧，属另一张卡（不在本需求范围，避免范围膨胀）。

## 四、D8/D9 的现场依据（企微出站安全）

| # | 事实 | 判据 |
|---|---|---|
| E1 | 新创建的自建应用（2022-06-28 后）**不配「企业可信IP」无法调用任何企微接口** | 企微官方：60020 `not allow to access from your ip` |
| E2 | 可信域名（应用详情「网页授权及JS-SDK」）只校验**入站**归属：网页授权回调、JS-SDK 安全域名 | OAuth 回调可用、但换 token / 发消息仍 60020 |
| E3 | dev 平台公网出口固定为 `175.27.189.123` | 用户确认（`docs/plans/2026-10-31-发布运行时与配置契约-改动清单.md` 同值） |
| E4 | console 单点在 dev，本地只作开发测试 | 项目既定架构 |

推理：**可信域名替代不了可信IP** —— 两者管的是相反方向。"接口层面解决"这个期望只能落在「把出站收敛成一个固定出口」上，而不是"换一种鉴权方式免掉加白"。

> 完整机制、60020 排查三步、本地借道四种方式 → [`docs/development/wecom-api-trusted-ip.md`](../../docs/development/wecom-api-trusted-ip.md)

## 五、否决方案存档（免得下次重走一遍）

| 方案 | 一句话否决理由 | 什么条件下重新考虑 |
|---|---|---|
| 纯群机器人 + 普通 markdown 链接（无签名、无身份） | 无身份、无幂等、无审计主体 | 永不（连 A 都不如） |
| A 签名链接作为**唯一**方案 | 链接外泄 = 审批权外泄 | 只有"单人 + 群也只有自己"的临时应急场景 |
| C 企微 OA 审批 | 模板字段固定 + 审批人双维护 + 双向回调 | 出现"需要多级审批 / 需要企微侧合规留痕"的真实需求 |
| console 自建映射表 | 未来每个端都要重建一次 | 若有一天 console 独立于 web_system 部署且不能调 user-service |
| 独立 `user_external_identities` 表（**现在做**） | 双真源 + 动登录链路 | 要支持"一人多公众号/多小程序"时（见 §二 升级路径） |
| 用 MCP Key 让 AI 代批 | 与「手动确认」语义相反 | 永不作为本需求方案（MCP 通道已独立存在） |
| 把本地动态公网 IP 加进企业可信IP | 家庭/办公 IP 会变、无过期机制、留审计债 | 永不作为常态方案；仅极应急且用完立刻删 |
