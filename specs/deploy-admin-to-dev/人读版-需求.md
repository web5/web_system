# admin 发到 dev —— 需求（人读版）

> **这份文档只讲「要什么、为什么、怎么算成功」**，5 分钟可读完。
> 要写代码 / 改配置时再看：字段与判据 [`requirements.md`](./requirements.md) · 接口 [`api-design.md`](./api-design.md) · 脚本 [`scripts.md`](./scripts.md) · 任务 [`tasks.md`](./tasks.md) · 设计 [`人读版-设计.md`](./人读版-设计.md)

**一句话目标：让本机控制台能一键把 admin 真正发到 dev 环境（而不是只打个 dev 标签）。**

---

## 1 现在的毛病

在本机控制台选「环境 = dev」发布 admin，**看起来成功，dev 什么都没变**：

| 环节 | 实际发生了什么 | 后果 |
|---|---|---|
| 投递产物 | 配置是 `PIPELINE_UPLOAD_TARGET=local` → 产物进了**本机**发布目录 | dev 机上没有产物 |
| 写版本 / 切指针 | 写的是**本机**的发布库 | dev 的 gateway 读不到新指针 |
| 探活 | 查本机 `localhost:6000/__manifest__` | 断言必然失败 → 触发自动回滚 |

说白了：**「环境」现在只是个标签，不是真的目标。** 这是本次要解决的核心问题。

---

## 2 做成什么样算成功

发布一次之后，下面 5 件事同时成立：

1. 本机控制台页面提交 `环境=dev + 模块=admin + 分支`，流水线**显示成功**
2. dev 机上出现了这次 commit 的产物：`/data/web_system/servers/gateway/public/static/modules/admin/default/<commit>/`
3. dev 的版本指针切到了这次 commit（dev 自己的库记录）
4. 打开 `https://dev.kedouai.com/__manifest__`，admin 的版本 = 这次 commit
5. 直接访问产物 URL 返回 200

**并且**：`环境=local` 的发布行为**和现在一模一样**，一点没变。

---

## 3 谁怎么用

| 角色 | 怎么用 |
|---|---|
| 运维 | 本机控制台 → 发起发布 → 选 `dev` / `admin` / 分支 → 一键提交，看探活结果 |
| 研发 | 改完 admin 代码 push，然后在页面上发一次 dev 验证 |
| Agent | 调 MCP `publish_pipeline(env=dev, moduleKey=admin, branch=...)`，等价于页面操作 |

两个入口（页面 / MCP）走的是同一套逻辑，结果必须一致。

---

## 4 关键选择（已拍板，看结论即可）

| 问题 | 结论 | 为什么 |
|---|---|---|
| 版本 / 指针怎么写？ | **本机不碰 dev 的数据库**，改由**远端控制台接口**代写 | 数据库写操作只留一个出口，安全、可审计、自带幂等 |
| 用哪个接口？ | 复用已有的 `POST /api/hooks/release`（HMAC 签名） | dev 机已有；锁 / 审计 / 回滚语义免费继承，不用新造接口 |
| 远端会不会顺手重新构建一遍？ | **不会**：请求带上 commit 后，远端发现产物已存在 → 跳过拉码 / 构建 / 投递 | 产物由本机构建后投递过去，远端只做「写版本 + 切指针」 |
| 探活谁做？ | **本机做**（curl dev 域名断言） | 本机能直连 dev 域名，一次请求就能判定闭环，不用等远端任务结束 |
| 代码拉取怎么写？ | 落成 **DB 脚本**（与其它阶段同一种存放方式），但**锁定不可编辑** | 既进"真相源"（可审计 / 可 SQL 调整 / 可随迁移同步），又不允许页面乱改 |
| 拉哪个分支、怎么确认？ | 分支由发起端传入；**最终代码由 commit 决定**；拉不到就失败 | 见 §5「不许静默降级」 |
| 出问题怎么办？ | dev 指针不动即"没发"；本机探活失败会标记失败并按既有规则回滚 | 复用平台既有回滚语义 |

> 完整的 D1~D10 决策记录（含每条的依据）在 [`requirements.md`](./requirements.md) §决策记录。

## 5 前提与风险（动手前必看）

**前提**

- 本机能 SSH 到 dev 应用机（{{DEV_HOST}}），且私钥可读
- dev 应用机的发布目录是 git clone（`/data/web_system`，master，origin 可达）—— 已实测
- 两端的 `RELEASE_HOOK_SECRET` 相同（已存在）
- 需要在配置中心补两条 dev 的地址：远端控制台地址、远端 gateway 地址

**风险 / 需要知道的坑**

| 风险 | 说明 | 我们的处理 |
|---|---|---|
| 发错版本（最危险） | "传了 commit 却打出分支最新代码" 是历史高危 | 拉码脚本**前置校验 + 自证**，拉不到直接失败；平台再做一次全量校验（双保险） |
| 本机已有同 commit 产物 | 平台的"复用产物"逻辑会连**投递**一起跳过 → dev 没产物但指针已切 | 明确要求：复用只跳构建，**投递必须执行** |
| 远端被顺带切分支 | 只有"远端没有该产物"时远端才会真拉码，会切换远端目录的分支 | 正常链路因"复用"根本不拉码；实现上强制带 commit + 分支 |
| 两端各有一把发布锁 | 同一模块不能同时从两端发 | 约定：同一模块同一时间只从一端发 |
| 两端脚本不一致 | dev 机若没跑新迁移，它的拉码走内置逻辑 | 本期远端不拉码，不影响；后续靠迁移补齐 |

---

## 6 范围

**做**：admin 从本机控制台发到 dev（页面 + MCP 两个入口）；产物投递、版本/指针接口化、探活闭环；`local` 零回归。

**不做**：从 dev 机发起发布；prod 验证；远端灰度；远端旧版本清理（现状本来就是跳过）。

---

## 7 一页流程图

```
① 本机：拉码（DB 锁定脚本）→ ② 构建 admin 产物
                                       ↓
③ 本机：tar + scp 投递到 dev 机 /data/web_system/.../modules/admin/default/<commit>/
                                       ↓
④ 本机调 dev 控制台接口（HMAC）：dev 写版本记录 + 切指针（唯一动 DB 的入口）
                                       ↓
⑤ 本机：等 10s 缓存过期 → 断言 dev 的 __manifest__ 版本 = 本次 commit、产物 200
                                       ↓
                                  成功 / 失败（失败则留日志，按既有规则回滚）
```
