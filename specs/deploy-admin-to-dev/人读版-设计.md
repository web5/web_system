# admin 发到 dev —— 设计（人读版）

> **这份文档讲「怎么实现、为什么这样分工」**，10 分钟可读完。
> 要落地时再看：设计 [`design.md`](./design.md) · 接口 [`api-design.md`](./api-design.md) · 脚本 [`scripts.md`](./scripts.md) · 任务 [`tasks.md`](./tasks.md) · 需求 [`人读版-需求.md`](./人读版-需求.md)

**一句话设计：本机负责「构建 + 投递 + 探活」，dev 机负责「写版本 + 切指针」，两者之间只通过一个 HMAC 接口对话。**

---

## 1 一张图看懂

```
             本机（发起端 · :6200）                        dev 环境（{{DEV_HOST}}）
 ┌────────────────────────────────────────┐        ┌────────────────────────────────────┐
 │ ① 拉码   DB 锁定脚本，拉本机发布目录     │        │                                    │
 │ ② 构建   vite build --mode mf           │        │                                    │
 │ ③ 投递   tar + scp ─────────────────────┼───────►│ /data/web_system/servers/gateway/  │
 │                                         │        │   public/static/modules/admin/     │
 │ ④ 调接口 HMAC ──────────────────────────┼───────►│   default/<commit>/                │
 │                                         │        │ dev 控制台 :6200                   │
 │ ⑤ 探活   curl dev 域名 ◄────────────────┼────────│   → 写版本表 + 切指针（唯一动 DB） │
 │    断言 manifest 版本 + 产物 200         │        │ gateway :6000 → 读指针出 manifest  │
 └────────────────────────────────────────┘        └────────────────────────────────────┘
```

**为什么这么切？** 产物必须在**有代码的机器**上构建（本机），指针必须在**服务该环境 gateway 的库**里改（dev）。所以一端管"物"，一端管"账"，中间用接口对接。

---

## 2 三件事、三种做法

这是本次设计的核心取舍：**能用脚本的用脚本，不得已才做接口，碰数据库的一律走接口。**

| 事情 | 做法 | 为什么 |
|---|---|---|
| 拉码（git） | **DB 脚本**（锁定，页面只读） | 与其它阶段同一种存放方式；可在 DB 审计 / 调整 / 随迁移同步到另一台机器，但不允许页面改坏发布语义 |
| 投递、探活、重启、清理 | **DB 脚本**（页面可编辑） | 与机器 / 环境强相关，运维需要按环境微调 |
| 写版本、切指针 | **接口**（远端控制台的 HMAC 端点） | 数据库写操作只留一个出口：锁 / 审批 / 审计 / 回滚全部继承，本机不需要持有 dev 的库凭证 |

## 3 五个环节各自怎么工作

### ① 拉码：代码从哪来，怎么保证没错

- **拉哪台机的目录？** 各自拉各自的。本机拉本机发布目录（`~/web_system_release`），dev 机拉 `/data/web_system`；本机**不会** SSH 到 dev 去跑 git。
- **拉哪个分支？** 发起时选的分支（下拉来自远端 `origin/*` 列表，缺省 master）。
- **最终代码是什么？** **由 commit 决定**（`reset --hard <commit>`），分支只决定"从哪取"。所以分支名不一致不会发错代码。
- **怎么保证不错？** 脚本四处 fail-fast：没有 origin → 失败；分支不存在 → 失败；commit 拉不到 → 失败（提示先 push）；重置后自证 HEAD = 目标 commit。
- **平台还会再验一遍：** 拉完读实际 HEAD，和请求里的 commit 做**全量比对**，不一致就停止 —— 脚本可以换，这道端到端校验不能少。

> 关键：**正常链路远端根本不会拉码**。请求带 commit 后，远端发现产物已存在（本机刚投递的）→ 跳过拉码 / 构建 / 投递，只写版本 + 切指针。
> ⚠️ 但这条**目前还不成立**：负责"发现产物已存在"的 `check` 阶段现在被整段跳过（实测日志 `[check] 校验 未配置脚本，已跳过（optional）`）→ 必须先修，见 §7 第 0 步。

### ② 构建：本机构建

用现有 R6 构建命令（`vite build --mode mf`），产物在 `apps/admin/dist`。**这一步没有变化**，只是产物不再只留本机。

### ③ 投递：tar + scp 到 dev

- 打包本机产物 → `scp` 到 dev 机 → 解包到 `.../modules/admin/default/<commit>/`
- 目标目录已存在时**先改名移出**（不用 `rm -rf`，避免触发批量删除审批）
- 解包后断言 `index.js` 存在（提前暴露"投递成功但内容为空"）

### ④ 写版本 + 切指针：走接口

- 调 `POST http://{{DEV_HOST}}:6200/api/hooks/release`，HMAC-SHA256 签名 + 时间戳窗口
- 请求带 `deliveryId`（`local-<commit>-admin`）做幂等：重复提交不会发第二次
- 远端收到后：因产物已存在 → 直接写版本表 + 切指针 → 完成
- **本机不写 dev 的库**，也不需要 dev 的数据库密码

### ⑤ 探活：本机自己断言

- 等 10 秒（gateway 版本缓存 TTL）+ 2 秒余量
- 断言 1：`https://dev.kedouai.com/__manifest__` 里 admin 的版本 = `default/<commit>`
- 断言 2：`.../static/modules/admin/default/<commit>/index.js` 返回 200
- 任一失败 → 流水线标记失败并打印实际值 vs 期望值

> 为什么不改执行体、而是把断言写进 DB 的 verify 命令？因为**模板已配 verify 命令，会覆盖内置执行体** —— 只改执行体的话断言永远不会被执行（这是个"看起来成功"的陷阱）。

## 4 数据与配置从哪来

| 需要什么 | 从哪取 | 现状 |
|---|---|---|
| dev 机 host / 用户 / 私钥 / 部署目录 | `deploy_servers` 表的 `dev-default` 行 | 已存在 |
| dev 的 gateway 地址 / 控制台地址 | 配置中心（环境级，env=dev） | 需补 2 条 |
| HMAC 密钥 | 两端 `.env` 同值 | 已存在 |
| 分支下拉 | 本机发布目录的 `origin/*` 列表 | 复用现有接口 |

**缺任何一项都不许"悄悄退回本机"** —— 直接报错，并提示缺哪个配置。

---

## 5 `local` 为什么不会受影响

| 场景 | 结果 |
|---|---|
| 发布 `env=local` | 完全走原路径：本机投递、本机写库、本机探活，**行为与现在一致** |
| `env=local` 的 verify | 保持现状（跳过探活），**不新增断言** → 本机发布的严格度不变 |
| 没 seed 拉码脚本的模板 | 回退到内置拉码逻辑，行为不变 |

保证方式：所有新行为都由「环境 = dev」这个条件分支触发，`local` 分支原样保留，并由单测守护。

## 6 要改哪些地方（人话版）

| 改什么 | 目的 |
|---|---|
| 环境 → 发布目标的解析器 | `local` 发本机、`dev` 发远端；配不到就报错 |
| 目标机读取 | 从 `deploy_servers` 表按环境取，不再只看全局配置 |
| 下发变量 | 给脚本补上目标机、地址、commit 等变量 |
| 节点命令表加 `locked` 列 + 迁移 seed 拉码脚本 | 拉码进 DB 但不可编辑 |
| 引擎执行拉码节点 | 有 DB 脚本执行脚本，没有就回退内置 |
| 投递 / 探活脚本 | 按环境走远端 |
| 探活断言落 DB verify 命令 | 真正执行 manifest + 产物断言 |
| 页面提示 | 提示"这是远端发布，目标机是谁" |
| 文档 | 运维手册 + Agent 技能各加一节 |

## 7 上线顺序（重要）

> ⚠️ **第 0 步是必修的阻塞项**：现在 `check` 阶段在节点模式下被整段跳过，导致"产物已存在就跳过构建"的复用逻辑从未生效。
> 不修它，远端会自己重新拉码 + 构建 + 投递 —— 本方案"本机构建、远端只记账"的分工就不成立。

0. **先修 `check`（阻塞项）**：让 `check` 在安全基线内置逻辑之外再叠加脚本；顺带把"请求里的 commit"存下来供事后校验
1. 平台级前置：节点命令表加"锁定"标记 + 拉码脚本随代码落库 + 引擎支持执行 DB 脚本（影响**所有**模板，含 local，必须零回归）
2. 目标解析 + 投递（此时 dev 能拿到产物，但指针还没切）
3. 版本 / 指针接口化（dev 正式生效）
4. 探活断言（闭环）
5. 页面提示与文档

**发布本机 console 自身**用 `scripts/publish-deploy-console.sh`（走流水线会把自己重启掉）。
**dev 机的 console 本期不用升级** —— 我们复用的是它已有的接口。

## 8 排查用的一张表

| 现象 | 大概原因 |
|---|---|
| 投递失败提示缺 `REMOTE_HOST` | `deploy_servers` 里没有 `dev-default` |
| 接口返回 401 | 两端 HMAC 密钥不一致，或本机时钟偏差超过 5 分钟 |
| 接口成功但 manifest 没变 | 缓存 TTL 没过（等 12s），或远端指针没切 |
| manifest 版本对但产物 404 | 投递路径与指针引用不一致 |
| 拉码阶段报"commit 不可达" | 该 commit 没 push 到 origin |
| 页面提交成功但 dev 没产物 | 本机已有同 commit 产物，复用逻辑把投递也跳过了（必须修） |
