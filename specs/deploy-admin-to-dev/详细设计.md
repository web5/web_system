## 0 两个实测事实（直接影响实施计划）

### 0.1 ⛔ 阻塞项：v5 模式下 `check` 被跳过，**复用从未生效**

**证据（本机真实流水线 `1789113846813-crzopdc`）**

- 实例 nodes：`[{"key":"git","kind":"platform"}, {"key":"check","kind":"script","label":"校验","optional":true}, {"key":"build",...}]`
- 日志：`[check] 校验 未配置脚本，已跳过（optional）`
- 库字段：`reuse_artifact = 0`

**为什么**：`PIPELINE_V5_NODES=on`（两端实测均开）→ 模板懒转存为 v5 nodes；转换时 `check` 变成 **script 节点**（`optional=true`）；而 `reuseArtifact`、`branch` 缺省 `master`、`prod` 分支约束**全部只在 `CheckExecutor` 里实现**，DB 无 `check` 命令 → script 节点直接跳过 → 这些语义**全部丢失**。

**影响（对本设计是致命的）**：

| 原本的假设 | 实际 |
|---|---|
| 远端 `check` 命中已投递产物 → `reuseArtifact=true` → 跳过拉码/构建/投递 | 远端会**全量 pull + build + upload**（还带切分支副作用） |
| 本机发历史版本可复用产物 | 同样不复用，每次都重新构建 |

→ **必须新增「零期-B：恢复 v5 下 check 的 base 语义」**（见 §2），否则本期架构不成立。

### 0.2 `synchronize: true`：加列不用写迁移 SQL

`servers/deploy-console/src/app.module.ts:45` 已开启 TypeORM `synchronize`（注释写明「开发/本地运维工具：自动建表」）。
→ **改 Entity 后重启即自动 `ALTER TABLE ADD COLUMN`**；回滚需反向 `ALTER TABLE ... DROP COLUMN`（见 §7）。仍建议在 `migrations/` 留一份等价 DDL 备查。

## 1 零期-A：`git` 节点 DB 脚本化

### 1.1 数据模型

```ts
// entities/deploy-pipeline-step-command.entity.ts
@Column({ type: 'boolean', default: false, comment: '平台托管：接口拒写、页面只读' })
locked: boolean;
```

- 无需迁移脚本（§0.2 自动加列）；老行默认 `false`
- 语义：`locked` 是**通用标记**（D8），本期只给 `git` 置位

### 1.2 seed：脚本随代码落库

**关键设计**：脚本正文作为**代码常量**，启动时幂等 upsert 到所有模板 → 无需 SQL 迁移、两端随 console 上线自动一致。

```ts
// pipeline/step-scripts.ts（新增）
export const GIT_SCRIPT = String.raw`#!/usr/bin/env bash
…（正文 = scripts.md S0，含四处 fail-fast 与 HEAD 自证）…`;
```

```ts
// pipeline-step-command/pipeline-step-command-seed.service.ts（新增，OnModuleInit）
async seedPlatformScripts(): Promise<void> {
  const tpls = await this.templates.find({ where: { enabled: true } });
  for (const t of tpls) await this.seedForTemplate(t.id);
}
async seedForTemplate(templateId: string): Promise<void> {
  const row = await this.repo.findOne({ where: { templateId, nodeKey: 'git' } });
  if (row?.locked && row.command === GIT_SCRIPT) return;      // 无变化
  const next = row ?? this.repo.create({ templateId, nodeKey: 'git' });
  Object.assign(next, { command: GIT_SCRIPT, actions: null, locked: true, enabled: true, updatedBy: 'system' });
  await this.repo.save(next);
}
```

| 要点 | 说明 |
|---|---|
| 触发点 1 | `onModuleInit` → 全量模板（含存量模板，首启即补） |
| 触发点 2 | 模板创建后（`PipelineTemplateService.create` / `ensureDefault`）→ `seedForTemplate(id)`，新模板立刻有脚本 |
| 覆盖语义 | **代码是真相源**：手工 SQL 改过脚本，重启会被重置（与 `locked` 语义一致，也是"重置手段"） |
| 模块依赖 | seed 服务需注入模板 repo；`PipelineTemplateService` 若要反向调用，注意依赖方向（建议 seed 服务单向依赖两个 repo，由 module 组装） |
| 远端 | dev 机 console 上线新版时自动 seed（本期远端不拉码，非必需但建议同步） |

### 1.3 引擎改造（`pipeline.service.ts:executeV5Node`）

```ts

  if (node.key === 'git') {

    await this.resolveGitIdentity(p);                // ④ 回填 + 一致性断言（两种路径都要）
    return;
  }
  …version/pointer 原样…

```

`resolveGitIdentity`：

```ts
private async resolveGitIdentity(p: DeployPipelineEntity): Promise<void> {
  const commit = this.git.shortHead(this.releaseWorkspace);          // 实际 HEAD（短哈希）
  p.gitCommit = commit;
  p.versionTag = p.templateKey ? `${p.templateKey}/${commit}` : commit;
  p.logs = [...(p.logs ?? []), `代码已就绪: ${p.gitBranch}@${commit} → 版本 ${p.versionTag}`];

  if (p.requestedCommit) {                                           // 入参 commit（见 §2.2 新列）
    const want = this.command.exec(`git rev-parse --verify ${p.requestedCommit}^{commit}`, this.releaseWorkspace).trim();
    const got  = this.command.exec(`git rev-parse HEAD`, this.releaseWorkspace).trim();
    if (want !== got) {
      throw new Error(`拉码结果与请求不一致：实际 HEAD=${got.slice(0,8)} 期望=${want.slice(0,8)}（版本引用 ${p.versionTag}）`);
    }
  }
}
```

| 细节 | 决定 |
|---|---|
| DB 命令 key | **固定 `nodeKey='git'`**（v5 platform 节点名）；legacy 兜底见下 |
| 进度/日志阶段名 | v5 用 `git`；legacy 用 `pull`（`runStageCommand` 增加可选的"进度阶段名"参数，避免 `p.stage` 写入不在 `PIPELINE_STAGES` 的值） |
| 依赖同步 + 共享包预构建 | **不写进脚本**，仍在平台：把 `PullExecutor` 内的 deps/prebuild 段抽成 `PullExecutor.afterSync(ctx)`，git 节点执行完（脚本或内置）后统一调用 |
| legacy 兜底 | legacy `pull` 阶段也先查 `nodeKey='git'` 命令，再查历史 `nodeKey='pull'`，最后内置（低成本，防 v5 flag 关闭时行为断裂） |

### 1.4 接口与 UI（`locked`）

| 位置 | 改动 |
|---|---|
| `pipeline-step-command.service.ts` | `upsert`/`remove` 先读行：`row?.locked` → `throw new BadRequestException('节点 git 为平台托管，不可编辑')`；新增 `upsertLocked()` 供 seed 内部使用（绕过保留字校验） |
| `pipeline-step-command.controller.ts` | `list` 响应加 `locked: !!r.locked` |
| `PipelineDetail.vue` / `PipelineEdit.vue` | platform 节点点击 → **加载并只读展示脚本**（替代现在的「点击无反应 + warning」）；`StageActionsEditor` 加 `readonly` prop（`a-textarea disabled`、隐藏保存/删除），顶部提示「平台托管，仅可查看；变更走代码/seed」 |

### 1.5 单测

| 目标 | 断言 |
|---|---|
| `seedForTemplate` | 无行 → 新建 + `locked=1`；同内容 → 不写库；内容变更 → 覆盖 |
| git 节点分派 | 有 DB 脚本 → 走脚本且不再调内置；无脚本 → 调内置 |
| `resolveGitIdentity` | 回填 `gitCommit`/`versionTag`；`requestedCommit` 不一致 → 抛错 |
| skip 守卫 | `reuseArtifact=true` → 不执行 git（脚本与内置都不执行） |
| locked 拒写 | `upsert`/`remove` 对 locked 行 → 400 |

## 2 零期-B：恢复 v5 下 `check` 的 base 语义（阻塞项修复）

### 2.1 改法（与 legacy `commandMode='base'` 对齐）

```ts
// executeV5Node：script 节点分支前置
if (node.kind === 'script' && node.key === 'check') {
  await this.builtinSteps.check.run!(ctx);       // ① 安全基线恒执行（复用检测 / 分支缺省 / prod 约束 / moduleType 快照）
  await this.runStageCommand(p, 'check', stage); // ② 配置了命令则在其后叠加
  return;
}
```

> 不改 `PLATFORM_RESERVED`（那会让含 `check` script 节点的存量模板校验失败），改动最小且与 legacy 语义完全一致。

### 2.2 配套：记录入参 commit（供 §1.3 断言用）

`submit` 现在把入参 commit 直接写进 `versionTag`，而 `versionTag` 随后被拉码结果覆盖 → 入参丢失。新增：

```ts
// entities/deploy-pipeline.entity.ts
@Column({ type: 'varchar', length: 64, nullable: true, comment: '请求的 commit（入参快照，用于拉码一致性断言）' })
requestedCommit?: string;
// submit: requestedCommit: dto.commitId ?? dto.versionTag
```

### 2.3 影响面（恢复后）

| 语义 | 恢复后效果 |
|---|---|
| 复用检测 | `reuseArtifact=true` → git/build/upload/restart 守卫跳过（**本设计与 4a 的前提**） |
| 分支缺省 | 未传分支 → `master`（不再出现 `git checkout -B ""` 这类失败） |
| prod 约束 | `env=prod 且分支≠master` → 拒绝 |
| `moduleType` 快照 | 供 `resolveStageVars` 与守卫判断（避免只依赖模块注册表） |

### 2.4 验收

```bash
# 同一 commit 发第二次 → 复用生效
```

## 3 一期：环境 → 目标解析、变量、投递

### 3.1 解析器（`pipeline.service.ts`）

```ts
/** 环境 → 投递目标（缺配置 fail-fast，不静默投本机） */
private async resolveTargetForEnv(env: string, explicit?: 'local'|'remote', tplDefault?: string) {
  if (explicit) return explicit;                                   // ① 入参最高
  if (tplDefault && tplDefault !== 'auto') return tplDefault;      // ② 模板 defaultTarget
  const cfg = await this.configs.resolve(env, '*');                // ③ 环境级配置 PIPELINE_TARGET
  if (cfg.PIPELINE_TARGET === 'local' || cfg.PIPELINE_TARGET === 'remote') return cfg.PIPELINE_TARGET;
  if (env === 'local') return 'local';                             // ④ 内置规则
  if (env === 'dev' || env === 'staging' || env === 'prod') return 'remote';
  throw new BadRequestException(`环境 ${env} 无法判定投递目标，请配置 PIPELINE_TARGET`);
}
```

- **`submit` 时解析并固化**：`runTarget` 不再留 `'auto'`（守卫/脚本都读得到确定值）
- remote 模式缺目标机/地址 → 阶段 fail-fast，错误信息带缺失项与配置指引

### 3.2 变量下发（`resolveStageVars`）

新增：`GIT_COMMIT`（纯短哈希；`COMMIT_ID##*/` 兜底）、`REMOTE_HOST/USER/KEY/DIR/ARTIFACT_DIR/GATEWAY_URL/CONSOLE_URL`。
⚠️ `COMMIT_ID` 是**完整引用** `default/<commit>`，`GIT_COMMIT` 是纯哈希 —— 两者不可互换（历史踩坑点）。

### 3.3 目标机改读 `deploy_servers`

```ts
// remote/remote-delivery.service.ts
async resolveTarget(env: string): Promise<RemoteTarget> {
  const srv = await this.serverService.resolveEnvDefaultServer(env);   // ← 已存在，直接复用
  if (!srv) throw new BadRequestException(`deploy_servers 缺少 ${env}-default（页面「服务器管理」配置）`);
  return { remoteHost: srv.host, remoteUser: srv.sshUser, remoteKey: expandTilde(srv.sshKeyPath), remoteDir: srv.remoteDir };
}
```
回退旧 `DEV_SERVER/PROD_SERVER`（保留一个版本，便于灰度）。

### 3.4 upload 改造（remote）

- 旧目录 `mv` 移出后再解包（**不用 `rm -rf`**，避免触发批量删除审批）
- 解包后断言 `index.js` 存在
- 日志打印 `ssh target` 与远端目录；脚本正文见 `scripts.md` S1

### 3.5 复用与投递的取舍（P9 / R6）

```ts
// steps/step-registry.ts
upload: {
  skip: (p) => p.moduleType === 'backend' || (!!p.reuseArtifact && p.runTarget !== 'remote'),
  run: (ctx) => ex.upload.run(ctx),
}
```
理由：`reuseArtifact` 反映的是**本机磁盘**状态；remote 时远端可能没有该产物 → 投递必须执行（投递幂等，重投成本低）。

## 4 二期：版本 / 指针接口化

### 4.1 `remote/remote-release.client.ts`（新增）

```ts
sign(rawBody: string) {
  const ts = Math.floor(Date.now() / 1000);
  const sig = 'sha256=' + createHmac('sha256', this.secret).update(`${ts}.${rawBody}`).digest('hex');
  return { ts, sig };
}
async publish(input: { env; moduleKey; branch; commitId; deliveryId }): Promise<ReleaseHookResult> {
  const body = JSON.stringify({ deliveryId, env, moduleKey, branch, commitId, mode: 'direct', source: 'local-console', target: 'local' });
  const { ts, sig } = this.sign(body);                      // 必须对「原始字节」签名
  …POST `${REMOTE_CONSOLE_URL}/api/hooks/release`，超时 30s…
  // duplicate=true 视为成功；401/400 映射为可读错误；日志打印 jobId/status

```
- 幂等键：`local-<commit>-<moduleKey>`
- **禁止**在本机直连远端库（D1 / api-design ①）

### 4.2 `pointer` / `version` 分支

| 模式 | 行为 |
|---|---|
| `local` | 原逻辑（写本机库） |
| `remote` | 调 4.1；本机库**不写入**；`version` 阶段日志记录远端受理结果 |

### 4.3 守卫与前置校验

- `remote + mode=grayscale` → `BadRequestException`（本期不支持）
- hook 必带 `branch` + `commitId`（T5c）：缺 `commitId` → 远端全量构建；缺 `branch` → 远端兜底 master

## 5 三期：探活断言落 DB

- `verify` 命令改为「原有分支保留 + remote 断言」的分派版（`scripts.md` S3）—— 分派条件 `DEPLOY_ENV != local && REMOTE_GATEWAY_URL 非空`

- 远端模板 verify 保持跳过（避免双口径）
- 断言失败 → 流水线 failed；`rollbackAnchor` 语义不变

## 7 回滚方案

| 变更 | 回滚方式 |
|---|---|
| `locked` / `requested_commit` 加列 | `ALTER TABLE deploy_pipeline_step_commands DROP COLUMN locked;` / `ALTER TABLE deploy_pipelines DROP COLUMN requested_commit;`（列留着不影响旧代码，可暂不回滚） |
| git DB 脚本 | 删掉该行（`delete from deploy_pipeline_step_commands where node_key='git'`）→ 引擎回退内置 `pull`；或把 `PIPELINE_V5_NODES=off` |
| check base 恢复 | 代码回退（恢复"script 节点未配命令即跳过"语义） |
| 环境 → target 解析 | 删除配置中心 `PIPELINE_TARGET` 并回退代码；或显式传 `target=local` |
| upload / verify 脚本 | 恢复旧脚本正文（`scripts.md` 版本可从 git 历史取回） |
| console 自身 | `git -C ~/web_system_release checkout <上一 tag>` + `publish-deploy-console.sh --skip-sync` |
