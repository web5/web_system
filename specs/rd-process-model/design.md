> 版本：v1.0（2026-09-23，用户已采纳建议版，待按 §7 拍板后落码）
> 定位：把 `rd-digital-agent` 现有的扁平「0–7 评审链」重构为**环节 × 角色**矩阵，补齐独立 reviewer 空缺、发布与运营环节、人审节点与回流边，并给出双仓（web_system / ai-agent-kit）落地路径。

## 0. 一页速览

| 项 | 内容 |
|---|---|
| 要解决的问题 | 评审链是**一条串行主链**：设计侧缺评审子步、代码/架构侧只有自查无第三方、**无发布与运营环节**、无人审节点标注、无回流边、无分级短路 |
| 做法 | ① 环节拆为 S0–S9；② 每个环节拆「生产者 / 自查（下限）/ 独立评审 / 人审」四格；③ 补 6 个子步（0.1 / 1.2 / 3.2 / 4.2 / 5.2 / 8.1）与 2 个环节（8 交付、9 运营）；④ 固定 4 个人审节点；⑤ 用**改动面**机检驱动 reviewer 分派，不靠语义判断 |
| 三个标注 | ◆ 人审 ·（自查）生产者自过，是下限不替代第三方 ·（独立）盲审隔离 + 独立上下文 + 判据外部化 |

| 上游改动 | Hub 评审链重构 + 分级短路 + 回流边，属上游 `web5/ai-agent-kit`，**另仓另 PR**，经 sync→apply 两跳落地 |
| 分期 | P0 本 spec 与判据源 → P1 两个可机检 reviewer（契约 / 发布）+ 机检分派 → P2 独立代码评审 + 运营回流 → P3 上游 Hub 重构收口 |

## 1. 问题与根因（现行评审链的五个洞）

现行链（Hub v4.7.0）：`0 需求转换 → 1 产品方案 → 2 D1 设计输入 → 3 UX 质检 → 4 技术方案 → 5 代码评审 → 6 D3 一致性 → 7 测试盲测`。

用户已采纳的改进版（两级结构 + 转换确认 + 交付清单）已修好三处，但仍留五个洞：

| # | 洞 | 证据 / 后果 |
|---|---|---|
| H1 | **2、3 没有 `.1` 子步，不对称** | 4→4.1、5→5.1 已两级化，但 `D2 独立设计评审` 与**原型人确认**发生在图外 → 图上看似审过，实际人审缺失 |
| H2 | **评审 ≠ 独立评审，图上未区分** | `4.1 技术方案评审` = `tech-review`（AI 自查）；`5.1 代码评审` = `rd-review`（实现者自查）。对照 `7 测试盲测`（`test-verification`，独立）与 `design-reviewer`（独立），**代码侧与架构侧至今无第三方** |
| H3 | **缺发布环节** | 流程止于测试。而高频故障（pm2 端口冲突、跨服务密钥不一致、`packages/types` 只 tsc 不 build 致 cjs 不更新、DB 绑定早于发布目录同步）**全在测试之后** |
| H4 | **缺分支与短路** | 一条直线 = 默认每个改动跑 9 步。小改动全跑 → 摩擦过大 → 流程被绕过（kit-sop-enforcement §3.7 头号失败模式） |
| H5 | **只有正向无回流** | D3 发现漂移回哪、盲测发现判据缺失回哪，图上无逆向边；评审价值恰在回流 |

**根因**：把「环节」与「角色」压扁进一条链。真实研发是二维的——环节有先后，但环节内「生产 / 自检 / 独立评审」是并列的三种角色，且架构可行性必须与产品方案交叉而非串行其后。

## 2. 目标与非目标

### 做成（可验证）

1. 任一改动能**按改动面**确定它该过哪几道评审，且该判定**可机检、可回归**（不依赖语义理解）。
2. 每个环节都能回答「生产 ≠ 评审吗」——四个空格（架构 / 代码 / 发布 / 运营）按优先级补齐。
3. 4 个人审节点固定且可见，人只做**裁决**不做「找问题」。
4. 小改动有明确的短路路径，且豁免口径在所有规则中一致。
5. 评审结果有回流边，能回到生产环节与判据源。

### 不算做成

- 不追求每个改动跑满全链（分级短路是设计的一部分，不是偷懒）。
- 不新增角色替代人审：评审只给「阻塞/重要/建议 + 反例 + 判据编号」，裁决权在人。
- 不在本期把 `code-reviewer` 上到 error（主观性最强、成本最高，放 P2）。
- 不改上游运行源（S7/R12 会拦），上游改动一律走 `sync → apply` 两跳。

### 3.3 三条标注规则（固化到流程图与 Hub）

| 标注 | 含义 |
|---|---|
| ◆ | **人审节点**，全流程固定 4 个：需求定稿 / 方案与交付物确认 / 原型确认 / 放行上线 |
| （自查） | 生产者自过，是**出稿下限**，不替代第三方 |
| （独立） | 盲审隔离 + 独立上下文 + 判据外部化，**缺一即退化为自审**；不出稿、不改码，只出报告并回流 |

### 3.4 本期新增的六处（相对用户改进版）

| 新增 | 治哪个洞 | 说明 |

### 3.5 分级与短路（否则流程会被绕过）

| 级别 | 判定 | 路径 |
|---|---|---|
| L0 微改动 | ≤5 行、单文件、纯文案 / 纯配置值 | `0 → 5`，免评审，commit 带 `Micro-exempt: <理由>` |
| L1 小改动 | 单模块、无契约变更 | `0 → 1 → 4 → 5 → 5.1 → 7`（7 可省） |
| L2 中改动 | 单模块 + 契约 / 接口变更 | 全链 + **S4.2 强制** |
| L3 大改动 | 跨模块 / 跨端 / 数据迁移 / 发布 | 全链 + 4 个 ◆ + **S8.1 强制** |

短路分支（画在流程图上）：◆② 交付物确认时判定**是否需要原型**——纯后端改动直接 `1 → 4`，跳过 S2/S3/S6。

### 3.6 回流边（质疑边）

沿用 `challenge-playbook` 格式（质疑须落**反例 + 判据编号 + 严重级 + 是否阻塞**，禁「感觉不对」）：

| 边 | 发起 | 目标 | 内容 | 回流 |
|---|---|---|---|---|
| 可测性→需求 | S0.1 | `requirement-translation` | 判据不可测 / 反例缺失 | 补判据 |
| 契约→方案 | S4.2 | `rd-plan` | 契约未登记 / 迁移不可逆 / 破坏既有消费方 | 改方案或登记契约 |
| 一致性→开发 | S6 | `rd-execute` | 实现漂移（锚点缺失/新增/改名） | 交开发修复，评审不改码 |
| 盲测→开发 | S7 | `rd-execute` | 产物未满足验收判据（可复现反例） | 交开发修复 |
| 盲测→需求 | S7 | `requirement-translation` | 验收判据缺失 / 不可测 | 补判据 |
| 发布→开发/方案 | S8.1 | `rd-execute` / `rd-plan` | 依赖顺序错 / 密钥不一致 / 无回滚锚点 | 整改后放行 |
| 运营→判据源 | S9 | 各 reviewer 判据源 | 新故障模式 | 回灌为判据条目 |

### 3.7 机器强制：用「改动面」驱动分派，不靠语义

**核心原则**（与 UI 动作门同构）：语义分派已被证明不可靠（触发词失配），reviewer 分派同样必须挂在**改动对象**上。

| 改动面（可机检） | 必需评审 | 规则 | 级别 |
|---|---|---|---|
| `scripts/migrations/*`、跨库变更 | S4.2 数据变更 + S8.1 发布 | **R13 + R14** | warning（Q3 已拍板保持） |
| `servers/*/.env`、`ecosystem.config.cjs`、端口 / 密钥 | S8.1 发布 | **R14** | warning（Q3 已拍板保持） |
| 新增/改对外接口、MCP 工具、`packages/types`、权限码 | S4.2 契约 | **R13** | warning（Q3 已拍板保持） |
| `servers/**` 新增控制器 / 权限点 | S5.2 独立代码 | **R15** | warn → strict（P2） |
| `apps/**` UI 源码 | S3.2 设计（D2/D3） | R11 / R11b | error |
| 纯文档 / 脚本微调 | 无 | — | **零摩擦** |

> 级别：R13/R14 为 **warning**（`--strict` 下 error）。**Q3 已拍板（2026-09-24）：先保持 warning** —— 存量 commit 无 `Contract:` / `Release:` 凭证，直接 error 会让历史 PR 全红；待积累使用观察后，转 error 须配套存量过渡策略。
> 契约面已按实测**收窄**（移除 `packages/agent-core/*`）并对控制器加行数阈值 5，理由与防回退断言见 §7.3。

**实现约束（沿用既有基建）**：
- `scripts/redline/scan-rules.sh` 新增 `check_r13_r14`（两个面**共用一次遍历**，各自遍历会让 commit 级 git 调用翻倍）+ `_trailer_check_one` 单条校验，**不改调用方**；CI 接入 `quality-gate.yml` 的 `redline-scan` job（该 job 于 2026-09-24 恢复，缺口经过见 §7.5）。
- 报告沿用 `design-reviewer` 的机器可读头 `阻塞: N` / `重要: N`，复用 R11 的解析逻辑。
- commit trailer 沿用既有风格：`Design:` / `Contract:` / `Release:`，值为 `pass` 或报告路径。
- **`Micro-exempt: <理由>` 必须同时豁免 R9b / R10 / R11 / R13 / R14 / R15**——口径不一致会制造「记了豁免还报错」的新摩擦源。
- `selfcheck-ui-gate.sh` 追加 V 断言（含零摩擦边界）。

## 6. 风险与权衡

| 风险 | 缓释 |
|---|---|
| **角色通胀 → 摩擦过大 → 门禁被关**（头号失败模式） | P1 只落两个**可机检**的 reviewer；作用域按改动面收窄，纯文档零摩擦；`Micro-exempt` 口径统一；V6/V10 守零摩擦边界 |
| **评审沦为形式**（换个角色名自审） | 三条独立性机制沿用 `design-reviewer`；无判据的结论强制降级为「建议」并标注个人偏好 |
| **判据源不足 → 主观评审** | **W2 先于 W3**（判据源先于角色），与 design-reviewer「T1 先于 T2」同纪律 |
| **Hub 撑爆行数上限** | U2 强制外置 `references/review-chain.md`；机检分派把复杂度从 prompt 挪到脚本 |
| **R12 误报阻断 CI** | W5 与 W3 同批，不允许先落技能后补清单 |
| **上游两跳漏一跳** | V12 显式校验；apply 后必跑 R12 |
| **`code-reviewer` 主观成本高** | 放 P2 且先 warn，不上 error |
| **人审节点超载** | AI reviewer 负责「找问题」，人只裁决；每个 ◆ 交付的是差异清单 + 建议 + 未决项，不是原始产物 |

### 7.4 附加项：auto-pr 残影 PR 治理（W0）

**现象**：`feature/kedou-ai-minigram` 被自动建出 #130 —— 129 commits / 203 files / 12 个冲突文件。

**根因两条**：

1. `.github/workflows/auto-pr.yml` 只对 `feature/*`、`fix/*` 建 PR（已排除 `feature/test`），**长期集成分支不在排除内**；
2. 幂等检查只查 `state: 'open'` 的 PR —— 同名 PR（#129）合并后再 push，会**再建一个新的**（残影）。

**处置**：排除清单改为 JSON 数组（`feature/test` + `feature/kedou-ai-minigram`），并把两条成因写进 workflow 注释。

**纪律**：长期 / 集成分支不自动建 PR；这类分支的改动应按主题拆成**短命分支**各自走 auto-pr，才可评审、可回滚。

|---|---|---|---|
| L0 项目专属 | — | 技能 + 判据 + 机检 | **当前态** |

**现在就该做的三件准备（零额外成本）**：

1. **判据源外置**到 `references/<role>-checklist.md`，SKILL.md 只留 `loads:` 指针（同时满足行数上限）。

- 上行后**必须从 R12 保护清单移除该角色名**。保护清单语义是「只在运行源、能力源没有」；能力源一旦有了同名文件，继续跳过比对就会**掩盖真实漂移**。

**何时不该上行**：仅单一项目在用就上行 = 把项目维护成本转嫁上游，且每次改判据都要过上游门禁。判据是**第二个真实项目明确要装配时**才启动 L1。
